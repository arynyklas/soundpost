The actual browser fixture tests real cross-source interleaving; exact approved browser matrix rows, source-mapped frames and replay remain separate unmet gates.

Config requires the source's real registered resource IDs/instance and its signed policy. This entrypoint always selects `X-Soundpost-Source`, `credentials:omit`, no referrer and forbidden redirects; it never sends private bearer auth or ingestion cookies. ## Explicit browser causality

`withSpan` implements native C04 elapsed spans with registered operation/dependency aliases. A browser has no qualified implicit async-local scope: `traceContext()` is valid only during synchronous callback invocation. Save the closed context before await and pass it explicitly to the next adapter; otherwise the new operation is a root, not guessed causality.

`installNavigation(client,{operations:["navigation"]}).navigate("navigation", async context => { ... })` measures the caller's actual router/navigation commit promise. Its callback receives an explicit context to pass across async boundaries. It reads neither location/history values nor DOM content. This is elapsed navigation timing, not Long Task CPU profiling or inferred page-load internals.

`installFetch(client,{operation:"http.call",origins:[{origin:"https://api.example",dependency:"dependency"}]}).fetch(input,init?,parent?)` accepts that explicit parent as its third argument. Without one it starts a root. It adds W3C/closed companion propagation only for exact registered origins, removes baggage/foreign trace headers for ordinary data-only options, and returns the original Response without reading its body. It never patches global fetch. Opaque/accessor init values are delegated without inspection or invented attribution. Failed/CORS-denied foreign requests are honest missing external internals.

Workers receive only closed `serializeWorkerContext(context)` envelopes, never a serialized application message or source/project/credential. Initialize the worker independently, then use `withWorkerContext(workerClient,envelope,callback)`. Parent causality never authorizes another tenant or relabels local clock stamps. Closing integrations is idempotent, single-install is enforced per client, and unfinished navigation/streams remain incomplete.

Actual browser→Express→HTTP dependency→PostgreSQL fixtures live under `fixtures/sdk/browser/`. Parent builds app/worker separately and serves an independently configured public browser source; no private/read credential enters a bundle or worker message. The driver asserts actual browser build IDs and verifies admitted native records with an independent server-side read credential. ## Replay recorder

`createRecorder(config, emit)` records only an owned, masked structure: ids, the server's closed tag enum and the constant `"[masked]"` text mask. Text content, input values, attributes, ids, classes, CSS, pseudo-content, canvas/media pixels, clipboard, console and key events are never read, and no layout is ever recorded (the only layout read is the yes/no box test of the closed-shadow inference below, never stored or sent). Frames, editable regions, textarea/select and media are one opaque node. `ReplayStream` is the bounded `AsyncIterable<ReplayChunk>` shared with the renderer. Closed shadow roots are not observable by page script (`shadowRoot` is `null`), so the recorder recognises them when they are created: while capture is active `Element.prototype.attachShadow` is wrapped (the receiver, arguments, result and any exception are forwarded unchanged; the init dictionary is never read a second time) and a host whose call returned a root while its own `shadowRoot` getter answers `null` is recorded as one opaque node. Stopping capture restores the platform method (or leaves an inert wrapper when page script wrapped it in between).

**Closed roots attached before capture started** (03.07-C7). No script can prove such a root exists: the host answers `shadowRoot === null` like any element. The recorder therefore infers it from platform answers only, never from content: an element whose name is a valid custom element name, that is upgraded (`matches(":defined")`), whose `shadowRoot` is `null`, that has no light-DOM child, and that occupies a layout box (`offsetWidth`/`offsetHeight` > 0) is rendering something the page cannot read, and is recorded as the **closed-shadow mark**. All reads use accessors captured from the platform prototypes, so page-planted getter traps never run; nothing inside the host is ever read, so no content can leak. The mark stays inside the server's closed node vocabulary (D2): an opaque node (`class` `"masked"`) whose `text` is the constant `"[masked]"`, the one opaque shape no other cause produces (frames, widgets, editable regions, overflow and truncation are opaque with empty text). The viewer shows it as `[opaque: closed shadow root not observable]` and never its light children. A custom element is re-walked, never appended to, because the inference ends the moment it has a child. **What the inference cannot see (a platform limit; no owner decision records an acceptance):** a pre-existing closed root on a plain `div`/`span` host, on a host that has light children, or on a zero-size box is walked as an ordinary element; its content is still never read. The inference can also mark a defined custom element that never had a root and renders only through CSS (the label then claims more than the platform proves). Install replay before page script that builds closed roots when that matters.

**Supported install and late start (D100).** The supported install loads the recorder synchronously and first in `<head>` (a classic script, before page script and before any custom element is defined), so the `attachShadow` hook sees every closed root being made and no pre-existing root exists. `createRecorder`/`startReplay` check at the first start whether the page is already past that point: `document.readyState` is not `"loading"` (reason `document_ready_state`) or `document.body` already has content (`body_content_present`), read through the platform prototype getters; the optional `lateStart` config replaces the probe, and a probe that throws counts as late (`probe_failed`). A late start is recorded in the only places the closed wire (D2) allows: `recorder.lateStart()` returns the reason and the first checkpoint is gap-marked (`gap: true` at sequence 1, which has no other meaning there). The viewer then shows the banner "Recording started after the page had loaded: pre-existing closed shadow roots may be unobservable." The closed-shadow inference above stays on for late starts; coverage is never claimed complete after a late start. Detection of custom elements defined before the start is not done separately (a page that defines them early is past `loading` in practice). A dedicated replay capability record needs a wire kind the server does not have and was not added.

**Node cap:** the 20,000-node cap is a running total over the live tree: ids come from one counter that restarts only at a checkpoint, a node the replay already holds keeps its id when a delta re-walks it (so only new nodes allocate), every delta may add at most `MAX_NODES` minus what the counter holds, and a delta that would pass the cap is replaced by a fresh checkpoint that recounts the live tree exactly (a live tree that itself reaches the cap becomes an opaque placeholder plus a gap); that recount is prepared in slices between callbacks before the cap is reached (see "Id-space checkpoint prepared between callbacks"). One chunk is still limited to 4096 nodes by the server (`MAX_CHUNK_NODES`).

**When a checkpoint is due** (design: "checkpoint every 30 seconds or after a gap"): every 30 s, after a gap (a rejected chunk, a re-enabled capture, a burst of more than `MAX_MUTATION_RECORDS` = 4096 records, the recorder's bound on main-thread work per observer callback), when a delta would pass the node cap, and when a record names something the recorder cannot attribute (a shadow root it does not hold, a climb cut by the depth bound, a document). Everything else is a delta: a record on a detached node that was never in the replay tree (added and removed in one batch) is covered by the record that removed it from the tree, a node the replay holds that has left the tree is not re-walked, and each distinct target of a batch is attributed once, so an ordinary list re-render of hundreds of rows is one delta, not one of the 1024 checkpoints of a replay.

**Appends are recorded once** (03.07-C7): a node the replay holds that only gained new children (child-list records at the end of its child list, the new nodes ending it, the parent showing its children) and whose children read back from the page are the replay's own children node for node from the first to the last (a record whose `nextSibling` is null may stand for a whole batch, e.g. a `replaceChildren(...)` reported as one record; a held child out of place or a shown node before the first is the re-walk) emits the new subtrees only, under the parent's id, with one `mutation` event on the first new node; the viewer, which deletes the descendants of a mutation event's node, deletes nothing for a node it has never held and adds the nodes after the siblings it holds. Removal of a node that is not the last, a move, an insertion before a sibling (any child-list record whose `nextSibling` is not null, including an insertion before a node added in the same batch), an attribute/character-data record, a widget/input/editable parent and an append the chunk cannot hold stay the re-walk of the nearest known node (the wire has no removal event; adding one is a recorder_version bump the design leaves to the contract owner). `test/replay-append.test.ts` and `packages/replay-viewer/test/append-delta.test.ts` (random page histories, including histories of tail records only, through the real recorder and the real viewer against a fresh checkpoint) pin it; golden scenario `fixtures/replays/recorder/append`.

**No record node lists** (03.07 Firefox p95): a MutationRecord's `addedNodes`/`removedNodes` make the platform create a NodeList wrapper per record (about 960 per 400-node batch, most of what the observer callback still allocated). The recorder asks a record for its `type`, `target` and `nextSibling` only (`DomAccessors.recordKind`: `"tail"`, `"inside"` or `"other"`) and answers an append from the page's own children at the end of the batch. The replay keeps its child order as two number columns indexed by node id (`src/replay/links.ts`: the last recorded child of each node and each child's predecessor, written as nodes are walked). A parent whose records were all at the end is a pure append when its last children, read back from the page, are the unknown trailing nodes (the new subtrees) after the replay's own last children, node for node, for as many children as the batch's records could have changed (each tail record adds or removes one place at the end); an unknown node the replay would show (text, or an element it does not skip) between known ones, a missing known child or one out of order is the re-walk of the parent. Nothing in the answer depends on what a record claims to have added or removed. `test/replay-records.test.ts` pins that no list is read (real platform accessors over a fake platform whose list getters count) and the random histories above are the oracle. Eight mutants of the append check and of the preparation below were run: seven are killed and one, a window one place short, is equivalent (the check already covers one place more than a batch can change).

**Id-space checkpoint prepared between callbacks** (03.07 Firefox p95): a checkpoint recounts the live tree, so a delta that would pass the cap used to be replaced by one inside the observer callback that reached it (5-8 ms for a few thousand nodes, the slowest batches of the 400-node row). Once `PREPARE_HEADROOM` = 4096 ids are left (and at least as many were used since the last checkpoint, so a live tree that fills the cap does not recount all the time) the recorder walks the page into a second epoch of ids (its own id map, shadow-root set, node table and child links) in slices of `PREPARE_SLICE_NODES` = 512 nodes between the page's tasks (zero-delay timers on the configured `timers`), fits the nodes to one chunk in a slice of its own and writes the chunk in a last one. The walk is an explicit stack (`Walker` in `src/replay/tree.ts`), so it stops and resumes at any node and produces the same order, ids and decisions as the recursion it replaced. Deltas go on in the old epoch meanwhile; any batch that arrives after the walk began makes it stale and it starts over (`PREPARE_RESTARTS` = 8 times, then the recount is left to the callback that reaches the cap, as before); a checkpoint made for any other reason, a loss that takes room the fit did not leave, a stop or revoked consent cancels it. The written chunk is an ordinary checkpoint (same wire, `recorder_version` `"1"`, same hash chain), equal node for node to what a synchronous recount would write (`test/replay-prepare.test.ts`). The slices' own cost is measured by the budget spec (`slice_max_ms` of each row).

**Flat nodes, no node object per batch** (03.07 Firefox p95): the observer callback is the recorder's whole per-batch cost against the <=5 ms budget, and Firefox charged its minor garbage collections (a nursery filled with one object and one id string per node) to that callback. The recorder therefore keeps the nodes of an emission as numbers: `NodeTable` (`src/replay/nodes.ts`) is three typed arrays (id, parent id, a mark packing tag code, class and text) that every walk of a recorder reuses, `walk` fills it, and its canonical form is written byte by byte into the hash buffer (`sha256ChunkHex`, exactly `canonicalJSON` of the node objects), so the hash chain and every golden chunk are unchanged. The chunk object handed to `emit`/`startReplay`'s tap is the same closed wire object as before (same keys in the same order); it keeps a frozen copy of the numbers, and its `nodes` is a memoized getter that makes the `ReplayNode` objects the first time a consumer reads it (a viewer, `JSON.stringify(chunk)`, core's object-form `captureReplay({...chunk})`; `startReplay`'s own delivery does not, see below). Batch code loops by index and owns its scratch collections (a `for...of` allocates an iterator result per step in code that runs once per batch), so a steady batch allocates the chunk, its events and strings, and what the platform itself creates for the records it reports (`MutationRecord`; the `NodeList` wrappers of `addedNodes`/`removedNodes` are no longer asked for, see "No record node lists").

**Production consumer, no node object either** (`startReplay` -> core): `startReplay`'s delivery does not read `chunk.nodes`. A chunk the recorder emitted keeps its number columns (`chunkNodes(chunk)`); `Nodes.canonicalText()` writes their canonical JSON array (sorted keys, ASCII) into one reused byte buffer and decodes it once, and `client.captureReplay(fieldsOf(chunk), nodesJson)` takes the chunk's other fields plus that text. Core checks the text against the closed node schema with one anchored regular expression (at most 4,096 nodes, each exactly `id`, `parent`, `tag`, `class`, `text` with the closed values) without making a node object, parses the rest of the record with `"nodes":[]` standing in, and splices the text in, so the queued record is byte for byte what `captureReplay({...chunk})` queues (pinned by `test/replay-consumer.test.ts` over every golden session). A chunk not made by this module is still delivered through `captureReplay({...chunk})`, which reads `chunk.nodes`. The `tap` receives the chunk itself: a viewer that reads `chunk.nodes` makes the objects then, once. Measured through this path by `fixtures/sdk/replay/mutation-batch.spec.ts` ("through the production consumer", row `MUTATION_BATCH_ROW_PROD`).

Replay is its own entry, `@soundpost/browser/replay` (design 13 budgets the core entry `@soundpost/browser` at <=40 KiB gzip and replay separately at <=60 KiB; the core entry imports no recorder and no profiler, so an application opts in by importing the entry it needs). `startReplay(client, config, tap?)` plus `setReplayConsent(client, enabled)` is the delivery path: every chunk the recorder emits is enqueued by the client itself on its ordinary queue (closed wire validation, batching, retry, receipts; `deploymentReplay: true` and a source policy with replay on are both required), so a chunk the queue refuses is the recorder's counted loss, healed by a gap-marked checkpoint. `tap` is an optional local consumer (for example a `ReplayStream` feeding a viewer) that sees every chunk; its failure never affects delivery. Closing the client closes the recorder. Revoking consent stops capture at once and destroys this client's replay chunks that are queued but not yet part of a batch; acknowledged chunks are not recalled and a resumed recording starts with a gap-marked checkpoint.

Parent-run checks: `bun test packages/browser packages/replay-viewer packages/core`; real browser: `playwright test -c fixtures/sdk/replay/playwright.config.ts recorder.spec.ts` (`SOUNDPOST_BUN` = bun binary used to bundle the recorder and the viewer's tree renderer, `SOUNDPOST_CHROME` = optional Chrome executable; `SOUNDPOST_FIREFOX` = stock Firefox, which turns the run into the Firefox project alone; `SOUNDPOST_PLAYWRIGHT_WEBKIT=1` = Playwright's WebKit engine alone, which needs a host with the GStreamer base and good plugins because the canary page carries a `<video>` element). ### Replay chain hash, one chunk per emission (cross-language contract)

Each chunk's `previous_hash`/`checkpoint_hash` is SHA-256 over `canonicalJSON(chunk)` (`src/replay/policy.ts`): sorted keys, no whitespace, integers only, exactly what Go's `replays.ChunkHash` computes, so the server verifies the chain whatever order the wire object serializes in. `fixtures/sdk/replay/chain-vectors.json` (generated by the real Go validator) is asserted by both this recorder and `packages/replay-viewer`.

One emission is exactly one chunk (at most 4096 nodes and 120,000 own-accounted bytes, under the 128 KiB protocol cap). When a snapshot or mutation subtree does not fit, `fitSubtrees` replaces whole low-priority subtrees (later in document order and deeper first, smallest first) with opaque placeholders (same id and parent, tag and class `masked`, empty text) until it fits, counts the loss, adds a `gap` event (a truncated checkpoint is also gap-marked) and suppresses deltas under the replaced ids until the next complete checkpoint. There is no fragmented-checkpoint format. A flat run of thousands of siblings can only shrink by collapsing their parent.

### Wire schema (decision D2: the server's closed schema is the contract)

The recorder emits exactly `model.ReplayChunk` of the server and nothing else; the server allowlist (`internal/replays` `ValidateChunk` after `model.StrictJSON`, and the ingest replay gate) stays closed and was not widened for it. A node is exactly `id parent tag class text`: `tag` is one of `div span p button input section canvas masked` (every other element, SVG and custom elements included, is the generic structural tag `masked`), `class` is empty or `masked` (opaque subtree; an opaque node whose `text` is `[masked]` is the closed-shadow mark), `text` is empty or exactly `[masked]`. There is no geometry, presentation, style or attribute field; the recorder records no layout and reads no computed style, and its one layout read is the yes/no box-size test (`offsetWidth`/`offsetHeight`) of the closed-shadow inference, made only on an empty upgraded custom element and never stored. An event is `at_ns kind node x y`; `at_ns` is the monotonic reading of the chunk's clock (the server's `MonoNano`), and pointer/scroll/resize coordinates are quantized to 8 CSS px and clamped to ±32768. Node ids are per chunk and restart at every checkpoint (the server admits at most 2^31). `replayId`, `sessionId` and the clock domain are 32 lowercase hex digits (not zero) and `capturePolicyRevision` is a decimal revision; `createRecorder` throws on anything else.

A replay has a server-side budget of 65536 chunks and 1024 checkpoints. The recorder ends capture for good when the next chunk would exceed either, rather than emit a chunk the server would refuse (a refused chunk would fail its whole ingest batch).

Cross-language contract tests: `packages/browser/test/replay-wire.test.ts` drives the real recorder over a scripted page and asserts the closed schema, masking (no canary text, value, class or id in any chunk) and that the committed golden chunks `fixtures/replays/recorder/{session,recovery}` are byte-identical to what the recorder emits now (regenerate after an intentional change with `SOUNDPOST_UPDATE_RECORDER_FIXTURES=1 bun test packages/browser/test/replay-wire.test.ts`). `fixtures/replays/recorder/recorder_test.go` decodes those same chunks with the Go strict decoder, validates them with `replays.ValidateChunk`, checks that Go's `ChunkHash` equals the hash chain computed in the browser, and shows the schema stayed closed against the former recorder shapes; `internal/replays/recorder_chain_test.go` admits them through the production path and reads the stored chain (continuous, a lost chunk as a gap, a refused chunk healed by a gap-marked checkpoint). The evidence smoke row `replay_real_recorder_chunks` and the journeys row `replay_masked_interaction_real_recorder` run the same chunks and a real Chrome recording against a real `soundpost serve`.

## Browser JS Self-Profiling (optional, off by default)

```ts
import {startProfile} from "@soundpost/browser/profile";
const handle = await startProfile({durationMs: 5000, intervalUs: 10_000, scope: "main", longTasks: true});
// ...application work...
const report = await handle.stop(); // idempotent, bounded, never rejects
```

`startProfile` wraps the W3C JS Self-Profiling `Profiler` (method `browser_js_self_profile`, signal `profile_chunk`) and never throws into the application: every expected failure is a report with a capability `status` + `reason`, empty `frames/stacks/samples`, `sample_count: 0` and `stopped_by: "not_started"`. Detection is by actually constructing the API, never by browser version:

| Situation | status | reason |
| --- | --- | --- |
| `Profiler` is not a constructor (Firefox, Safari, old Chromium, Chrome workers) | `unsupported` | `js_self_profiling_unavailable` |
| constructor throws `NotAllowedError` (what Chrome 156 throws, "JS profiling is disabled by Document Policy") or `NotSupportedError` | `denied` | `document_policy_missing` |
| any other `DOMException` (`SecurityError`, ...) | `denied` | `permission_denied` |
| any other constructor failure | `error` | `sampler_failed` |
| a second start while one is running (one lease per global, held under `Symbol.for("soundpost.profile.lease.browser_js_self_profile")`, so duplicate module copies conflict) | `denied` | `profiler_owned` |
| declared `scope` differs from the real global (Window vs WorkerGlobalScope) | `denied` | `isolate_scope_mismatch` |
| invalid options (`durationMs` integer 1..60000, `intervalUs` 1000..1,000,000, `maxSamples` 1..8192, `origin` an http(s) origin) | `denied` | `invalid_options` |
| `Profiler.stop()` does not settle within 5 s | `error` | `stop_timeout` (no samples, `timeout_cleanup` loss) |

The page must be served with `Document-Policy: js-profiling` (an HTTP response header on the document; the browser fixture proves Chrome refuses without it). A profile only covers the calling global: `coverage` is `{frames: partial, threads: partial, workers: none, tasks: none}` (JS frames only; native frames and cross-origin scripts without CORS are anonymized by the browser), and a worker needs its own start (Chrome 156 does not expose `Profiler` in dedicated workers at all, which is reported as `unsupported` with `scope.isolate: "worker"`).

Privacy: frames are `{module_id, function, artifact_id, line, column, offset: "0", reason}` code identities only. A script becomes its origin-relative path (`assets/app.js`) only when it is on `origin` (default: the global's own origin) with no query, fragment, user info or unsafe path characters; everything else (other origins, query/fragment URLs, the document itself, native frames) collapses to one `external` placeholder frame (consecutive duplicates removed). Function names must match a conservative identifier regex, otherwise the function is empty with `reason: "not_captured"`. Stacks are leaf-first (`stack_order: "leaf_first"`, at most 128 frames, root-most frames cut, counted in `scope.stack_depth_truncated_samples` and `truncated`), at most 4096 frames/stacks and `maxSamples` (<= 8192) samples; the passed `origin` is never copied into the report. Samples without a stack are engine idle: they are counted in `scope.idle_samples`, never invented as frames. Script-path secrets that are part of the path itself (e.g. `/u/12345/app.js`) cannot be detected and are kept.

Honest timing: `interval.requested_us` is what you asked for; `interval.achieved_us` is the median gap of the returned sample timestamps and `scope.granted_interval_us` is the `sampleInterval` the browser says it granted (Chrome 156 granted 10 ms for a 5 ms request in the fixture). Timestamps are `DOMHighResTimeStamp` milliseconds since the time origin; `samples[].at_us` are decimal-string offsets from the first sample and nothing is converted to wall time (`clock.uncertainty_ns` is the uncalibrated maximum). A `sample_gap` loss is reported for gaps over twice the effective interval (count = estimated missing samples) and whenever the document was hidden or its visibility changed during the run (background throttling; `scope.visibility`). A full browser buffer (`samplebufferfull`) or samples dropped at the caps is `truncated` with a lower-bound `truncated` loss count. Units are `samples`; no CPU unit exists anywhere in the report. `longTasks: true` adds `long_task` entries (`duration_ms`, `start_ms` relative to the profile start, nothing else, at most 256, overflow in `scope.long_tasks_dropped`) as separate `non_profile` metric entries, never inside the samples.

`createProfiler(env)` in `src/profile.ts` is the test seam (fake `Profiler`/`PerformanceObserver`/clock/timers); `startProfile` reads the real globals when it is called. Importing the module has no side effects and imports no replay code, so core capture/replay is unaffected where profiling is unsupported.

Checks: `bun test packages/browser/test/profile.test.ts` (fakes only); real Chrome: `playwright test -c fixtures/sdk/profiles/playwright.config.ts --project=chromium` (`SOUNDPOST_BUN` bundles `src/profile.ts`, `SOUNDPOST_CHROME` optional executable); the spec prints one `SOUNDPOST_PROFILE_EVIDENCE {...}` JSON line. Not qualified: Firefox, Safari, Edge, Chrome 142, Windows/macOS Chrome, headed runs.

### Delivering a profile (`startClientProfile`)

The module-level `startProfile` above returns a local report and sends nothing. To deliver, start the run on a client:

```ts
import {init} from "@soundpost/browser";
import {startClientProfile} from "@soundpost/browser/profile";
const client = init({...config, deploymentProfiles: true});
const handle = await startClientProfile(client, {durationMs: 5000, scope: "main"});
// ...
await handle.stop();   // the finished report is already queued; client.flush() sends it
```

The finished report (a refusal at start, a caller `stop()`, the duration timer or the stop timeout; exactly once per run) goes through the client's ordinary queue and transport: same batching, retry, durable-receipt ACK and loss counters as errors and spans. There is no second transport. `submitProfile(client, report)` does the same for a report you already hold (`createProfiler(env, report => submitProfile(client, report))` is the test seam).

What is sent, by `src/profile_wire.ts`:

| Report | Wire |
| --- | --- |
| any run (supported, `denied`, `unsupported`, `error`) | one `capability` record: `runtime/version/build/os/arch`, `signal: profile_chunk`, `method: browser_js_self_profile`, `status`, `reason`, `coverage`, `clock_domain`, `expires_ns`. Its record id is the capability id the chunks name. |
| `status: supported` only | one or more `profile_chunk` records: `profile_id`, a per-client `process_id`, `capability_id`, `method: runtime_cpu` (the server's closed method vocabulary has no browser value), `units: samples`, the same clock domain, frames `{module_id, function, artifact_id, offset, reason}` (no line/column: the closed server frame has none), stacks, samples `{at_ns, stack, count: "1", thread}` and `loss`/`truncated` from the report's losses. |

A refused or failed run is therefore the capability truth record alone: no chunk, no samples, never a fabricated profile. Sample times are offsets from the first sample (`at_ns = at_us * 1000`, `clock.mono_ns = "0"`, `clock.wall_ns = wall_start_ns`) with the report's maximal `uncertainty_ns`: no wall alignment is claimed. Threads map `main -> "1"`, `worker -> "2"`. A profile too large for one record (the queue refuses records over 262,144 bytes) is split into several chunks with the same `profile_id`, each with its own frame/stack tables; the loss count and `truncated` ride on the first chunk only. Long Tasks are never chunk samples; they are delivered as spans (below).

**Long Tasks (`longTasks: true`, decision for 10.17#13).** A Long Task is an elapsed interval of the main thread, not a profile sample and not CPU time. Each one the run observed (start and duration only, the entry's attribution is never read; at most 256 per run, the overflow is `scope.long_tasks_dropped` in the local report only) is delivered, after the profile's own records, as a root span of operation `long_task` (`span_kind: internal`, status `ok`, no parent, no dependency, monotonic start/end on the client's own clock) through the ordinary span path: the project opts in by listing `long_task` in the client's `operations` and in the signed policy, and traces must be allowed. The span path is `captureElapsedSpan` / `spanRefusal` of `@soundpost/core/elapsed`, not part of the core entry (which is at its size budget); an interval that cannot have happened (reversed, ending in the future, before the clock's epoch) is counted as `invalid_clock` and refused. A capability record of its own states what the observation could do once a run observes (`signal: span`, `method: long_task`, `status` `supported` / `unsupported` (the engine has a Profiler but no Long Tasks entry type) / `denied` with reason `unregistered_operation` or `traces_not_allowed`; coverage frames none, threads partial, workers none), so a missing span is never "no long tasks". Long Tasks are observed only while a profile run is observing: an engine without the JS Self-Profiling API (Firefox, Safari/WebKit) refuses the run before any observation, so it delivers the profile's own `unsupported` capability and neither a `long_task` capability nor a span (`web/e2e/browser-long-task.spec.ts` shows that answer in the real engines). Each task is its own one-span trace. Entries beyond the 256 cap are not delivered and not recorded as a durable loss. Checks: `test/profile-delivery.test.ts` (long tasks block), `packages/core/test/elapsed-span.test.ts`, `test/entries.test.ts` (the core bundle carries none of it), and end to end through a real server `web/e2e/browser-long-task.spec.ts` (Chromium: the real ingest route admits the capability and one span per reported task, the console reads the spans back through Explore and the trace view; Firefox, WebKit: nothing is stored).

Privacy is the report's: origin-relative script paths without query/fragment, conservative-regex function names or `external`, nothing else. `test/profile-delivery.test.ts` proves with canaries that a query string, a fragment, a foreign origin, an argument-bearing function name and extra trace fields (`arguments`, `locals`, `source`) never reach the serialized batch.

**Policy.** Delivery is off unless `deploymentProfiles: true` (`client.policyDecision.profiles`). There is no signed-policy flag for profiles: the server enforces the source policy's `kinds`, and a record whose kind is not listed makes the whole batch fail with 403, which stops the client's delivery. Enable `deploymentProfiles` only for a source whose policy lists both `profile_chunk` and `capability`. With the flag off nothing is enqueued and the drop is counted (`diagnostics().policy_disabled`, `profile_chunk_dropped`). Failures are counted, never thrown: `invalid_profile_record`, `profile_wire_failed`, `queue_full`, `record_too_large`, `closed`. A run still active when the client closes is delivered into a closed client and counted as `closed`.

Checks: `bun test packages/browser/test/profile-delivery.test.ts`; the real-process proof is the `journeys` smoke row `profile_linkage_with_capability_truth`.
