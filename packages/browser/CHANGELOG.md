# Changelog

## Unreleased

- Replay recorder, 03.07 Firefox p95 (the two remaining costs inside the observer callback): (1) A batch no longer reads any record's `addedNodes`/`removedNodes` (about 960 platform NodeList wrappers per 400-node batch). `DomAccessors.childListChange` is replaced by `recordKind(record)` (`"tail"`: a child-list record whose `nextSibling` is null; `"inside"`: any other child-list record; `"other"`: attributes, character data, a record the platform cannot describe), and the append check is made from the page: new `src/replay/links.ts` keeps the replay's child order as two typed-array columns by node id (last recorded child, previous sibling), `Walker`/`walk` (`src/replay/tree.ts`, now an explicit stack instead of recursion) write them, and at the end of a batch a parent whose records were all at the end is an append only when its last children read back from the page are the replay's own children (node for node, all the way down to the first child: one record can stand for a batch, so no older child is assumed unmoved) followed by nodes the replay does not hold. Anything else is the re-walk of the parent, as before. One deliberate difference from the former rule: an insertion before a node that was itself added in the same batch (a record with a following sibling) is now the re-walk of the parent where it used to be an append in document order; the replay shows the same page and the chunk is bigger (`test/replay-append.test.ts`, "new nodes are shown in document order…"). `MAX_RECORD_NODES` is gone with the lists it bounded (a record that adds thousands of nodes is one append the chunk fit may collapse, as for any other). Pinned by `test/replay-records.test.ts` (no list is ever read, real platform accessors over counting getters; red on the previous recorder: 43 added / 43 removed / 86 length reads), the random histories of `packages/replay-viewer/test/append-delta.test.ts` (a new variant of tail-record-only histories, with removals of the last child and re-appends of held nodes, against a fresh checkpoint) and eight mutants of the check and the preparation below (seven killed, one equivalent; `sh0307-evidence/fc2-mutants.txt`). (2) The id-space checkpoint (the recount a delta that would pass the 20,000-id cap is replaced by) is prepared between callbacks: once `PREPARE_HEADROOM` = 4096 ids are left the page is walked into a second epoch of ids in slices of `PREPARE_SLICE_NODES` = 512 nodes on zero-delay timers, fitted in a slice of its own, then hashed and written in a last one; a batch after the walk began makes it start over (`PREPARE_RESTARTS` = 8, then the recount is left to the callback that reaches the cap as before), any other checkpoint, a loss that takes the fit's room, a stop or revoked consent cancels it. The chunk is an ordinary checkpoint, node for node what a synchronous recount writes (`test/replay-prepare.test.ts`; red on the previous recorder: no preparation, the recount inside the callback). Wire v1, golden chunks, masking canaries unchanged; core 40,921 B gzip with the consumer change above, replay entry unchanged in kind.
- Replay production consumer without node objects: `startReplay` delivers a recorder chunk with `client.captureReplay(fieldsOf(chunk), chunkNodes(chunk).canonicalText())` instead of `captureReplay({...chunk})`, so the chunk's lazy `chunk.nodes` is never read on the delivery path (no `ReplayNode` object, no node JSON parse). New `Nodes.canonicalText()` (`src/replay/nodes.ts`): the canonical JSON array text of the nodes, written into a reused byte buffer and decoded once. The queued record text is byte-identical to the object path's (`test/replay-consumer.test.ts`: every golden session, the scripted session and a 1,500-node chunk; a spy on `Nodes.prototype.toArray`/`at` and a heap count show no node object), and a `tap` that reads `chunk.nodes` still gets the closed objects. `fixtures/sdk/replay/mutation-batch.spec.ts` gains "recorder p95 per mutation batch through the production consumer" (real `startReplay`, real core client, in-page ledger transport; row `MUTATION_BATCH_ROW_PROD`), same 5 ms budget.
- Replay recorder allocation per mutation batch (03.07 Firefox p95; Firefox profiler: GCMinor pauses of 2-5 ms, up to 15 ms, charged to the observer callback). A batch no longer creates an object or an id string per recorded node: the nodes of one emission are three reused typed arrays (`src/replay/nodes.ts` `NodeTable`: id, parent id, mark), `walk` writes numbers into them (parent ids are numbers now; `WalkState.nodes.toArray()` gives objects), and their canonical form goes straight into the hash buffer. The chunk handed to the consumer is the same closed wire object (same keys in the same order, `recorder_version` `"1"`, every golden chunk byte-identical) whose `nodes` is a lazy, memoized getter over a frozen copy of the numbers (three small typed arrays; id strings are shared): the array of node objects is made, once, by the first consumer that reads it (a viewer, `JSON.stringify(chunk)`, core's `captureReplay({...chunk})`). `fitSubtrees` edits a `NodeTable` in place. The observer callback also loops by index (a `for...of` allocated an iterator result per step in code that runs once per batch) and owns its scratch maps and arrays instead of creating them per batch. Firefox profiler, same workload: in-callback allocation sampled 218 KB to 78 KB per run (the rest is the platform's own MutationRecord/NodeList wrappers), minor GCs 17 to 11.
- Replay (D100): a start after the page has loaded (`document.readyState !== "loading"`, or body content present; `lateStart` config overrides the probe) is recorded: `ReplayRecorder.lateStart()` names the reason and the first checkpoint is gap-marked. The supported install is a classic script first in `<head>`. Chunk hashing writes nodes straight into the hash buffer (`sha256ChunkHex`, identical bytes) and `canonicalNodes` is gone, which removes about 100 KB of strings per large batch; it did not change the Firefox 400-node p95 (6.5-7 ms, see docs/support/budgets.md).
- Replay (03.07-C7): a closed shadow root attached BEFORE capture started is now inferred, never read. An upgraded autonomous custom element (`:defined`, valid custom element name) whose `shadowRoot` is `null`, with no light-DOM child and a layout box, is recorded as the closed-shadow mark: an opaque node (`class` `"masked"`) with the constant `"[masked]"` text, the one opaque shape no other cause produces, inside the server's closed vocabulary (no wire change, recorder_version `"1"`; the viewer renders it as `[opaque: closed shadow root not observable]`). Plain-tag hosts, hosts with light children and zero-size boxes stay undetectable (a platform limit, documented in the README). A custom element is no longer appended to (its record re-walks it, the inference ends with its first child). Real-browser spec `recorder.spec.ts` "a closed shadow root attached BEFORE capture started" on Chrome 142, Firefox 144.0.2 and Playwright WebKit; `fixtures/sdk/replay/playwright.config.ts` runs the WebKit engine alone with `SOUNDPOST_PLAYWRIGHT_WEBKIT=1`.
- Replay: a pure append is recorded once (03.07-C7, 03.09-C9). A node the replay holds that only gained new children (child-list records naming nothing the replay holds, the new nodes ending the parent's children, parent a node that shows children) emits the new subtrees only, under the parent's id, with one `mutation` event on the first new node (a node the viewer has never held, so it deletes nothing). Every other change (removal, move, insertion before a known sibling, attribute/character-data record, widget parent, an append the chunk cannot hold) is still the re-walk of the nearest known node. recorder_version stays `"1"`, no wire field or vocabulary changed, chunks of both shapes play on the unchanged viewer, and chunks stored by earlier recorders still play. `DomAccessors` gained `lastChild`, `previousSibling` and `childListChange`. Real Chrome 142 on the Debian 12 (6.1) lab VM (idle, 10 runs): p95 10/100/400-node bursts 0.5 / 1.0 / 2.6-4.3 ms (HEAD 1.6 / 4.4 / 5.2), declared gaps per row 0 / 0 / 1 (HEAD 0 / 21 / 24).
- Replay fix found by the new random-history test: a node the replay holds but that now sits below a region the replay shows nothing of (inside a widget or placeholder, or under an input) was sent again as a root of the replay (parent "0") or under the widget; it is now not sent, and a known node directly under an open shadow root is a full checkpoint.
- Long Tasks (10.17#13): with `startClientProfile(client, {longTasks: true})` each observed Long Task (start and duration only; attribution is never read; at most 256 per run, overflow in `scope.long_tasks_dropped`) is delivered as an elapsed-time root span of operation `long_task` through the client's ordinary span path (the project opts in by listing `long_task` in `operations` and in the signed policy; traces must be allowed), plus a capability record of its own (signal `span`, method `long_task`, status supported / unsupported / denied with a reason) so that "no spans" is never read as "no long tasks". Report entries are now `signal: "span"` and carry `start_mono_ns`/`end_mono_ns`. The span path is `captureElapsedSpan(client, operation, startMono, endMono)` and `spanRefusal(client, operation)` of `@soundpost/core/elapsed` (`core/src/elapsed_span.ts`, imported only by the profile entry; bigint ns on the client's monotonic clock; same trace switch and sampling as any span; an unlisted operation is refused without a record, and an interval that cannot have happened - not bigints, reversed, ending in the future, starting before the clock's epoch - is counted as `invalid_clock` and refused). The long-task code is not in the core entry: it is 40,784 B gzip (budget 40,960 B), the size at the commit before this wave.
- Core bundle budget restored: the core entry measured 42,239 B gzip (budget 40,960 B, `fixtures/sdk/overhead.mjs --only bundle` on the pinned Bun 1.3.14; 40,184 B at the commit before lane 4 waves 20-27) because the Node/Bun compact span store (`@soundpost/core` `lean_slab.ts`) was reachable from the browser entry through the delivery queue. The core queue no longer carries it (browser spans are serialized when they end, with the same bytes), and the core bundle is now 40,704 B. `test/entries.test.ts` now fails the core entry above 40 KiB and the replay entry above 60 KiB gzip, measured as the qualification row does.
- Type fix: the SHA-256 round variables in `replay/policy.ts` are annotated `number` (tsc reported TS7022 on the round loop; no behavior change).
- Replay recorder cost per mutation batch: nodes are sized and canonicalized by the recorder directly (no per-node `JSON.stringify` sizing when the chunk fits, `CanonicalText` for the node array in the hash chain), canonical JSON caches quoted keys and skips an unnecessary sort, SHA-256 reuses one message buffer. Wire bytes and hashes are unchanged (the committed fixtures are byte-identical). Worst per-burst p95 on the real-Chrome spec: 7.2/7.3/6.4 ms -> 4.1/4.7/4.5 ms (budget 5 ms).

- Replay: closed shadow roots attached while capture is active are recorded as opaque nodes (`attachShadow` interception, restored on stop); the 20,000-node cap is a running total over the live tree (a delta that would pass it becomes a fresh, exactly-recounted checkpoint). Roots attached before capture starts remain a documented limitation.
- Breaking: split the replay recorder and the profiler out of the core entry so the core bundle meets its design 13 budget (<=40 KiB gzip; measured 36,411 B, was 47,728 B with replay and profiler inlined). `@soundpost/browser` no longer exports `createRecorder`, `ReplayStream`, `startProfile` or the replay/profile types, and `Client` no longer has `startReplay`, `setReplayConsent`, `startProfile` or `submitProfile`. Use `@soundpost/browser/replay` (`startReplay(client, config, tap?)`, `setReplayConsent(client, enabled)`, `createRecorder`, `ReplayStream`) and `@soundpost/browser/profile` (`startProfile`, `startClientProfile(client, options)`, `submitProfile(client, report)`, `createProfiler`). Closing a client still closes its recorder.

## 0.1.0 — 2026-11-03

- Expose policy-first error graphs and explicit non-destructive global error/rejection listener leases.
- Use only available intrinsic native error brands and native event descriptors; retain explicit original-frame/aggregate-boundary limitations.
- Bind pending episodes to weak error identity and event source; actual browser fixture now covers unrelated rejection interleaving before error rethrow.
- Add cookie-free source-header HTTPS delivery with exact durable/historical receipt validation and bounded flush; prohibit disk spools and unread page-exit ACKs.
- Add explicit synchronous-only browser context, native spans, navigation commit timing, allowlisted fetch and closed worker propagation without guessed async parents.
- Add actual browser→Express→HTTP→PostgreSQL fixtures and exact driver/build checks; real Safari is not replaced by Playwright WebKit.
- Add manual job attempts with synchronous-only actual context and explicit terminal/error rebinding across await; author overlapping-job/real-browser C03/C05 fixtures without ambient-link or scheduler-health fiction.
- Add the owned replay recorder (`src/replay/`): capture only when project policy, deployment opt-in and explicit consent are all true; traverse the DOM directly into closed structural `ReplayNode`s (constant `"[masked]"` text/input masks, 8 CSS px quantized rectangles, inert tag enum, opaque frames/editable/textarea/select/media, 20,000-node cap with gap); `Client.startReplay`/`setReplayConsent` delegate to it and revocation destroys pending replay state without touching other queue entries.
- Hash the chain over canonical sorted-key JSON (`canonicalJSON`) instead of insertion-order `JSON.stringify`, so the hash equals Go's `replays.ChunkHash`.
- Emit every snapshot/delta as exactly one chunk: oversized content now collapses whole low-priority subtrees to opaque placeholders (`fitSubtrees`), reports the truncation (loss, `gap` event, gap-marked checkpoint) and suppresses deltas under the replaced ids until the next complete checkpoint; the continuation-chunk (fragmented checkpoint) behavior is removed.
- Add the optional JS Self-Profiling supplement `startProfile(options): Promise<ProfileHandle>` / `ProfileHandle.stop(): Promise<ProfileReport>` (`src/profile.ts`, method `browser_js_self_profile`): off unless started, feature-detected by constructing the real `Profiler` (never by version), one process-global lease (`profiler_owned`), bounded duration/buffer/stop, honest capability status+reason with zero samples for Firefox/Safari (`js_self_profiling_unavailable`), a missing `Document-Policy: js-profiling` header (`document_policy_missing`), scope mismatch and bad options; frames are leaf-first, origin-relative scripts or an `external` placeholder, never URLs with query/fragment; achieved interval, `sample_gap` loss (throttling/visibility) and separate non-profile `long_task` entries; no CPU unit. Real Chrome 156 qualification: `fixtures/sdk/profiles/browser.spec.ts`.
- Deliver profiles through the client queue: `client.startProfile(options)` / `client.submitProfile(report)` enqueue one `capability` record per run (refusals included, never a fabricated chunk) plus bounded, split `profile_chunk` records for a genuinely sampled run, via `src/profile_wire.ts`. Off unless `deploymentProfiles: true`; `createProfiler(env, deliver?)` gains the delivery sink. Module-level `startProfile` is unchanged (local report only).
- Make the recorder emit the server's closed replay schema exactly (decision D2; the server allowlist is unchanged): nodes are `id parent tag class text` only (`rect`/`pres` and every layout and computed-style read are gone), tags are `div span p button input section canvas masked` (anything else is `masked`), event `at_ns` is the monotonic clock reading, node ids restart at each checkpoint, identifiers and the policy revision are validated at construction, and capture ends at the server's 65536-chunk / 1024-checkpoint budget instead of emitting refusable chunks. `DomAccessors.rect`/`presentation` and the `ReplayRect`/`ReplayPresentation` types are removed.
- Deliver recorder chunks through the client queue: `client.startReplay(config, tap?)` enqueues every chunk itself (closed wire validation, batching, receipts); the second argument is now an optional local tap instead of the required sink. Revoking consent destroys the not-yet-batched replay chunks.
- Add the cross-language contract: `test/replay-wire.test.ts` (real recorder over a scripted page; golden chunks in `fixtures/replays/recorder`), `test/replay-delivery.test.ts`, `test/replay-limits.test.ts`.
