# Verified Customer Adoption Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Status:** Product design and subagent-driven implementation approved by Aryn Yklas on 2026-11-03 (m1 implementers, m2 reviewers). Preparation is authorized; actual customer access, production deployment/cutover and disruptive drills require the owning environment's separate authorization. No private inventory or runtime result is asserted here.

**Goal:** Replace legacy normal investigation/notification paths only after real source, application, isolation and failure evidence, while retaining required history and an independent external deadman.

**Architecture:** Read-only inventory and isolated shadow adapters precede SDK instrumentation and no-send policy comparison. A durable cutover barrier chooses one canonical normal-notification owner; reverse barriers support explicit rollback. Legacy retained history is read-only and visibly linked, not silently imported/deleted.

**Tech Stack:** Actual customer versions/configurations discovered from current refs/live state under authorization; Soundpost native custom SDK/protocol and source adapters; plan07 generic harness/evidence contracts. No assumption that a TypeScript gateway runs Node instead of Bun.

**Spec:** [requirements R17–R24](../specs/2026-11-03-soundpost-requirements.md), [design sections15–16](../specs/2026-11-03-soundpost-design.md), [contracts](../specs/2026-11-03-soundpost-contracts.md).

## Global Constraints

- Private customer adoption material lives outside this public repository/history; only generic schemas, sanitized evidence summaries and fixture recipes belong here.
- All three actual journeys are required: gateway→real model/dependency; maintained frontend→API→DB with mapped release/error; background failure→retry/recovery.
- Source adapters use Soundpost-owned normalized admission. No Sentry/OTLP/full upstream backend API promise is introduced by migration.
- No silent normal-notification retirement, legacy history deletion or independent deadman removal. Only one normal sender owner after a verified barrier.
- Cross-org/team/project denials and pipeline/node-loss/recovery are required, not dashboard screenshots alone.
- Customer production changes and disruptive drills need separate owning-environment authorization even after product approval.

## Review Focus

1. Stale repository checkout misrepresents current alert/control ownership: current-ref plus live evidence with explicit discrepancy ledger (Task1).
2. Imported source version ordering differs from delivery order: late/retry/duplicate/recovery shadow cases preserve newer state (Tasks2,4).
3. “Traced” journey has IDs but lacks actual HTTP/DB/dependency child spans: real request/operation evidence and visible inaccessible internals (Task3).
4. Cutover creates two normal senders or neither: durable ownership barrier and rollback gate with observed delivery IDs (Tasks5,6).
5. Legacy history disappears or deadman shares product failure domain: retention/export ledger plus independent outage proof (Tasks6,7).

## Completion evidence

Real customer code/runtime refs and infrastructure authorization stay private. Public closure reports only generic exercised criteria, dates and sanitized evidence hashes. Adoption is incomplete until all three actual journeys, isolation and pipeline/failure acceptance pass; lack of production authorization is reported precisely, never bypassed or relabeled a successful rollout.
