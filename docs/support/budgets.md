Server numbers use a synthetic loopback handler, 5 alternating runs of 3 s at 1000 req/s; raw series and requested/observed intervals are in the report JSON. Other jobs ran on the host. Linux arm64, Node 24 and Python rows are not exercised.

Release platform scope (owner decision D10, 2026-11-15): the release contains only linux/amd64. Budget rows for linux/arm64, Windows and macOS hosts and platform-specific browsers are reported as `out_of_release_scope` with D10 as the reason, not as met, failed or not exercised; they are listed separately from the rows above and never count as passed. Browser SDK rows run on Linux browsers. A later release that adds a platform re-enables its rows unchanged.

Withdrawn claim (owner decision D65, 2026-11-18): the "Server SDK p95 latency, core capture", "Server SDK CPU per request" and "Python / Bun core capture" budgets (<=5%) stay unchanged, the rows above stay **FAILED**, and this release makes no claim that server SDK capture meets them. Lane 4 optimisation is closed (D65). The release gate accepts exactly the 12 linux/amd64 server overhead rows of `qualification/matrix.yaml` (Node 22, Node 24, Python 3.12/3.13/3.14, Bun 1.3.14; 3 and 100 handler hashes) as `claim withdrawn (D65)` when each is `failed` with the structured `failure_class` `budget_miss` (an exercised row that was measured, missed a budget and had nothing else wrong; the exporter derives the class from the row's structure, never from its detail text), never as passed; a row that was not measured (`not_run`, `not_exercised`, missing, `harness` failure, `dropped_records`) still blocks, and every other overhead row (SDK queue, browser bundle and recorder, native, single-host, distributed, queries) is unaffected. The gate lists the withdrawn rows in its output and manifest, and the release notes state them (docs/releases/checklist.md, "Withdrawn claims").
