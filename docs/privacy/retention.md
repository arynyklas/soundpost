## Retention defaults (design section 12)

| Signal | Days | Note |
| --- | --- | --- |
| metrics, logs, traces (spans) | 14 | |
| capability and loss reports | 14 | ambiguity: the design names neither; they describe the data they accompany |
| errors, lifecycle conditions, job attempts | 90 | the declared lifecycle evidence journal |
| replay chunks, profile chunks | 7 | a replay checkpoint outlives its own deadline while a retained chunk depends on it |
| restricted raw sources | 1 (24 h) | never longer than 7 days (model validation) |
| source maps / symbols | 90 | or until the last retained error/profile of the same build expires, whichever is later (how the served process enforces it, and what it does not yet: [artifacts/lifecycle.md](../artifacts/lifecycle.md)) |
| audit | 365 | |

`retention.Defaults()` holds these values; `retention.Resolve` layers the audited, append-only versions in control state (`RetentionPolicies`, organization default then project) over them. A new version only affects batches admitted after its effective time. **Receipts keep the absolute deadlines they were issued with**; a policy change, a disk-pressure event or a restore never recomputes or rewrites a receipt time. Every version records actor, reason and time and appends an audit record (`retention.policy`).

## Capacity (storage/pressure.go)

80% used: warning. 90%: new low-priority batches (spans, replay, profile only) are rejected. 95%: every telemetry admission is rejected, before the consensus/audit reserve is exhausted. Rejections are retryable `unavailable`/`capacity` faults (503). Level changes are recorded in a bounded warning ring (`PressureStatus`), visible through the worker status. **Pressure never expires, trims or compacts away ACKed data and never alters a receipt deadline**: it has no such API. Retry of an already ACKed batch still returns the original receipt, and so does a retry of an artifact upload whose fragments are all stored: the gate runs only when a fragment still has to be written, so a new or partial upload is refused but a complete one is not. Deletion barriers, control writes, cancellations and maintenance are not subject to telemetry admission pressure, so freeing space by deleting always works. A failing disk meter fails closed (rejects).

**Host meters.** Linux, macOS and FreeBSD use `statfs(2)` (space available to unprivileged writers); Windows uses `GetDiskFreeSpaceExW` (space available to the calling user, quota-aware). On any other platform no meter exists: the engine is bound *unmetered*, intake is not gated by disk usage (rejecting every write with a capacity fault that can never clear would make the platform unusable), and the fact is surfaced, not hidden: `PressureStatus.Unmetered` is true and the warning ring holds one `disk_unmetered` entry. That is absence of a meter only; a meter that exists and errors still fails closed.

## Deletion (C11/C12)

Modes: `retire_org`, `retire_project` (permanent source/read denial), `historical_range` (persistent `[start,end)` predicate per signal; an empty signal list is rejected, never "all"), `entity` (replay/profile/artifact roots; records that merely link a deleted replay are retained and the link resolves as unavailable). There is no arbitrary field-text predicate.

1. **Begin** (`DeleteScope`, one control commit): the org delete generation advances, retirement removes the project/org from the authorizable set, bumps the org policy epoch (every earlier scope dies at revalidation) and retires its sources. Reads of covered data are denied from this instant by control state, before any slot has a barrier. Receipt phase `fencing` (HTTP 202) is not success.
2. **Barriers**: the worker commits a `delete_barrier` in each of the 64 data slots (a replicated `Barrier` entry validated against control). A write ordered before a slot's barrier may be ACKed under the old policy; a matching write ordered after it is rejected at apply and never ACKed; data outside the predicate keeps flowing in the new epoch. Control records every cursor (`RecordBarrier`). An unavailable slot, a failing authority checkpoint or a missing cursor leaves the operation `fencing`; a group is never skipped.
3. **Complete**: only with all 64 barriers and, when off-host backup is enabled, a verified authority checkpoint (`CheckpointDeletion`) whose generation covers the operation. The generation advances again.
4. **Physical cleanup** (separate from logical completion, target 24 h healthy). The worker advances the generation, then, per pass:
   1. erases covered records, artifact roots and their derived rows (one bbolt transaction per batch; the stored command becomes a `batch_redacted` that keeps the original hash and receipt, and the same transaction stamps the physical index the slot had applied), rewrites the segments that held them, and then **redacts the replication layer** (the paragraph below);
   2. **scrubs the free pages of `apply.db`**: bbolt never zeroes a page it frees, so after step 1 the deleted bytes still sat in the raw file. In bounded chunks, each inside its own write transaction, every page the freelist reports free is overwritten with zeros (nothing can reach a free page when no read transaction is open; if one is, the chunk is deferred and the pass reports `ScrubPending`). The owed scrub is a durable counter set by the erasing transaction, so a crash after step 1, or a rerun that finds nothing left to erase, still completes it. Rejected alternative: `bbolt.Compact` into a new file plus an atomic swap needs every one of the engine's ~30 `e.db` users quiesced and a second full copy of the database on disk; the in-place scrub is crash-safe by construction (a failed chunk rolls back, zeroed free pages are harmless);
   3. re-commits the operation's barrier in every group (`CheckpointErasure`, a no-op duplicate: the tombstone row is kept) so the applied index moves, because a snapshot cut at an index the group already has is a no-op and journal compaction at an index it already holds keeps the old snapshot inside the journal; then cuts a verified snapshot, drops every older snapshot directory (`DropSupersededSnapshots`; the store would otherwise keep the pre-deletion snapshot as the "previous" one, with its pinned segment copies) and compacts the journals onto it;
   4. only then records `physical: done`. A veto (hold), an owed scrub or any failure in 1-3 leaves it `pending`/`held` and the next pass retries.

   **Replication-layer redaction.** The replication layer keeps its own copy of every committed command, payload included: the retry table (`completed`, which makes a retried proposal idempotent and is serialized into every snapshot's `envelope.json`), the Raft journal (`ready.wal`) and the backup pin archives. Once the erasing transactions committed, the engine reads every redacted command of the slot back out of `replica_commands` and calls `replica.Group.RedactCompleted` with the command's application index and the redacted command as its replacement. The group keeps the command's ID, kind, term, physical and application index, reservation and outcome, so a retry still answers with the original receipt (a retry of an ACKed batch returns the stored receipt byte for byte; tested), and replaces the payload by the replacement, which is exactly what the machine stores for the command, so a voter that replays the entry applies the same redacted command. It keeps the SHA-256 of the payload the command was proposed with (`Entry.Original`): a retry carrying the original payload is still recognized, a different payload under the same ID is still a conflict. The journal is rewritten record by record into a temporary file, fsynced and renamed over `ready.wal` (a crash leaves the old or the new journal, never a mix); the in-memory log that is sent to a voter that is behind is rewritten too, so such a voter receives the redacted entry and never stores the original; every pin archive is rewritten the same way. What cannot be rewritten in place is a snapshot directory and the snapshot record a compacted journal begins with: they are sealed at their cut and checksummed. They carry the old payloads until step 3 replaces them (the checkpoint moves the applied index, the cut is a new snapshot built from the already redacted retry table and machine state, `DropSupersededSnapshots` removes the older ones, the journal is compacted onto the cut). Each erasure stamps the physical index its slot had applied (`replica_data` key `redact_floor`), and `Engine.ResidualStores` **measures** what can still hold a copy: `raft_journal` while the journal begins at or retains entries from a cut at or before that index, `raft_snapshots` while such a snapshot directory exists, `raft_completed_entries` while a redaction is owed, `storage_legacy_wal` while the pre-replication WAL of an upgraded node (below) still holds an entry that differs from the redacted command stored for the same index. After step 3 it is empty and the receipt's `residual_stores` is omitted; the deletion smoke requires the canary to be found in no store (`apply.db`, segments, snapshot files, snapshot state, snapshot retry table, journal, `control.db`).

   **Upgraded nodes (the pre-replication WAL).** A node that ran the 01.03 single-node layout has `data/slot-NN.wal` holding every command it admitted before replication was enabled. `EnableReplication` imports that history into `replica_commands` and leaves the file in place, because the 01.03 reader validates it on every open and a node that never replicates reads its state from it. After the import the file is no longer an authority, so the erase pass redacts it the way it redacts the journal: the file is streamed into `slot-NN.wal.redact` with every entry whose stored command is a redaction replaced by the stored redacted command (new length, header and payload checksums), every other entry copied byte for byte; the temporary file is fsynced, closed, renamed over the WAL and the directory is synced. The result is still a valid legacy WAL (same entry count and indexes, every entry decodes), so `recover` accepts it; a node that never replicates has no stored command, can erase nothing, and its WAL is never rewritten. Until the rewrite has run `ResidualStores` names `storage_legacy_wal`, measured by comparing each WAL entry with its stored redacted command, and the erase pass fails (so `physical: done` is not recorded) if the rewrite fails.

   Crash safety: the stored redacted command is the durable authority and is written atomically with the erasure, so no separate record of the redaction has to survive a crash. The redaction is idempotent and is repeated from that authority at the end of every erase pass, before every snapshot cut (`CreateSnapshots`), for every slot when replication is enabled (open) and after a snapshot is installed on a voter. The kill hooks `redact_replica` (engine), `redact_begin`, `redact_pins`, `redact_write`, `redact_sync`, `redact_switch`, `redact_renamed` and `redact_memory` (group) are exercised by tests; after each, an ACKed command still answers its retry with the original receipt and a rerun converges. The legacy WAL rewrite has its own hooks, `legacy_wal_begin`, `legacy_wal_write`, `legacy_wal_sync`, `legacy_wal_switch` and `legacy_wal_renamed`; after a crash at each the WAL in force is the complete old or the complete new file, a leftover `slot-NN.wal.redact` holds no erased byte and is removed by the next pass, and the next open converges. An error in the group's redaction before the journal was replaced (the begin, pin, write, sync and switch hooks, a read or temp-file error, a pin archive error) is returned to the caller without failing the group, so the next worker pass retries it; an error after the journal rename (`redact_renamed`, the directory sync, reopening the journal) or in the in-memory swap (`redact_memory`) can leave the group torn and still fails it until restart.

   **Still not covered (stated, not hidden):** (1) every voter erases its own local layout (stored commands, retry table, journal, snapshots) from its own worker pass, and `retention.Service.physical` selects only operations whose replicated control record has no physical-cleanup time. Once one voter records `physical: done`, the other voters' workers no longer select the operation, so their local copies are not erased by that worker: this is a multi-voter gap in the retention driver that was observed in the code and has not been exercised by a three-voter test; the replication-layer redaction itself is idempotent and is applied by any voter that runs an erase pass. On a voter that did not run the pass, `residual_stores` is **not a measurement**: the floor it is measured against (`replica_data` key `redact_floor`) is local and is stamped only by the erasing transaction, so such a voter reports nothing while it still holds every original byte, and a client polling that voter is told that nothing is residual. (2) A matching write that was ordered after a barrier is rejected at apply and never ACKed; its payload was never stored and is not identified by the erase pass, so the retry table, journal and snapshots keep it until it is compacted away; it is not redacted. (3) Freed filesystem blocks of files that were rewritten, renamed or removed (`ready.wal`, pin archives, snapshot directories) are not scrubbed, exactly as the OS leaves them; only `apply.db` free pages are zeroed, and unlinked files and freed blocks may survive on the device below the filesystem: this is not secure deletion of media. (4) `backup_deadline_ns` is recorded, validated and shown in the receipt, but nothing compares it with the clock and `residual_stores` never describes off-host copies: a backup object that was already uploaded keeps the pre-erasure bytes until the destination's own lifecycle policy removes it. Treat the deadline as advisory. (5) A snapshot cut at the index of the erasure itself (an expiry-driven erasure with no later write) is reported as residual until the index moves, although it may already be clean. (6) `control.db` held no telemetry values when this redaction was written (tombstone predicates carry none), but the rule, incident and condition control state added since (`RuleBooks`, `RuleOutputs`, `IncidentBooks`, `ConditionBooks`) can hold values derived from telemetry (a recording output carries a whole batch, a rule book the committed evaluation payload). Reads of those outputs are suppressed once a deletion covers their origin, but neither the deletion saga nor the erase pass removes or redacts the entries, the control group's journal and snapshots keep the commands that created them, and `ResidualStores` does not name `control.db`; they are not covered. Backup expiry is at most 30 days and suppression (the ledger) survives restore. Expiry erasure (no deletion operation, hence no checkpoint) refreshes snapshots and journals only as the groups' applied indexes advance with later writes.

`held`: an active legal hold overlapping the request blocks Begin (receipt `held`, nothing denied or erased). Releasing a hold never starts the deletion on its own; `Resume` (BeginFence) does. A hold placed after logical completion keeps the bytes physically present (receipt `physical: held`) while reads stay suppressed; releasing it lets the next worker pass erase after advancing the generation. Holds are checked again at erase time: the erase pass asks the guard before each batch or blob is removed, against the control state the erasing node has applied, and `RecordPhysicalCleanup` refuses, in the same control update, to stamp an operation a hold overlaps (the receipt says `held`, never `done`). Residual window: a hold that has committed but is not yet applied on the erasing node is invisible to the erase-time check, so its bytes can already be gone; the record-time gate still reports the operation `held`, and `WorkerStatus.ErasedBeforeHold` counts what that pass erased for such an organization. On a single voter the window is zero; it has not been tested with three voters.

`failed` is terminal for automation; the predicate stays active, nothing is ever un-deleted.

**Which control revision a retention command may carry.** `DeleteScope`, `BeginFence`, `CompleteFence`, `PolicyChange` and `RecordEvidenceGap` carry the control revision of the view their caller decided on. Control keeps `AuthorityRevision` in its replicated state: the revision of the last transition that could change authority, policy, retention, deletion or access state (every org, membership, grant, project, source-policy, source-grant, SSO, hold, retention-policy and deletion change, and every writer nobody classified). These commands commit when `AuthorityRevision <= expected_revision <= Revision`, that is, when the caller's view is at least as new as the last such transition; a view older than one, or newer than the current revision, is a `conflict`. Intake admissions, quota accounting, artifact reservations and the rule, condition, incident, delivery, issue, release and job books move `Revision` but not `AuthorityRevision`, so saturating intake can no longer starve a deletion's Begin (before this rule every Begin conflicted under saturating intake). Every other command kind keeps the exact `Revision == expected_revision` rule. A control state written before the field existed has it unset: it is treated as strict (only the current revision commits) and the first conflicting retention command stamps it. Retrying a committed `command_id` returns its stored outcome before any revision check. The classification lives in `internal/control/authority.go`; a writer wrongly classified as non-authority would let a deletion commit on a view older than a change that mattered, so that table is the review surface.

### Control state

The control store holds payloads derived from telemetry: rule evaluation values and recording batches (`RuleBooks`, `RuleOutputs`), incident and condition state (`IncidentBooks`, `ConditionBooks`), notification bodies (`DeliveryBooks`), issue evidence (`GroupingIssues`, `IssueBooks`), job state (`JobBooks`) and notification-cutover operator text (`CutoverBooks`). A committed deletion reaches them in the control apply itself, not in a later pass: one deterministic function of (state, predicate, transition time), with no clock, no randomness and sorted iteration, so every replica, snapshot install and journal replay installs the same bytes. It runs when a deletion begins, when it completes, when it fails, when a tombstone is re-imported from the restore authority, and whenever a control writer commits an effect of a project a finished deletion covers (see "Derived effects"). It is idempotent, and it appends a `delete.control_erased` audit only when it dropped something. Identities, versions, digests, counts, receipts and phases stay; payloads go.

* `retire_project` / `retire_org`: every payload of the covered projects (every project of the organization for `retire_org`), including the issue books (an issue book that cannot be read is dropped when its key names a covered project; another project's is left in place, and its reads fail closed) and the cutover operator text.
* `historical_range`: rule evaluations and outputs by their scheduled time in `[start,end)` of the named signals; issue evidence by event time in `[start,end)` when the range names the error signal; deliveries whose evidence interval overlaps; incident, condition and job states by the rule below.
* `entity`: outputs of the replay and profile signals of the project, issue evidence that links the entity by ID, and the rule books of exactly the rules that produced such an output. Jobs, incidents, conditions, deliveries and cutover records link replay/profile roots only by ID and are not covered.

**Opaque states fail closed, not exactly, when a deletion begins, completes or is imported.** An incident, condition or job state is opaque to this package. At those three points a range covers it when the newest evidence time it names (any number or numeric string under a key `at`, `*_at` or `*_ns`, at any depth) is **at or after `start`**, and also when it names no time or a time that cannot be read. This rule has no `end` bound and ignores the signal list: a `[start,end)` metric deletion tombstones an incident whose evidence is ten years after `end`. That is tolerable only because the payloads under it really are old at that moment, and it is the reason the rule must not run on later commits (see "Derived effects": the late pass uses the exact rule below). It differs from the rule and issue books, which are half-open and signal-gated; the difference is deliberate (a payload that cannot be attributed is dropped, never kept) and errs toward erasing. A covered state keeps only its closed header and the erasing operation; the services that read it see an erased record: `jobs` reads an empty state at the preserved version, `conditions` returns the erased marker (`State.Erased`) and the next event starts a new history on the kept version, and `incidents` returns the erased marker from `Get` and answers any action on it with `not_found` / `incident_erased`. An erased record is never reported as `corrupt`; a record that is neither a live state nor its own tombstone still is.

**control.db scrub.** bbolt never zeroes a page it frees, so the state an erasure replaced stays in the free pages of `control.db`. `Store.ScrubErased` zeroes every free page, in bounded chunks each inside its own write transaction (it defers while a reader is open: 40 attempts x 25 ms per chunk, then `Unavailable`, and the debt stays owed). Two debts keep it owed, and `control_state` is reported while either is: the replicated one, derived from the audit log (an erasing audit with no `delete.control_scrubbed` audit after it), which the scrub settles by committing a `delete.control_scrubbed` audit naming the operations whose erasing audits it covered; and the local one of each file (next paragraph). An erasure committed after a scrub owes a new one. The scrub runs first in the physical step (`RecordPhysicalCleanup`, which does not record `physical: done` when it fails) and on every retention worker pass of every voter, which is the only way the scrub of a failed operation (never physically recorded), of an effect erased after its operation's physical step, or of a follower's own file ever runs.

**control.db scrub is a fact about one file.** `delete.control_scrubbed` is replicated: it records that *some* node's `control.db` was scrubbed, normally the leader's. Every voter receives it, by replaying the log or inside an installed snapshot, while its own file was never scrubbed: the commit that applies an erasure frees the pages that held the payload on every voter and zeroes none of them, and an install rewrites the tree through copy-on-write pages and frees the replaced state the same way (a voter that had not applied the erasure yet still holds the payload live until then). So each file keeps its own debt, a marker (`local_scrub` in the `control` bucket of that `control.db`): `Apply` sets it in the transaction that adds an erasing audit (live, replayed or on the leader itself), and `Restore` sets it in the transaction that installs a snapshot whose log names an erasure or over a file that already owed a scrub (the marker is still set, or the log it replaces held an unsettled erasing audit). `control_state` is reported while the marker is set, whatever the log says, and a replicated scrubbed audit from any node never clears it; it survives a restart; only a `ScrubErased` that completed on this file afterwards clears it (a generation from the bucket's own sequence keeps a scrub from clearing an erasure or install that landed while it ran). When the log owes nothing itself, that scrub commits nothing replicated: no audit, no revision. The marker is not part of the state, of the snapshot metadata, of a seed, of any command or digest; no state transition reads it, so every voter computes the same bytes with or without it. The key's presence is the fact that a build with the marker has seen the file: `Open` writes it into every file it creates (nine zero bytes: settled, generation 0), and, as an OWED marker, once into an existing file that has none (below); it never rewrites a key that is there, so an owed marker stays owed under its generation and a settled one stays settled. A node that never applied an erasure owes nothing, and a seeded replica stays unmarked after its group opens: `OpenSeed` creates the file with the settled key, and the install that the group's first open makes of that same seed (the file's watermark is below the seed's index) replaces nothing, so `Restore` owes nothing when the marker key is present and settled, the file's own log owes nothing, and the installed state equals the stored one after canonical re-encoding; installing the identical state frees only pages that hold that same state. **What a bbolt scrub cannot reach:** blocks the filesystem keeps for earlier versions of the file (journal, snapshots of the volume, a copy-on-write filesystem's old extents), a backup or copy of `control.db` taken before the scrub, and the control Raft files, which are the journal's business (next paragraph); it zeroes the pages bbolt's freelist reports free at the time and nothing else. **A file written by a build that predates the marker** has no key and no record of the erasures it applied then, and its replicated log is not a complete memory of them: the leader's scrubbed audit may already be in it, and an install from another lineage by an earlier build could have dropped the erasing audit while the payload stayed in the free pages (a review reproduced a clean receipt over 24 payload copies that way). So `Open` marks EVERY such file owed, whatever its log names. A node that had already scrubbed before the upgrade, or never erased anything, does one redundant, bounded scrub on its first start under the new build, because the information that it had does not exist; that cost is accepted, since a false clean would be a privacy defect. The key vouches only for commits made by a build that has the marker: running an earlier build on the file after this one has settled it, and this build again afterwards, is not detected, and that downgrade path is not supported. A rejected `OpenSeed` over an existing file of another installation still goes through `Open` first, so it leaves that file's key behind. **A second accepted cost:** every later install, over a clean file, of a log that names an erasure and of a state that differs from the one the file holds owes one more scrub, because the audit log is append-only (an installed log names every erasure that ever happened) and the file cannot tell which pages the replaced state occupied. A voter that is cut off and catches up by snapshot therefore names `control_state` after each catch-up until its next worker pass zeroes the file again: one scrub per install, O(file size) writes, never a stuck debt for a readable state (a state that cannot be decoded is owed until an operator makes it readable, because `ScrubErased` answers Corrupt meanwhile).

**The control Raft journal.** Every control command replicates the whole control state, so the Raft journal (`raft-control/ready.wal`), its snapshots, the in-memory log and the replication layer's retry table keep complete earlier copies of the state, erased payloads included. `Store.RedactRetainedControlCommands` (the retention worker calls it on every pass, after the `control.db` scrub) removes them from **this node's** copy once every erasing deletion has finished (complete or failed; while one is fencing the live state still holds effects its completion will drop, so nothing is redacted for it and the journal stays named). It hands `replica.Group.RedactMachineCommands` the rule of `Store.RedactControlCommand`, which rewrites every retained command of kind Control (retry table, every `ready.wal` entry including superseded ones, the in-memory log a lagging voter is sent, the pin archives) to the same command minus the payloads a committed deletion covers; the command keeps its ID, indexes and outcome, so a retry still answers with the original receipt, and the digest of the payload it was proposed with is kept, so a retry of the original is still recognized. A replay of the redacted journal reaches the same control state: each command carries the whole next state, so redacted older commands are superseded by newer ones, and the command that establishes the current state is never rewritten (the redactor refuses a current state that still holds a covered payload instead). Snapshot directories and the journal's sealed head snapshot cannot be rewritten in place; the pass commits one empty control revision when no command is newer than the redaction, cuts a snapshot at the applied index, drops the superseded snapshots and compacts the journal onto it. `control_raft_journal` stops being reported exactly when `Group.MachineResidue` for the erasures committed so far is empty; it is reported again as soon as a newer erasure commits, after a restart (the proof is a fact about the process and is not persisted: the next pass finds the files clean and proves it), when a snapshot is installed from the leader, when a command rejected as stale is committed after the pass, while a backup pin is live, and whenever the pass fails.

**What that does not cover.** The proof is per voter: a voter redacts only its own copy, and a receipt is about the node that issues it. A voter that has not run the pass (down, partitioned, not yet applied the deletion) still holds and still names the residue; one voter's pass says nothing about another, and nothing observes the other voters, so a cluster-wide statement is not made. Not reached: backups and pin archives taken before the pass, snapshots already shipped off the node (a lagging voter sent the leader's sealed snapshot before the leader's pass completed stores it until its own pass), and copies the filesystem keeps in freed blocks of rewritten files.

**Per-voter bytes and passes that race an erasure.** The replacement a pass writes for a retained command is computed from the state of the voter that runs it (its live state and its finished deletions when the pass reads its rules), so the same command holds different redacted bytes on two voters, and their snapshot envelopes, hence the `snap-<index>-<checksum>` directory names and `Manifest.Checksum`, differ between voters, until every voter has run every pass; the live state is identical at once. Nothing may compare those bytes or digests across voters (repair, deduplication, "do these two nodes hold identical journals"). Retry recognition and conflicts are unaffected: the command keeps the digest of the payload it was proposed with. A pass reads its rules once, when it starts, so it can introduce a copy of a payload that an erasure committed after those rules were read: an erasure that commits while the pass runs leaves its covered payload in the `ready.wal` the pass rewrites and in the snapshot envelope it cuts. The receipt stays honest (it re-reads the live state, so `control_raft_journal` stays named) and the next pass removes that copy.

**Receipts.** `residual_stores` of a receipt names the stores of the whole installation only when the retention `Service` is built on `retention.NewResidualPlane(engine, controlStore)`: it reports the union of the engine's measurement and the control store's (`control_raft_journal` until this node's pass is proven, and `control_state` while a scrub is owed). On such a Service a `physical: done` receipt of an organization whose control payloads were erased lists `control_raft_journal` until the worker's pass has completed on this node (and again whenever the pass is not proven, see above); an empty list means nothing in either store of THIS node is owed. A Service built on the bare engine reports the engine's list only.

**Free text that survives a retirement (open owner decision).** The erasers drop payloads, not every field an operator or a consumer typed or the pipeline derived. The following stay after `retire_project` / `retire_org` (found by a field sweep of the book types; none is touched by any eraser): `RuleOutput.Reason` (consumer free text up to 512 bytes; the rules worker puts data-derived text in it, for example `series_conflict:<n>`), `RuleBook.Replays[].Reason` (operator free text up to 512 bytes), `RuleMissedRecord.Count` (records dropped by a query over the window), `RuleOutput.Inputs` and `RuleEvaluationRecord.Cursors` (data-group positions), `IssueBook.Checkpoints` and `IssueBook.Gaps` (including the evidence-gap reason up to 64 bytes and the interval times of expired telemetry), `State.EvidenceGaps`, `IssueBook.Commands[].Action.Fingerprint` and `GroupingIssue.Fingerprint` of surviving evidence, `State.GroupingMigrations[].Reason`, `State.Releases[].DisplayLabel` and history, the series identity of `State.Quotas` and `Reservations` (canonical hashes of deleted label sets) and `DeliveryRecord.Provider` (the vendor message id, kept after the body it identifies is erased). Most are hashes, counters and cursors that the design keeps as evidence ("identities, digests, receipts and phases stay"); the free-text ones (`RuleOutput.Reason`, `RuleBook.Replays[].Reason`, evidence-gap reasons, `GroupingMigrations[].Reason`, `DisplayLabel`) are what a reader of "nothing telemetry-derived stays" would expect gone after a retirement. Whether to drop them on the retire modes (as the cutover eraser does for step reasons) or to keep them as audit text is an **owner decision that has not been made**; this section states the current behaviour, it does not change it.

### Delete generation
`retention.Service` implements `auth.DeleteGenerations`: source-lifecycle base plus a durable per-org counter that advances at Begin, at completion, before physical erasure, on artifact GC cancellation, on expiry erasure and on erasure after a hold release. Caches, cursors, live positions and export tickets bound to an older generation die.

### Restore
`BuildLedger` derives the digest ledger plus exact tombstones from control state; the authority stores both on every completion. `Service.Restore(authority)` imports the missing tombstones into the restored control state, records the barrier in every slot and only then opens the engine's restore gate. A restore whose authority is unavailable or unverifiable stays closed. Task 01.09 implements `CheckpointDeletion`/`CurrentDeletionLedger` (and `CurrentDeletionTombstones`) in `internal/backup`.

### Derived effects
Every control writer that commits an effect derived from telemetry (rule evaluation, incident action, condition, job update, issue evidence, delivery enqueue) runs the control-state erasure (section "Control state" above), for the committed deletions that cover its project and have completed or failed, inside the same control transition that commits the effect. An effect that a worker read before a barrier and commits after its deletion completed therefore never leaves its covered payload in the live control state or the `control.db` pages it occupied (free pages are zeroed by the scrub above). That statement is about the control state only: the command that carried the effect is itself retained in the control Raft journal, its snapshots and the retry table, and that residue is removed from a node's copy by `Store.RedactRetainedControlCommands` (section "The control Raft journal" above; a command committed after a pass withdraws its proof until the next one). `control.EffectSuppressed(state, org, project, kind, at, entity)` remains a read-side predicate for a consumer that wants to skip work early; it is not how the control state is kept clean, and no writer relies on it. A deletion that is still fencing is the exception: an effect committed meanwhile is erased when the deletion completes (or fails).

**Temporal scope of the late pass.** The pass that runs in an effect's own transition is not the begin/complete erasure over again; it covers exactly what the effect could have derived from the deleted range. Rule evaluations, issue evidence and deliveries are half-open and signal-gated as above (an evaluation, evidence item or delivery interval at or after `end`, or before `start`, is kept). An incident, condition or job state is covered by a `historical_range` only when it names an evidence time **inside `[start,end)`** (the same half-open interval the exact books use), or names no time or one that cannot be read (unattributable: dropped whole, as at begin). A state is read for those times by the rule above, except that a zero or negative time (unset) and the duration keys `grace_ns`, `max_runtime_ns` and `observer_stale_after_ns` are not instants and are ignored. So a state first committed from data at or after `end` (the incident, condition or job a worker opens after the deletion, whose own times are its evidence time, its arrival and its evaluation time) or from data before `start` is **never** erased by the late pass, whatever other times it names; a state that mixes evidence inside the range with later times (a worker that read in-range data before the barrier and commits after) is erased whole. A retirement still covers every payload of its projects, an entity deletion still covers no opaque state, and the signal list is still ignored for opaque states (a state does not name the signal its evidence came from), so a metric range erases an in-range incident whatever signal fed it. The late pass appends a `delete.control_erased` audit, and so owes a `control.db` scrub, only when it dropped something: a commit that erases nothing appends no audit and re-owes nothing. The begin/complete/import rule is unchanged, so a state first committed while a deletion is still fencing is erased at completion by the coarse rule even when its evidence is outside the range; that window is the cost of not attributing opaque states. Redacting a retained control command (`Store.RedactControlCommand`) uses the rule its own commit used: the coarse one for a command whose state has the deletion still fencing, the late one for a command committed after it finished.

## Evidence journal and gaps
Error, condition and job evidence expires only through `EraseExpired` gated by the lifecycle processing checkpoint. Unprocessed evidence is erased only after a durable `RecordEvidenceGap` (interval, count, signals) commits; expiry never advances a processing checkpoint, and a gap that cannot commit keeps the evidence (`EvidenceHeld`). Journal truncation (`CreateSnapshots` + `CompactJournals`, default hourly) retains the whole history inside the verified snapshot, so it never loses evidence.

## Known limits
Expired-but-unerased data stays readable until the next expiry pass (default hourly). Evidence gaps are declared per contiguous run of expired candidates and count each entry once, so a gap never covers a not-yet-expired entry between candidates. Only gaps declared by the worker authorize expiry: control decides who declared a gap from the path it arrived on, an administrator-declared gap is recorded and audited but authorizes nothing, gaps recorded before this rule (no declarant) authorize nothing, and every gap is audited with declarant, interval and count. Quota charges of erased data are not refunded. While a hold or an open reader keeps `physical` from being recorded, the deleted bytes are still physically present everywhere (reads stay denied). During physical cleanup, until the next snapshot cut, a group has no "previous" snapshot to fall back on.
