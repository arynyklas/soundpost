## Retention defaults (design section 12)

| Signal | Days | Note |
| --- | --- | --- |
| metrics, logs, traces (spans) | 14 | |
| capability and loss reports | 14 | ambiguity: the design names neither; they describe the data they accompany |
| errors, lifecycle conditions, job attempts | 90 | the declared lifecycle evidence journal |
| replay chunks, profile chunks | 7 | a replay checkpoint outlives its own deadline while a retained chunk depends on it |
| restricted raw sources | 1 (24 h) | never longer than 7 days (model validation) |
| source maps / symbols | 90 | or until the last retained error/profile of the same build expires, whichever is later (how the served process enforces it, and what it does not yet: [artifacts/lifecycle.md](../artifacts/lifecycle.md)) |
| audit | 365 | |

`retention.Defaults()` holds these values; `retention.Resolve` layers the audited, append-only versions in control state (`RetentionPolicies`, organization default then project) over them. A new version only affects batches admitted after its effective time. **Admission applies it.** `policy.Service.BindRetention(retention.NewAdmissionResolver(control))` makes `ResolveSource` resolve the retention in force for the source's organization and project at the instant of admission (`retention.Resolve`, one linearizable control read), and `policy.Normalize` stamps each signal's absolute deadline from it (restricted_raw sources use the resolved `RawDays`, default 1). Once bound, the retention days a source policy carries no longer decide deadlines (the audited organization/project versions do); an unbound service keeps the old behaviour. The admin `retention` command (organization setting `retention:<id>` with `project_id`, `signal` in metrics, logs, traces, errors, replay, profiles, audit, and `days`) appends such an audited version for every signal kind the signal names (`errors` covers errors, conditions and job attempts); `audit` is stored as a setting only, the audit period is not an admission deadline (task 01.08-W2 owns audit expiry). The `PolicyChange` `retention_policy` control command appends the same kind of version. **Receipts keep the absolute deadlines they were issued with**; a policy change, a disk-pressure event or a restore never recomputes or rewrites a receipt time. Every version records actor, reason and time and appends an audit record (`retention.policy`).

## Capacity (storage/pressure.go)

80% used: warning. 90%: new low-priority batches (spans, replay, profile only) are rejected. 95%: every telemetry admission is rejected, before the consensus/audit reserve is exhausted. Rejections are retryable `unavailable`/`capacity` faults (503). Level changes are recorded in a bounded warning ring (`PressureStatus`), visible through the worker status. **Pressure never expires, trims or compacts away ACKed data and never alters a receipt deadline**: it has no such API. Retry of an already ACKed batch still returns the original receipt, and so does a retry of an artifact upload whose fragments are all stored: the gate runs only when a fragment still has to be written, so a new or partial upload is refused but a complete one is not. Deletion barriers, control writes, cancellations and maintenance are not subject to telemetry admission pressure, so freeing space by deleting always works. A failing disk meter fails closed (rejects).

**Host meters.** Linux, macOS and FreeBSD use `statfs(2)` (space available to unprivileged writers); Windows uses `GetDiskFreeSpaceExW` (space available to the calling user, quota-aware). On any other platform no meter exists: the engine is bound *unmetered*, intake is not gated by disk usage (rejecting every write with a capacity fault that can never clear would make the platform unusable), and the fact is surfaced, not hidden: `PressureStatus.Unmetered` is true and the warning ring holds one `disk_unmetered` entry. That is absence of a meter only; a meter that exists and errors still fails closed.

## Deletion (C11/C12)

Modes: `retire_org`, `retire_project` (permanent source/read denial), `historical_range` (persistent `[start,end)` predicate per signal; an empty signal list is rejected, never "all"), `entity` (replay/profile/artifact roots; records that merely link a deleted replay are retained and the link resolves as unavailable). There is no arbitrary field-text predicate.

1. **Begin** (`DeleteScope`, one control commit): the org delete generation advances, retirement removes the project/org from the authorizable set, bumps the org policy epoch (every earlier scope dies at revalidation) and retires its sources. Reads of covered data are denied from this instant by control state, before any slot has a barrier. Receipt phase `fencing` (HTTP 202) is not success.
2. **Barriers**: the worker commits a `delete_barrier` in each of the 64 data slots (a replicated `Barrier` entry validated against control). A write ordered before a slot's barrier may be ACKed under the old policy; a matching write ordered after it is rejected at apply and never ACKed; data outside the predicate keeps flowing in the new epoch. Control records every cursor (`RecordBarrier`). An unavailable slot, a failing authority checkpoint or a missing cursor leaves the operation `fencing`; a group is never skipped.
3. **Complete**: only with all 64 barriers and, when off-host backup is enabled, a verified authority checkpoint (`CheckpointDeletion`) whose generation covers the operation. The generation advances again.
4. **Physical cleanup** (separate from logical completion, target 24 h healthy). The worker advances the generation, then, per pass:
   1. erases covered records, artifact roots and their derived rows (one bbolt transaction per batch; the stored command becomes a `batch_redacted` that keeps the original hash and receipt, and the same transaction stamps the physical index the slot had applied), rewrites the segments that held them, and then **redacts the replication layer** (the paragraph below);
   2. **scrubs the free pages of `apply.db`**: bbolt never zeroes a page it frees, so after step 1 the deleted bytes still sat in the raw file. In bounded chunks, each inside its own write transaction, every page the freelist reports free is overwritten with zeros (nothing can reach a free page when no read transaction is open; if one is, the chunk is deferred and the pass reports `ScrubPending`). The owed scrub is a durable counter set by the erasing transaction, so a crash after step 1, or a rerun that finds nothing left to erase, still completes it. Rejected alternative: `bbolt.Compact` into a new file plus an atomic swap needs every one of the engine's ~30 `e.db` users quiesced and a second full copy of the database on disk; the in-place scrub is crash-safe by construction (a failed chunk rolls back, zeroed free pages are harmless);
   3. re-commits the operation's barrier in every group (`CheckpointErasure`, a no-op duplicate: the tombstone row is kept) so the applied index moves, because a snapshot cut at an index the group already has is a no-op and journal compaction at an index it already holds keeps the old snapshot inside the journal; then cuts a verified snapshot, drops every older snapshot directory (`DropSupersededSnapshots`; the store would otherwise keep the pre-deletion snapshot as the "previous" one, with its pinned segment copies) and compacts the journals onto it;
   4. only then records `physical: done`. A veto (hold), an owed scrub or any failure in 1-3 leaves it `pending`/`held` and the next pass retries.

   **Replication-layer redaction.** The replication layer keeps its own copy of every committed command, payload included: the retained Raft log and the journal that mirrors it (`ready.wal`) and the backup pin archives. Its retry table (`completed`, which makes a retried proposal idempotent and is serialized into every snapshot's `envelope.json`) keeps, for a slot command, only the receipt and the SHA-256 of the payload (`slotMachine.RetryByDigest`) and only the newest `slotRetryMax` (1024) commands, so it holds no payload; a snapshot written by an earlier build still carries payload-bearing entries until a later cut replaces it. Once the erasing transactions committed, the engine reads every redacted command of the slot back out of `replica_commands` and calls `replica.Group.RedactCompleted` with the command's application index and the redacted command as its replacement. The group finds the command's copies by ID in the retry table and, for a command the bounded table has already forgotten, by application index in the retained log and in every pin archive (`Group.locateRetainedLocked`; the journal file mirrors the retained log), so the redaction does not depend on the table having kept the command. The group keeps the command's ID, kind, term, physical and application index, reservation and outcome, so a retry inside the table's window still answers with the original receipt (a retry of an ACKed batch returns the stored receipt byte for byte; tested; a retry the table no longer holds is refused as stale by the application index every slot command carries, and an ACKed batch is answered from the engine's own receipts), and replaces the payload by the replacement, which is exactly what the machine stores for the command, so a voter that replays the entry applies the same redacted command. It keeps the SHA-256 of the payload the command was proposed with (`Entry.Original`): a retry carrying the original payload is still recognized, a different payload under the same ID is still a conflict. The journal is rewritten record by record into a temporary file, fsynced and renamed over `ready.wal` (a crash leaves the old or the new journal, never a mix); the in-memory log that is sent to a voter that is behind is rewritten too, so such a voter receives the redacted entry and never stores the original; every pin archive is rewritten the same way. What cannot be rewritten in place is a snapshot directory and the snapshot record a compacted journal begins with: they are sealed at their cut and checksummed. They carry the old payloads (in the snapshot's window files) until step 3 replaces them (the checkpoint moves the applied index, the cut is a new snapshot built from the already redacted machine state, `DropSupersededSnapshots` removes the older ones, the journal is compacted onto the cut). Each erasure stamps the physical index its slot had applied (`replica_data` key `redact_floor`), and `Engine.ResidualStores` **measures** what can still hold a copy: `raft_journal` while the journal begins at or retains entries from a cut at or before that index, `raft_snapshots` while such a snapshot directory exists, `raft_completed_entries` while a redaction is owed, `storage_legacy_wal` while the pre-replication WAL of an upgraded node (below) still holds an entry that differs from the redacted command stored for the same index. After step 3 it is empty and the receipt's `residual_stores` is omitted; the deletion smoke requires the canary to be found in no store (`apply.db`, segments, snapshot files, snapshot state, snapshot retry table, journal, `control.db`).

   **Upgraded nodes (the pre-replication WAL).** A node that ran the 01.03 single-node layout has `data/slot-NN.wal` holding every command it admitted before replication was enabled. `EnableReplication` imports that history into `replica_commands` and leaves the file in place, because the 01.03 reader validates it on every open and a node that never replicates reads its state from it. After the import the file is no longer an authority, so the erase pass redacts it the way it redacts the journal: the file is streamed into `slot-NN.wal.redact` with every entry whose stored command is a redaction replaced by the stored redacted command (new length, header and payload checksums), every other entry copied byte for byte; the temporary file is fsynced, closed, renamed over the WAL and the directory is synced. The result is still a valid legacy WAL (same entry count and indexes, every entry decodes), so `recover` accepts it; a node that never replicates has no stored command, can erase nothing, and its WAL is never rewritten. Until the rewrite has run `ResidualStores` names `storage_legacy_wal`, measured by comparing each WAL entry with its stored redacted command, and the erase pass fails (so `physical: done` is not recorded) if the rewrite fails.

   Crash safety: the stored redacted command is the durable authority and is written atomically with the erasure, so no separate record of the redaction has to survive a crash. The redaction is idempotent and is repeated from that authority at the end of every erase pass, before every snapshot cut (`CreateSnapshots`), for every slot when replication is enabled (open) and after a snapshot is installed on a voter. The kill hooks `redact_replica` (engine), `redact_begin`, `redact_pins`, `redact_write`, `redact_sync`, `redact_switch`, `redact_renamed` and `redact_memory` (group) are exercised by tests; after each, an ACKed command still answers its retry with the original receipt and a rerun converges. The legacy WAL rewrite has its own hooks, `legacy_wal_begin`, `legacy_wal_write`, `legacy_wal_sync`, `legacy_wal_switch` and `legacy_wal_renamed`; after a crash at each the WAL in force is the complete old or the complete new file, a leftover `slot-NN.wal.redact` holds no erased byte and is removed by the next pass, and the next open converges. An error in the group's redaction before the journal was replaced (the begin, pin, write, sync and switch hooks, a read or temp-file error, a pin archive error) is returned to the caller without failing the group, so the next worker pass retries it; an error after the journal rename (`redact_renamed`, the directory sync, reopening the journal) or in the in-memory swap (`redact_memory`) can leave the group torn and still fails it until restart.

   **The group redaction does not hold the group lock while it rewrites files.** `RedactCompleted` plans under the lock (the commands to redact in the retry table and the retained log, the journal handle and its length, the pin archives and their lengths), stages the rewritten journal and pin archives as temporary files without it, so Propose and ReadIndex keep answering during a long rewrite (`TestRedactCompletedDoesNotHoldTheGroupLockWhileItRewrites`), and installs them under the lock only when the group is exactly what the plan read: the same applied index, retained log, journal file at the same length, and pins with the same archive files at the same lengths. A commit, a cut and compaction, or a new or changed pin in between discards the staged copies and starts over (`TestRedactCompletedStartsOverWhenTheGroupChangesWhileItStages`); the fourth attempt holds the lock throughout, so a group that never stops committing still gets its redaction (`TestRedactCompletedOverAGroupThatNeverStopsCommittingStillCompletes`). A pin archive keeps only the commands above its `After`, so a pin whose `After` is at or above the highest application index of every copy of the commands to redact cannot hold one and is not opened (`RedactResult.PinsSkipped`, `TestRedactCompletedDoesNotOpenAPinThatCannotHoldTheCommand`); a command located by application index because the retry table forgot it has no known bound and every pin is read. Not covered: a second committed copy of an ID that the retry table still holds, with an application index above a pin's `After` and no copy anywhere but in that pin's archive (the leader refuses to propose such a copy).

   **Still not covered (stated, not hidden):** (1) **Fixed (was a multi-voter gap):** every voter erases its own copy from its own worker pass. `retention.Service.physical` selects an operation for a voter when the control record has no physical-cleanup time OR the voter has no durable local marker for it (`storage.Engine.ErasedLocally`, a `replica_data` key `erased:<operation>` written after this voter erased, scrubbed `apply.db` and cut its own snapshots and journal), so a voter that was up while another recorded `physical: done`, a voter that was stopped, and a voter that installed a snapshot all erase their own live keys (`batches`, `metrics`, `scan_postings`, `scan_pages`, `replica_commands`) and zero their own free pages. Each voter then proposes one replicated `erase_ack` command (slot 0, `storage.Engine.AckErasure`) naming the operations it erased, but only while its own `ResidualStores` is empty. The author of an acknowledgement is the PROPOSER the replica layer recorded in the committed entry (`replica.Entry.Proposer`: the leader for a proposal made on it, the member whose mTLS certificate authenticated the hop for a forwarded one; whatever the entry claimed about its author is discarded), never a name inside the payload: an acknowledgement that does not name its proposer is refused at the leader (`Validate`) and writes nothing on apply, so one voter cannot state another voter's erasure, and a command written before the proposer existed is never counted (see the limits). The receipt of a `physical: done` operation adds `data_apply_db` to `residual_stores` (`Engine.ErasureResidual`, merged by `Service.receipt`) until THIS voter has its marker and every member of the committed configuration has an acknowledgement for the operation that still stands, so a stopped or lagging voter keeps the data store named on every other voter's receipt until it catches up, erases and acknowledges. `Engine.ResidualStores` also names `data_apply_db` while a scrub of this voter's `apply.db` free pages is owed (a snapshot install or an interrupted pass). Limits: (a) an acknowledgement stands only for the bytes it measured. A snapshot install that replays a stored `batch`, `batch_redacted` or `artifact_fragment` command into the live buckets (`slotMachine.Restore`: a voter catching up from a sender whose stored commands still carry the erased payloads, or from an old pin) can bring erased rows back, so it clears ALL of the voter's `erased:` markers (not only those of the operations whose rows it carries) and raises the voter's installation epoch; the voter then proposes `erase_unack` for that epoch from a goroutine of the engine (retried until it commits, again from every `AckErasure` before it acknowledges, and after a restart, because what is owed is durable), and every acknowledgement it made under an earlier epoch stops counting on every voter, so the receipt names `data_apply_db` again until the voter's worker erased, cut and acknowledged anew under the new epoch (the worker selects the operation again because its marker is gone). A standing acknowledgement whose marker is gone, or whose stores turn dirty (`ResidualStores` non-empty), is withdrawn the same way by the voter's next `AckErasure`. `MarkErased` also refuses an erasure that started before an install (or in another process), so an install that lands between the erase and the mark cannot be certified. The install's own withdrawal commits after the install, so the window between them is closed from the SENDER's side (task 11.04): before a snapshot message leaves, the group that sends it commits a replicated `erase_notice` naming the receiving member in slot 0 (`replica.SnapshotGate`, `Engine.beforeSnapshotSend`; a gate failure or timeout withholds the message and Raft sends it again, and the notice index is the message's token). An acknowledgement carries the notice counter of its voter that the voter had applied when it measured (`basis`), and stands only while that is still the voter's latest, so a receipt answered on ANOTHER voter names `data_apply_db` from the notice on, before the snapshot can even arrive (`TestAReceiptReadOnAnotherVoterIsDirtyFromTheNoticeOfASnapshotToAnAcknowledgedVoter`, with the snapshot held in transit while the other voters erased and acknowledged). The receiving voter acknowledges nothing while a notice it applied is unsettled: the snapshot it announced is being stepped (`AdmitSnapshot`, released after `Step`), or the grace period (2 minutes) has not lapsed; once it lapses the voter gives the announcement up and REFUSES that snapshot if it still arrives, and so does it any token at or below a counter an acknowledgement was stamped under. A receipt is also read from the answering voter's applied state, and a voter that has not applied the notice entry would still count the acknowledgement it voided, so `Engine.ErasureResidual` gives a clean answer only after the slot-0 group confirmed with a read index that this voter has applied everything committed (the notice included): a voter that is cut off, has no leader or quorum, or is not caught up within the read's bound (5 s) answers `data_apply_db`. A dirty answer is decided from local state and needs no read; a would-be clean one costs one quorum round (`TestAReceiptOnAVoterThatHasNotAppliedTheLatestNoticeIsNotClean`: the cut-off voter 2 answered clean while voters 1 and 3 had committed a notice naming voter 3, red before the read, green after). Residual: a notice committed after the read is seen by the next receipt, not by this one, and a snapshot sent by a sender that does not implement the gate (an older binary) is admitted as before, covered only by the withdrawal. (b) A voter that marks an operation before it applied the tombstone (a lagging voter whose pass ran on state that never held the rows) and then catches up: by a snapshot install its marker goes like any other (limit (a); `TestLaggingVoterThatMarkedBeforeItsCatchUpLeavesNoLiveCanaryBehindACleanReceipt` measured the marker cleared and the voter erasing again); by log append the covered records ordered before the barriers are applied live AFTER the erase read the state, and nothing but the marker said otherwise. `EraseDeleted` therefore registers its predicates, the apply of any stored batch or artifact fragment a registered predicate covers marks that erase dirty (`noteApplied`), and `MarkErased` refuses (conflict) a dirty erase, so the worker erases again on its next pass (`TestAVoterThatErasedBeforeItAppliedTheTombstoneAndCaughtUpByLogAppendIsNotCertified`, which drives exactly that order: 6 covered records applied live behind a marker, red before the rule). A covered record ordered after the barrier is rejected at apply and never marks anything, so an erase that began after the barrier is not made dirty by it. (b2) Every data directory carries a random incarnation id (`meta/incarnation`, created at the first open of the directory; `Engine.Incarnation`). Once every member declared the protocol, a voter declares its incarnation in an `erase_unack` that names it; an acknowledgement carries the incarnation it was made on and stands only for the one the voter LAST declared, and declaring a new one restarts the voter's floor, so a disk that replaced another under the SAME node id and identity inherits none of its acknowledgements and is not held back by its floor (`TestAnAcknowledgementDoesNotOutliveTheDiskItWasMadeOn`). Until the replacement disk's declaration commits (it needs a leader and the replacement's slot 0 caught up) the old acknowledgements still stand on other voters, and the supported replacement stays a new identity (`distributed.md`). (b3) **Mixed versions.** The entries above are new shapes (`erase_notice`; `basis` and `incarnation` on an acknowledgement; an `erase_unack` that declares a disk) that the previous binary (be4070f, 10.35) decodes strictly and cannot apply, and since 10.35 every `erase_ack`/`erase_unack` carries a `proposer`, which the binary before it cannot decode either. Upgrade order: roll every voter and learner to this version before expecting the new protection, one at a time as `upgrade.md` says; nothing is proposed in a new shape until every member of the committed configuration has declared the protocol (an acknowledgement of a reserved operation, `erase-protocol-1`, in the shape the previous binary applies and ignores: at worst it withdraws its own acknowledgements once), so a half-upgraded installation keeps writing the previous shapes and its receipts behave as before. A member that joins later on an older binary does not make the entries it cannot read go away: the gate is evaluated at every proposal, falling back to the previous shapes, and the previous-shape acknowledgements of a voter that declared a disk never stand (a receipt stays dirty rather than false clean). A binary that predates 10.35 is not supported in a mixed installation. `TestANewBinaryReadsEveryOlderEraseEntryShape` decodes and re-encodes to the same bytes every shape the earlier binaries wrote and shows the new shapes are not readable by them; `TestNothingNewIsProposedUntilEveryMemberDeclaredTheProtocol` shows the gate. (c) An acknowledgement written by the previous version (a one-byte value, a stored command with no proposer) never counts: each voter acknowledges once more after the upgrade and the receipt names `data_apply_db` until all have; an operation completed before this version has no marker on any voter, so each voter re-runs the (idempotent) erase for it once; learners are members and must acknowledge too. (2) A matching write that was ordered after a barrier is rejected at apply and never ACKed; its payload was never stored and is not identified by the erase pass, so the retry table, journal and snapshots keep it until it is compacted away; it is not redacted. (3) Freed filesystem blocks of files that were rewritten, renamed or removed (`ready.wal`, pin archives, snapshot directories) are not scrubbed, exactly as the OS leaves them; only `apply.db` free pages are zeroed, and unlinked files and freed blocks may survive on the device below the filesystem: this is not secure deletion of media. (4) `backup_deadline_ns` is recorded, validated and shown in the receipt, and the worker compares it with its clock: `WorkerStatus.BackupLagOps` counts the completed deletion operations whose backup deadline has passed (`TestWorkerCountsOperationsWhoseBackupDeadlinePassed`). It is an upper bound, not a measurement: nothing in this installation attests that a destination expired the backups that predate an erasure (`backup.ExpireBackups` and the destination's own lifecycle policy run outside the worker, and control keeps a completed operation indefinitely, so the count never falls), and `residual_stores` never describes off-host copies: a backup object that was already uploaded keeps the pre-erasure bytes until the destination's own lifecycle policy removes it. Treat the deadline as advisory and the gauge as "deadline due, expiry not verified". (5) A snapshot cut at the index of the erasure itself (an expiry-driven erasure with no later write) is reported as residual until the index moves, although it may already be clean. (6) `control.db` held no telemetry values when this redaction was written (tombstone predicates carry none), but the rule, incident and condition control state added since (`RuleBooks`, `RuleOutputs`, `IncidentBooks`, `ConditionBooks`) can hold values derived from telemetry (a recording output carries a whole batch, a rule book the committed evaluation payload). Reads of those outputs are suppressed once a deletion covers their origin, but neither the deletion saga nor the erase pass removes or redacts the entries, the control group's journal and snapshots keep the commands that created them, and `ResidualStores` does not name `control.db`; they are not covered. Backup expiry is at most 30 days and suppression (the ledger) survives restore. Expiry erasure (no deletion operation, hence no checkpoint) refreshes snapshots and journals only as the groups' applied indexes advance with later writes.

`held`: an active legal hold overlapping the request blocks Begin (receipt `held`, nothing denied or erased). Releasing a hold never starts the deletion on its own; `Resume` (BeginFence) does. A hold placed after logical completion keeps the bytes physically present (receipt `physical: held`) while reads stay suppressed; releasing it lets the next worker pass erase after advancing the generation. Holds are checked again at erase time: the erase pass asks the guard before each batch or blob is removed, against the control state the erasing node has applied, and `RecordPhysicalCleanup` refuses, in the same control update, to stamp an operation a hold overlaps (the receipt says `held`, never `done`). Residual window: a hold that has committed but is not yet applied on the erasing node is invisible to the erase-time check, so its bytes can already be gone; the record-time gate still reports the operation `held`, and `WorkerStatus.ErasedBeforeHold` counts what that pass erased for such an organization. On a single voter the window is zero; it has not been tested with three voters.

`failed` is terminal for automation; the predicate stays active, nothing is ever un-deleted.

**Which control revision a retention command may carry.** `DeleteScope`, `BeginFence`, `CompleteFence`, `PolicyChange` and `RecordEvidenceGap` carry the control revision of the view their caller decided on. Control keeps `AuthorityRevision` in its replicated state: the revision of the last transition that could change authority, policy, retention, deletion or access state (every org, membership, grant, project, source-policy, source-grant, SSO, hold, retention-policy and deletion change, and every writer nobody classified). These commands commit when `AuthorityRevision <= expected_revision <= Revision`, that is, when the caller's view is at least as new as the last such transition; a view older than one, or newer than the current revision, is a `conflict`. Intake admissions, quota accounting, artifact reservations and the rule, condition, incident, delivery, issue, release and job books move `Revision` but not `AuthorityRevision`, so saturating intake can no longer starve a deletion's Begin (before this rule every Begin conflicted under saturating intake). Every other command kind keeps the exact `Revision == expected_revision` rule. A control state written before the field existed has it unset: it is treated as strict (only the current revision commits) and the first conflicting retention command stamps it. Retrying a committed `command_id` returns its stored outcome before any revision check. The classification lives in `internal/control/authority.go`; a writer wrongly classified as non-authority would let a deletion commit on a view older than a change that mattered, so that table is the review surface.

### Control state

The control store holds payloads derived from telemetry: rule evaluation values and recording batches (`RuleBooks`, `RuleOutputs`), incident and condition state (`IncidentBooks`, `ConditionBooks`), notification bodies (`DeliveryBooks`), issue evidence (`GroupingIssues`, `IssueBooks`), job state (`JobBooks`) and notification-cutover operator text (`CutoverBooks`). A committed deletion reaches them in the control apply itself, not in a later pass: one deterministic function of (state, predicate, transition time), with no clock, no randomness and sorted iteration, so every replica, snapshot install and journal replay installs the same bytes. It runs when a deletion begins, when it completes, when it fails, when a tombstone is re-imported from the restore authority, and whenever a control writer commits an effect of a project a finished deletion covers (see "Derived effects"). It is idempotent, and it appends a `delete.control_erased` audit only when it dropped something. Identities, versions, digests, counts, receipts and phases stay; payloads go.

* `retire_project` / `retire_org`: every payload of the covered projects (every project of the organization for `retire_org`), including the issue books (an issue book that cannot be read is dropped when its key names a covered project; another project's is left in place, and its reads fail closed) and the cutover operator text.
* `historical_range`: rule evaluations and outputs by their scheduled time in `[start,end)` of the named signals; issue evidence by event time in `[start,end)` when the range names the error signal; deliveries whose evidence interval overlaps; incident, condition and job states by the rule below.
* `entity`: outputs of the replay and profile signals of the project, issue evidence that links the entity by ID, and the rule books of exactly the rules that produced such an output. Jobs, incidents, conditions, deliveries and cutover records link replay/profile roots only by ID and are not covered.
* Saved views (`SavedViewBooks`, C11): project-owned query text, which can hold sensitive literals the caller typed. Only `retire_project` / `retire_org` covers them: every view of a covered project is dropped whole, name and expression included, by the `eraseSavedViews` hook (`internal/control/erase_saved_views.go`). A range or an entity deletion covers none, and another project's views stay. A view carries no telemetry, and its audit rows (`saved_view.save`, `saved_view.delete`) hold the actor, the organization, the project and the view ID, never the name or the expression.

**Opaque states are erased exactly by their recorded window; a state with none is erased fail-closed and reported (CD-9).** An incident, condition or job state is opaque to this package. When a deletion begins, completes or is imported, a range covers such a state when its **recorded window** meets the range's half-open `[start,end)`, the interval the data rows and the precise books use. The window of a state is the span from the oldest to the newest evidence time it names (any number or numeric string under a key `at`, `*_at` or `*_ns`, at any depth; a zero or negative time is unset and the duration keys `grace_ns`, `max_runtime_ns` and `observer_stale_after_ns` are not instants, so none of them is read). A state whose evidence all lies before `start`, at or after `end`, is kept, however late: a `[start,end)` metric deletion no longer tombstones an incident whose evidence is ten years after `end`. A state that spans the range (oldest before `start`, newest after `end`) is covered, because an accumulated state (an incident timeline, a job's runs) may hold in-range evidence in a part the times do not name; that is also why the rule is a window and not "names a time inside". A state that records **no window** (it names no usable time, or one that cannot be read) cannot be attributed to anything: it is dropped whole, as before, and the erasure **reports** it. The operation record carries `over_erased`, a list of `{book, count}` entries (`incident`, `condition`, `job`; only books with a non-zero count), accumulated across the begin, completion, import and late passes; the deletion receipt (`GET /api/v1/operations/{id}`, `POST /api/v1/admin/deletions`, `retention.DeleteReceipt`) shows it as `over_erased`. A retirement covers every state of its projects exactly and an entity deletion none, so both report nothing. The rule still ignores the signal list (a state does not name the signal its evidence came from). A condition or a job state that carries a **provenance** (next paragraph) is also covered when that interval meets the range. Two limits, stated: a state **written before the provenance existed** whose in-range evidence has rolled out of a bounded part (a condition's sixteen recent events, a compacted job run) and whose remaining times are all after `end` is kept with whatever it derived from the rolled-out evidence (such a state never gets a provenance, see below); and a time exactly at `end` belongs to no range. A covered state keeps only its closed header and the erasing operation; the services that read it see an erased record: `jobs` reads an empty state at the preserved version, `conditions` returns the erased marker (`State.Erased`) and the next event starts a new history on the kept version, and `incidents` returns the erased marker from `Get` and answers any action on it with `not_found` / `incident_erased`. An erased record is never reported as `corrupt`; a record that is neither a live state nor its own tombstone still is.

**Per-state provenance closes the rolled-out-evidence residual for states written from now on (09.08x-W1, 11.03-W4).** A condition (`conditions.State.Provenance`) and a job (`jobs.JobState.Provenance`) record, at fold time, the earliest and the latest record time they were ever derived from: the event time of every accepted condition event and of every evaluation health that changed the state, and the `Observed` time of every accepted job attempt event. These are the times a historical range deletion ranges the data rows by, not payload times (a job's terminal time, the worker's arrival time and an operator correction are not recorded), and an event that changed nothing (old, duplicate, older than the compacted history) was not folded and is not recorded. A job's schedule observations are not recorded: what they leave in the state (the observer's newest observation, the definitions, the incomplete intervals) names its own times, which the window rule reads, and is never rolled out. The member is `provenance` (`model.Provenance`, `{"from_ns","to_ns"}`, a closed interval of two decimal-string times, omitted when absent): two numbers however much the state folded, and the join of the times folded, so it does not depend on the order they arrive in. It outlives the bounded parts of the state: an event that rolled out of the sixteen `recent` events, a run that left through `compaction`, is still covered. A state that carries a provenance is covered by a `historical_range`, at begin, completion, import and in the late pass alike, when its interval meets `[start,end)`, **in addition to** what the rule over the times the state names covers; the provenance is not read as a named time and never narrows that rule. The interval is an over-approximation: it also covers the times between its ends that were never folded, so a condition or a job whose evidence lies before and after the range but never inside is **erased**. The window rule erased such a state at begin too, but the late pass kept it; with a provenance the late pass erases it, which is the cost of the interval (measured in the residual below). A provenance that is present but cannot be read (not an object, an unset or backwards interval, an unknown member) is unattributable: the state is dropped whole and counted in `over_erased`, as a state with no window is; a state with a readable provenance that names no time is attributed by it and is not counted. **Old states migrate to the old rule**: a condition without a provenance, and a job that holds runs (or has compacted some) without one, is never given one by a later event (what it folded before, and what had already rolled out of it, is unknown, so a provenance started late would read as complete); it keeps the window rule, fail-closed, until a deletion erases it, after which its next event starts a new history with a provenance. A job that has folded no attempt yet starts one with its first attempt. The residual therefore stays open for the conditions and jobs that existed when the build was installed. For incidents there is nothing to close: an incident's timeline is never rolled out (a full timeline is a `quota` error), so every action time stays in the state and incidents keep the window rule. The numbers measured on a generated corpus are in the lane 1 wave 11 evidence (`l1w11-evidence/L1W11Provenance/report.md`).

**control.db scrub.** bbolt never zeroes a page it frees, so the state an erasure replaced stays in the free pages of `control.db`. `Store.ScrubErased` zeroes every free page, in bounded chunks each inside its own write transaction (it defers while a reader is open: 40 attempts x 25 ms per chunk, then `Unavailable`, and the debt stays owed). Two debts keep it owed, and `control_state` is reported while either is: the replicated one, derived from the audit log (an erasing audit with no `delete.control_scrubbed` audit after it), which the scrub settles by committing a `delete.control_scrubbed` audit naming the operations whose erasing audits it covered; and the local one of each file (next paragraph). An erasure committed after a scrub owes a new one. The scrub runs first in the physical step (`RecordPhysicalCleanup`, which does not record `physical: done` when it fails) and on every retention worker pass of every voter, which is the only way the scrub of a failed operation (never physically recorded), of an effect erased after its operation's physical step, or of a follower's own file ever runs.

**control.db scrub is a fact about one file.** `delete.control_scrubbed` is replicated: it records that *some* node's `control.db` was scrubbed, normally the leader's. Every voter receives it, by replaying the log or inside an installed snapshot, while its own file was never scrubbed: the commit that applies an erasure frees the pages that held the payload on every voter and zeroes none of them, and an install rewrites the tree through copy-on-write pages and frees the replaced state the same way (a voter that had not applied the erasure yet still holds the payload live until then). So each file keeps its own debt, a marker (`local_scrub` in the `control` bucket of that `control.db`): `Apply` sets it in the transaction that adds an erasing audit (live, replayed or on the leader itself), and `Restore` sets it in the transaction that installs a snapshot whose log names an erasure or over a file that already owed a scrub (the marker is still set, or the log it replaces held an unsettled erasing audit). `control_state` is reported while the marker is set, whatever the log says, and a replicated scrubbed audit from any node never clears it; it survives a restart; only a `ScrubErased` that completed on this file afterwards clears it (a generation from the bucket's own sequence keeps a scrub from clearing an erasure or install that landed while it ran). When the log owes nothing itself, that scrub commits nothing replicated: no audit, no revision. The marker is not part of the state, of the snapshot metadata, of a seed, of any command or digest; no state transition reads it, so every voter computes the same bytes with or without it. The key's presence is the fact that a build with the marker has seen the file: `Open` writes it into every file it creates (nine zero bytes: settled, generation 0), and, as an OWED marker, once into an existing file that has none (below); it never rewrites a key that is there, so an owed marker stays owed under its generation and a settled one stays settled. A node that never applied an erasure owes nothing, and a seeded replica stays unmarked after its group opens: `OpenSeed` creates the file with the settled key, and the install that the group's first open makes of that same seed (the file's watermark is below the seed's index) replaces nothing, so `Restore` owes nothing when the marker key is present and settled, the file's own log owes nothing, and the installed state equals the stored one after canonical re-encoding; installing the identical state frees only pages that hold that same state. **What a bbolt scrub cannot reach:** blocks the filesystem keeps for earlier versions of the file (journal, snapshots of the volume, a copy-on-write filesystem's old extents), a backup or copy of `control.db` taken before the scrub, and the control Raft files, which are the journal's business (next paragraph); it zeroes the pages bbolt's freelist reports free at the time and nothing else. **A file written by a build that predates the marker** has no key and no record of the erasures it applied then, and its replicated log is not a complete memory of them: the leader's scrubbed audit may already be in it, and an install from another lineage by an earlier build could have dropped the erasing audit while the payload stayed in the free pages (a review reproduced a clean receipt over 24 payload copies that way). So `Open` marks EVERY such file owed, whatever its log names. A node that had already scrubbed before the upgrade, or never erased anything, does one redundant, bounded scrub on its first start under the new build, because the information that it had does not exist; that cost is accepted, since a false clean would be a privacy defect. The key vouches only for commits made by a build that has the marker: running an earlier build on the file after this one has settled it, and this build again afterwards, is not detected, and that downgrade path is not supported. A rejected `OpenSeed` over an existing file of another installation still goes through `Open` first, so it leaves that file's key behind. **A second accepted cost:** every later install, over a clean file, of a log that names an erasure and of a state that differs from the one the file holds owes one more scrub, because the audit log is append-only (an installed log names every erasure that ever happened) and the file cannot tell which pages the replaced state occupied. A voter that is cut off and catches up by snapshot therefore names `control_state` after each catch-up until its next worker pass zeroes the file again: one scrub per install, O(file size) writes, never a stuck debt for a readable state (a state that cannot be decoded is owed until an operator makes it readable, because `ScrubErased` answers Corrupt meanwhile).

**Recurring install scrub: decision proposed by lane 1 wave 6, recommendation: accept (not yet taken by the owner).** The accepted cost stated at the end of the paragraph above (one bounded `control.db` scrub per snapshot install of an erasure-era log over a different state, O(file size) writes, until the voter's next worker pass) is proposed as the standing rule, and the install exemption is NOT extended beyond what it is: an install over a settled file whose own log owes nothing and whose canonical state equals the installed one owes nothing; every other install of a log that names an erasure owes one scrub. Reason: the audit log is append-only, so a node cannot tell from the installed log which pages the replaced state occupied, and a false clean (a receipt that does not name `control_state` over a file that still holds an erased payload) is a privacy defect while a redundant scrub is only a cost. Until the owner records the decision this paragraph is a proposal; the behaviour it describes is what the code does today.

**The control Raft journal.** Every control command replicates the whole control state, so the Raft journal (`raft/control/ready.wal` under the data directory), its snapshots and the in-memory log keep complete earlier copies of the state, erased payloads included. The replication layer's retry table keeps no payload for a control command (`replica.DigestRetryMachine`: the receipt and the digest of the payload the command was proposed with, a fixed-size record per command), so it has nothing to redact and the snapshot envelope that serializes it no longer grows with the bytes of every command ever committed; a snapshot cut by an earlier build still carries payload-bearing retry-table entries until a later cut replaces it. `Store.RedactRetainedControlCommands` (the retention worker calls it on every pass, after the `control.db` scrub) removes them from **this node's** copy once every erasing deletion has finished (complete or failed; while one is fencing the live state still holds effects its completion will drop, so nothing is redacted for it and the journal stays named). It hands `replica.Group.RedactMachineCommands` the rule of `Store.RedactControlCommand`, which rewrites every retained command of kind Control (every `ready.wal` entry including superseded ones, the in-memory log a lagging voter is sent, the pin archives) to the same command minus the payloads a committed deletion covers; the command keeps its ID, indexes and outcome, so a retry still answers with the original receipt, and the digest of the payload it was proposed with is kept, so a retry of the original is still recognized. A replay of the redacted journal reaches the same control state: each command carries the whole next state, so redacted older commands are superseded by newer ones, and the command that establishes the current state is never rewritten (the redactor refuses a current state that still holds a covered payload instead). Snapshot directories and the journal's sealed head snapshot cannot be rewritten in place; the pass commits one empty control revision when no command is newer than the redaction, cuts a snapshot at the applied index, drops the superseded snapshots and compacts the journal onto it. `control_raft_journal` stops being reported exactly when `Group.MachineResidue` for the erasures committed so far is empty; it is reported again as soon as a newer erasure commits, when the durable proof record is missing or damaged (the proof is the rule set the last completed pass covered and the physical index it finished at, a checksummed file `machine.proof` next to the journal, written after the pass's journal rewrite is durable and surviving a restart, a compaction and a snapshot cut; it is removed before a snapshot from the leader is installed and before a control command is applied, and written back only if that command applied cleanly, so a crash cannot leave a withdrawn proof standing; a missing, short, damaged, foreign or implausible record is no proof and the next pass proves it again), when a snapshot is installed from the leader, when a command rejected as stale is committed after the pass, while a backup pin is live, and whenever the pass fails.

**What the per-voter passes do not cover.** The passes and the proofs behind `ResidualStores` stay per voter: a voter redacts and scrubs only its own files, and `Store.ResidualStores` reports only the answering node. What a receipt says is no longer that list alone: see "The receipt waits for every node" below. Not reached by any pass, attested or not: backups and pin archives taken before the pass, snapshots already shipped off the node (a lagging voter sent the leader's sealed snapshot before the leader's pass completed stores it until its own pass), and copies the filesystem keeps in freed blocks of rewritten files.

**Residual and backup expiry: decision proposed by lane 1 wave 6, recommendation: accept (not yet taken by the owner).** What a per-voter pass leaves behind is stated, not hidden: copies the filesystem keeps in freed blocks of rewritten files, backups and pin archives taken before the pass, and snapshots already shipped off the node. Proposed acceptance: (1) the filesystem residual is accepted as the residual of any file rewrite without a verified secure-erase primitive, and the receipt keeps naming it rather than claiming a physical wipe; (2) a backup taken before a deletion is not rewritten: it holds the erased payloads until it expires under the backup retention in force, and the statement a deletion receipt makes about backups is exactly that, with the expiry horizon (the configured backup retention) as its bound, never a claim that the backups are clean; a restore from such a backup replays the deletion ledger (`Service.Restore`, "Restore" below) before the engine opens, so the erased data does not become readable again, but the bytes stay in the backup until it expires; (3) the redaction proof (`replica` `machine.proof`) is a durable local fact about this voter only, and never extends to another voter or to a backup. Until the owner records the decision, this paragraph is a proposal and the receipts keep naming the stores above.

**The receipt waits for every node.** The control Raft journal and `control.db` are rewritten and scrubbed per voter, so the receipt does not take the answering node's word for the others. The deletion receipt's `residual_stores` is built per operation (next paragraph) from the same view as `Store.ClusterResidualStores`, which stays the operation-independent answer: everything `ResidualStores` names for this node, plus `control_raft_journal` and `control_state` for as long as any node of the control group's committed configuration has not attested the matching fact for every erasure committed so far. An attestation (`internal/control/attest.go`) is one record per node in the replicated control state (an `OIDC` resident under `control_attest:<node id>`, a closed JSON DTO) with two independent facts, `journal` (this node's journal, snapshots, retained commands and pins hold none of the erased payloads: `ResidualStores` does not name the journal) and `state` (this node's `control.db` free pages were zeroed and its local marker is settled), each stating the number of erasing audits it covers and the applied index of the proposer. The retention worker writes it after its own `ScrubErased` and `RedactRetainedControlCommands` (`Store.AttestControlResidue`), only for facts this node measures as true when the transition runs, only for itself (no argument names a node: the node comes from the replica group's own identity), and commits nothing when the record already says that. A fact covers every erasing audit up to its number, so a later erasure owes only the deletions it adds (next paragraph); a node that can no longer prove an older fact drops it. It does not outlive the facts it states: when the group drops this node's redaction proof (a snapshot installed from the leader, a stale control command committed after the pass, and the opening of a group on a snapshot, where the group tells the store that the proof is in question while it re-reads the durable proof record, so a node whose record is missing or damaged holds no proof) the store withdraws this node's facts with a retried commit, and the worker reconciles on every pass; an install also re-owes the `control.db` scrub, which withdraws the `state` fact. Membership is read from the committed configuration of the control group: every node in it counts, voter or learner (a learner receives the payload by snapshot and keeps the same files); a node that left no longer counts; a node that joined after the erasure has no record and so must attest; an unknown configuration, an unreadable state, a record that does not decode strictly or names another node or node identity, all name both stores. There is no command kind for an attestation, so no client scope reaches it, and any other control writer (a handler, `Store.Update`, `UpdateReplayIndex`) that adds or changes one is refused with `Forbidden`; the record is evidence, not authority, so the write is classified non-authority and leaves `AuthorityRevision` alone. **What stays per voter and unobserved:** the attestation is the node's own claim about its own files, made by its own worker (a node whose worker never runs is named; a node that attests falsely is not detected, because no one else reads its files); the window between a snapshot install and the commit of the installing node's withdrawal is still open for the other nodes' receipts (next paragraph; the window of a stale command is closed); concurrent control commits can drop a node's in-memory proof (a stale command), which withdraws its attestation until its next pass; and the receipt of a node that has not yet applied an erasure cannot name what it does not know.

**The receipt of one deletion names the control stores only for that deletion; a stale command can no longer hide behind a pending withdrawal (10.14-W1, W2).** The receipt is built per operation (`retention.ResidualPlane.OperationResidual`, which the receipt uses when the data plane has it): the control part is `Store.ClusterOperationResidual(op)`. The operation's erasing audit is the n-th of the control log; a node has paid when its attestation states a proof for at least n erasing audits, so an attestation now covers every erasure up to its number and a later deletion that is still being cleaned re-owes only itself, not the receipt of an earlier one (before: any later erasure made every earlier receipt name both control stores again). The answering node is judged from its own files (what the group proves for n audits, the operation's scrub debt, the local scrub marker unless its own record covers n and no snapshot was installed since), the others from their records. A node keeps its older fact while a later erasure owes it a new proof, and only while it can still prove the older one: a stale command, a snapshot install or a restart without a durable proof drop it. The window between a stale command and the withdrawal commit is closed by the log index: a stale control command is committed at one index on every node and every node stores it durably (`replica_control` key `stale_applied`, written in the transaction that rejects it), and a journal fact whose proposer had applied less than that index is not valid, so a receipt answered by any node that applied the command never trusts an attestation made before it, with or without the withdrawal commit (the group reports the event through `replica.ProofWatcher.ProofWithdrawn(ProofWithdrawal{Index, Install})`). **Still open, by construction:** a snapshot install is local to the installing node and is not in the log, so another node answers a receipt from the old record of the installing node until that node's withdrawal commits (milliseconds in the tests). The retry backoff of the withdrawal (at most two seconds) bounds the attempts, NOT the window: the withdrawal is a control write that needs a leader, so while the installing node cannot commit (for example a follower cut off from the leader right after the install, which is a reachable state because an install arrives from a leader that can then be lost) the window is unbounded, and every other node keeps answering receipts from that node's pre-install record (independent review L1-R wave 7 control, finding M2; `TestAReceiptOfAnotherVoterTrustsAnInstallersRecordsOnlyUntilItsWithdrawalCommits` pins the window, it does not bound it). The installing node itself never trusts its earlier record (`installAt`). Closing it needs the sender of a snapshot (the leader) to withdraw the receiver's facts before the install, which the replication layer does not expose, or a durable install watermark written in the restore transaction and replicated to the other nodes (the mechanism `stale_applied` already uses for the stale-command half). Decision proposed by lane 1 wave 7, restated with the unbounded case by wave 11, recommendation: accept the install window as documented, because it exists only while the installing node is cut off from the log it needs for the withdrawal and its own receipts name the residue; the owner has not taken it.

**Attestation and acknowledgement limits (non-Byzantine members, nothing off the node): decision proposed by lane 1 wave 6, recommendation: accept (not yet taken by the owner).** Both the control attestation (`control_attest:<node>`) and the data `erase_ack` are a voter's claim about its own files, made by its own worker and bound to its own identity (the group records the proposer; no client scope and no other member can write them). Nothing reads another node's files, so a member that states a false fact about its own store is not detected: the model is crash-faulty, honest members, which is the model the replication layer itself assumes. Also out of reach of every pass and so of every attestation: filesystem blocks freed by rewritten or removed files (`ready.wal`, pin archives, snapshot directories), backups and pin archives taken before the pass, and snapshots already shipped off the node. Proposed acceptance: (1) the receipt states exactly these claims, one per member, and keeps naming a store until every member of the committed configuration made its claim, never a measurement of another node's disk; (2) a Byzantine or compromised member, and any copy outside the node's own stores, is outside what a deletion receipt promises, and is stated as a limit rather than detected; (3) cross-node verification (a verifier that can read a node's files and signs what it found) is not built and is not proposed for this release. Until the owner records the decision this paragraph is a proposal.

**Per-voter erasure marker and acknowledgement in place of a replicated erase command: decision proposed by lane 1 wave 6, recommendation: accept (not yet taken by the owner).** The brief for 10.23 asked for the erase to be a replicated command applied in log order on every voter. What is built instead: the tombstone (`delete_barrier`) and the completed control operation are replicated and every voter already derives its local redaction from them, so each voter's own worker erases its own copy, driven by a node-local durable marker (`erased:<operation>`) rather than the cluster-wide `PhysicalAt`, and then proposes a replicated `erase_ack` (slot 0) that the receipt waits for from every member. Consequences to accept: holds are evaluated per voter against its own applied control state, and a voter that was down during Begin or installed a snapshot erases when its worker next runs after catching up, not at the log position of an erase command, so its copy persists until then and the receipt names `data_apply_db` meanwhile. The per-voter path is exercised in-process on three voters and by the deletion-cluster smoke on three real processes; it has not been re-run on three separate machines. Until the owner records the decision this paragraph is a proposal.

**Per-voter bytes and passes that race an erasure.** The replacement a pass writes for a retained command is computed from the state of the voter that runs it (its live state and its finished deletions when the pass reads its rules), so the same command holds different redacted bytes on two voters, and their snapshot envelopes, hence the `snap-<index>-<checksum>` directory names and `Manifest.Checksum`, differ between voters, until every voter has run every pass; the live state is identical at once. Nothing may compare those bytes or digests across voters (repair, deduplication, "do these two nodes hold identical journals"). Retry recognition and conflicts are unaffected: the command keeps the digest of the payload it was proposed with. A pass reads its rules once, when it starts, so it can introduce a copy of a payload that an erasure committed after those rules were read: an erasure that commits while the pass runs leaves its covered payload in the `ready.wal` the pass rewrites and in the snapshot envelope it cuts. The receipt stays honest (it re-reads the live state, so `control_raft_journal` stays named) and the next pass removes that copy.

**Receipts.** `residual_stores` of a receipt names the stores of the whole installation only when the retention `Service` is built on `retention.NewResidualPlane(engine, controlStore)`: it reports the union of the engine's measurement and the control store's (`control_raft_journal` until this node's pass is proven, and `control_state` while a scrub is owed). On such a Service a `physical: done` receipt of an organization whose control payloads were erased lists `control_raft_journal` until the worker's pass has completed on this node (and again whenever the pass is not proven, see above); an empty list means nothing in either store of THIS node is owed. A Service built on the bare engine reports the engine's list only.

**Free text inside a deleted scope is redacted (CD-8).** The erasers drop payloads and also the free text an operator or a consumer typed or the pipeline derived, in the records the deletion covers; the fixed token `erased` replaces it (a closed system reason, such as the retired-project reason of a suppressed output, is not text anybody typed and stays). The fields: `RuleOutput.Reason` (consumer text and data-derived text such as `series_conflict:<n>`; the output's own scope: every output of a retired project, the outputs of the named signals scheduled inside a range, the replay and profile outputs of an entity deletion), `RuleBook.Replays[].Reason` (operator text; every replay window of a retired project's books, the windows that meet a range, the books of the rules an entity deletion erases), `IssueBook.Gaps[].Reason` (a range that meets the gap's interval and names one of its signals; a retirement drops the whole issue book), `State.GroupingMigrations[].Reason` (a retirement, or a range that names the error signal and contains the migration's time) and `State.Releases[].DisplayLabel` with its history (a retirement only: a release is not time-bound). Redacting rewrites the record in place, so it counts as an erasure: the erasing audit is appended and `control.db` owes its scrub like for any dropped payload. A later step of the same output with the original reason is still an idempotent success (the compare treats the redacted text as equal). **Stays, by design:** hashes, counters and cursors that are evidence rather than text (`RuleMissedRecord.Count`, `RuleOutput.Inputs` and `RuleEvaluationRecord.Cursors`, `IssueBook.Checkpoints`, `IssueBook.Commands[].Action.Fingerprint`, `GroupingIssue.Fingerprint` of surviving evidence, the series identity of `State.Quotas` and `Reservations`, `DeliveryRecord.Provider`); `State.EvidenceGaps[].Reason`, which the backup attestation (`backup.GapDigest`) and the data plane's declared gap bind to that exact text (the retention worker writes a closed vocabulary into it, and redacting it would break the restore proof); and the audit log, the append-only record of who did what (an operator replay or a gap declaration audits its reason, never rule content).

### Delete generation
`retention.Service` implements `auth.DeleteGenerations`: source-lifecycle base plus a durable per-org counter that advances at Begin, at completion, before physical erasure, on artifact GC cancellation, on expiry erasure and on erasure after a hold release. Caches, cursors, live positions and export tickets bound to an older generation die.

### Restore
`BuildLedger` derives the digest ledger plus exact tombstones from control state; the authority stores both on every completion. `Service.Restore(authority)` imports the missing tombstones into the restored control state, records the barrier in every slot and only then opens the engine's restore gate. A restore whose authority is unavailable or unverifiable stays closed. Task 01.09 implements `CheckpointDeletion`/`CurrentDeletionLedger` (and `CurrentDeletionTombstones`) in `internal/backup`.

### Derived effects
Every control writer that commits an effect derived from telemetry (rule evaluation, incident action, condition, job update, issue evidence, delivery enqueue) runs the control-state erasure (section "Control state" above), for the committed deletions that cover its project and have completed or failed, inside the same control transition that commits the effect. An effect that a worker read before a barrier and commits after its deletion completed therefore never leaves its covered payload in the live control state or the `control.db` pages it occupied (free pages are zeroed by the scrub above). That statement is about the control state only: the command that carried the effect is itself retained in the control Raft journal, its snapshots and the retry table, and that residue is removed from a node's copy by `Store.RedactRetainedControlCommands` (section "The control Raft journal" above; a command committed after a pass withdraws its proof until the next one). `control.EffectSuppressed(state, org, project, kind, at, entity)` remains a read-side predicate for a consumer that wants to skip work early; it is not how the control state is kept clean, and no writer relies on it. A deletion that is still fencing is the exception: an effect committed meanwhile is erased when the deletion completes (or fails).

**Temporal scope of the late pass.** The pass that runs in an effect's own transition is not the begin/complete erasure over again; it covers exactly what the effect could have derived from the deleted range. Rule evaluations, issue evidence and deliveries are half-open and signal-gated as above (an evaluation, evidence item or delivery interval at or after `end`, or before `start`, is kept). An incident, condition or job state is covered by a `historical_range` only when it names an evidence time **inside `[start,end)`** (the same half-open interval the exact books use), or names no time or one that cannot be read (unattributable: dropped whole, as at begin, and counted in the operation's `over_erased`). A state is read for those times by the window rule above (zero or negative times and the duration keys are not instants). So a state first committed from data at or after `end` (the incident, condition or job a worker opens after the deletion, whose own times are its evidence time, its arrival and its evaluation time) or from data before `start` is **never** erased by the late pass, whatever other times it names; a state that mixes evidence inside the range with later times (a worker that read in-range data before the barrier and commits after) is erased whole. The late pass is slightly narrower than the begin rule: a state that only spans the range (oldest before `start`, newest after `end`, nothing inside) is kept by it, because a state first written after the deletion is not an accumulation of older evidence. That narrowing is for a state **without** a provenance. A condition or job state that carries one is also covered when its interval meets `[start,end)`, as at begin (see "Per-state provenance" above): this catches a state whose in-range evidence rolled out, and it erases a state whose interval spans the range with no record inside, which the interval cannot tell from one with a record inside. A retirement still covers every payload of its projects, an entity deletion still covers no opaque state, and the signal list is still ignored for opaque states, so a metric range erases an in-range incident whatever signal fed it. The late pass appends a `delete.control_erased` audit, and so owes a `control.db` scrub, only when it dropped something: a commit that erases nothing appends no audit and re-owes nothing. Redacting a retained control command (`Store.RedactControlCommand`) uses the rule its own commit used: the window rule for a command whose state has the deletion still fencing, the late one for a command committed after it finished.

**A write whose effect is erased as it commits answers `erased`, not `applied` (09.08x-W3).** When a command's own evidence lands inside a range a completed deletion already erased (a worker that read in-range data before the barrier and commits after), the late pass erases the state in the same control transaction that commits it, so the committed record is a tombstone at the version the command reached. Each writer now says so with a typed result instead of returning the payload it submitted and reporting the effect as applied: `incidents.Service.Act`, `conditions.Service.Apply` and `jobs.Service` (`ApplyAttempt`, `ObserveSchedule`, `Correct`) answer `model.NotFound` with the SafeDetail `incident_erased`, `condition_erased` and `job_erased` (`incidents.IsErased`, `conditions.IsErased`, `jobs.IsErased`), which differs from success and from `model.Corrupt` (storage damage) and from a not-found of a missing entity by its detail. The command did commit (the control version moved, the tombstone keeps the closed header) and repeating it can only erase again, so no caller retries it: `conditions.Service.Consume` finalizes the output and lists it in `Report.Erased` (a retry could only rebuild the same tombstone, and every rebuild would append an erasing audit and owe a scrub), the job journal producer advances past the row, and the incident producer skips it. The jobs store learns of the erasure by reading the committed record after the update (`ControlStore.Update`, one extra control read per non-replayed job update); a deletion that completes after that read is the ordinary erasure of a stored state, not this result. Tests: `TestEventInsideACompletedRangeIsReportedErasedNotApplied`, `TestConsumedOutputWhoseStateIsErasedAtOnceIsReportedErased`, `TestAttemptInsideACompletedRangeIsReportedErasedNotApplied`, `TestIncidentOpenedInsideACompletedRangeIsReportedErasedNotApplied`.

**Two residuals of the CD-8/CD-9 erasure, recorded for the owner (lane 1 wave 7).**

1. *Evidence gap reasons and audit text are not redacted.* `State.EvidenceGaps[].Reason` is part of the committed gap fact that `backup.GapDigest` hashes into the backup attestation and that the data plane's declared gap repeats; redacting it in the control state would make every earlier attestation fail `reconcile` and break the restore proof, and changing the digest would invalidate attestations already issued. The text is bounded (`recordGap`: 1 to 64 bytes) and the retention worker writes the closed token `unprocessed_expiry`; the only way free text reaches it is an organization administrator's own gap declaration (`GapDeclaredByAdmin`), which is operator text, not telemetry. The `evidence.gap` and `rules.operator_replay` audit rows repeat that operator text and the audit log is append-only evidence of who did what. `IssueBook.Gaps[].Reason` is a different copy and is redacted. A test pins that the committed gap fact keeps its reason across a retirement (`TestCD8CommittedEvidenceGapKeepsItsReasonForTheBackupDigest`). Decision proposed by lane 1 wave 7, recommendation: accept (operator-typed gap reasons of at most 64 bytes and the audit rows that repeat them stay after an erasure; operators must not type customer data into a gap reason; changing this later means changing the digest rule together with the attestations already issued, and redacting both copies in one release).
2. *Evidence that rolled out of a bounded part.* A condition keeps its sixteen most recent events and a compacted job keeps only its newest runs, and a state written before the per-state provenance (09.08x-W1, "Per-state provenance" above) does not record where a rolled-out time came from. A range that covers evidence which already rolled out of such a part, when every time such a state still names lies after `end` (or before `start`), keeps the state: its window does not meet the range, and the rolled-out evidence left only free pages that the control scrub zeroes. What the state derived from that evidence (a status, a count) survives. **Closed for the states written from the provenance build on**: they carry the earliest and latest record time of everything they folded, rolled out or not, and a range erases every state whose interval meets it. Measured on a generated corpus (200 conditions, 54 jobs, `TestRangeDeletionOver*`): with the evidence rolled out past the range, 40 of 40 conditions and 6 of 6 jobs survived as legacy states and 0 of both with a provenance. The cost is the interval's coarseness: a condition or a job whose evidence lies before and after the range but never inside is erased at begin (40 conditions and 12 jobs of the corpus, as for a legacy state) and, with a provenance, also by the late pass, which keeps such a legacy state (40 and 12 more erased there, counted nowhere in `over_erased`, because the state has a readable provenance). **Still open** for the conditions and jobs that already exist when the build is installed: they never get a provenance (what they folded earlier is unknown) and keep this residual until a deletion erases them; the alternative that closes it at once, covering such a state for every range that starts before its newest time, would erase most of a project for every range and is not taken. Decision proposed by lane 1 wave 11, recommendation: accept the residual for pre-existing states and the late-pass coarseness of the interval; there is no residual for incidents, whose timeline is never rolled out.

## Evidence journal and gaps
Error, condition and job evidence expires only through `EraseExpired` gated by the lifecycle processing checkpoint. Unprocessed evidence is erased only after a durable `RecordEvidenceGap` (interval, count, signals) commits; expiry never advances a processing checkpoint, and a gap that cannot commit keeps the evidence (`EvidenceHeld`). Journal truncation (`CreateSnapshots` + `CompactJournals`, default hourly) retains the whole history inside the verified snapshot, so it never loses evidence.

What counts as processed is read from the control state the projections commit, in the worker's own pass and without any configuration: an error occurrence is processed when its journal index is at or below the project's issue checkpoint for its data group (committed in the transaction that applied it), and a job attempt record is processed when the job book holds its attempt command (the command ID is a function of the record's origin, `jobs.AttemptCommandID`). Evidence that no projection reads (condition records), a job record the reducer rejected for good, and a job command the book has already evicted (1024 commands per job) are not provably processed and keep expiring only behind a gap. A control state read earlier in the pass is only ever behind the present, so it can only make the worker declare a gap it did not strictly need, never skip one.

## Known limits
Expired-but-unerased data stays readable until the next expiry pass (default hourly). Evidence gaps are declared per contiguous run of expired candidates and count each entry once, so a gap never covers a not-yet-expired entry between candidates. Only gaps declared by the worker authorize expiry: control decides who declared a gap from the path it arrived on, an administrator-declared gap is recorded and audited but authorizes nothing, gaps recorded before this rule (no declarant) authorize nothing, and every gap is audited with declarant, interval and count. Quota charges of erased data are not refunded. While a hold or an open reader keeps `physical` from being recorded, the deleted bytes are still physically present everywhere (reads stay denied). During physical cleanup, until the next snapshot cut, a group has no "previous" snapshot to fall back on.

**Retained by design after an erasure: charged series identities (N5).** Erasing a batch removes its values, pages and index entries and redacts its stored command, but the data group's `consumed` row for the batch's reservation stays: it holds the reservation's `series` (canonical series IDs, which are hashes, not names or values), its byte charge and its cursor. Quota reconciliation, the backup quota certificate and the bundle's per-window charge digest are computed from exactly these rows (`internal/storage/snapshot.go`, `window.go`, `evidence_spans.go`), and quota charges are not refunded, so the rows are kept rather than pruned. They are **not** a measured residual: `ResidualStores` does not report them, and the smoke's canary probe cannot see them because they are hashes. What they reveal is an oracle ("a series with this identity was once charged against this project"), never a value.

**Two things called "generation" (N6).** A slot's deletion ledger generation (what `replica.Ledger` and a snapshot manifest carry, read by backup and restore verification) is the manifest's tombstone generation plus the number of deletion operations fenced in that slot. A `CheckpointErasure` tick re-commits an already fenced barrier as a no-op log entry and does not change it. `meta/deletion_generation` is a different, installation-wide number set by `ApplyDeletionLedger` from the control ledger. A consumer reads the one its own layer owns.

## Control log expiry and the erase-time hold read

**Bounded control state (01.08-W2).** The control state is re-read and re-proposed whole on every control transition, so its logs are expired by the worker's expiry pass (`control.Store.ExpireControlLog`, the hourly schedule). Audit rows live 365 days by default (`retention.Defaults().AuditDays`); an organization's own `audit` retention setting (admin `retention` command) can only lengthen that, never shorten it. The erasing and scrubbing audits (`delete.control_erased`, `delete.control_scrubbed`) and rows with no time are never expired: the control scrub, the journal-residue and the attestation accounting are derived from them, and the scrub's coverage is an ordinal of erasing audits, not a position in the log, so an expiry between the scrub's read and its settle cannot shift it. Applied commands (`Commands`, `CommandOwners`) are kept for the D4 dedup window (24 h) or 100 000 entries, oldest first, whichever bounds first; the age comes from `RevisionClock`, a stamp of (revision, leader clock) the update funnel adds once per minute and prunes to the window, so a day of traffic costs about 1440 stamps, not a time per command. A retry of an expired command is a fresh command and the expected-revision rule refuses it. The expiry commit is not an authority transition. The worker status counts `ExpiredAudits` and `ExpiredCommands`.

**Consumed admission reservations (01.07-W1 residue, lane 1 wave 7; decision proposed by lane 1 wave 7, recommendation: accept).** The third part of the control state that used to grow without bound was one row per consumed admission reservation (with its idempotency key and series list): a consumed reservation is never refunded and the data holds the whole of it in the batch that consumed it, yet control kept it for ever. The worker's expiry pass now also settles them (`control.Store.SettleAdmissions`): for a sealed data window whose consumed reservations control holds exactly (the digest of the window the engine reports equals the digest of control's rows), the rows are replaced by one settled-window record and their charge is folded into the settlement's per-key totals; quotas, and therefore admission decisions, do not change, a retry of a settled batch is answered from the data's receipt without a second charge, and a backup proves the folded charge against the data windows at restore. Erasure refunds no quota, and a reservation whose batch was redacted stays charged inside the settled totals; a window that carries a redacted batch is not settled (its rows stay, bounded by the number of erasures), and a window redacted after it was settled is listed in full in the next backup's evidence. Details and what stays linear: docs/operations/recovery.md, "Settled reservations".

**Hold check at erase time (01.08-W4).** Right before each erasing transaction takes the engine lock the engine consults the erase guard with `Sync` set, and the retention guard answers it with a linearizable read of the control group (`control.Store.CurrentHolds`: ReadIndex, then the applied state). A hold whose placement was acknowledged before that read is therefore in the state the Final consultation inside the transaction reads locally, even on a voter that lags in applying the control log; a voter that cannot confirm it is current (partitioned from the control quorum, no leader) fails the pass and erases nothing. The remaining window is a hold that commits after that read and before the removal inside the transaction: the bytes go and the receipt says `held`, never `done` (`ErasedBeforeHold`).
