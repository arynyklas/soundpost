# Rolling upgrade, certificate rotation and maintenance of a three-voter installation

A three-voter installation keeps acknowledging writes while **one** voter is down. It stops acknowledging (a typed retryable `503` with code `stale`, `unavailable` or `timeout`; never a local acknowledgement) while **two** are down. Every procedure below therefore has the same rule: **never two members down, and never start the next member's restart before the previous member reports ready.** Nothing in Docker, Compose, Kubernetes or Helm enforces this for you by default; the manifests are built so that a routine `helm upgrade` or `docker compose up -d` does *not* restart everything at once, and the order is then yours.

"Ready" is exactly `GET /readyz` of that member returning `200` with `ready:true` (`internal/httpapi/health.go`, `docs/operations/install-single.md` section 5): its own quorum round, apply backlog, disk, policy fences and schema. A listening port, a running container or a Kubernetes `Running` phase is not readiness. `soundpost ready --data-dir /var/lib/soundpost` asks the same route and is the Compose/Docker health check.

## Preconditions (check before the first restart)

1. All three members ready: `kubectl get pods -l app.kubernetes.io/component=member` shows `1/1` for every pod, or `docker compose ps` shows three `healthy`; or `GET /readyz` returns 200 from each.
2. The control `applied_cursor` in the three `/readyz` answers is equal (quiescent) or within a few entries; a member that is behind is still catching up and must not be the one that makes the other two the only voters.
3. A current verified backup exists and its label is `deletion-safe-disaster-backup` (`backup-authority.md`). A recovery copy on the same host is not enough to roll back a failed migration. This is an offline, operator-checked precondition: a running distributed server does not build or check the backup service (`config.BackupChecker` runs only from the CLI), and multi-voter restore seeding is still an open item (see `backup-authority.md`), so a restore of that backup into a rolled cluster has not been demonstrated.
4. The target version is documented as rolling-compatible with the running one. A member whose binary supports a different stored format than its data reports `schema_old` or `schema_newer` and stays unready: that member will not serve. Do not roll across a release that needs a data migration; use a planned full stop with a backup instead.
5. Disk: every member's volume is below the 80% warning level.

## Order

Upgrade one member at a time, **followers first if you can tell the leader** (there is no operator command to move leadership in this release; a leader restart simply causes one election, during which writes through any member are retried with `503` with `retryable: true`, and then succeed). Keep at most one member down at a time so a quorum remains. Rolling a member onto a *different binary* has not been exercised by any test or drill (the cluster drills restart the same binary; Kubernetes was never run, see `distributed.md`), so the ordering above is a precaution, not a verified guarantee; check each member's `/readyz` before moving on.

For each member in turn:

1. Confirm the other two members are ready.
2. Restart that one member on the new image (below).
3. Wait until **that member's** `/readyz` is 200 again. A restarted member rejoins from its own durable journal and catches up from the other two; it is not ready until its quorum read round and apply backlog pass. Allow minutes for a large journal.
4. Confirm the control `applied_cursor` of the three members agree, and a write plus a read through the upgraded member succeed.
5. Only then move to the next member.

If the restarted member does not become ready within your bound (suggested: 10 minutes), **stop**. The other two voters still form a quorum and the installation is serving. Read that member's log (safe to read: it holds no credential), fix the cause, or put the previous image back on that one member. Never restart a second member while one is unready. Rolling back after the member has migrated its data is not possible (`schema_newer`).

### Compose (`deploy/compose.distributed.yaml`)

`SOUNDPOST_IMAGE` is the default for all three members; `SOUNDPOST_IMAGE_A`, `_B`, `_C` pin one member. Pin all three to the running image first so that a later plain `docker compose up -d` cannot move more than the member you choose:

```sh
export SOUNDPOST_IMAGE_A=soundpost:1.0.0 SOUNDPOST_IMAGE_B=soundpost:1.0.0 SOUNDPOST_IMAGE_C=soundpost:1.0.0
# member c first
export SOUNDPOST_IMAGE_C=soundpost:1.1.0
docker compose -f deploy/compose.distributed.yaml up -d --no-deps soundpost-c
until [ "$(docker inspect -f '{{.State.Health.Status}}' "$(docker compose -f deploy/compose.distributed.yaml ps -q soundpost-c)")" = healthy ]; do sleep 5; done
# then, with the cursors equal and a test write through c, b and finally a
```

`--no-deps soundpost-c` recreates only that container; its named data volume (its durable identity) is reused. Never `docker compose down -v` an installation you intend to keep: `-v` deletes the data volumes.

### Kubernetes (`deploy/helm/soundpost`)

Each member is its own single-replica StatefulSet with `updateStrategy: OnDelete`. **That is deliberate.** The StatefulSet controller does not consult a PodDisruptionBudget when it applies a rolling update, so three `RollingUpdate` sets (or one set with three replicas and a misconfigured `partition`) would restart voters without waiting for each other and could lose quorum. With `OnDelete`, `helm upgrade` only changes the desired pod template; no pod restarts until you delete it:

```sh
helm upgrade soundpost deploy/helm/soundpost -f values.yaml --set image.tag=1.1.0   # nothing restarts
for member in c b a; do
  kubectl delete pod "soundpost-$member-0"
  kubectl wait --for=condition=Ready "pod/soundpost-$member-0" --timeout=600s   # /readyz via the readiness probe
  # verify the other two are still Ready and the applied cursors agree before the next one
done
```

**Chart data layout change (`--data-dir=/var/lib/soundpost/data`).** Earlier chart versions passed `--data-dir=/var/lib/soundpost`, the PVC root. The chart now uses the `data/` subdirectory, which `serve` creates itself with mode `0700`; the PVC root cannot be private because `fsGroup` makes the kubelet set it group-writable (and a root-owned root on some provisioners cannot be chmod-ed by uid 65532). If you have a release whose members already hold data at the volume root, `helm upgrade` is still safe, because `OnDelete` restarts nothing. The old root holds `control.db`, `raft/` and the storage engine's own `data/` directory (`data/apply.db`, the slot WALs), so the new `data/` is the old engine directory and **the whole old root, including that `data/`, moves one level down**. For each such member, before `kubectl delete pod`, with the pod stopped (scale is not available; use a one-off pod that mounts the claim `data-soundpost-<m>-0` while the member is down, or do it on the node's volume), run once as uid/gid 65532 in the volume root:

```sh
cd /var/lib/soundpost            # the volume root as mounted in that pod; <m> is the member's claim
mkdir -m 0700 .layout-move
for e in $(ls -A); do case "$e" in .layout-move|lost+found) ;; *) mv "$e" .layout-move/ ;; esac; done
mv .layout-move data             # control.db -> data/control.db, raft/ -> data/raft, the old data/ -> data/data
ls -A                            # expect: data (and lost+found where the volume has one)
```

Then delete the pod and verify `/readyz` as above. A fresh install needs no step. (An earlier revision of this section said `mkdir -m 0700 data && mv <every entry except data> data/`; that cannot work, because `data/` already exists in the old root as the engine directory.)

**Guard against a missed move (`legacy_volume_layout`).** A pod deleted before the move would start its member on a fresh control state inside the old engine directory (the new `data/`), with the old `control.db` and `raft/` sitting unread one level up. `serve` therefore refuses to start when its data directory is named `data` and the directory above it holds `control.db` or `raft/` (the earlier layout). It checks first, before it creates or opens anything, prints `soundpost: legacy_volume_layout: ...` (no path) and exits 1; the volume is left exactly as it was. On Kubernetes the pod crash-loops and `kubectl wait --for=condition=Ready` times out, which is the "does not become ready: stop" case above: read the log, do the move, and delete the pod once more. The guard also fires when `control.db` or `raft/` is left beside a `data/` that already holds the member's data (a copy instead of a move): delete the stale copy once you have verified `data/`, and the member starts. Only a directory named `data` is judged, so the Compose files and the systemd unit (which pass the volume root itself) are not affected. The chart's `--data-dir` must stay `<mount>/data`; `TestChartDataDirIsWhatTheLegacyVolumeLayoutGuardJudges` fails if it does not.

Decision D47, accepted as proposed. The check is in `serve` and not in a Helm pre-upgrade hook Job: a hook Job would have to mount each member's ReadWriteOnce claim while that member's pod is running, and a Job pod scheduled on another node cannot attach it; it would also guard only `helm upgrade`, not a pod recreated by any other means. `serve` runs with the volume mounted, on every start. What it cannot decide: old data that was moved somewhere other than `data/` is not recognised, and when both `data/` and the old files exist as copies (for example a member that ran once on a fresh `data/` under a build without this guard) it fires but which copy is current is the operator's call.

`kubectl wait` returns when the pod's readiness probe (`GET /readyz` over HTTPS) is satisfied. Run the loop by hand, one iteration at a time, if you want to check the cursors in between. The PodDisruptionBudget (`minAvailable: 2`) protects against a *second voluntary eviction* (node drain, cluster autoscaler) while one member is down; it is not an upgrade orchestrator.

Draining nodes: drain one node at a time and wait for the evicted member to become ready elsewhere before the next drain. Required anti-affinity means a member can only land on a node without another member; with exactly three eligible nodes the evicted member stays `Pending` until its node returns, which is correct (two voters keep serving).

## Tested upgrade and rollback of the produced binaries

`RunUpgradeRollback` (`tools/smoke/upgrade_rollback.go`; `go test ./tools/smoke -run TestUpgradeRollbackOfProducedBinaries` with `SOUNDPOST_UPGRADE_OLD_RELEASE` and `SOUNDPOST_UPGRADE_NEW_RELEASE` naming two `go run ./build release` outputs of different versions) installs the old binary, bootstraps and ingests every signal, stops it, and keeps a copy of the data directory. It then starts the new binary on the same directory (every receipt, query and investigation answer must be unchanged), rolls back by restoring the copy under the old binary (answers unchanged again), and crosses schema versions: the persisted format marker is set to a future and to a past value, and the new binary must stay unready with `schema_newer` / `schema_old` and acknowledge nothing. This last stage is currently RED: the observed product behaviour is that `serve` exits at start with `reason=corrupt` (the auth bearer-key check fails before readiness exists), so `ready` answers `unreachable`; the smoke stays strict and the product item belongs to lane 1. What the old binary does on a directory the new binary wrote is recorded, not promised (see above: not supported). The rollback path is the restored pre-upgrade copy, never the old binary on newer data.

## Running an older binary on a control.db (downgrade)

Not supported, and detected where it matters. Every state write of a build that keeps the node-local scrub marker also stores the SHA-256 of the stored state next to it (`state_seal` in the `control` bucket of `control.db`). An older binary that commits on the file does not know the seal, so the stored state no longer matches it; the next start of the newer binary then refuses the file at open with a typed `unsupported` fault instead of trusting a settled scrub marker the older binary never maintained (it applied erasures without recording that the free pages still held their payload). The refusal changes nothing in the file. Recovery is to restore a backup taken before the downgrade, or to roll the data onto a member rebuilt from the other voters (`Replacing a lost voter`). Residual: an older binary that opened the file and committed nothing leaves state and seal equal; nothing changed, so nothing is lost. A file written before this seal existed gets one at its first open. The same applies to `soundpost` rollbacks across the release that introduced the seal: a member that must go back to the older image has to be rebuilt, not rolled back in place.

### Format marker refusal (`schema_newer` / `schema_old`)

The control state carries one format marker (`auth.SchemaMarker`, the persisted `BearerHashKeyVersion`; the build in this tree supports 1). `serve` decides it first of everything that touches the data directory: `auth.NewService` reads it before it initializes, seals or opens the hash key, and `appcore.Open` has opened nothing else yet (no data store, no replication group, no peer listener of a distributed member survives the refusal). A marker above the supported one was written by a newer build and is `schema_newer`; a lower one over an installation in use (a sealed key, or users, sessions, tokens or sources stored) is `schema_old`; a pristine root (marker 0 with nothing stored) is not old, the first start initializes it. Neither is corruption and neither is a failed start.

The member then **stays up unready and serves nothing**: its HTTPS listener (from before storage opens) answers `GET /readyz` with `503 {"ready":false,"reason":"schema_newer"}` (or `schema_old`), every other route with the gate's retryable `503`, and it logs one line carrying the two format numbers and the reason, never a path. `soundpost ready` prints `not ready: schema_newer` and exits 1; a Compose health check or a Kubernetes readiness probe reports the member unready rather than crash-looping. SIGTERM stops it cleanly (exit 0). The refusal writes nothing to the stored control state (it is decided before the hash key could be initialized). A marker that cannot be decoded, a `control.db` that does not open, or a supported marker over lost key material is `corrupt` and `serve` exits with `reason=corrupt`, as before: only a number the binary can read and does not support is a schema decision. Recover by running the release that wrote the data, or by restoring a backup taken before the format changed; there is no migration in this release, and a data directory with a foreign marker cannot be opened by `appcore.Open` (so a tool that rewrites the marker has to restore a file copy, as the `upgrade-rollback` smoke does). Tests: `TestServeRefusesAForeignSchemaMarkerWithATypedReadinessReason`, `TestNewServiceRefusesAnUnsupportedSchemaMarkerWithATypedDecision`, and the `upgrade-rollback` smoke on the produced binaries.

`schema_old` on an installation that never ran an older format (no older release was ever deployed on it) is not an upgrade case: the marker is most likely damaged. Do not attempt a migration. Check the data directory's disk, compare it with the last good backup, and restore that backup if the marker cannot be explained.

## Per-state provenance in condition and job states (stored format)

Condition and job states gain one optional member, `provenance` (`model.Provenance`: the closed interval `{"from_ns","to_ns"}`, two decimal-string times, of the earliest and the latest record time the state was folded from; omitted when absent). It lets a historical range deletion erase a state whose evidence has rolled out of the state's bounded part (`docs/privacy/retention.md`, "Per-state provenance"). Nothing is migrated at upgrade and no format marker moves:

* **Old states stay valid and are never rewritten.** A state without the member is decoded by every reader as before, and the new build keeps deleting it by the old window rule, fail-closed (`over_erased` reports a state with no window). A later event does not give it a provenance (what it folded earlier is unknown); only a state that starts empty (a new condition or job, or one a deletion erased) carries one. The rolled-out-evidence residual therefore stays open for the conditions and jobs that exist when the build is installed.
* **Older readers fail closed.** A control build before this one validates the members of a job state against a closed list and refuses a job update that carries `provenance` (`invalid`); it never accepts one it cannot interpret. A condition state, whose members control does not list, is read by it as before: the older window rule reads `from_ns` and `to_ns` as ordinary `*_ns` times, which can only widen the window (never keep a state the new rule erases), and the older reducers drop the member the next time they rewrite the state, which returns the state to the old rule. Running the older binary on a control.db this build committed on is, as above, refused at the next start of this build (state seal).
* **Rollback.** A rolled-back build ignores the member. A state it rewrites loses its provenance (old rule from then on); no data is lost and nothing needs repair.

## Deletion receipts across an upgrade (erase protocol)

The replicated acknowledgements a deletion receipt waits for (`docs/privacy/retention.md`, "Deletion") have three shapes: the attributed one of the release before this (`erase_ack` / `erase_unack` carrying a `proposer`), and the new ones (`erase_notice`, an acknowledgement with `basis` and `incarnation`, an `erase_unack` that declares a disk). A binary decodes these entries strictly, so a member that does not know a shape cannot apply it. The rule that keeps a rolling upgrade safe:

1. Roll every voter and learner to the new binary, one at a time, as above. A binary older than the one that introduced `proposer` is not supported in a mixed installation at all.
2. Until every member of the committed configuration has declared the protocol, the new binary proposes only the previous shapes; each upgraded member declares itself once it has a leader (an acknowledgement of a reserved operation in a shape the previous binary applies and ignores). A deletion receipt during that time names `data_apply_db` for every completed deletion, however many voters acknowledged: an acknowledgement of the previous shape is never counted, because no snapshot notice can void it before an install (retention.md, "A receipt states its read point"), and the protection against a snapshot install and a replaced disk (limits (a) and (b2)) is not in force yet. This is the only visible effect of the change on a running installation: deletions stay logically complete and physically erased, and their receipts report the data store as outstanding until the last member declared and every voter acknowledged again (step 3).
3. Once the last member declared, the new shapes start on their own; every voter acknowledges its completed deletions once more (previous-shape acknowledgements of a voter that declared its disk never stand), so receipts name the data store again until each voter has.
4. Never add a member that runs the older binary to an installation that already declared the protocol: it cannot apply the new entries and its group would fail. Upgrade a replacement before it joins. A member that was added and has not declared yet (a new binary that has not found a leader) closes the gate for everybody until it does: receipts name the data store again, and a voter that declared its disk refuses a snapshot that carries no notice, so a voter that has to be repaired by a snapshot waits for that declaration (seconds for a member that is starting, until the member is removed for one that never starts).

## Bounded-state rules across an upgrade (control apply rules)

Five rules of control and of the notification policy keep the issue, incident, condition and notification books from growing without limit (`docs/user/issues.md`, `incidents.md`, `rules.md`, `notification-policy.md`): the issue book coalesces the 129th gap of a data group into its oldest and evicts the oldest command record at the 1025th; an incident pruned at the project cap stays as a stub that holds its ID and version; a condition creation past the project's 8 MiB budget collects settled conditions; and a notification policy's late and backfill counters saturate (`late_saturated`) instead of forgetting the oldest command. The release before them refuses at each bound (`quota`), removes a pruned incident, has no byte budget and rolls the counters' memory.

A control command is decided by the member that proposes it, against the state it reads, and the group installs the resulting state on every member, so a mixed group does not hold two states. But it would answer the same command differently depending on which member the caller reached, and a member without the rules rewrites a book that holds what it does not know (`merged`, `rev`, the stub marks, `late_saturated`) and drops it. So the rules follow the same discipline as the erase protocol above, on the same declaration (a member declares one version: 2 for the erase entries, 3 for these rules; a larger version satisfies every check of a smaller one):

1. Roll every voter and learner to the new binary, one at a time, as above.
2. Until every member of the committed configuration declared version 3, every member decides under the previous rules, exactly as the release before this one does: a full gap list or command list answers `quota`, a pruned incident is removed, a condition creation has no byte budget, and the counters' memory rolls. A project at a bound during the roll sees the old behaviour until it ends. None of these five rules writes anything the previous release does not write while the gate is closed (no `merged`, no `rev`, no stub, no collected condition, no `late_saturated`).
3. Once the last member declared (each upgraded member declares itself once it has a leader, within a few seconds), the rules engage on every member without an operator step. State the previous rules left stays valid and is continued by the new ones (a gap list at 128 coalesces at the next gap; a full command list evicts, records without a book revision first).
4. Never add a member that runs the older binary to an installation that already declared version 3: it applies the previous rules to books the new ones wrote (a stub counts against its incident cap, `merged` and `rev` are dropped when it rewrites a book). Upgrade a replacement before it joins. A member added at the new version that has not declared yet closes the gate again until it does, and the previous rules apply meanwhile (a notification state that had saturated then rolls again, so its counters are not lower bounds while `late_saturated` stays set).

Two rules of the same change are not gated because they only accept what the previous rule refused and leave no state it cannot read: evidence of a resolved issue folds on either side of the resolution boundary, and an issue's stored regression evaluations are pruned by size (`docs/user/issues.md`, "Evidence window"). Tests: `TestControlBoundsWaitForEveryMemberToDeclareTheirProtocol` (storage: the declaration, with a member that declared only the erase protocol), `TestAMixedVersionGroupAppliesOneRuleAndConvergesOnOneState` (control: three voters, one on the previous rules), `TestIssueGapListRefusesAtItsBoundUntilTheBoundedRulesApply`, `TestIssueCommandRecordsRefuseAtTheirBoundUntilTheBoundedRulesApply`, `TestIncidentPruningRemovesTheRecordUntilTheBoundedRulesApply`, `TestConditionByteBudgetWaitsForTheBoundedRules`, `TestPolicyLateMemoryRollsUntilTheBoundedRulesApply` and `TestOutboxDecidesUnderThePreviousRuleUntilTheGateOpens` (the outbox's decision).

## Audit delta command across an upgrade (control apply, protocol 4)

Every control command is the whole next state, which every voter decodes and rewrites. An elevated read audits each released chunk of bytes with one control commit (`auth.Service.CommitElevatedRead`, one audit row per chunk, committed before the bytes are released), and at a production-sized state that was one whole-state rewrite per chunk (about 0.26 s and 180 MB per marshal, decision D49). This release commits that row as a second command shape, the **audit delta**: `{"audit_delta":{"installation","expected","at","audits"}}`, a few hundred bytes. Every voter applies it exactly as the whole-state commit of the same row: the same compare-and-swap on the expected revision (a stale delta is rejected like a stale replacement), revision = expected+1, the revision clock stamped with the proposer's clock carried in the command, the rows appended, `AuthorityRevision` unchanged (the audit log is evidence, as for `ElevatedScope`: `CommitElevatedRead` therefore no longer moves it, in either path). A voter still decodes and re-encodes the whole committed state when it applies one; only what is proposed, journaled and replicated is small. A control journal redaction leaves a delta as it is (it carries no book a deletion erases).

A binary that does not know the shape fails to decode the entry and stops applying, so the rule is the one of the protocols above, on the same declaration (a member declares one version: 2 erase entries, 3 bounded-state rules, 4 audit delta):

1. Roll every voter and learner to the new binary, one at a time, as above.
2. Until every member of the committed configuration declared version 4 (each upgraded member declares itself once it has a leader, within a few seconds), `CommitElevatedRead` commits the row through the whole-state path, which every release applies (not moving `AuthorityRevision` either). Nothing in the delta shape is written while the gate is closed.
3. Once the last member declared, the delta is proposed on its own, without an operator step.
4. Never add a member that runs the older binary to an installation that already declared version 4: it cannot decode the entries and its group would fail. A member added at the new version that has not declared yet closes the gate again until it does. A rollback to the release before this one after deltas were committed is not supported (the older binary fails on the entries in its journal and on a snapshot taken from them): restore a backup taken before the upgrade or rebuild the member from the other voters.

The gate reads the slot-0 group's committed configuration and declarations at every proposal, while the delta is proposed in the control group, and `appcore.StepMembership` commits a membership change in each group separately. Between the control group's commit of a change and slot 0's, a freshly added member can therefore make the gate read one declaration of lag stale, in either direction. Stale-closed only keeps the whole-state path for a moment. Stale-open needs a member that has not declared to be in the control configuration and not yet in slot 0's, which step 4 excludes for any member added at the old binary and which for a member added at the new one lasts until the slot-0 change commits (the same moment its first declaration can be committed). While the gate is closed an elevated read commits the whole state, bounded by the 16 MiB command cap (`internal/replica/node.go`) like every other control write; a state beyond it cannot be committed through the fallback at all.

A store without a gate proposes no delta (the gate is fail-closed: the delta is a wire format an older peer cannot decode, so a caller that enables replication on several voters has to install `SetAuditDeltaGate`; a single-process test that wants the delta installs `func() bool { return true }`), and `TestAuditDeltaSurvivesAFollowerJournalReplayAfterARestart`, `TestAuditDeltaSurvivesASnapshotInstallOnALaggingVoter`, `TestAuditDeltaSurvivesTheRestartOfEveryVoter` and `TestAuditDeltaMixedVersionGroupTakesTheWholeStateFallbackAndConverges` drive it through a real three-voter control group. Tests: `TestControlAuditDeltaWaitsForEveryMemberToDeclareProtocolFour` (storage: a member that declared only version 3), `TestOpenEngagesTheAuditDeltaOnceTheGroupDeclared` (appcore wiring), `TestAppendAuditProposesTheDeltaOnlyWhenTheGateIsOpen`, `TestAuditDeltaApplyEqualsReplacementApply` (the delta leaves the state of the whole-state commit), `TestAuditDeltaWithAStaleExpectedRevisionIsRejected`, `TestAuditDeltaReplayIsVerifiedNotReapplied`, `TestAuditDeltaWithAnErasingRowOwesAScrub`, `TestControlPayloadDecoderIsStrict` and `TestJournalRedactionLeavesAnAuditDeltaUntouched` (control), `TestAnOverriddenUpdateSeesEveryElevatedAudit` (auth: a store wrapper that overrides `Update` sees every elevated audit).

## State patch command across an upgrade (control apply, protocol 5)

A whole-state control command is as large as the control state. The replica refuses a payload over 16 MiB (`replica.Entry.valid`), and the production-sized state of `authority_mask_bench_test.go` (100 organizations of 32 projects, 65 536 applied commands) is 23.5 MB encoded, so at that size no control command could be proposed at all; well before it every command wrote a whole-state record on every voter and, with the journal cadence, cut a snapshot. Larger entries are not the answer: the control state is not bounded by design (the audit log is kept 365 days, books grow with projects), and each command would still cost a whole-state journal record, replication and snapshot per write. This release therefore commits a control command as a third shape, the **state patch**: `{"state_patch":{"installation","expected","base","keys","ops"}}`, where `ops` are the members of the state the transition changed (`set`, `del` of a record of a map, `array` cut and append for the audit log, `Audits`, and the revision clock, `revision_clock`: the names are the JSON member names of the state). A voter applies it to its committed state with the same compare-and-swap on the expected revision, decodes the result strictly, and requires the installation and the revision step, so the state it ends in is the state a replacement would leave (`TestStatePatchEqualsReplacement`, `TestStatePatchOfTwoStatesAppliesToTheSecond`, `TestStatePatchChangesTheRevisionClockRowWise`).

Measured at the production-sized state (`TestStatePatchRunsEveryCommandClassAtProductionSize`, sp-w1): without the gate every command is refused as invalid; with it a session, a setting, an evaluation record, an audit row cost 386-499 bytes, a rule pass of 5 000 records 413 kB, an organization record replaced whole 398 kB, and the expiry of 64 500 applied commands (the largest legitimate change) 2.7 MB. A voter applies a patch, an audit delta and a stale rejection to the bytes of its state without decoding it (`state_raw.go`): the members the command does not name are carried over as they are, a value it names is decoded strictly into its type and encoded again, members keep the order the encoder writes, and what the splice cannot prove it does exactly (a value that is not what the encoder writes back, an omitted zero, a name that needs escaping, a state that is not the compact encoding of a State) it refuses, and the voter then decodes the state as before and applies the ops to it. Every voter therefore holds the bytes of the encoding of a State whichever way a command was applied, in a group that mixes releases too (`TestRawPatchEqualsDecodeEncode`: 1 500 random patches, equal to the byte; `TestPatchedStateBytesAreIdenticalOnEveryVoter`, `TestPatchedStateBytesAfterASnapshotInstallAreIdentical`: three voters, a restart and a snapshot install). `BenchmarkStatePatchCommandAtProductionSize` (one voter that proposes, validates and applies, 23.5 MB, sp-w1): a session command 2.20 s and 1.09 GB before, 0.68 s and 0.32 GB after; a setting 2.35 s and 1.14 GB, 0.72 s and 0.32 GB; an audit delta (the elevated read's row, per chunk) 0.99 s and 0.46 GB, 0.30 s and 0.13 GB; the apply alone, from the CPU and allocation profiles, about 1.0 s and 520 MB before and 0.08 s and 47 MB after, per command (`TestApplyAtProductionSizeDoesNotDecodeTheState` bounds the allocation and that no command decodes the state). What is still O(state) per command: the proposer's decode of the state and encode of the next state for the transition function (one voter per command), the digest of the base (one hash on the leader's validation, one on each voter), and the write of the new encoding to the control file with its seal.

The patch is a wire format an older peer cannot decode, so it is proposed only once every member of the control group's committed configuration (and of the slot-0 group's, where the declarations are kept) declared protocol 5 (`storage.statePatchProtocol`, `Engine.ControlStatePatchReady(members)`, `Store.SetStatePatchGate`, wired in `appcore/replicated.go`). The gate reads the control group's own members, not only slot 0's: a membership change that reached the control group but not the data group leaves a voter that never declared in the control configuration, and the gate stays closed for it (`TestControlStatePatchGateReadsTheControlGroupsOwnMembers`). Until then, and for a store without a gate, a command is a replacement, bounded by the 16 MiB cap.

A revision does not identify bytes: a stale command is rejected with the revision moved to its application slot and the older bytes kept, so two voters could hold different bytes at one revision, and a patch that only names what it changes would commit on both and keep the difference. The patch therefore carries `base`, the SHA-256 of every member of the state it was computed against, record maps included. The leader refuses a proposal whose base is not its own bytes (`stale`, the proposer reads again) or that has none (`invalid`); a voter that holds other bytes at apply refuses the command as `corrupt` and stops applying: it has to be resynchronised by a snapshot install, never given a patch (`TestStatePatchOfOneLineageIsRefusedByAVoterHoldingAnother`, `TestStatePatchOfOneLineageIsRefusedByAVoterWhoseRecordMapDiffers`, `TestStatePatchProposalNamesTheLeadersBytes`). The one place where voters legitimately hold other record maps at one revision is a voter that applies the log an erasure pass rewrote (it holds records the pass erased): in a pass, every retained patch from the first rewritten command on is rewritten without its `base` (`clearPatchBase`), so only those commands, which a voter that is behind applies, are unchecked; the voter reaches the committed state at the pass head, and patches after it carry the proposer's base again.

Redaction of retained commands (`RedactControlCommand`) rewrites the records of a patch with the same erasure functions and leaves a record that equals the committed state as written (`state_patch_redact.go`). It always uses the wide `stateErased` rule where a replacement committed after a deletion finished uses `stateErasedLate`: a patch does not carry the state it committed in, so an intermediate state of a voter that applies the rewritten patch is more erased than the replacement's would be, and the last write of every record (left as it is) leaves the committed state. `TestEachControlVoterRedactsItsOwnCopyWhenCommandsArePatches` runs the three-voter redaction scenario on patches. A patch that a pass rewrote carries no `base` (it is applied by a voter that is behind and holds records the pass erased), so the digest does not cover the rewritten log; what covers it is the replay itself, tested on a lagging voter that replays a rewritten log (`TestALaggingVoterReplayingARewrittenLogReachesThePassHead`, `TestAVoterBehindTheFirstRewrittenCommandReplaysTheRewrittenLogToThePassHead`: its state bytes equal the other voters' at the pass head, no erased record is left, and a patch with a base is accepted afterwards). One rule exists only for that window: when the pass emptied the whole-map write that created a book (an emptied omitted book is not written back), the next record of the book is a key-level write into a book that is not there, and a patch without a base creates the book where a patch with a base is refused (`TestAVoterReplayingARewrittenLogThatEmptiesAWholeBookReachesThePassHead` failed on the earlier tree with the voter stopped at `corrupt`; `TestARewrittenPatchWritesARecordIntoABookThatIsNotThere`).

## Admin saves compare the object, not the organization (no protocol, rollback is safe at any time)

`POST /api/v1/admin/commands` (`expected_epoch`) and `POST /api/v1/policies` (`expected_revision`) still carry the organization policy epoch the page read, and the console sends them unchanged. The server no longer refuses a save because the organization changed: it refuses it when the object the command targets (project, membership, org admin, grant, team, source policy, SSO, destination, retention, notification policy of one project) was changed after that epoch (`model.ControlOrg.ObjectChangedAfter`, `TrackChange`; the organization keeps `Epoch` as its security epoch and every change still moves it). The record of which epoch each object last changed at is part of the command's own state change, so no voter applies a different rule: nothing is re-evaluated at apply.

**Where the records live, and why nothing is declared or finalized (D59).** They are keys of the organization's `Settings` map, which the previous release already has: `obj_epoch:<object>` (the epoch the object last changed at), `obj_floor` (the epoch every object without a record counts as changed at) and `obj_seen` (the `Epoch` after the last tracked change). The previous release's strict decoder refuses an unknown *member* of a record but accepts any *key* of a map of raw values, and every reader of `Settings` in that release reads a key or a prefix of its own and ignores the rest (`destination:`, `source_policy:`, `team:`, `sso:`, `retention:`, `artifact_refs:`, `replay_index:`, the notification-policy key; the whole list of references in both trees is the evidence file `settings-consumers.txt`, and the candidate adds no reader of `Settings` but `model.ControlOrg`). A replacement command, a state patch, a snapshot or a stored state that carries the records therefore applies and installs on the previous release exactly as one that does not, so there is no protocol to declare, no operator step and no member list to check: the new binary writes the records from its first admin save. (An earlier design stored them as new members of the organization and gated them on a declared protocol 6 behind a `soundpost upgrade finalize` command; a state with a member the previous release does not know makes that release stop applying, `apply_failed`. That design, its command, route, live support check and declarations are gone.)

**What a mixed group does.** The previous release compares the whole organization epoch on every save and bumps `Epoch` without touching the records. After such a save `obj_seen` is behind `Epoch`, and the new binary reads that as "every object changed at the current epoch" (the whole-organization compare of the earlier releases) until its own next tracked save makes the records current again. So a save based on a page read before any other change to the organization is refused as before, a page read after it commits, and no stale save of an object that changed is ever accepted, on either release. A record that is missing, not a number, or whose floor/seen mark is missing can only make saves conflict, never pass: they read as a change at the current epoch (`TestMissingOrAlteredObjectRecordsOnlyMakeSavesConflict`); the previous release writes `Settings` only under keys of its own (restore keeps the other keys and bumps `Epoch`), so no write path of it drops a record while leaving the epoch where it was. A restore, a project retirement or any other change that does not track objects counts as a change to every object at the epoch it produced.

**Bound.** At most `model.MaxObjEpochs` (4096) objects of one organization are recorded: entries at or below the floor are dropped on the next tracked change, and past the bound the floor rises to the current epoch and the records are cleared (conservative). A tracked change is a patch of three keys whatever the number of records, the change that reaches the bound is at most one delete per record, the bytes spliced into the state equal what decoding and encoding it again leaves, and a record adds about a hundred bytes to the state a snapshot carries (`TestObjectRecordsKeepPatchesAndTheSpliceBounded`; `TestApplyAtProductionSizeDoesNotDecodeTheState` measures an object-record change at the production-sized state).

**Rolling upgrade and rollback.** Roll the voters one at a time as in "Order" above; nothing else is required. Any voter can be put back on the previous release at any time, before or after the records exist, and a member of the previous release can be added (as a voter or a learner) at any time: it applies the records the new binary writes and installs a snapshot that carries them. `TestMixedBinaryVoters` runs it on the real binaries of both releases: a group of one new and two previous-release voters saving through each side (states agree on every save, no voter leaves `/readyz`), the conflict rule above on both releases, the previous-release voters rolled to the new binary one at a time, one voter rolled back to the previous release after the records exist, that voter stopped while the new voters commit past the journal cadence and then started on the previous release (it installs a snapshot that carries the records), and a previous-release learner added through `membership add-learner` on an empty directory.

Tests: `TestControlOrgObjectChangedAfter`, `TestControlOrgTrackChange`, `TestObjEpochsCapRaisesTheFloorAndDropsTheOldest`, `TestObjectRecordsAreSettingsKeysNoOtherCodeReads` (the previous release's strict `ControlOrg`, member for member, decodes an organization with records; no other reader's prefix matches a record key), `TestObjectRecordsLeaveTheOrganizationDecodableByThePreviousRelease`, `TestObjectRecordsAreWrittenAtEveryProtocolAndEveryVoterHoldsThem`.

## Sharded artifact ledger index and per-replay pins: expand, then `soundpost upgrade contract-indexes`

This release stores the artifact reference-ledger index as 256 shards per project (`artifact_refs_index:shard:<project>:<xx>` with `...shardanchor:...`) and the replay pins as one small value per replay (`replay_pins:<project>:<replay>`), so that recording a ledger or a replay changes a bounded number of bytes whatever the size of the project. The previous release reads neither: it reads one value per project, `artifact_refs_index:<project>` (with `artifact_refs_index:anchor:<project>`), that pins the current `(Seq, Head)` of every ledger, and one map `replay_pins:<project>` of every replay's pin, and it answers `corrupt` for a ledger or replay it cannot find there. Keeping those values current is exactly the work the new layout removes (measured on the previous release's reader: 59,501 B per ledger write at 500 ledgers, 595,001 B at 5,000, 5,950,001 B at 50,000), so the two cannot both be had at once. The migration therefore has two phases (decision D70):

**Expand (the default for an installation upgraded from the previous release, from the first start of the new binary).** A write keeps both layouts current: the shards and per-replay pins, and the previous release's per-project index and pin map. Writes cost what they cost on the previous release, **every voter can be rolled back to the previous release at any time**, and the previous release reads everything the new one wrote (`TestExpandedWritesStayReadableByThePreviousRelease`, `TestExpandedPinWritesStayReadableByThePreviousRelease`, and the real-binary `TestUpgradeRollbackOfProducedBinaries` with ledger writes and new replays between the rolls). Reads use the shards and pins; a ledger or replay the previous release wrote after a rollback (its own layout is all it knows) is found through the per-project values and brought up to date by the next write (`TestExpandedLoadFollowsAWriteOfThePreviousRelease`, `TestExpandedPinReadsFollowAWriteOfThePreviousRelease`; a replay the previous release swept leaves a dangling per-replay pin that reads as no replay and is dropped by the contraction). In this phase the tamper evidence of the sharded layout is the previous release's (the per-project index is the authority and a tampered one refuses the write); it is the per-shard evidence once contracted.

**A fresh installation starts contracted (D72).** An installation that this release bootstrapped, one whose control state no previous release ever wrote, has no previous-release data to roll back to, so it does not pay the expand phase: it is contracted from its first write and so is every organization created on it, with no operator step. A write changes one ledger and one shard (and a replay its own two keys) whatever the size of the project, and no per-project index, anchor or pin map is ever written. How the installation is known to be one: the `Bootstrap` command that creates the first administrator of an installation that holds no user and no organization writes the mark `artifact_refs_index:contracted` into the replicated control state (the `OIDC` map of the state, whose other residents are pending logins, elevation records and attestations, and whose keys the previous release reads by name only) in the same transition, so every voter holds it, a snapshot carries it, state digests are equal, and nothing is derived per node or from a local file. `create_org` copies it to the organization's settings (the marker the contraction writes, so the readers of the ledger and the pins need no second rule), and the layout guards of a contracted installation below apply from the first start: a member that does not answer the live layout question cannot be added to it and is not sent its snapshots. A `Bootstrap` that follows a restore (the restored users and organizations are present) never adds the mark, and the restore quarantine keeps the mark a backup of a fresh installation carries, so a restored installation is in the phase of its backup. An installation the previous release bootstrapped never has the mark: a restart of this release, a write or an organization created later do not contract it; only `contract-indexes` does. **Rolling a fresh installation back to the previous or an older release is not an upgrade path** (the previous release cannot read the contracted layout, and plan 07 Task 8 covers release-to-release upgrades): to run an older release, restore a backup that release wrote or start a new installation on it. Tests: in `internal/auth`, `TestFreshInstallationIsContractedFromItsFirstWrite` (the first write and a project of 2,001 ledgers: one ledger and one shard, no per-project value), `TestUpgradedInstallationStaysExpandedUntilContractIndexes`, `TestFreshInstallationMarkIsReplicatedAndEveryVoterAgrees` (three voters over mTLS) and `TestRestoreKeepsThePhaseOfTheBackup`; on real binaries `TestFreshInstallOfTheCandidateIsContractedOnRealVoters` (three candidate voters on an installation the candidate bootstrapped, real ledger and replay writes through each voter, no per-project value on any voter, equal state digests) against `TestUpgradeRollbackOfProducedBinaries` and `TestMixedBinaryVoters` (installations the previous release, 5475ef6, bootstrapped: expanded, rolled back and forth, contracted only by the operator step).

**Contract (operator step).** When every voter runs the new binary and no rollback is intended:

```
soundpost upgrade contract-indexes --url https://HOST:PORT --email ADMIN --password-file PATH --reason TEXT [--ca PEM] [--code TOTP] [--command-id ID]
```

The command logs in as a system administrator (fresh session), posts `POST /api/v1/admin/upgrade/contract-indexes` and logs out. The server asks the **running** binary of every member of the control group, over the peer mTLS connection (`GET /internal/raft/v1/layout`), whether it reads the contracted layout. The previous release does not implement that question, so a member on the previous release, a member that is down and a member that does not answer are all named and the step is refused with `unsupported` (`layout_unsupported_by:<identity,...>`), fail closed; a stored declaration is never trusted because a voter put back on the previous release would keep it (`TestContractIndexesIsRefusedUntilEveryMemberAnswersTheLiveQuestion`, `TestMixedBinaryContractRefusal`). Each organization is one control transition (a large project does not make the command large) that rebuilds the shards and per-replay pins from the verified per-project values, deletes those values and marks the organization (`artifact_refs_index:contracted`, a key the previous release ignores), with one audit row (`contract_indexes`) per organization. The command is idempotent: when every organization is contracted it prints `indexes already contracted` and writes nothing, and a call interrupted half way is finished by repeating it. An organization created after the step starts contracted.

**After the contraction** the per-project values are deleted and never written again, writes are O(1) in the size of the project (`TestContractDropsThePerProjectIndexAndMakesWritesBounded`: one ledger write changes less than 24 KiB of Settings in a project of 3,000 ledgers; `TestContractPinsKeepsNewestAndMakesWritesBounded` for replays), and **a voter must not be rolled back to the previous release without restoring the backup taken before the step**: it would report the ledgers and replays `corrupt`. Take the backup (`docs/operations/backup-authority.md`) before running the command. The step only checks the members that exist when it runs; the guards below cover a previous-release member that joins or is put back afterwards.

**Guards after the contraction (the previous release cannot be changed, so the new binary refuses and says).** From the moment any organization of the installation is contracted (an organization created after the step is born contracted, and so is every organization of an installation this release bootstrapped), a member whose RUNNING binary does not answer the live layout question (`GET /internal/raft/v1/layout` over the peer mTLS connection, the question the step asks; the previous release does not implement it, a member that does not answer in five seconds is the same: fail closed) is treated as layout-incompatible, and the typed reason is `layout_incompatible:<node identity>` (`unsupported` with that detail). A member that is not running at all (nothing accepts a connection at its peer address) is the one exception, and only for adding a learner (below): it has no binary to ask. Before the first organization is contracted none of this applies (the previous release reads the expanded layout).

* **(a) Adding a member.** `soundpost membership add-learner` and `replace` (the promotion of a learner to voter) ask the question about the member being added or promoted before they propose anything, once per run and only for a group the run would change and this node leads. A member that does not answer is refused in every such group: the group reports `layout_incompatible`, the output names the member (`group <id>: layout_incompatible:<identity>`, the summary line counts `layout_incompatible=N`), the exit status is 1, nothing is proposed and no configuration changes. Start the new member on the new binary (it answers) and run the step again. The one exception is `add-learner` of a node nothing is running for yet (the order of the replacement is add-learner, start the node, `replace`; the `membership-replace` drill and `docs/operations/distributed.md` do it in that order, and every installation this release bootstraps is contracted from its first write): it is added as a learner. It then receives no snapshot of the contracted state until it answers (b), `replace` refuses to promote it until it answers (this paragraph), and `membership status` names it until it does (c); a previous-release binary that is running is refused at `add-learner` as above. What the exception cannot stop: a node started on the previous release after it was added catches up from the log as the rolled-back voter of (c) does, so take such a node out of service (it never becomes a voter). (`TestMembershipRefusesAMemberThatCannotReadTheContractedLayout`, `TestStepMembershipAsksTheLayoutQuestionOnlyWhereItWouldChangeAGroup`, `TestStepMembershipAddsALearnerNothingRunsForYetButPromotesOnlyOneThatAnswers`, `TestStepMembershipChecksThePromotedLearnerAndFailsClosed`, `TestQueryLayoutTellsAMemberNothingRunsForFromOneThatDoesNotAnswer`; real binaries: `TestMixedBinaryPostContractGuard`, a previous-release learner alive on its peer port is refused in every group, a candidate learner is added; the `membership-replace` drill, a candidate learner is added before it starts.)
* **(b) Snapshots.** The sender of a control-group snapshot (the leader) asks the same question about the receiver before the message leaves while the state it would install is contracted. A receiver that does not answer is sent nothing (the delivery counts as failed and Raft offers the snapshot again), so a previous-release member can no longer install the contracted state, report ready and answer `corrupt`. A snapshot of a state that is not contracted is sent as before. Nothing is added to the message, so a receiver that predates the guard is not affected. A member that stays behind for this reason is the member `membership status` names (below). (`TestSnapshotOfAContractedStateIsNotSentToAMemberThatCannotReadIt`, `TestSnapshotGuardWithholdsTheSnapshotFromAMemberItRefuses`.)
* **(c) A voter put back on the previous release after the step.** It cannot be stopped from outside, and it catches up from the log, so the new voters report it: `soundpost membership status` on a new voter prints `reasons=layout_incompatible:<identity>[,...]` on the control group's line (the other groups carry none; the node itself and members that answer are never listed; nothing is listed before the contraction). The list is computed live, so it disappears when the voter runs the new binary again. `/readyz` is unchanged on purpose: it is unauthenticated and its reasons are a closed set about this node, and a new binary always reads the layout; a rolled-back peer does not make a new voter unready. The previous-release voter itself, put back on a contracted state, comes up ready and answers the artifact read of a ledger it cannot read `corrupt` (recorded in `TestMixedBinaryPostContractGuard`): take it out of service, roll it forward or restore the backup taken before the step. (`TestMembershipReportNamesAControlMemberThatCannotReadTheContractedLayout`, `TestMembershipCommandReportsAndRefusesMembersThatCannotReadTheContractedLayout`; real binaries: `TestMixedBinaryPostContractGuard`.)

Also in this release: an `authority_rev` key in an organization's settings, written by its admin commands and by its retention-class commands (deletion, hold, retention policy, saga steps) while they are proposed as state patches and verified to have written only that organization's rows. Such a commit also moves the installation-wide `AuthorityRevision` (an older binary judges a retention command against it alone and keeps refusing a same-organization view older than the commit, which needs no protocol level), and records in `State.OIDC["authority:scope"]` that the floor this release judges against did not move. A previous-release voter may still answer a false 409 to a view that is stale only for another organization while it is a member; this release never does. ## Fragment envelope (artifact fragments on the wire)

An artifact fragment is proposed to the replica group either as the JSON command every release has used (the fragment base64-encoded, then base64-encoded again by the replica layer) or, in this release, as a binary envelope (`internal/storage/envelope.go`: magic `0xF7 S P F`, version 1, head JSON, SHA-256, cursor, raw bytes). The envelope is a wire form only: every voter decodes either form, re-verifies the fragment digest while decoding, and stores the command as the same JSON text, so `replica_commands`, snapshots, backups, redaction digests and state digests do not depend on which form a proposer chose (`TestMixedFormatProposersLeaveIdenticalState`). Records written by older releases are JSON and keep reading (`TestDualFormatReaderReadsOldRecords`, golden `e805349` fragment).

A release without the dual-format reader refuses an envelope: its JSON decoder answers the typed `corrupt` fault for the leading `0xF7` byte (never a misread), and on a voter that is an apply failure of that group. A reader that knows the envelope but not its **version byte** is refused the same way, one level up: it answers `invalid` with the detail `unsupported_fragment_envelope_version`, which Apply turns into the same fail-stop (`FailApply`). Recognizing the magic is therefore not enough; a proposer that writes a version newer than a voter reads breaks that voter's group exactly as a pre-envelope proposer would, so a future envelope version needs the same roll-then-enable rule as the envelope itself.

**There is no operator switch for the envelope in this release.** The envelope is off by default and the only way to turn it on is the engine option `Engine.EnableFragmentEnvelope(true)`, which an embedding process calls on its own `storage.Engine` after the engine is created; no flag, environment variable, configuration key, manifest value or API exposes it, and nothing in `cmd/` or `internal/appcore` calls it (`serve` therefore always proposes JSON). To use the envelope the owner of the embedding code adds one line after the engine is created, behind their own rollout decision: `engine.EnableFragmentEnvelope(true)`. What that decision has to establish is **not checked by the software**: there is no gate, capability probe or handshake that verifies that every voter runs a release that reads both forms before the first envelope is proposed, and `envelopesProposed`, the engine's counter of envelope proposals, is not exported as a metric or status field (it exists for tests). The rule is a procedure, not a mechanism: roll every voter to a release that reads both forms first (confirm it from your own release inventory, not from the cluster), enable proposing only after the last voter runs it, and never add a member that runs an older release once it is enabled (the same rule as the erase protocol above).

**One proposal, one wire form; the switch is safe to flip at any time.** The replica layer recognizes a retry of a command by the exact bytes of its payload (`Entry.proposed()`, the SHA-256 of the payload once the retry table keeps it by digest), and the envelope and the JSON form are different bytes for one fragment, so the same replica command ID proposed once in each form would be a conflict. That cannot happen through the engine: `commitReplicated` mints a fresh command ID for every proposal and encodes its payload once, the replica layer carries that payload verbatim (a follower forwards it unchanged), and `slotMachine.Validate` answers `stale` to any later proposal of an applied application index before the retry table is consulted. The retry of an upload (a `WriteBlob` whose acknowledgement was lost) is recognized by the artifact's own receipt, ordinal and hash, not by command ID, so it is unaffected by a flip between the attempts (`TestFragmentUploadRetriedAcrossAWireFormFlip`, both directions; `TestRetryByCommandIDOfAnAppliedFragmentIsStaleInEitherForm`). The operator rule that remains is for code that embeds the engine or the replica group directly: a caller that retries a replica command under the same ID must resend the stored payload bytes verbatim and must not re-encode the command, because a re-encoding under the other form is an `ErrConflict`.

**Erase gate: the snapshot sender is upgraded before the receivers it installs on.** A voter that runs the erase gate (storage) refuses a snapshot whose `Context` does not start with the gate's advertisement, which includes one from a sender of the build before the advertisement existed (it sent the token bare). In a rolling upgrade a not-yet-upgraded leader therefore cannot install a snapshot on an already-upgraded storage voter: the delivery fails and is retried until the leader is upgraded. The digest gate below constrains the other direction (an upgraded leader cannot install on a voter that is not yet upgraded). The two together mean that no order lets a voter that has fallen behind the leader's compacted journal catch up while the voters run different binaries: keep every voter caught up during the roll (one member down at a time, as above, and no long pause between members), and a lagging voter catches up as soon as it and the leader run the same binary.

## Snapshot protocol gate: the retry table kept by digest

A group whose machine keeps its retry table by digest (the control machine and every storage slot machine: `replica.DigestRetryMachine`) writes a Raft snapshot envelope whose retry table holds, per command, the receipt and the SHA-256 of the proposed payload and **no payload** (`Entry.Original` set). A build that predates the digest table reads the field but not its meaning; installing such a table on it would leave that voter with a retry table it cannot use as the leader's. So the format is gated, and the rule is the same as for the erase protocol and the fragment envelope: **upgrade every voter before relying on it; a voter that still runs the older binary cannot install a snapshot from an upgraded leader**.

* **What an upgraded sender does.** A snapshot whose retry table holds a digest-kept command carries `"retry":"digest-1"` as the first member of its envelope (`snapshotEnvelope.Retry`), and the message that sends it carries the capability advertisement `soundpost/snapshot-retry/digest-1\x00` at the front of its `Context`, in front of the erase gate's advertisement and token (`internal/replica/snapshot_gate.go`). A table that holds payloads (a group whose machine does not keep digests, an envelope written by an older build) is sent exactly as before.
* **What an older receiver does.** It refuses, and the leader sees a failed delivery and sends the snapshot again until the voter is upgraded: a member that runs the erase gate (storage) finds its own advertisement missing from the start of the `Context` and refuses the message before it admits it; a member that runs no gate (control) decodes the envelope strictly and rejects the unknown `retry` member. Nothing is installed, nothing is ordered, nothing is lost. The member keeps following by log replication for as long as the leader's journal still holds the entries it is missing; once the leader has cut and compacted past it (a cadence cut, `docs/operations/recovery.md`), it stays behind, `/readyz` of the group is unaffected for the other two voters, and it catches up the moment it runs the new binary.
* **What an upgraded receiver does.** It reads an older, payload-bearing envelope as before and converts its retry table to digests (`TestPayloadBearingEnvelopeIsInstalledAsDigestsOnTheNewBuild`). It refuses an envelope with digest-kept commands from a sender that did not name the capability (`TestGatedReceiverRefusesDigestKeptEnvelopeFromASenderWithoutTheCapability`, `TestReceiverWithoutAGateRefusesDigestKeptEnvelopeFromASenderWithoutTheCapability`); an upgraded pair works (`TestSenderNamesTheCapabilityOnlyForADigestKeptEnvelope`, and the three-voter storm in `internal/control/cadence_voters_test.go`, which installs a snapshot on a voter that was cut off for more than 4096 commands).
* **Operator rule.** Roll one member at a time as above, and do not leave a member down or on the older binary while the group keeps committing: the longer it lags, the likelier the leader has compacted past it. A leader that runs the older binary sends payload-bearing envelopes, which upgraded members accept, so a mixed installation is safe in both directions; only an older receiver of an upgraded leader's snapshot is refused. A snapshot cut by a build between the digest table and this gate (digest-kept, no `retry` member) is recognised by its content, so an upgraded leader still names the capability for it.

## mTLS certificate rotation

A member loads its certificate, key and CA once at start (`tls.LoadX509KeyPair`, one CA pool); rotation therefore replaces files and **restarts that member**, one at a time, under the rules above. Identities never change: the leaf's URI SAN stays `spiffe://soundpost/node/<identity>` and its DNS/IP SANs still cover the member's peer address. A certificate with another identity or without the exact peer name is refused by the other members.

* **Leaf rotation (same CA).** Issue the new leaf and key for one member, replace that member's files (Compose: that member's configuration volume; Kubernetes: update its `pkiSecret`), restart that member, wait for `/readyz`, continue with the next. Peers that still hold the old leaf keep verifying the new one against the same CA.
* **CA rotation.** (1) Put the old and new CA certificates in one bundle file and roll every member to trust the bundle. (2) Roll every member to a leaf issued by the new CA. (3) Remove the old CA from the bundle and roll every member again. Each step is a full one-at-a-time roll; the installation is never trusting a CA that was not distributed everywhere first.
* Expiry: certificates must outlive your roll time by a wide margin. A member whose certificate has expired cannot be reached by peers and is a lost voter (two members still serve; a second expiry loses quorum).

This release rotates by restart. The live-rotation behaviour is documented from the code (`internal/appcore/replicated.go`), and the `install-distributed` smoke (process mode) exercises both procedures above: a leaf rotation under the same CA, then a CA rotation (bundle, new-CA leaves, bundle without the old CA), restarting one member at a time with the cluster ready and converged after each, and then requires a peer to refuse a client presenting an old-CA leaf. Container (Compose) mode does not run the rotation.

## Replacing a lost voter

A voter whose disk is lost is **not** restarted empty under its old identity. Follow `distributed.md` (new identity, learner first, joint-consensus replacement). The Compose/Helm manifests install the three initial voters; replacement is a membership operation, not a redeploy.
