## What a snapshot is

Every owned group (control and the 64 data slots) cuts its own snapshot at its current applied index, under the group lock, so state, receipts and ledger agree. A snapshot is a directory under `<group directory>/snapshots/`:

| File | Content |
| --- | --- |
| `envelope.json` | Raft snapshot payload: the machine's serialized state, the completed-command table that makes proposals idempotent, membership and the C05 application cursor. For a data slot the state of a locally cut snapshot is the **window table** (see "Windowed slot snapshots"): it names the files that hold the ordered command history instead of containing it. The whole-history form (`version` 1: every normalized batch, original receipt, fence and GC fence inside the envelope) is what a snapshot sent to a peer and every snapshot written before 01.07-W1 carries, and is still read |
| `ledger.json` | The deletion ledger: every tombstone-class command (source fence, cancellation fence, artifact GC) with its application index and digest, plus the tombstone generation |
| `raft.conf` | Raft configuration at the cut |
| `files/<name>` | Machine-supplied immutable files pinned during the copy. Every data slot carries `win-NNNNNNNN.cmd` (the commands of one window) and `win-NNNNNNNN.evd` (that window's consumption evidence) per window; slot 0 also carries the storage manifest and every cold segment (`storage-manifest.json`, `segment-NNNNNN.sps`) |
| `MANIFEST.json` | Checksummed manifest: group, physical index/term, application cursor, ledger generation/count/digest, every file with size and SHA-256, and a SHA-256 over the manifest itself |

Segments and indexes are derived from the command history, which is the authoritative byte set. They are copied as a verified transfer set, and an installed receiver rebuilds typed rows and indexes by replaying the history it received; installed segment files are not adopted as live state.

### Windowed slot snapshots (01.07-W1, decision D21)

A data slot's command history is cut into **windows** of `snapshotWindow` (4096) consecutive commands. A locally cut snapshot no longer carries the history inside its envelope: the envelope's state is the *window table* (`slotSnapshotV2`: slot, identity, application index, the window size and, per window, its number, first index, count, the size and SHA-256 of its two files, the window's *identity*, its batch/redacted/cancel counts and its charge digest). The history travels as two files per window under `files/`: `win-NNNNNNNN.cmd` (the exact stored command bytes, length-prefixed) and `win-NNNNNNNN.evd` (a JSON sidecar of the reservations the window's batches consumed and the cancellations it carries). Their sizes and hashes are in `MANIFEST.json`, so the existing install gate (every file hashed as it is written, exact file list) covers them, and the table must name exactly the files the manifest hashed (`compactState`).

* **A cut is incremental.** A window is *sealed* once it holds all its commands; a sealed window never changes except by redaction. The node keeps one record per sealed window in `replica_data` (`wrec:<n>`: file and sidecar hashes, identity, charge digest and the window's share of the deletion ledger). A cut reads the records, derives only the windows that have none (those sealed since the previous cut) and the open window, assembles the deletion ledger from the records (it no longer scans the history), and takes every window whose files the selected snapshot already holds, by name, size and hash, **without reading them**: a hard link, or a copy verified against the hash where links are unavailable (`replica.PinnedFile.Reuse`, `SnapshotStore.create`). Slot 0's cold segments are reused the same way. `CreateSnapshots` verifies the new snapshot with `SnapshotStore.VerifyCut` (hashes only the files that cut wrote, plus the envelope and the ledger); `CompactJournal` still re-hashes every byte (`Verify`) before it truncates. A cut that finds a window changed between the table and the file write (a redaction in that gap) or the selected snapshot replaced is repeated (up to three times).
* **Redaction is the only writer of a sealed command** (`eraseBatchTx`, `eraseBlobTx`), and it drops that window's record in the same bolt transaction. The next cut derives the window again, so the redacted bytes, not the previous snapshot's window file, are what the new snapshot carries. The old snapshot directory is replaced by the cut at an advanced index exactly as before (see "Known limits").
* **Identity.** A window's identity is a digest of its commands that redaction leaves alone (a redacted command counts as the original it replaced, as `sameCommand` already decides). `VerifySnapshot` of a compact state compares window identities with the local ones instead of byte-comparing every command, so a snapshot cut before a redaction still verifies afterwards. The sealed-window records are what it compares to; they are re-derived from the commands by the background full verification (`validateWindowRecordsTx`), so a record that no longer matches its commands fails the engine closed (the weaker-guarantee wording of "Bounded startup verification" applies to them too).
* **Peers never see a compact state.** `slotMachine.Snapshot` still produces the whole-history state; a snapshot offered to a peer is always cut with it (`snapshotSource.Snapshot`, a `CompactMachine` never offers its stored snapshot), and `Restore` installs that form unchanged. A compact state is resolved against the group's own snapshot store (`SnapshotStoreUser`): after a backup restore the installed directory is that store's selected snapshot, and the node replays the windows from it one command at a time (hashing each file as it goes). A compact state whose directory is missing or is not the snapshot it names is refused.
* **What this bounds.** The cut reads the windows written since the previous cut plus the open window, the table and the records (memory: one command at a time). The snapshot record of `ready.wal` and the journal-open `VerifySnapshot` no longer carry or decode the history. What stays proportional to history: the completed-command (retry) table inside the envelope and the journal record that holds it, the window *table* (one entry per window, so history / 4096 entries), `CompactJournal`'s full re-hash, uploading a backup (every snapshot byte is streamed), and a restore (see below).

**Backup bundle version 2.** `BackupBundle.Version` 2 carries `QuotaEvidence.Windows` (one `WindowEvidence` per window of every group: counts, charge digest, identity) and lists reservations (`Consumed`) **only for the windows control's cut does not already hold**. For every other window the reservations are the ones the control cut holds as consumed in it, and the window's charge digest (digest of the consumed reservations' id, org, project, source, hash, bytes, series and cursor in cursor order) must equal exactly the digest of those reservations (`QuotaEvidence.resolve`); a mismatch is `corrupt`. A window is a *detail* window when the digests differ (a reservation admitted after the cut, a consumed reservation control still holds as reserved, a cancelled one) or when it carries redacted batches (the series they retain are not in control). `BackupBundle.ConsumedEvidence` returns the full list both `ReconcileQuota` and the control-state reconciliation (`internal/backup/restore.go`) work from, so the certificate is the one version 1 gave. The bundle's size and `Seal`'s memory therefore follow the number of windows and of detail reservations, plus the control cut itself; `Cancelled` is still listed in full (cancellations, not batches). `Seal` derives the evidence from the window table the cut wrote and reads the commands only of the windows past each group's processed highwater H (the replay certificate); `InstallBackup` re-derives every window's record, sidecar and charge digest from the installed command files (one command at a time) and refuses a bundle whose evidence digest differs, so a forged window table cannot pass by being internally consistent.

**Old backups.** A version 1 bundle (written before this change: whole-history slot snapshots, the full consumed list) is **still restorable**: `ReconcileQuota`, `InstallBackup` and the control reconciliation read it in the form it was written in, `Restore` installs its whole-history snapshots, and the node's next cut is windowed (`TestLegacyBundleVersion1StillRestores`, against a bundle written by the tree before this change, `internal/storage/testdata/legacy_bundle_v1.json.gz`). A version 1 bundle's evidence is still compared with the installed bytes (`TestLegacyBundleTamperedEvidenceIsRefused`). `InstallBackup` refuses a bundle of any other version and a bundle of another installation as `invalid`; `ReconcileQuota` refuses an unknown version, a version 1 bundle relabelled as 2 (or the reverse) and snapshots whose form disagrees with the bundle's version as `corrupt`. A **restore** still reads every installed command file once (O(history) time, one command of memory) to prove the evidence; that is the price of not trusting the bundle.

**Settled reservations (01.07-W1 residue, lane 1 wave 7; decision D46, accepted as proposed).** Control used to keep a row (the reservation, its `AdmissionKeys` entry and its series list) for every consumed reservation for as long as the installation lived, and those rows are part of the state every control command re-reads and re-proposes, of every control snapshot and of the control cut a backup seals, so the bundle's `cut` part and `Seal`'s memory grew with the batches ever admitted. `control.Store.SettleAdmissions` (internal/control/settle.go) bounds them. The retention worker asks (on every pass, one minute; it was the hourly control log expiry pass until L2w20Admission7, and at the single-host load an hour of rows was ~1 GB of control state that every control snapshot cut rewrote) the storage engine for its sealed windows (`Engine.SettleCandidates`: a full window with no redacted batch, its batch count and its charge digest); when the consumed reservations control holds for a window digest (`model.ChargeDigest`) to exactly the window's own digest, control drops those rows and their `AdmissionKeys` entries and keeps one `model.SettledWindow` (group, window number, span, count, digest) and, folded into `Settlement.Charges`, the charge they put on each quota key (bytes, and per series the number of settled reservations that reference it). `Quotas` is not touched, so no quota decision changes. Cancelled reservations, reservations of an open window and windows that carry a redacted batch keep their rows; an installation upgraded with existing rows settles them as their windows seal.

* **A retry of a settled batch.** No row answers it any more. `ReserveAdmission` asks the installed owner (`Engine.AdmittedBatch`: the receipt stored for the same batch key, read after the slot's read fence), checks the hash and answers the reservation consumed at the receipt's cursor with nothing stored and nothing charged; `ingest.Admit` finalizes nothing for a reservation that comes back consumed at the receipt's cursor, and the data's own duplicate check returns the stored receipt. `FinalizeAdmission` of a settled reservation and `ReconcileAdmissions` outcomes inside a settled window are accepted (`ReconcileAdmissions` now reads control once for all outcomes instead of one linearizable read per outcome). A store that has seen a settled state asks the owner before its first update; any other store learns it from the first update that finds no row (one aborted update, once). The cost on an installation that settles is one read-fenced receipt lookup per new admission.
* **Backups.** `ControlCut.Settlement` carries the settled windows and the folded charge; the manifest's `reservations_sha256` binds it (`canonicalCutBinding`, equal to the old binding when nothing is settled). For a settled window the bundle lists nothing: the window's own charge digest must equal control's settled digest (`QuotaEvidence.resolve`, `quotaEvidenceWindowed`), a settled window the data does not hold is `corrupt`, and `InstallBackup` (restore time, windows re-derived from the command files) requires the sidecars of all settled windows to add up to exactly `Settlement.Charges`, so a folded charge that the data does not carry is refused whatever the bundle's own digests say. `ReconcileQuota` starts the certificate's charges from `Settlement.Charges`, adds the unsettled rows and the evidence created after the cut, and derives the restored-index series cross-check from the settled series refcounts corrected by the reservations the evidence lists for a settled window that was redacted since (its erased records' series stay charged and are no longer indexed). A version 1 (whole-history) bundle verifies the settlement inside the bundle. The quota evidence of settled windows is therefore the window table only.
* **Upgrade.** `ControlState.Settlement` and `ControlCut.Settlement` are new fields (omitted while nothing is settled): upgrade every reader of a control state or a bundle before the first settlement (an older reader fails closed: strict control snapshot JSON, bundle digest).
* **What stays linear in history.** The settled window table (one record per 4096 commands) and `Settlement.Charges` (bounded by series cardinality, the same bound as `Quotas`), cancelled rows (bounded by the cancellations the data holds fences for), windows carrying a redacted batch (bounded by erasures), and restore (every settled window is re-derived).
* **Settled in parts while the window is open (D86 condition 4, L2w20Admission17).** A window used to settle only once sealed (4096 commands per group): at 2,000 records a second the consumed rows of the 64 groups piled up to 150,000 in 270 s and about 250,000 in steady state, and every control command paid for them. The engine now also offers the complete *parts* of each open window (`SettleCandidate.Open`, `Part`, `Parts`; `settlePartSpan`, 64 commands by default; the window size must be a multiple of it) and the retention worker settles every `WorkerConfig.SettleInterval` (5 s) between its passes, so the rows left are at most a part per group plus what one interval admits (a few thousand at the single-host load), whatever the load. A part is proven exactly as a window is: the data states the digest of the reservations the part consumed, control holds exactly those rows and drops them. A window settled in parts is an incomplete `SettledWindow` record (`Part`, `Parts`: number, count and digest of each settled part; no window digest): one record per open window of a group. When the data seals the window it offers it whole with the digest of every part; control checks the parts it settled against them, settles the parts it still holds rows of and replaces the record with the complete one (digest = the data window's). The persisted span of a group (`adm_spans`) is the span of its windows and is **not** changed: windows settled whole by an earlier release stay valid beside the parts of the windows after them, so there is nothing to migrate or clamp. Backups: `WindowEvidence.Part/Parts` state the data's parts of such a window; `QuotaEvidence.resolve` and `quotaEvidenceWindowed` require control's settled parts to be among them and the rows the cut holds to be exactly the others, per part (a window that does not match is a `Detail` window), and `InstallBackup` adds the settled parts' sidecar charges to the folded-charge check. Parts exist only in the runs layout (a contracted installation, so no member runs a release that would refuse the new records); window records written before keep working and are offered whole.
* **A settle command drops at most 64 rows and never reads the reservation table (L2w20Admission18/19).** The command is applied by the control group under the lock every control writer shares, and it rewrites the charge rows (one per quota key and series) of each reservation it drops, so what it costs grows with the rows it carries: a pass every 5 s carried about 3,000 rows in one command, held the control group for most of a second and put the p95 of the acknowledgements at 700 ms against a p50 of 35 ms at the single-host load. Bounding the command at 256 rows was not enough, because each command also read the whole reservation table again under that lock to find the rows of the offered windows (3,000 rows decoded when steady, 15,000 once the group is behind, so the stall fed itself): at that load every pass was a second of rounds of 80 ms among acknowledgement rounds of 8 ms. `SettleAdmissions` now reads the reservation table once per call, outside the lock, and settles what it found with commands of at most `settleRowsPerCommand` (64) reservations (a part is never split; a window settled whole, which only an installation that predates settling in parts holds, is taken alone when it exceeds the bound). Each command only looks up the rows it drops and drops them only while they are exactly the rows the pass read (otherwise the pass ends and the next one reads again), so what a command costs the writers that wait is a function of its rows, not of the rows control holds. The proofs and the records are unchanged: a sealed window whose parts were settled by several commands becomes the complete record by the command that settles its last part. The diagnostic build counts the rows read by settle planning (`settle_scan_rows`).

### When a snapshot is ready

A snapshot is selected only if all of these hold, checked when it is created, when it is installed, at startup repair and again before any truncation:

* the manifest checksum verifies and its file list is exactly the directory content (no missing, extra or resized file);
* every file hashes to its manifest value;
* the deletion ledger exists, parses, belongs to the group, has the manifest generation, strictly ascending indexes not beyond the cursor, and the manifest's count and digest. A ledger of `null` or a missing file is not an empty ledger; an empty ledger is `"entries": []`;
* the envelope's application cursor equals the manifest cursor;
* its ledger generation is not older than the store's generation fence (`RequireGeneration`, called by the restore authority before any data read) or than the snapshot already selected.

Violations return `ErrCorrupt`, `ErrNoLedger` or `ErrStale`/`ErrConflict`. A snapshot that fails any check never becomes `CURRENT`, so a node opened on it refuses to start rather than serving data it cannot prove.

## Creating and installing

`Group.CreateSnapshot(ctx, at)` waits for `at`, cuts under the group lock, pins the machine's files (`FileMachine.PinFiles`) for the duration of the copy and releases them exactly once, even on failure. A storage compaction that retires a pinned segment while it is being copied defers the removal until release. Snapshot directories are written to `tmp-*`, every file and directory is fsynced, the directory is renamed into place and only then is the `CURRENT` pointer replaced by temp-file + fsync + atomic rename + parent fsync. The previous valid directory is kept.

`SnapshotStore.InstallSnapshot(ctx, manifest, reader)` consumes exactly the stream `Snapshot.WriteTo` produces into a fresh `install-*` directory, verifying each file's hash as it is written, refuses a short or over-long stream, validates content and the generation fence, and switches `CURRENT` only after file and directory sync. Installing the snapshot that is already selected is a no-op; a different snapshot at the same index is a conflict. A group opened on an empty journal whose store has a selected snapshot starts from it (deep-verified first), so replay of the committed suffix begins at `index + 1`.

Replacing a node that lost its disk must use a new member identity through the existing learner/joint membership change; a node must not come back under the same Raft identity with less history than its peers recorded. The leader repairs a fresh learner from its snapshot when its journal no longer holds the history.

## Journal truncation

`Group.CompactJournal` is the only code that shortens `ready.wal`. It requires a deep-verified selected snapshot, the machine's durable applied index at or beyond the cut, and an in-memory Raft snapshot at exactly the cut. It then writes `ready.wal.compact` (snapshot record, the retained tail, current HardState), fsyncs it, renames it over `ready.wal`, fsyncs the directory, reopens the append handle and compacts the in-memory log. Startup removes a leftover temp file. Because the journal now begins at the snapshot, only the Raft journal **replay** after a restart is bounded by the retained suffix: entries before the cut are never re-proposed or re-applied. That is not the whole cost of starting the engine, which is still O(history) in several places; see "Engine startup cost" below. The completed-command table travels in the snapshot, so a retry after truncation still returns the original receipt and a changed payload under an old ID is still a conflict.

Storage exposes `Engine.CreateSnapshots` (all 64 groups) and `Engine.CompactJournals`. The storage manifest records the verified cuts in `SnapshotCoverage`.

## Engine startup cost

Truncation bounds Raft journal replay. It does not make engine startup independent of history. Read from `internal/replica/{node,ready,install,repair}.go` and `internal/storage/{replicated,manifest,index_integrity}.go`:

**O(retained suffix)**

* Re-applying journal entries. `Group.applyCommitted` skips every entry at or below the machine's durable applied index, so only entries after it run through `slotMachine.Apply`, and entries before a truncation cut are never re-proposed or re-applied.
* `Group.rebuildKnown` indexes the retained in-memory log entries.

**O(history), paid at every start whether or not the journals were truncated**

* Reading the journal. `openReadyWAL` reads and CRC-checks every record. After truncation the first record is the snapshot: since 01.07-W1 its envelope carries the window table and the completed-command (retry) table, not the slot's command history (a journal truncated by an older build still carries the whole history in that record until its next truncation). Truncation bounds the number of retained log entries; the record's size is the window table (one record per window of `snapshotWindow` = 4096 commands), the retry table (bounded, below) and the membership.
* Verifying that snapshot record. `Group.restoreSnapshot` calls `slotMachine.VerifySnapshot`. For a compact state (the form every cut now writes) it compares each window's identity with the sealed-window record held locally, deriving only a window that has no record, so it no longer decodes the history or byte-compares every command; for the whole-history form it still byte-compares every command of the slot with `replica_commands`. `slotMachine.Restore`, a full `applyTx` replay of every command above the local applied index, runs only if the local database is behind the snapshot (a node rebuilt from a snapshot); that node pays the whole replay once, reading a compact state's windows one command at a time from its snapshot directory.
* A start does not derive a window the verified record covers (D15; L2w20Admission32). The open window of each data group's snapshot (up to 4,096 commands) is the one window `VerifySnapshot` derives, one random read of the payload log per command: at the 900 s run of the single-host gate that was 842 MB and about 130,000 reads from a cold disk before the node could answer, a third of the bytes of a 7.4 s start whose harness measurement was 22.1 s. While the engine is starting (`ver.starting`: the end of `Open` to the return of `EnableReplication`) a window whose last command is at or below the verified point of its group (`Engine.verifiedThrough`) is skipped: a start verifies what lies above the verified point, and the background full pass and the advance re-check the rest, exactly as for every other command (the verified point of a node killed under load is at most `verifyAdvanceInterval`, a minute, behind its last command; a graceful close records it whole). A window with a command above the point, every window when there is no valid record, and every snapshot received while the node runs are derived whole, as before. Reading the journals ahead of the groups (a background prefetch while `control.db` and `apply.db` open) was measured and dropped (L2w20Admission33): on the 900 s data it left the cold start at 5.3-6.3 s as without, and read 560 MB more before the node answered.
* Structural checks over the apply database were O(history) until the verified record below; they are now bounded by what was written since the last verified point, except when the record forces a full verification (see "Bounded startup verification"). What stays O(history) is listed there.
* The completed-command (retry) table is serialized into every snapshot envelope and loaded whole into memory. A data slot's table keeps for each command only the receipt and the SHA-256 of the payload it was proposed with (`slotMachine.RetryByDigest`: no payload, so a batch or an artifact fragment is never copied into it) and only the newest `slotRetryMax` (1024) commands inside the 24 h window (`replica.DefaultRetryWindow`; Decision R1 below). The envelope, the journal head record and the table in memory are therefore bounded by that number, not by the history. A snapshot written by an earlier build, which carries payload-bearing entries without a bound, is converted when it is loaded (`Group.restoreSnapshot` keeps every entry by digest and `rebuildRetryOrder` applies the bound).
* Snapshot cuts and the C12 backup evidence no longer re-walk the full history (01.07-W1, see "Windowed slot snapshots"): a cut reads the windows written since the previous cut, `Seal` reads only the windows past each group's processed highwater and the window table, and neither holds the history in memory. The first cut after an upgrade derives every window once, under the engine mutex (O(history) once). `CommitQuotaReconciliation` still walks the restored `batches` bucket once (restore time). A node whose database is gone while its journal head names a compact state older than its selected snapshot fails to open (`corrupt`) and is replaced like a node that lost its disk. Measured (`TestMeasureCutAndBackup`, window 64, retry bound 64, history 500 -> 2000 commands, a lab VM): the envelope 1,938,784 -> 6,582,146 bytes before the retry table was bounded and 35,624 -> 49,757 after; `ready.wal` after compaction 2,585,522 -> 8,776,674 before and 47,978 -> 66,822 after (the remainder is the window table, 24 more windows); commands a warm cut reads 284 -> 176 (the open window and the new ones, not the history); the evidence in the bundle 81,948 -> 72,954 bytes. What still grows with history, stated rather than hidden: (1) the window table, one record per window (history / 4096 records); (2) `CompactJournal` re-hashes every byte of the selected snapshot (`SnapshotStore.Verify`, 17 -> 27 ms at these sizes, O(snapshot bytes) per hourly compaction); (3) `Seal` work and the bundle's `cut` part (343,844 -> 1,261,346 bytes; `Seal` peak heap 6 -> 37 MB, allocation 30 -> 74 MB) grow with the number of reservations the control cut holds, because the control state keeps every consumed reservation and the bundle carries them; that is a property of the control state, not of the data slots' snapshots, and is not bounded by this work.
* The read that finds what an expiry or an erasure may touch (`Engine.eraseCandidates`: the journal-expiry plan every 15 minutes, the retention pass) walks every stored command, and it used to do so in one bbolt read transaction. A read transaction blocks the remap of `apply.db`: the first write that has to grow the mapping waited for it and every new transaction waited behind that write, so every acknowledgement stopped for as long as the walk lasted (single-host gate, L2w20Admission22: 45 s at minute 15, more than 400 s at minute 30). The walk now takes read transactions of at most `eraseScanChunk` (512) commands, each resuming after the last key it saw, so no transaction outlives a chunk. The view is no longer one snapshot: a command appended meanwhile is seen or not and one a redaction rewrites is seen before or after it, which both callers accept (an erasure re-verifies each command by digest before it writes; a plan only lists). The plan skips the decode of every stored batch that does not contain the JSON string `"error"`. The walk still reads the whole history once per plan; it no longer stops the engine.

**Not part of a plain restart.** The SHA-256 of every byte of the snapshot directory (`SnapshotStore.Verify`) runs when a journal is created from an installed snapshot (no `ready.wal`, `loadInstalledSeed`), when the `CURRENT` pointer is unusable (`repair`), and on every `CompactJournal`. A plain restart that finds `ready.wal` validates the selected snapshot only structurally (manifest, file presence and sizes, ledger parse).

### Bounded startup verification (decision D15)

This is a **weaker guarantee than the earlier start**, chosen deliberately so that startup does not re-prove the whole history. State it as such to operators:

> Everything written or changed since the last fully verified point (new segments, index entries, the command tail above each group's verified index) is still verified before readiness, so "never ready on corruption" holds for it. Bit rot in an older, already verified segment, command or index entry is no longer caught before readiness. It is caught by a background full re-verification, which fails the node closed.

Mechanism (`internal/storage/verified.go`):

* Each node keeps `verified-record.bin` in its data directory: magic, a SHA-256 over the body, and a body that names, per group (64), the last fully verified applied index and, for the node, the verified segment set (id, file, SHA-256, size) and the digests of `scan_time` and `scan_postings`. It is bound to the node's identity, to its group ids and to the digest of the node's own manifest (the digest the apply database points at, which `Open` proves against the manifest file on every start).
* **Condition 1.** A missing, unreadable, corrupt (bad magic, checksum or JSON), foreign (another identity, other group ids, another format version) or wrongly bound record (manifest digest differs; a group behind the record; a database exactly at the verified point whose index digests differ) is never trusted: the start verifies in full, exactly as before, before readiness. `Engine.StartupVerification()` reports `Full` and the reason.
* With a valid record the start verifies: every command above each group's verified index (presence, plus that nothing sits above the applied index); for every such command's commit entry its pages (parse, hash of a hot page) and, per page, that exactly `Count` `scan_time` entries carry the page id and a valid CRC; any manifest segment the record does not list (hashed and header-checked); the manifest file and the index digests' own CRCs. A snapshot verified at startup (`VerifySnapshot`) is byte-compared with the local commands only above the verified index.
* The start then records the new point. A manifest publication (`Flush`, `Compact`, `Publish`) rebinds the record to the new manifest: its new segments were hashed by the publication. A start with no new writes verifies no command and hashes no segment.
* **The point follows the running node.** The record used to be written only by a start and by the full pass at that start, so a node that ran for an hour under load still held the point of its first second and its first restart verified that whole hour before readiness (L2w20Admission22: the first restart after the single-host hour; a restart on a copy of the same data, whose record a previous start had refreshed, took a fraction of it). A running engine now advances the point itself: every `verifyAdvanceInterval` (one minute, in the same background loop as `VerifyFull`) `Engine.advanceVerified` verifies what was applied above the record exactly as a start does (the command tail, the index entries and pages of those commands, any segment the record does not list) inside one read transaction, builds the new record from that same transaction and writes it. A pass with nothing new writes nothing; damage found fails the engine closed like `VerifyFull`, removes the record and leaves nothing recorded as verified; a manifest publication or identity install during the pass drops it (the publication already rebound the record). The tail a start verifies is therefore at most about one interval of writes, whatever the uptime. Its counters are not part of `StartupVerification`.
* **Writing the record does not stop the node.** The pass holds no engine lock while it reads (a bolt read transaction, which does not delay the writer while `apply.db` is mapped ahead of its growth, `durablefs.BoltInitialMmapSize`) and none while it writes the record: `Engine.recordVerified` writes under the record's own file lock and keeps the result only if no manifest publication, identity install, start or failure moved what the record is bound to meanwhile (`ver.gen`; the next pass records the point then). The write is a file fsync, a rename and the directory's fsync (two commits of the file system's journal, not five: the temporary name needs no directory fsync of its own, and a leftover temporary file is removed by the next write). Each commit waits for everything the engine has dirtied meanwhile; held under `e.mu`, which the 64 slot groups take for every apply, the write froze every acknowledgement of the node for seconds once a minute at the single-host gate's write rate (L2w20Admission29). Tests: `TestVerifiedRecordWriteDoesNotHoldTheEngine`, `TestVerifyAdvanceReadTransactionDoesNotHoldTheEngine`.
* **Condition 2.** `VerifyFull` (every cold segment hash and header, every command, every index entry, the global counts) runs in the background from every engine start and then every 24 h (`verifyInterval`). A mismatch is a typed `corrupt` fault (`Engine.VerifyFailure()`): the engine is failed closed like a startup failure (`replica.FailEngine`, so the node's groups stop and no read is served), and the record is removed so the next start verifies everything before readiness.
* **A pass is stopped within a bounded stretch of work (L2w20Admission31).** `Engine.Close` cancels the background verification and waits for it, and at the size the single-host gate leaves that wait was 67 s and more than 3 minutes right after a start (`VerifyFull`'s read transaction walks every command, every index entry and page and every window of the node). Every loop of a pass and of an advance (`validateReplicaNamespacesTx`, `validateIndexIntegrityPolled`, `validateWindowRecordsTx`, `validateIndexTail`) counts its units of work through a `cancelPoll` and looks at the pass's context every `cancelPollEvery` (256) of them; the hash of a segment looks between 1 MiB blocks (`hashFileCtx`). A stopped pass returns `cancelled`, which is not damage: it does not fail the engine and records nothing. The start's own validation is not polled (it is before readiness and has nothing to cancel it).
* **Identity install.** A node that joins an installation re-binds its (empty) engine to the installation's identity after `Open` (`InstallReplicationIdentity`), while the background pass may already be running. The pass copies the identity under `e.mu`, builds the record from that one value and keeps it only if the identity is still the same when it commits; the install drops the record of the old identity (memory and file) and wakes the background loop, which records the new point at once instead of after `verifyInterval`. A record is therefore never bound to two identities, and the old identity's record never outlives the install.

Conditions of the guarantee. The tail check can only tell that an erased batch's pages are gone from `scan_pages` because it also finds no entries; a page that was deleted from `scan_pages` without its entries is therefore invisible to it and is found by the background pass. The `scan_time` range walk for a page examines every entry in the page's time range of its namespace, so the tail check is bounded by the tail and by how many other entries share those timestamps, not by history. The record advances at start, at every completed background pass and (for the segment set) at every publication; writes since the last of those are the tail a crash restart verifies.

Opening an existing journal no longer builds a snapshot of the slot's whole history: `replica.Config.SeedFunc` builds the seed only when a fresh journal is created. After a restart `EnableReplication` seeds the snapshot coverage the next publication records from each group's selected snapshot (structural read), so a flush before the next cut no longer reports "nothing snapshotted". `Engine.Close` waits at most `closeDeadline` (30 s) for a running publication, which stops at its next check once Close has begun, and reports a timeout otherwise.

Still O(history / window) at every start, and not changed by the record: reading and CRC-checking `ready.wal` and decoding its snapshot record (the window table, one record per 4096 commands; the bounded retry table; the membership), the journal-open `VerifySnapshot` comparison of each window with its local record, and `rebuildKnown` over the bounded retry table and the retained log. The record removes the per-command lookups, the per-entry index walk and the per-segment hashing from `Open` and `EnableReplication`.

## Local maintenance on every voter

A voter's physical layout (storage manifest, segment files, page locations) is node-local: every voter rebuilds it independently from the replicated command history, and clients and peers see only logical contents, through that node's own fenced reads. Publishing a manifest (`Engine.Flush`, `Engine.Compact`, `Engine.Publish`) therefore needs **no Raft leadership, no quorum round trip and no group lock**. A leader, a follower, a node that leads only some groups and a node that has just lost leadership all flush hot pages, rewrite segments, record snapshot coverage and truncate their own journals. An earlier version took a quorum fence and then the lock of every one of the 65 groups, and required the caller to be leader of all of them at once; a follower could never publish and, once leadership was spread across nodes, nobody could.

Which interleavings still need serialization, and what serializes them:

| Interleaving | Serialized by |
| --- | --- |
| publication vs apply of any slot | the engine mutex `e.mu`. `Apply` (called with its group lock held) takes it for the whole bolt transaction; a publication holds it from choosing the pages to relocate until the durable compare-and-swap, so a hot page cannot grow or move while it is flushed and the recorded `Applied` watermarks and `SnapshotCoverage` come from the state that was verified. Lock order is group lock, then `e.mu`; a publication never takes a group lock |
| publication vs snapshot installation (`Restore`) | `e.mu` |
| publication vs snapshot cut (`Snapshot`, `DeletionLedger`, `PinFiles`) | `e.mu` per call. A cut needs its own slot's history, ledger and cursor to agree (the slot's group lock) and one consistent pinned file set (`PinFiles` under `e.mu`); the layout is not part of a slot's state, and a segment retired by a publication is removed only after the last pin is released |
| publication vs journal truncation (`CompactJournal`) | independent: truncation touches only the group's journal and in-memory log under the group lock and requires a verified snapshot, not a manifest revision |
| two publications | `e.mu` plus the compare-and-swap on the manifest revision |

The only fences that remain are those protecting an externally visible effect: `Group.Fence`/`ValidateFence` for workers and external destinations, and the quorum read fence of reads and appends. A publication cannot change `TombstoneGeneration` and cannot drop a retained page, so it can neither delete nor hide data; deletion, retention decisions and anything sent outside the node must be replicated commands, never this local path. The manifest `Term` is an on-disk format constant (always 1), not a Raft term, and has no leader meaning.

Publication cost follows the data published, not the whole store: segments that the previous publication (or the engine's open) already verified are immutable and are carried forward after an existence, size and header check; a new or altered segment is hashed and every page is read back before the manifest can point at it, and only then are retired files removed.

## Repairing a learner added after a truncation

etcd raft refuses to restore a snapshot whose configuration does not contain the recipient. The stored snapshot anchors the truncated journal and predates any member added later, so a fresh learner (a replacement voter under a new id) added after a truncation would ignore every snapshot forever. The leader therefore offers such a recipient a snapshot cut at its applied index with the current configuration (`internal/replica/joinsnapshot.go`). That snapshot is sent only: it is never stored in the in-memory log or the journal, so truncation keeps anchoring on the verified snapshot directory, and it is released once delivered. Startup (`appcore.OpenDistributed`) waits for each group's readiness round until its 60-second startup budget is spent (each round has its own 5-second freshness window, which previously ended startup at the first slow group); intake still opens only after every group answered.

## Crash hooks

`Config.Fault` (the engine's fault function) is called immediately before each step below; an error simulates process death at that step, and nothing is cleaned up in process. `OpenSnapshotStore` removes `tmp-*`, `install-*` and `*.tmp` leftovers and prunes unselected orphans on the next open, and re-selects the newest fully verified directory only when `CURRENT` itself is unusable.

| Phase | Hooks |
| --- | --- |
| Create | `snapshot_cut`, `snapshot_pin`, `snapshot_file_write`, `snapshot_file_sync`, `snapshot_manifest_write`, `snapshot_dir_sync`, `snapshot_switch`, `snapshot_renamed`, `snapshot_current_write`, `snapshot_current_switch`, `snapshot_published` |
| Install | `install_begin`, `install_file_write`, `install_file_sync`, `install_manifest_write`, `install_dir_sync`, `install_switch`, `install_renamed`, `install_current_write`, `install_current_switch`, `install_published` |
| Truncate | `compact_begin`, `compact_archive`, `compact_write`, `compact_sync`, `compact_switch`, `compact_renamed`, `compact_memory` |
| Redact (`Group.RedactCompleted`) | `redact_begin`, `redact_pins`, `redact_write`, `redact_sync`, `redact_switch`, `redact_renamed`, `redact_memory`; the engine adds `redact_replica` before it calls the group |
| Redact the pre-replication WAL (engine, `data/slot-NN.wal` of a node upgraded from the 01.03 layout) | `legacy_wal_begin`, `legacy_wal_write`, `legacy_wal_sync`, `legacy_wal_switch`, `legacy_wal_renamed` |
| Restore | `quota_certificate_persisted` |

An error from a redact hook up to and including `redact_switch` (or a read, temp-file or pin-archive error before the journal rename) is returned without failing the group and the next pass retries it; `redact_renamed`, `redact_memory` and any failure after the journal rename fail the group until restart. The legacy WAL rewrite is streamed into `slot-NN.wal.redact`, fsynced and renamed, so a crash leaves the complete old or the complete new file; a leftover `*.wal.redact` holds no erased byte and is removed by the next pass.

At every hook the tests prove: an ACKed entry is never lost, a retry returns the original receipt, an unacknowledged write is retried rather than duplicated, the selected snapshot (if any) verifies, and a snapshot without a deletion ledger is never selected. Only `*_published` hooks leave the new snapshot selected; all earlier ones keep the old valid directory.

## C12 installation backup and restore

The typed C12 certificate interface lives in `internal/storage/snapshot.go` because no other module defines it yet: `ControlCut` (control checkpoint C: processed highwater H per data group and the reservations control held), `DeclaredGap` (a committed `RecordEvidenceGap`), `ReplayInterval`/`ReplayCertificate`, `QuotaEvidence`, `BackupBundle` and `QuotaReconciliation`.

1. `Engine.BeginBackup(ctx, cut)` requires exactly the 64 owned groups with H not beyond the applied data, and pins every group's committed journal beyond H (`Group.PinJournal`). Truncation archives pinned entries durably before discarding them. A pin carries an owner (the group instance, i.e. the process lifetime that created it) and a lease (`Config.PinTTL`, default 24 h, judged by `Config.Now`) in its durable header, and `Open` re-validates every pin file: a header that never became durable was never a pin and is removed, a pin without a lease or whose lease lapsed is removed, a header that names another pin is refused (`ErrCorrupt`). A pin of a dead process whose lease has not lapsed survives the restart and keeps archiving until the lease lapses (truncation drops an expired pin instead of archiving into it and a backup that still holds it fails closed: `Entries` returns `ErrStale`) or until it is dropped. `Group.Pins()` lists them (`Orphaned` marks those no live backup in this process can hold) and `Group.DropPin(id)` drops one, idempotently; `Engine.JournalPins()` and `Engine.DropJournalPin(id)` are the engine-level adapter over the 64 groups for `internal/backup`'s `PinReaper` (the wiring is described on `JournalPins`). A privacy deletion touching pinned evidence calls `Backup.NoteDeletion`, which aborts the backup so it restarts after the deletion fence; `Group.RedactCompleted` also rewrites the pin archives, so a pin never keeps a redacted payload.
2. `Backup.Seal(ctx, gaps)` cuts D>=H and proves, for every group, that every command in `(H, D]` is either replayable from the pinned journal or inside an exactly matching declared gap. The certificate is re-derived from the command history inside the sealed snapshots. Missing groups, undeclared holes, inexact gaps and altered digests fail the backup; there is no partial success. Consumption and cancellation evidence is derived from the same sealed bytes.
3. `Engine.InstallBackup` installs all 64 snapshots and keeps intake closed (a durable `restore-quota.pending` marker, reloaded by `EnableReplication`) until reconciliation. It re-derives the quota evidence from the installed bytes and refuses a bundle whose evidence differs.
4. `ReconcileQuota` reconstructs exactly one charge per consumed reservation including reservations created after C, releases reservations that D proves cancelled by a committed fence, retains charged reservations that are neither consumed nor fenced (pending intents), and fails on consumed-in-C-without-proof, fenced-and-consumed and cancelled-without-fence. `Engine.CommitQuotaReconciliation` checks the certificate against the bundle and against the series recomputed from the restored project index, persists it, and only then removes the marker. Until then `Append`, receipt lookup and cancellation return unavailable. `QuotaReconciliation.Apply` yields the exact per-key charge for the control quota objects.

## Known limits and open items

* The control snapshot has no deletion ledger of its own beyond the machine hooks of the control group; the data-slot ledger is implemented. The deletion ledger and the restore-authority journal (`retention.BuildLedger`, `Service.Restore`, `CheckpointDeletion`) are implemented by 01.08/01.09: a restore re-imports the authority's tombstones into the restored control state and re-applies their control-state erasure (`control.Store.ImportDeletions`), so a restored backup does not bring back control payloads a completed deletion erased. A backup cut between a deletion's begin and its completion restores the operation as fencing: the import finds it and applies nothing, and the resumed operation erases the restored payloads when it completes. The control Raft journal and its snapshots of the restored installation (the retry table inside a snapshot cut by an earlier build included; the group drops its payloads when it loads it, the snapshot file keeps them) hold earlier copies of the control state until the retention worker's pass has run on that node (`Store.RedactRetainedControlCommands`, see docs/privacy/retention.md, "The control Raft journal"): `control_raft_journal` is reported until then. That pass is per voter (each voter redacts its own copy; nothing observes the others) and does not reach a backup cut before it, a pin archive a live backup holds, or a snapshot already shipped off the node; the control group is also compacted by that pass, which keeps no previous snapshot to fall back on until the next cut.
* Artifact quota reservations are not part of the admission-reservation reconciliation. Per-retention live-byte classes do not exist yet, so charges are per quota key only.
* A backup pin archives evidence on the node that took it; a snapshot of another voter is not a substitute.
* The completed-command table of a data group is bounded (Decision R1: digest records, newest 1024 commands, 24 h; see "Engine startup cost"). For the control group (`replica.DigestRetryMachine`) each record is the receipt plus the digest of the proposed payload, a fixed-size record per command, and no longer the bytes of each command's whole-state payload (measured 10.13: retry table, log index and in-memory snapshot together were 3.3x the sum of all payloads before).
* Decision R1 (data-slot retry table, 01.07-W1, lane 1 wave 6; recommendation: accept). The slot machine is a `replica.DigestRetryMachine` for every kind, with `replica.Config.RetryMax` = `slotRetryMax` = 1024 (the 24 h window also applies). The table answers a command that is retried under the ID it was proposed with, which only the proposer's own call (10 s long, including a forwarded proposal) does; every slot command also carries the application index it expects, so a retry the table no longer recognizes is refused as stale and never applied twice, and an acknowledged batch that a client sends again is answered from the engine's own receipt records in the apply database (`TestEraseRemovesTheDeletedBytesFromTheReplicationLayerAndKeepsTheReceipt` retries an acknowledged batch and gets its original receipt). A cancellation of a reservation whose batch left the table is still refused by `Engine.Cancel`, which reads the receipt there. Redaction does not depend on the table: `RedactCompleted` finds the copies of a command it forgot by application index in the retained log (the journal file mirrors it) and in every pin archive (`Group.locateRetainedLocked`), and the table holds no payload to redact (`TestRedactionReachesACommandTheRetryTableForgot`, `TestRedactionReachesAPinArchivedCommandTheRetryTableForgot`).
* Decision D4 (control retry table and journal cadence). The control group's retry table keeps an applied command for 24 h or 100 000 commands, whichever bounds first (`replica.DefaultRetryWindow`, `replica.DefaultRetryMax`); the clock is the time the leader stamped into the command (`Entry.At`), so every voter and every snapshot restore evicts the same entries at the same applied index. A retry inside the window is answered with its original receipt (`TestRetryTableForgetsACommandAfterTheWindowAndKeepsItInside`). A retry outside it is not recognized and is proposed as a fresh command; that is safe for the control machine only because every control command carries the revision it expects and its application index, so a replayed command is refused (`ErrStale`/`ErrConflict`) and never applies twice. A machine whose commands have no such precondition must not opt into `DigestRetryMachine`. Independently of any deletion, the control group cuts a snapshot and compacts its journal every 4096 applied commands or 8 MiB of applied entry bytes (`control.DefaultJournalCadence`, `replica.Cadence`; decision D4 said 64 MiB and the byte bound was lowered after the replay measurement below), dropping the superseded snapshot directories; the cut runs in the background and is retried on the next command when the machine is momentarily behind. The measured effect is in `TestControlCommitStormJournalIsBoundedWithoutAnyDeletion` (its log lines carry the journal bytes with and without the cadence). **Why 8 MiB.** Opening the control store replays its journal (WAL parse, `rebuildKnown`, the committed tail through the machine), so Open-to-ready grows linearly with the journal: measured on a Debian 13 VM with `TestControlStartupMeasure` (median of three reopens, journals of real control commands through the replicated store, each carrying the whole state), about 28 to 35 ms per MB of `ready.wal` without the race detector and 0.55 to 0.75 s per MB with it. A never-cut journal of 31.5 MB reopened in 0.9 to 1.0 s (17.4 to 22.6 s under `-race`, which is what overran the 20 s startup budget in the issues restart test); a journal at the old 64 MiB bound (about 90 MB on disk after the encoding below) would take about 2.6 to 3 s and, extrapolated linearly, 50 to 65 s under `-race`. The journal file holds entry data base64-encoded inside JSON records, so a store that sat at the 8 MiB bound has a `ready.wal` of about 11.5 MB (peak 11.8 MB in `TestControlJournalIsBoundedByBytes`) and reopens in 0.35 to 0.41 s (6.3 to 8.2 s under `-race`, flat and nested state shapes); the same 2081-command history that left a 31.5 MB journal under the old cadence leaves 7.2 to 7.9 MB at the new one and reopens in 0.38 s (4.3 s under `-race`) instead of 0.91 s (17.4 s). `TestControlStartupDoesNotScaleWithCommands` holds Open-to-ready flat across a history of 2.3 times the commands. A state larger than the byte bound cuts on every command: that is the cost of a snapshot per commit, not of a journal.
* The retry table is rebuilt from the selected snapshot on open, so a redaction that reached only the table is repeated after a restart; the engine does so from the stored redacted commands (see docs/privacy/retention.md, "Replication-layer redaction"). A snapshot directory and the snapshot record a compacted journal begins with are sealed and cannot be redacted in place: they are replaced by a later cut (`CreateSnapshot` at an advanced index, `SnapshotStore.DropSuperseded`, `CompactJournal`), and `Group.Residue(floor)` / `Engine.ResidualStores` report them until then.
* A snapshot whose generation is lower than the store's is refused even when its index is higher, with or without a `FENCE` file (`TestSnapshotHigherIndexLowerGenerationIsStaleWithoutAFenceFile`, and at every install crash point). `CompactJournal` refuses a cut the machine has not durably applied (`TestCompactJournalRefusesACutTheMachineHasNotDurablyApplied`).
* Manifest publication (flush, compaction, snapshot coverage) takes no Raft leadership, quorum round trip or group lock (see "Local maintenance on every voter" above). Its remaining limits: the manifest `Term` stays pinned to 1; a publication holds the engine mutex for the whole flush or compaction, so a long segment write delays apply (and therefore heartbeats) of groups with committed entries on that node and maintenance rounds should stay short; it still walks the whole page index (metadata only) under that mutex; and bit rot inside an already published, unchanged segment is detected when the page is read or the node next opens, not at every publication. A failed publication leaves an orphaned new segment file behind (it is never referenced); reclaiming such files belongs to retention.
* Local process kills and loopback tests do not establish durability under power loss, lying fsync hardware or distinct failure domains.

## Control group snapshots on a contracted installation (D86, L2w20Admission15)

The journal record that follows a compaction of the control group used to hold the whole control state. That state grows with the admission rows that are not settled yet (about 1.2 KiB per acknowledged request until the request's data window settles, 141 MB at 115,000 requests at the single-host load), and a journal record is bounded (256 MiB): the first compaction past that size failed the bound and stopped the node (`maintenance_failed`).

Once the installation is contracted (no previous release is a member or can become one; the same condition as the query-index runs layout) the control group cuts **compact snapshots** for itself: the snapshot names the control state by its revision and a seal of the stored state (`{"compact":1,"revision":N,"seal":...}`) and carries none of it. The state is `control.db`. A snapshot sent to a peer, the seed of a new member and a backup are still cut whole (`Store.Snapshot`). An installation that is not contracted keeps whole snapshots, which the previous release can read.

**What changed in the loss model.** With a whole snapshot, a `control.db` that was lost or damaged while `raft/control` was intact was rebuilt from the journal head at the next start. With a compact snapshot it cannot be: the journal alone no longer holds the state. This is the model of the data groups, whose `apply.db` is not rebuilt from the journal either. At every start the control journal's compact snapshot is verified against `control.db`: the file must be at or past the snapshot's revision and, at that revision, carry the seal the snapshot names. A `control.db` that is missing, older than the snapshot or sealed differently is refused with a typed fault (a missing or re-sealed file by the consistency checks of `Open`, an older one by the snapshot check with `control_state_not_backed: ... replace this node (membership replace) or restore a backup`). The node serves nothing and never serves an empty or an older state. Recover by replacing the node from the other voters (`membership replace`) or by restoring a backup.

**The whole snapshot is cut in parts when it exceeds a record (D86, condition 3).** A snapshot sent to a peer, the seed of a new member or of a first journal, the snapshot a restored backup starts a journal from and the whole snapshot an installation that is not contracted anchors its journal on used to travel in one journal record (and, to a peer, in one request), and a record is bounded (256 MiB; the control state is encoded twice as text inside it, so a state of about 140 MB reaches the bound). A snapshot that does not fit one record is now written to the journal as a chain of part records (each carrying one slice of the snapshot) followed by the record that completes it, and sent to a peer as a run of part requests that the receiving member joins before it steps the message. Nothing else changes: a snapshot that fits one record is written and sent exactly as before, so a journal or a peer of the previous release is unaffected until a state exceeds the bound, which the previous release could not carry at all. A chain whose last record never reached the disk (a crash while it was written) is a write nothing acknowledged: the next start cuts the journal back to where the chain began, as for a torn record. A chain with a part missing or damaged is corruption and the journal is refused. The compaction of the journal no longer stops the node when the snapshot it anchors on is larger than a record; a request a member of the previous release receives for a part is refused (it is not a route of that release), so such a snapshot reaches members of this release only.

**The retry table is kept in parts of the snapshot, and a cut writes only what is new (D87, L2w20Admission17).** The control group's retry table (up to `replica.DefaultRetryMax` = 100,000 entries of about 425 bytes: 42 MB) used to be serialized into the envelope of every snapshot, and the journal record that follows a compaction carried the same envelope. Under the single-host load the group cut every few seconds, so every cut wrote, read back, hashed and later removed a 20 to 40 MB file again, and the cut grew from 0.1 s to 3.3 s as the table filled (L2w20Admission16). A group whose machine cuts compact snapshots and whose cut state is the compact form (`replica.CompactStateMachine`; the control machine once the installation is contracted) now keeps the table in immutable files of the snapshot directory: runs of `retryPartEntries` (2048) entries in apply order, named by the first and last log index they hold (`files/retry-<first>-<last>.json`). The envelope names them (`retry_parts`) and the log index of the oldest entry the table still holds (`retry_from`) and is a few kilobytes. A cut takes the sealed parts of the previous cut that still hold retained entries from the selected snapshot by hard link (the way a `FileMachine`'s files are reused), writes the entries applied since (and rewrites the one partial last part), and drops a part when everything in it is older than `retry_from`; what a cut serializes is the entries since the previous cut plus fewer than 2048, never the table (`TestACutOfACompactRetryTableWritesOnlyWhatIsNew`, `TestCadenceCutsOfAGrowingRetryTableCreateNoLargeFiles`). The cadence cut hashes only the files it wrote itself before it compacts the journal (`SnapshotStore.VerifyCut`) and compacts the journal **before** it drops the superseded snapshot: until the compaction the journal head is anchored on the superseded snapshot, and a group that is opened resolves the parts the head names in the snapshot directory cut at the head's index (`TestAJournalAnchoredOnTheSupersededSnapshotStillFindsItsRetryParts`). A snapshot sent to a peer, the journal head `Group.Snapshot` writes and every snapshot of a group whose state is not compact carry the whole table inline as before, so nothing a previous release can read changes; an envelope with `retry_parts` is refused by a build that does not know the field (`snapshotEnvelope` is strict), which is why only a contracted installation cuts it. A cut whose selected snapshot lost a part it meant to link writes the table whole once (`TestACutWhoseRetryPartsAreGoneWritesTheTableWhole`).

## The restart does not read the admission ledger (D89, L2w20Admission18)

A restart of a node whose control file holds a large admission ledger (single-host gate: 98,000 acknowledged requests, 67,000 unsettled rows, a 368 MB `control.db`, a 167 MB seed) used to assemble the whole ledger several times before it served: the open of the application read `DataInitialized` through a `View` that carries the admission books, `EnableReplication` built the whole control snapshot as a seed and decoded it again to read its revision (every start, though a journal that exists ignores the seed), and the artifact-reference check, the attestation precheck and the installation lookup each read the state with the ledger. Measured on the gate VM with a copy of the e1 data (graceful stop, cold page cache): 45 s to `/readyz`, of which about 14 s were these reads.

Now: `Store.DataInitialized` and `Store.Installation` read the state blob and the keys that hold the installation and the revision; `EnableReplication` passes `replica.Config.SeedFunc` (the snapshot is built only when a fresh journal is created) and the revision read from the file; `ValidateArtifactReferences`, its heal step and the attestation reads use `viewCore` / `localCore`, the committed state without any member of the ledger. No format, journal or snapshot byte changes: a node of the previous release reads everything this build writes, and the reverse, so there is no rollback boundary (`upgrade.md` needs no change). `replica.Open` also validates and decodes each journal entry it replays once, not twice (rebuildKnown hands its decode to the first apply). Tests: `TestStartOfAnExistingJournalDoesNotReadTheLedger`, `TestStartupChecksDoNotReadTheLedger` (allocation bounds with a 14 MB ledger: 142 MB, 55 MB and 19 MB before, under 0.5 MB after) and `TestDataInitializedIsTheAnswerOfView`.

Measured on the gate VM, same copy of e1, restart after a graceful stop / after `kill -9`: cold cache 45.2 s to 28.6 s, warm 14.7 s to 8.8 s (both stops alike). What remains is the replay of the 64 data journals (`storage.Engine.EnableReplication`, about 1.3 GB just under the cadence bound): CPU when warm, and when cold the apply of each replayed entry reads `apply.db` page by page under the engine lock (about 90 MB/s of a disk that reads 1 GB/s sequentially). That part is in `internal/storage` and is not changed here.

## The windows of a slot are derived off the engine lock; the restart compares identities (L2w20Admission21)

The 64 data groups of a node are loaded alike, so they seal their first window of 4,096 commands together: at the single-host load (4.8 commands a second a slot) at about 800 s. The settlement pass (`SettleCandidatesFor`, every 5 s) derived the sealed windows the engine had not derived yet while it held `Engine.mu`, the lock every append and every `AdmittedBatch` (every admission) takes: 64 derivations of 4,096 commands of 10 KB, a second of CPU each, one after the other. The live run collapsed at 820 s every time (p95 114 ms to 290 ms, then 24 s; goroutine dump of the collapse: 1,444 waiting in `AdmittedBatch`, 149 in `Append`, the holder in `SettleCandidatesFor` -> `windowTableOf` -> `computeWindow`; goroutines 320 -> 4,128; 5,500 requests shed). Now the pass reads the slots' indexes under `Engine.mu` and derives each slot holding `Engine.cutMu` shared, as a snapshot cut does (`windowTableForCut`); erasure, the one writer that rewrites stored commands, takes `cutMu` exclusively. The same live run on the new tree has no collapse at 820 s (p95 180-220 ms in 800-840 s; one 840-860 s window at 394 ms).

The restart verified the compact state of each group (`verifyCompact`) by deriving the open window of its slot under `Engine.mu`, so the 64 groups, opened 8 at a time, verified one after the other: 27 s of the 34 s restart on the copy of the 900 s run, 58.9 s and 67.1 s after the load itself (31-32 s after `kill -9`; `ready_ms` of the live runs). The check now holds `cutMu` shared and no engine lock, and compares what it compares, the identity of the window: `windowIdentity` hashes the stored bytes of the commands (`commandIdentity`, the redaction-invariant digest) and decodes none, where it derived the whole record (decoding every command, 0.25 ms each). The persisted records themselves are still re-derived in full by the background pass (`VerifyFull`, D15). Measured on the gate VM (copy of the data of a 900 s run, graceful stop, warm cache, CPUs 0-7): 34.4 s to `/readyz` before; 12.8 s with the derivation off the lock (parallel); 6.3 s with the identity check as well. Tests: `TestSettlePassDoesNotHoldTheEngineLockWhileItDerivesTheWindows`, `TestSnapshotVerificationDerivesTheWindowsOffTheEngineLock`, `TestWindowIdentityEqualsTheDerivedWindowsIdentity`. A bbolt freelist that is not synced (`NoFreelistSync`) was measured and rejected: the open of a 7.5 GB `apply.db` then scans the tree, 68.6 s cold and 2.0 s warm.

## Rows of the data engine in block runs (D88, L2w20Admission18)

An acknowledged request writes one row into each of five tables of `data/apply.db`: the stored records (`batches`), the receipt (`receipts`), the metric sample dedupe rows (`metrics`), the page of its rows (`scan_pages`) and the commit record (`scan_commits`). Their keys are random (organisation, project, source, producer and batch id; a hash of the series; a page id), so in a B-tree every row dirties its own leaf, the branches above it and now and then a split: with a dozen requests to a commit, five of the 22 page nodes an acknowledged request wrote at the single-host load, and the writer of `apply.db` was held 97 % of the time (L2w20Admission14). In a contracted installation (`meta/scan_index_version` 3, `upgrade.md`) the five tables are one logical index, `scan_rows`, in the block-run format of the query indexes (`scan_time.r<id>` and `scan_postings.r<id>`: sorted, prefix-compressed pairs in blocks, one run bucket per commit, merged in the background, the run that reaches 64 MiB is final). One commit writes the rows of all the requests it carries as **one** run, sorted by key, whose blocks are contiguous: a pair is the tag of the table (`b` batches, `c` commits, `m` metrics, `p` pages, `r` receipts) followed by the key of the row, so each table is one range of every run. The blocks of a run of the row store are 32 KiB, not the 128 KiB of the query indexes: a row that is erased or replaced rewrites the block it lives in.

* **The table buckets stay as the oldest source of their tables.** A file that was contracted before the row store (version 2) or adopted from version 1 keeps every row it has in them; a table is the merged view of its runs (newest first) and its bucket, and nothing is migrated. A cursor over a table is the merged cursor of the ranges of the runs and of the bucket, in key order, each key once.
* **Point reads ask a bloom filter first.** A receipt, a metric sample and a page are looked up by key at every apply (the batch must be new, the sample must not conflict, the page must not exist) and on every retry; a run answers only when the filter of its keys (12 bits a key, blocked so that a probe touches one cache line, stored beside the run's registry entry in `scan_runs` under `scan_rows.bloom/<id>`) may hold the key. A merge writes the filter of its output and drops those of its inputs, a deleted key stays in the filter of its run (a false positive that the run then answers), and a filter that does not parse holds everything. The rows a commit has collected but not written yet are found first, so a transaction sees the rows of the requests before it.
* **A read-only transaction opens the bucket of a run only when a lookup asks it.** Every acknowledged append runs several read transactions (the receipt, the admitted batch, the validation of the ordered commands, the finalization check), and each loads the row store; opening the bucket of every run was 8 % of the cpu of the single-host gate (L2w20Admission38, `TestRowStoreOpensOnlyTheRunsAReadAsks`). A read-only load now reads the registry and the filters only, a `Get` opens the runs whose filter may hold the key, and a cursor opens all of them. A ready run whose bucket is missing is `corrupt` where the damage is read: a writing transaction fails at the load, `tableGet` and `rowStore.Err` report it to a reader that looked a key up.
* **Loading the row store allocates a constant number of times, whatever the history.** The registry is read in one pass that pairs every ready run with its bloom filter (two cursors, the entries under `scan_rows/` and the filters under `scan_rows.bloom/`, both in id order; a run without a filter is asked, a filter no entry names is skipped), into a slice that the previous load's size presizes; and a read-only transaction opens the legacy bucket of a table when a lookup reaches it (bolt opens a bucket afresh on every ask of a read-only transaction), where a writing transaction still opens all six at the load and fails `Corrupt` on a missing one. A load of 48 runs allocated 134 times and now allocates 9 (`TestRowStoreLoadAllocationsDoNotGrowWithTheRuns`, `TestRowStoreLoadPairsRunsAndFilters`, `TestRowStoreOpensLegacyBucketsWhenAsked`); it is done ten times a request (L2w20Admission39).
* **Erasure and redaction work in place.** Deleting a row (an erased metric sample, the pages of an erased batch) or replacing it (the rewritten `batches` row, the commit record of a batch whose kept rows are indexed again, the publication of segments, which turns hot page rows into references) rewrites the block that holds the row, once per block however many rows of it change (`blockRun.edit`): the block is rebuilt without the row, refiled under its new last key, and removed when it had no other pair; a merge in flight gets the same change in its unfinished output. bbolt frees the old pages and the scrub (`scrub.go`) zeroes them like any other freed page, so an erased row is physically gone from the file by the same argument as before, and a block never keeps a value that the erasure removed (a block stores a value as a difference to the previous one, so the rows that followed the erased one are re-encoded against the new neighbour). A row that an erasure re-indexes (the kept rows of a batch) is written to the table's bucket, not to a run: a rewrite is not an append. The bound for erasure is therefore one block (at most about 34 KiB) rewritten per erased row and per block, where it was a leaf.
* **Reads, backup and restore use the merged view.** The scans (`read.go`), the page publication and the segment accounting (`flush.go`, `manifest.go`, `erase.go`), the startup verification of the tail (`verified.go`), the quota reconciliation (`snapshot.go`), the receipt, fence and settle lookups, the legacy-WAL import (`recovery_index.go`) and the change feed (`live.go`) read tables through it; a restore or a snapshot install replays the stored commands through the same apply and fills the runs of the new file. A damaged block is `corrupt` for the table that reads it, never an empty range.
* **Cost.** Measured with `TestAckPageNodesAreBoundedAndIndependentOfHistory` (single-record appends over 900 series, twelve in flight, a commit carries about three of them, 1,500 acknowledged requests): bolt page nodes written to `apply.db` per acknowledged request, 14.9 for the first 250 and 21.4 for the last 250 before the change (bound 14), 8.2 to 9.6 and 11.1 to 12.3 after (the bound for the later window is 1.25 times the earlier one plus 2). What a request still writes in `apply.db` is its replicated command (`replica_commands`, `replica_data`), the time-ordered `consumed` row, the cursor, and its share of the commit: the freelist and meta pages and, for each of the three runs the commit adds (`scan_time`, `scan_postings`, `scan_rows`), the run's bucket, its registry entry and the root-bucket page that names it. A commit that adds a run writes 4.8 page nodes beside no other run and 8.2 beside 120, so what grows with the history is the number of runs alive between merges, not the rows.
* **Restart.** A file that is opened reads the registry of the row runs (one entry and one filter per run: tens of runs after the merges) and no row; the tail validation of `verified.go` reads the commit records and pages of the commands above the verified index through the filters. A run that a merge was building when the process stopped is dropped at open, like those of the query indexes.

## A cut reads what was added since the last cut, not the window it is in (L2w20Admission34)

Every owned data group cuts a snapshot after 4,096 commands or 16 MiB of journal, whichever comes first (`DefaultSlotCadence`): about eight cuts in the window of 4,096 commands each group fills in 17 minutes at the single-host load (31 KB a command, 4.8 commands a second a group). Each cut used to derive the open window from the stored commands twice, once for its record (`windowTableOf`) and once to write its files (`writeWindowFiles`): a random read of the payload log and a decode for each of up to 4,096 commands, for each of the 64 groups. Measured on the gate VM (perf record on `pread64` with the Go frame pointers, 8 s at 600 s of load): 27,493 of the server's payload preads came from the first, 9,018 from the second, 3,840 from the settlement parts and about 2,700 from the row-run blocks that the acknowledgements look up. Added up over a window that is up to 8 GB of the payload log read again for the 64 groups, from the page cache while the scope has room and from the disk, as random reads of a log the groups share, once the scope's `memory.max` is full: the 3,600 s run left 250 ms of p95 at 1,560 s, the second the page cache of the scope was full (memory.current at memory.max), and collapsed at 3,060 to 3,240 s, where the third window seals in every group at once (G5: 17,091 requests shed).

Now the slot keeps the derivation of the window it is filling (`windowCache`, `Engine.windows`): the last window of the slot is extended by the commands applied since the derivation before (the hashes of the file and of the identity are running hashes, the evidence and the parts are rebuilt from the list it holds), so a cut reads the commands added since the cut before and a window that seals is sealed from the same builder. The files are written from the previous snapshot's file of that window and the commands added since (`writeWindowFilesFromPrior`): the prefix is copied and hashed (it must be the file the cache passed through, by size and SHA-256), the new commands are the only ones read from the store, and the result is checked against the record exactly as a whole derivation is; anything that does not hold (no cache of this very state, no previous file, a damaged one) derives the window whole as before. A cut's reads per command are two (the record, the file), whatever the position in the window and the length of the history (`TestCutReadsOnlyTheCommandsAddedSinceTheLastCut`: 24 cuts of 4 commands over three windows of 32 read 192 commands, 864 before; `TestIncrementalWindowFilesAreThoseOfAWholeDerivation`: the files are the files of a whole derivation).

The cache is valid while no stored command has been rewritten. Erasure (`eraseBatch`, `eraseBlob`), the only writer of a stored command, takes `cutMu` exclusively and bumps `Engine.cutEpoch` before it rewrites anything; a derivation built under another epoch is rebuilt from the commands, so a redacted command never comes from a cache or from the previous snapshot's file (`TestRedactionRewritesASealedWindowInTheNextCut`, whose open window holds the redacted command).

The files of a snapshot are written once and read again only by a restore, a transfer or the next cut's prefix, so `SnapshotStore.VerifyCut` and the deep `Verify` ask the kernel to forget their pages once they are hashed (`durablefs.DropCachedPages`), as the payload log's pages are forgotten after their sync: at the gate the sealed windows' files alone were 7.6 MB a second of page cache charged to the scope for ever.

## The verification of the tail reads each record once, forgets it, and looks the entries up in key order (L2w20Admission35)

The verified point (D15) follows what the node applies: once a minute `advanceVerified` verifies the commands above it, the page of each of their batches (the page's record in the payload log is read and hashed) and the page's entries in `scan_time` (one Seek for the range of each page), and a start does the same for what lies above the point it finds. At the single-host gate (G7, L2w20Admission34) that was the cause of two failures that looked unrelated. (1) The page records were read a minute after their write, after the log's pages had been dropped, and nothing dropped them again: 70 % of the payload log (every page record, 10 of 14 GB at 2,040 s) stayed in the page cache of the scope, and when the scope was full (2,280 s) the kernel kept them (active file 11 GB) and evicted `apply.db` and the journals: 5,500 major faults a second, per-10 s p95 correlated with them (r 0.72-0.81), p95 up to 9.6 s. (2) The Seek of a merged cursor is a Seek of every run, and a run of the log layout fetched, for each Seek, the 128 KiB block that holds the key from the log, whichever block the Seek before had stood in: 46,600 pages x one block per sealed window x 128 KiB a minute (each of the 562 blocks of a run read 83 times), 18 s of one thread holding a read transaction after one sealed window, more after each (one is sealed every 17 minutes), and the start after the hour spent its first 35 s in the same loop (one thread, 9 MB/s from the disk) before the 64 groups opened.

Now the page records are read with `payloadLog.readCold` (the read, then the kernel is asked to forget the pages the record touches: `dropPayloadRange` rounds out to whole pages, since a record of a few hundred bytes covers none; the log's read handles are opened with `POSIX_FADV_RANDOM`, since the records next to a record belong to other groups and a readahead filled the cache with them), the pages of a pass are collected (batches of 65,536) and looked up sorted by the start of their range, and a `blockCursor` keeps the block it stands in and answers from it every Seek that bolt's Seek would send to that block (`held`, `lo`): a pass reads each block of a run about once, whatever the number of runs. A graceful `Close` advances the point to what the node applied (`verifyAtClose`, 10 s at most, after the groups stopped), so the start after it has no tail to verify. Tests: `TestPayloadReadColdLeavesNoPageInTheCache`, `TestAdvanceLeavesNoPageOfThePayloadLogInTheCache`, `TestMergedCursorSeeksInOrderFetchEachBlockOnce`, `TestAdvanceReadsGrowWithBlocksNotWithPagesTimesRuns`, `TestGracefulCloseMovesTheVerifiedPointToWhatWasApplied`.

## The journal-expiry plan reads each command once, and a record just written stays cached for three minutes (L2w20Admission36)

G8 (the plain build with the cold reads of L2w20Admission35) still kept 65-88 % of the payload log in the page cache at 1,300 s and 2,200 s. The reader was not the advance: 174,773 of the 213,679 `pread64` of a 12 s window at 1,300 s (73,723 of 126,321 at 2,200 s) came from the journal-expiry plan (`appcore.journalExpiryProducer` -> `Engine.ExpiringErrorEvidence` -> `eraseCandidates`), which every 15 minutes read every stored command (the whole log, uncached, in read transactions of 512 commands) and, at the size of the log, never finished before the next one was due. `ExpiringErrorEvidence` now keeps the error evidence it finds (`expiryScan`: per slot the index of the last command read, and for each error record its cursor, signal time and deadlines) and a plan reads only the commands appended since, with `readCold`; an erasure (the one writer of a stored command, which bumps `Engine.cutEpoch` before and again after it rewrites) and a backup install start the reading again, and a cache of more than 2,097,152 error records is not kept. The candidate scan of an erasure reads cold as well. Tests: `TestExpiringErrorEvidenceReadsEachCommandOnce`, `TestExpiringErrorEvidenceLeavesNoPageOfThePayloadLogInTheCache`.

The first snapshot cuts (180-210 s of G8) came with `apply.db` growing from 0.33 GB to 2.66 GB in 20 s and a doubled write rate from 100 s to 480 s. The readers of a record that was just written (the settlement of its window, the derivation of the window of a cut, the advance a minute later) read it inside a read transaction of `apply.db`, and with every written byte dropped at its sync each of those reads was a read from the disk: a transaction held across disk reads keeps bolt from reusing the pages freed since it began. The log therefore queues the pages of what it syncs and drops them after `payloadKeep` (3 minutes; `dropSpan`, `payloadLog.dueDrops`), and `readCold` drops the pages of a record only once the record is past that window (`pastKeep`); a file a node opens, a file the log has rolled away from and everything when `payloadKeep` is zero are past it. Test: `TestSyncedRecordsStayCachedForTheKeepWindow`.

## No reader of the stored commands waits for the disk inside a read transaction (L2w20Admission37)

A command of 256 bytes or more lives in the payload log and `apply.db` holds its reference. A reader that follows the reference inside its read transaction holds the transaction open for as long as the read takes, and bolt reuses no page freed after the oldest open read transaction began: at the gate (about 80 MB/s of pages written) each such reader made the file grow and the writes fresh pages, whatever the page cache held at the start. The readers that follow references are the settlement of the open window (`tailPartsOf`), the derivation of a window for a cut (`windowTableOf`, `deriveWindow`), the window files of a snapshot (`stageWindows`, `writeWindowFiles`, `writeWindowFilesFromPrior`), the journal-expiry plan (`expiryScan`) and the candidates of an erasure (`eraseCandidates`). They now take the stored values in short read transactions (`fetchedCommands`: at most 256 commands or 4 MiB of inline values, references are a few bytes each; `scanChunksRange` copies its chunk the same way) and read the log after the transaction ended. `TestCommandReadersNeverReadThePayloadLogInsideAReadTransaction` counts the reads of the log made while the engine has a read transaction open (`payloadReadHook`) and fails on any of these readers. The whole pass of the background verification and the advance a minute after a write (`validateIndexTail`) still read inside one transaction on purpose: they are bounded by the verification interval and by the last minute's pages, which the keep window above holds in the page cache.

The expiry plan's cache is kept up by a loop (`expiryScan.keepUp`, every `expiryRefresh` = 1 minute) that reads the commands appended since, a minute after they were written, from the page cache, so a plan finds nothing new to read from the disk. The loop extends a cache that stands; a cache an erasure invalidated, or one grown past `expiryCacheMax`, is rebuilt by the plan only (`TestExpiryCacheIsKeptUpWithoutAPlan`).
