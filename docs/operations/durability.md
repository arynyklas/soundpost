# Single-host durability boundary

Copyright 2026 Aryn Yklas. SPDX-License-Identifier: Apache-2.0.

This implementation owns a single-host, non-HA telemetry WAL and ordered apply state. It is not a claim of implemented Raft, snapshots, segments, physical retention/deletion, backup, restore reconciliation or a qualified power-loss guarantee. Those later gates remain mandatory. Do not enable a distributed deployment by treating the current local lock or fsync as a quorum.

## Explicit control activation at the 01.06 cutover

Opening a control database does not activate a feature write path. Store.Update is unavailable until the actual Raft authority is enabled; no generic local feature-ACK fallback is allowed. Before activation, auth.NewService may only prepare and seal random bearer material and invoke the narrow InitializeBearerHashKey transition on pristine bootstrap state. Existing initialized/versioned authority is never overwritten or regenerated; a missing installed root is corrupt even when the token set is empty.

Auth-only HTTPS/CLI/test compositions explicitly call Store.EnableSingle(ctx, persistentRaftDirectory) after NewService and before Bootstrap, login mutations, administrative writes or other feature traffic. This enables a real one-voter group, not an in-memory fixture. Store.Close owns its group/loopback lifecycle. Restart must reuse the same Raft directory. Full application composition uses its actual control-plus-data activation, then publishes data-initialized state; neither constructor order nor a fixture may acknowledge features before that activation. These setup requirements are distinct from HA/power-loss qualification.

## What an intake acknowledgement waits for

1. Current source credential, scope, registered privacy policy, every record owner and the whole batch are validated.
2. One durable control transaction reserves organization/project/source canonical bytes and canonical-series charge, bound to batch identity/hash, owner slot and policy epoch. Ambiguity does not refund it.
3. The installed one-voter group serializes validation and proposal. It rejects equal-time metric conflicts and terminal job rewrites as a whole batch.
4. The group writes an owned WAL entry and fsyncs that file. A newly created WAL namespace is directory-fsynced before it can acknowledge.
5. A bbolt apply transaction persists admitted records, metric/job ordered state, the original complete receipt, the consumed reservation ID/cursor and the applied cursor. The transaction uses real synchronous bbolt commit, not NoSync or an in-memory substitute.
6. Control verifies the owning group's durable consumption proof and finalizes the existing charge. Credential/policy release checks still precede the returned success.

Concurrency does not change any of those steps. Appends of different data slots run steps 3-5 at the same time, each ordered within its slot by a per-slot lock that is held from the final receipt/ordering re-check to the end of the slot's proposal; every command that needs the engine free of other proposals (fences, barriers, snapshots, blob and erase commands) still takes the engine-wide proposal lock exclusively and so excludes all appends. The checks that ask the control group (credential, source, reservation, active deletions) run before the slot lock and are repeated by the replicated state machine at apply time. The apply transactions of the slot groups that are in flight together are committed as one bbolt transaction (`updateGrouped`): the caller that finds no commit in progress commits at once, the callers that arrive while it fsyncs form the next transaction, and every acknowledgement is returned only after the transaction that holds its row has been synchronously committed (two fdatasyncs, the same as a transaction of one). A function that fails is rolled back alone and re-run by itself, so its error is its own.

Two mechanisms keep that serialized chain short without moving any acknowledgement earlier. (a) A replica group that is a single voter and leads (the control group and the 64 slot groups of a single-host installation) answers a linearizable read (`ReadIndex`) from the cursor of the last command it applied, without waiting for the group lock that is held across the journal fsync and the state machine's commit of the command in flight: a leader that is its own quorum has no leadership to confirm, and a command is acknowledged only after it was applied, so the read sees every acknowledged command. A group with more than one voter, a joint configuration or a lost leadership keeps the Raft round of every read (`internal/replica`, `Group.soloRead`). (b) The query indexes of a database this release created (`scan_time`, `scan_postings`) are stored as the union of the base bucket and sorted *run* buckets: the bbolt commit that carries the apply transactions of the appends writes the index keys of all of them as ONE new run, in key order, instead of one random insert per key (an acknowledged append dirtied about 55 bbolt nodes, 32 of them `scan_postings` inserts), and a background merger folds runs into larger ones in transactions of about 2 MiB. Readers see the merged union through one ordered cursor, the multiset digests in `scan_integrity` and the verification are unchanged, and every acknowledgement is still after the journal fsync on a quorum and the synchronous commit that holds the row and its index keys. See `upgrade.md` (query-index layout) for the file-format gate.

**Restart time is bounded by cadences, not by the age of the installation (L2w20Admission7).** A start reads the freelists of `apply.db` and `control.db` when the last close wrote them and rebuilds them from the live trees after a crash (D91, below), replays the journal of each of the 64 data groups and of the control group since their last snapshot cut (every entry decoded and compared with the command the store already holds, ~10 MB/s), and only then answers `/readyz`. Each data group therefore cuts a snapshot and compacts its journal by itself every 4096 commands (one snapshot window; a tighter cadence re-decodes the open window at each cut and took 42 % of the server's CPU at the single-host load) or 16 MiB of journal (`storage.DefaultSlotCadence`; the control group's is `control.DefaultJournalCadence`), so the replay is at most 4096 commands per group, and the 64 groups open and replay concurrently. The worker's hourly snapshot pass remains for deletions. The settled-reservation pass (docs/operations/recovery.md) runs on every worker pass (one minute), so control state holds the rows of the open data windows only; with 64 active slots and 4096-command windows that is at most 64 x 4096 reservation rows (~1 KB each in the ledger and again in each control snapshot), plus `adm_series`/`adm_cseries` records, which are bounded by the series cardinality of the three quota tiers.

**The freelists of `apply.db` and `control.db` are not written by the commits (D91; L2w20Admission26, L2w20Admission27).** A bolt commit that persists the freelist writes one node that lists every free and pending page id of the file, 8 bytes each, and a file that churns (the index merges of `apply.db`, the copy-on-write pages of both) is mostly free pages that only grow: at the single-host gate `apply.db` wrote a 1.0-1.3 MB node per commit (64 % of the 3.25 GB the server wrote in 12 s), and `control.db` after the hour 455 KB (111 pages) per commit, 57 commits a second. Both files are therefore opened with `NoFreelistSync` and `PreLoadFreelist` (`storage.applyDBOptions`, `control.controlDBOptions`) and mapped ahead of their growth (`durablefs.BoltInitialMmapSize`, 8 GiB on Linux: a commit that grows the file past the mapping waits for every reader, and every new reader waits for it). A graceful close writes the freelist once (`syncFreelist`: one commit with the flag cleared), and the next start reads it from the file. After a crash the file names none and bolt rebuilds it from the live tree before the process answers: a pass over every branch and leaf node (an overflow node by its first page), not over the file. Measured on the file the gate leaves (L2w20Admission27, G3's `apply.db`: 5.39 GB, 1,153,845 of 1,315,000 pages free, 107,435 live nodes; its `control.db` is 1.09 GB with 200,422 live nodes) bolt's pass alone is 14.1 s for `apply.db` on a cold page cache (0.75 s warm), one page fault after the other, against the 20 s startup budget; the 200,000 nodes of `control.db` were not measured without the warm-up. `durablefs.WarmBoltTree` reads the same pages 64 at a time before bolt opens the file (only when the newest meta page names no freelist and the file is at least 32 MiB; it reads, never writes, and gives up silently on anything it cannot parse), so that bolt's pass finds them in the cache: files of the gate's shape built with the options of the store, the page cache of the file dropped, open in 2.3 s for a 5.2 GB `apply.db` (1,156,640 free pages found) and 3.2 s for a 954 MiB `control.db`. This is the concurrent rebuild D91 asks for, within each file instead of by splitting `apply.db` by data group. Tests: `TestCommitBytesDoNotGrowWithTheFreePagesOfTheFile` and `TestControlCommitBytesDoNotGrowWithTheFreePagesOfTheFile` (the bytes of a commit do not depend on the free pages: 206,711 against 10,103 bytes before), `TestFreelistIsWrittenByAGracefulCloseAndRebuiltAfterACrash` and the control twin, `TestCrashRestartOnAGateSizedApplyDBRebuildsItsFreelistWithinTheBudget` and `TestCrashRestartOnAGateSizedControlDBRebuildsItsFreelistWithinTheBudget` (files of the gate's size, the page cache of the file dropped, the open must rebuild every free page within half and a quarter of the budget, and the commits after it must reuse the pages; TMPDIR on a disk), `durablefs.TestWarmBoltTreeReadsExactlyTheLiveTree` (the pages it reads are exactly the pages bolt finds reachable), `TestGrowthOfApplyDBDoesNotWaitForAReader`. The single-host harness (`fixtures/overhead/singlehost`, `server --cold-restart`, root) drops the whole page cache between the stop and the start of every restart, so the gate's kill -9 restart is measured cold (`ready_ms` of the restart event).

**One option set, the array freelist (L2w20Admission28).** The options of the paragraph above live in one place, `durablefs.BoltOptions` (the former `storage.applyDBOptions` and `control.controlDBOptions` are gone): `NoFreelistSync`, `PreLoadFreelist`, the mapping ahead of the growth, and the array freelist type. bbolt's hashmap freelist hands out the first span of a Go map iteration, a random one, so the commits of a file with a million free pages would write 4 KiB pages scattered over the whole file; the array type hands out the lowest free page and keeps the writes at the front of the file (`durablefs.TestBoltOptionsWriteTheLowestFreePagesFirst`). Measured on the single-host gate at 20+900 s the hashmap build was not slower than the array build (p95 183 ms against 268 ms, within the spread of one tree), so this is a locality bound, not the cause of the slow L2a/L2b runs: those ran a diagnostic build (`soundpost_diag` and a patched bbolt that counts the pages of every commit), which gave 776 ms on the same load. Latency runs of the gate use plain builds.


**The random-key tables of the admission ledger are written through an overlay, so that a commit of `control.db` writes what it carries and not a page for each series it names (D83; L2w20Admission28).** At the single-host gate (2,000 records a second, 7.4 acknowledgements per commit) a `control.db` commit wrote 155 pages, 124 of them leaves of three tables keyed by a random name (`adm_series`, `adm_cseries`, `adm_keys`: every series or key a commit names is a leaf of its own, written at the reserve and again at the settle) and 29 the reservation rows and quota heads that every command rewrites: about 21 pages per acknowledgement, growing with the table. The five tables now keep their records in an overlay (`internal/control/ledger_overlay.go`). A commit appends the records it changed as one compressed blob to a log under sequential keys (bucket `adm_ov`, in pieces of 1,000 bytes: bolt writes a leaf of up to four elements whole each time one is added), and reads see the log first and the table behind it. When the active generation of the log holds as many bytes as four times what the last fold wrote (1-24 MiB; two generations are in memory at most, so the memory of the overlay is bounded by `ovFreezeMax`) it is frozen, and each of the next commits folds a bounded share of it into the tables in the order of the table, so that a page is written once for all the records of the generation that fall on it; the frozen generation is dropped, its blobs deleted as one range, when the last record is in. The series tables are `ovBlocks` (4,096) blocks by the hash of the series, a row holding the series once and its count under each quota key (the quota key as its number in `adm_tiers`): a fold writes at most that many blocks and at most the bytes of the tables, so the pages of an admission are the log of its commit (compressed bytes over 4,096), the share of the fold of its generation (bytes of the tables over the commits of the generation, a generation being a multiple of the tables) and what every commit writes (meta page, accumulator, `ov_meta`), whatever the history: no page is written for the number of series or admissions that came before, and the tables are the only thing that grows. It is a LOCAL layout: the records, their keys and values, the accumulator and every digest, patch and snapshot are those of the plain tables, so members that run the previous layout agree with it. The layout is `ledgerFormat` 5; a file of format 4 is moved at `Open` (`moveSeriesToBlocks`, in the transaction that opens it) and a build that does not know the overlay must not open it (the rule of every earlier layout of a contracted installation). `TestConcurrentAdmissionsWritePagesThatDoNotGrowWithTheKeysOfTheHistory` (100 sources of 1,000 series, batches of 20, 32 writers) holds it: 41.6 pages per admission before (32.4 at 600 admissions of history), 6.0-6.7 after 12,000 and 40,000 (growth x1.02 to x1.19 over five runs, the bound is 1.3, the absolute bound 8); `TestOverlay*` check the overlay against plain tables through freezes, folds, restarts, snapshots older than a fold, rolled back writes and bulk commits.

**The overlay's shared copy is loaded once for every transaction that needs it, and follows the commits that land during the load (L2w20Admission32).** Every transaction of the ledger reads the generations of the overlay from a shared copy (`ovShared`); one that found it invalid, or late, loaded the generations from the log itself (inflate and decode of up to two generations of 24 MiB of records, a second at the gate's size), and at the 900 s runs 454 loads took 179 s of load time, up to 41 at once, each stall of two to ten seconds with the p95 of its minute at 0.5-1.7 s (the t2 diagnostic run). A copy a reader installed was a version or fifty behind by then (the commits go on while it loads) and the first handler of a later commit dropped it, so the next reader loaded it again. Now one transaction loads (`ovShared.rebuild`, under a lock of its own; the readers older than the copy share one load per old version, `privateGens`), a commit whose handler ran ahead of its predecessor's, or while the copy was not installed, is parked under the version it started from and applied in order as soon as the copy holds that version (`apply`, `drain`, `install`), and a transaction waits half a second, not 50 ms, for the handler of the commit that made its version. `parked` in the diagnostic build's `control.overlay` counts the commits that came early.

**A snapshot cut does not stop the engine, and the 64 cuts of a node do not fall together (L2w20Admission19, L2w20Admission20).** At the single-host load the 64 data groups are loaded alike, so with one bound they all reached it at the same instant, and each cut derived the window table of its slot (the open window is decoded command by command, about a second of CPU for 2,048 commands of 10 KB) holding `Engine.mu`, the engine-wide lock that every append of every slot takes for the index of its command: every acknowledgement waited for a minute (the live run at 900 s collapsed at the first cut: p95 140 ms to 22 s, 22,683 requests shed). Two changes bound it. (1) The cut derives the windows holding `Engine.cutMu` shared and `Engine.mu` only for a moment (`windowTableForCut`, `stageWindows`, the tombstone read of `DeletionLedger`); the one writer that rewrites stored commands, erasure (`eraseBatch`, `eraseBlob`), takes `cutMu` exclusively (lock order `cutMu`, then `mu`), and `DeletionLedger` reuses the table `CompactSnapshot` just derived instead of decoding the open window again. Appends never wait for `cutMu`. (2) Each data group is given a share of the cadence bounds (`replica.Cadence.Stagger`, in 1/1024ths, set per slot by `storage.slotStagger`: 512/1024 for slot 0 up to 1016/1024 for slot 63; 0 or 1024 is the whole bound), so the first cuts of the 64 groups are spread over the second half of one bound instead of falling together; the bounds of a group still restart from its own cut, and the journal a restart replays stays at most the bound (4096 commands or 16 MiB per group). The control group's cadence is not staggered (one group). Tests: `TestAllGroupsCuttingAtOnceDoNotStallTheEngineLock` (64 cuts at once: the engine lock is unavailable for at most 150 ms), `TestSnapshotCutDoesNotHoldTheEngineLockWhileItDerivesTheWindows`, `TestDataGroupsAreGivenDifferentSharesOfTheirCadence`, `replica.TestStaggeredCadenceCutsAtItsShareOfTheBounds`, `replica.TestGroupsWithDifferentSharesCutAtDifferentCommands`. No format, journal or snapshot byte changes: a node of the previous release reads everything this build writes, and the reverse.

A failure at write, sync, apply, receipt or applied-cursor publication cannot return a new durable receipt. An uncertain append faults that engine instance rather than continuing behind a possibly committed entry. Restart replays the WAL. A failed post-data control finalize leaves a charged reservation; receipt lookup and an unchanged admission retry can recover the original result. A source policy restriction may require the separate historical lookup rather than a new-admission retry.

## Owned files and recovery

`control.db` remains the protected control authority. The first data adapter uses `data/apply.db` for transactional applied records/receipts/ordered indexes/consumption and `data/slot-NN.wal` for the fixed 64 logical groups. Group identity is installation-owned and persisted in the data authority; it is not derived from a caller's source descriptor or current replica placement.

Control publishes a data-initialized marker only after the data namespace, group identity and recovery are durable. Losing apply.db after that marker denies application startup rather than silently opening a fresh empty engine. An existing data authority missing its group identity or required buckets also denies. Group identity randomness is prepared outside deterministic state callbacks.

WAL v1 headers are 40 bytes, big-endian: magic `SPW1`, uint16 version, uint16 slot, uint32 payload length, uint32 entry CRC32C, uint64 term, uint64 ordered index, uint32 header CRC32C, and four reserved zero bytes. Entries contain the closed normalized input and its original receipt, or a cancellation/source barrier. The header checksum protects length/term/index before allocation or tail repair; the entry checksum covers the header (excluding its entry-CRC field) plus payload. Payload length is bounded at 8 MiB. The local term is 1; later Raft must feed this same apply state rather than introduce another telemetry implementation.

Recovery scans every installed WAL in order, validates magic/version/slot/term/index/length/checksums and replays committed but unapplied entries. It truncates only an incomplete final header or payload, syncs the truncation, and verifies the durable applied cursor is still covered. A checksum mismatch is corruption even in the final complete entry. Missing WAL coverage, interior corruption and unverifiable applied state deny opening the engine; they are not EOF, an empty query result, a newly generated group identity, or a successful repair. The implementation does not truncate acknowledged WAL for snapshots or reclamation.

Original receipt hash/cursor/per-kind deadlines/minimum deadline/dedup deadline persist in the same transaction as apply. Receipt lookup is source-owner authorized but independent of new capture admission. It cannot append, normalize, reserve, recreate rows or extend deadlines. Later data expiry and deletion must preserve this receipt contract and durable deny state.

## Authority side-file ordering (01.01 F5)

`internal/durablefs` is the shared ordering primitive; failures propagate, including unsupported directory flush/rename behavior.

- New data-directory ancestry is published by syncing each new directory and its parent.
- Initial `control.db` namespace publication is flushed before authority use.
- The private bootstrap token's bytes and containing directory entry become durable before the transaction commits its authority hash. Consumption commits first; token unlink is followed by directory sync. An old surviving token cannot restore consumed authority.
- A new envelope decrypt key's bytes and directory entry become durable before any acknowledged database envelope can reference its key ID. Existing key publication is re-established on use; an earlier failed sync is not silently accepted merely because a file exists.
- Rotation durably publishes the new decrypt key, fsyncs the active-pointer temporary file, atomically renames it, and fsyncs the pointer parent before activation acknowledges. Old decrypt keys remain. Missing/malformed key authority never silently acquires a replacement root.
- Generated TLS key and certificate files each receive file and namespace synchronization before HTTPS starts. Existing files are also flushed before use. Partial first-boot TLS identity remains explicit unavailable state; no silent key substitution occurs.

On POSIX, required directory `Sync` errors fail the operation. The Windows implementation calls real directory-handle `FlushFileBuffers` and write-through rename; it does not ignore ERROR_INVALID_HANDLE/access/unsupported errors. A Windows filesystem/privilege combination unable to establish the required namespace ordering is unavailable, including at control boot. This can prevent otherwise functional Windows authentication tests from opening their test store; it must not be worked around with a fake fsync or a production acknowledgement bypass. Linux server durability is the target of the first durability gate. Existing Windows functional results are not power-loss qualification.

Require an operator-owned private data directory, appropriately restricted host/volume access and backups of decrypt material. This change does not administer host ACLs or claim that Unix file mode alone establishes Windows ACL security. Network filesystems, WSL host-mounted filesystems and storage-controller/device write-cache behavior have no power-loss qualification from a process-kill drill.

## Source barriers and quotas

A source policy/revocation operation first commits closing state. The real installed owner drains prior ordered work and fsyncs a barrier to every one of the 64 slots. Only after all durable cursors are recorded does control mark complete. Startup resumes pending source barriers before opening intake. Unavailable groups block completion. Concurrent changes to an already closing source fail instead of overwriting an unfinished saga. Operation history is retained separately from the current source fence.

Cancellation is a distinct durable data entry: while holding the same order lock as append, the owner proves no receipt exists and commits a permanent reservation no-use fence. Control accepts only that installed owner's exact persisted proof, then commits the refund. An append or consumed reservation cannot be cancelled. TTLs and router death are not proofs. Retention/deletion live-charge release and backup/restore reconciliation certificates are later work, not an implied lazy refund.

The one-voter no-commit proof is safe only with the complete recovered ordered prefix plus the fault latch that prevents cancellation after uncertain append/apply errors. A Raft owner at 01.06 must replace that argument with commit-set-watermark evidence including committed-but-unapplied proposals; an absent applied receipt is not sufficient. Lock order is engine order mutex → control read. Owner verification must finish before a control write starts; no control Update/Transact/apply callback may call back into the engine.

Source authority failures use the same content-free forbidden/403 result for invalid, missing, expired or revoked credentials on admission and historical receipts. This does not change browser-session or server/API-token authentication. Historical denial never creates a new write, reservation or data resurrection.

## The payload log (`data/payload/*.spl`, `meta/scan_index_version` 4)

Once the installation is contracted the data engine keeps the bulk of what an acknowledged append stores outside `apply.db`, in append-only files of at most 256 MiB (`payload/NNNNNNNN.spl`; a record is a 12-byte header with a CRC32C and the bytes). `apply.db` keeps a 21-byte reference where the bytes were: the stored command (`replica_commands`), the stored records (`batches`), the hot page of the records (`scan_pages`) and, from D89 stage 2, the blocks of every **final** run of the query indexes and of the row store (a run of 64 MiB or more, which no merge rewrites again; its bolt keys stay, one pointer per block). The consumed reservation of every batch is a row of the row store (table `consumed`). What bolt holds per acknowledged batch after the merges is then the pointer of its command and of its logical index (~60 bytes), the block pointers of its runs (about one key and one reference per 32 KiB of rows or 128 KiB of index bodies) and the runs that are not final yet (at most fanout runs per level, below 64 MiB: the newest minutes of the history), whatever the history behind it (`TestBoltBytesPerBatchAreBoundedAndIndependentOfHistory`).

**Acknowledgement order.** The records of an apply are written to the log and the log is synced before the bolt transaction that carries their references starts; the append is acknowledged after that transaction is durable. A crash in between leaves bytes that no value names (dead space, never read) and never a reference to bytes that are not there (`TestPayloadLogIsSyncedBeforeAnyReferenceToItCommits`: the hooks `payload_sync`, `payload_synced`, `receipt_write`, `applied_cursor`).

**Migration.** A file that holds inline values when it adopts the layout (the commands, the legacy buckets `batches` and `scan_pages`, the blocks of final runs) moves them in the background in chunks of about 2 MiB, resumably (`payload_migrate` in `apply.db`); both forms are read until the last is gone (`TestInlineValuesMigrateOnceTheLayoutIsAdopted`). The legacy single-bucket query indexes and the legacy `receipts`, `metrics`, `scan_commits` and `consumed` buckets are not migrated (their size is the pre-layout history). The layout is adopted only when the installation is contracted: the previous release refuses a file of version 4, so a contracted installation is not rolled back.

**Erasure.** An erasure zeroes in place the log records that held the erased bytes, after no read transaction overlaps (owed references are listed in `payload_scrub`; the merger also drains them for published hot pages and replaced commands). Records that a crash or a failed apply left unnamed (the apply wrote them before the transaction that names them committed) are reached by a sweep: `apply.db` keeps a mark (`meta/payload_swept`), the log position up to which every record is named or zeroed. A graceful close moves the mark to the end of the log, unless the process failed or a background chunk failed after it appended; an open whose log is longer than its mark has a span a crash may have left such records in, and the erasure pass sweeps that span before it reports bytes gone: it collects every reference of the file (every bucket, the page rows that carry one, the owed list) and zeroes every byte of the span that no named record covers, torn tails included, then moves the mark. A process that itself left records it cannot name keeps its erasure pass pending until the restart sweeps them (`TestEraseZeroesPayloadRecordsOfACrashedApply`: crash at `payload_sync`, `payload_synced`, `receipt_write`, with graceful restarts between the crash and the erasure; the test scans the log files for the erased bytes).

**The mark means something only in a file that names the log (L2w20Admission31).** `meta/payload_swept` vouches for the records of the log below it because the file's values reference them. A file that is not in the payload layout (`scan_index_version` below 4: an image made by dropping the layout from a node that had the log, an older `apply.db` restored under the directory) references none, so a mark it carries is forgotten at open and the whole log is the span the erasure pass sweeps: it zeroes every byte no reference names, whatever the layout, and writes no mark into such a file (the next open finds the span again until the file adopts the layout and closes gracefully). Before this, an upgraded node's erased batch survived in `payload/00000001.spl` (`TestErasedBytesAreNotLeftInTheLegacyWALOfAnUpgradedNode`, `TestPayloadMarkOfAFileOutsideTheLayoutIsNotTrusted`).

**The sweep reads the references inside the blocks of the runs (power-cut defect, `TestSweepKeepsEveryRecordTheRowStoreNames`, `TestPayloadLogSurvivesPowerLossAtEveryCrashPoint`).** In the runs layout the page rows (the `Log` reference of the hot page of a batch) and the batch rows of the row store (`scan_rows`) are pairs inside the blocks of the runs: inline in a bolt value below the final size, or in a log record that a 21-byte reference of the run names. The sweep protects what a reference names, so it decodes every block of every run bucket (`scan_time`, `scan_postings`, `scan_rows`) and notes the references of its pairs, as well as the bolt values; a block it cannot read or decode fails the sweep instead of being skipped (what it names cannot be told, and zeroing it would destroy what is left). A walk of the bolt values alone zeroed the hot pages and the stored batches of acknowledged data on the first erasure pass after any stop that did not close gracefully (the mark moves only at a graceful close or a sweep), which a range read then answered 503 `corrupt`. The crash test runs the engine on a file system that loses what no fsync covered (`payloadFS`, `crashRecorder`) and cuts power at every write, fsync, directory fsync, file creation and commit of `apply.db`, under six treatments of the unsynced writes and of the unsynced directory entry; after each cut every reference reads, every acknowledged record is returned and no erased canary remains, also after the sweep and the erasure pass that follow.

**The index-run merges rewrite a key at most twice in the first hours (D83; L2w20Admission28).** Every commit of `apply.db` adds one tiny run to each of the three indexes (`scan_time`, `scan_postings`, `scan_rows`: ~17 KB of keys and values for two acknowledged requests of four records), and a background merge rewrites every key of its inputs once per level the key climbs. With 8 runs to a level that was four to five rewrites before a run reached the 64 MiB at which it is final (no run does in the first hour of a group at 50 KB/s of index bodies): `scan_runs` was 9.79 M of the 18.8 M pages `apply.db` wrote in a 900 s gate run. The levels hold 64 runs now (`storage.indexRunFanouts`: 64, 64, then 8): a key is rewritten once until 4,096 commits (about 17 minutes at four commits a second per group), twice until 32,768, and a final run is still never rewritten. An index holds at most 63 + 63 + 7 ready runs before a merge takes them (a few hundred for the three; a merge chunk is still at most 2 MiB, so the write lock is held no longer than before). Measured on the engine with gate-shaped batches (`TestGateWriteVolumePerAckIncludingMergesIsBoundedAndIndependentOfHistory`, 2,048 acknowledged requests of four records, two to a commit) the merges wrote 1.3 pages (0.2 page nodes) an acknowledged request, against 3.9 to 8.5 pages (1.8 to 2.2 nodes) with 8 runs to a level, and `apply.db` 10.5 to 11.7 pages an ack against 13.0 to 20.5; `TestGateMergesRewriteAKeyAtMostTwiceInTheFirstHours` bounds the bytes the merges write per byte committed (2.2 over 8,192 commits, against 5.7). What the merges do not change is the commit itself: ~15 pages for its three tiny runs (their buckets, registry entries and the meta page), the next cost to cut.

## The single-host gate's host shape (D90)

The load harness (`fixtures/overhead/singlehost`, role `server`) starts the product in a cgroup v2 scope of its own when it runs with `--scope` (as root, with `--cpus 0-7 --gomaxprocs 8`): `systemd-run --scope -p AllowedCPUs=0-7 -p MemoryMax=16G -p MemorySwapMax=0` replaces itself with `soundpost serve`, so the process id the harness signals is the product's. After readiness it reads the scope back from `/sys/fs/cgroup` and refuses to go on unless `cpuset.cpus.effective` is exactly 8 CPUs, `memory.max` is a number of bytes between 15,000 MiB and 16 GiB (the page cache is charged to it), `memory.swap.max` is `0` and the process was started with `GOMAXPROCS=8`; every restart starts a new scope and is checked the same way. `host.json` and the `server_host` of `result.json` carry the raw contents: `cgroup_path`, `cgroup_cpus_effective`, `cgroup_memory_max`, `cgroup_memory_swap_max` (beside `gomaxprocs`, `cpus_allowed`, and the VM totals `logical_cpus`, `mem_total_kib`); the series carries the scope's `memory.current` and its `oom_kill` count. Without `--scope` the harness pins the product with `taskset` and the facts are those of whatever cgroup the process happens to be in, which the qualification row reports as a reduced run.
