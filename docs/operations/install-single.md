# Install a single-host Soundpost

Single mode is one server on one durable local disk. It is **not highly available**: a host or disk loss is a restore from backup (`docs/operations/backup-restore.md`), not a failover. Production servers target **Linux amd64 and arm64**. The SDKs also run on macOS and Windows, but that does not certify server disk durability there. Nothing here is a power-loss qualification; the smoke below proves process-crash recovery only (`docs/operations/durability.md`).

## 1. Build the distribution (reproducible, pinned)

**Prerequisites (the build is offline).** `build` runs the compiler with `GOPROXY=off`, `GOTOOLCHAIN=local` and `GOENV=off`, so nothing is downloaded during `verify` or `release`. Provide these first, on a host that has network access once:

* The pinned Go toolchain (the version and sha256 in `build/toolchains.json`): unpack the `go<version>.linux-amd64.tar.gz` archive to `.tools/linux/go` (so `.tools/linux/go/bin/go` exists) and keep the archive itself at `.tools/go<version>.linux-amd64.tar.gz`. Elsewhere, set `SOUNDPOST_GO` to the toolchain's `bin/go` and pass `--archive <path to the archive>`. `verify` compares every file of the installed `GOROOT` with the archive.
* Every Go module of `go.sum` already in the module cache. The build passes only `HOME` through (not `GOPATH` or `GOMODCACHE`), so the cache is the default `$HOME/go/pkg/mod` of the user who runs the build; fill it beforehand with `go mod download` using the same pinned toolchain and the same `HOME`. Without it `go mod verify` fails with a `GOPROXY=off` lookup error.
* A prebuilt `web/dist` (below) and the pinned Node.

A missing toolchain, archive or module cache stops the build with a message naming what is missing.

```sh
go run ./build verify
go run ./build release --out dist --version 1.0.0 --commit "$(git rev-parse HEAD)" --reproduce
```

`verify` refuses to continue unless: the Go archive matches the sha256 pinned in `build/toolchains.json` **and** every file of the installed `GOROOT` equals that archive; `go mod verify` passes with the network off (module hashes from `go.sum`); every Python requirement in `sdk/python/requirements-*.lock` carries a sha256; and `pnpm-lock.yaml` is hashed into the manifest. `build` does not run pnpm: the release step only consumes a prebuilt `web/dist` and refuses to continue without it, telling the operator to build it with the pinned Node (`pnpm --filter @soundpost/web build`); the frozen-lockfile install (`pnpm install --frozen-lockfile`) is run by the CI workflows (`.github/workflows/verify.yml`, `qualification.yml`), not by `build`. It also reports whether `build/dependencies/node-licenses.json` still matches the current pnpm lock (`current` or `stale`); a stale inventory must be regenerated by its owner before publication, `verify` does not rewrite pins.

`release` builds `linux/amd64` and `linux/arm64` with `CGO_ENABLED=0 -trimpath -buildvcs=false -mod=readonly -ldflags "-s -w -buildid=" -tags netgo,osusergo,webembed`, checks each result is a static ELF (no interpreter, no shared library) and writes `SHA256SUMS` and `release.json` (inputs, build identity, per-binary sha256; no timestamps). `--reproduce` builds everything a second time with an empty Go build cache and fails unless every sha256 is identical. The binary carries the built UI (`web/dist`, build it first with the pinned Node 22 and `pnpm --filter @soundpost/web build`); `soundpost version --json` reports `ui_embedded`. Only the packages that exist in the tree are built; `release.json` lists what was skipped (`soundpost-agent` is built as soon as `cmd/soundpost-agent` exists).

```sh
./soundpost version --json     # version, commit, build id, go version, platform, supported platforms, ui_embedded
```

## 2. Container (nonroot, immutable root, persistent volume)

```sh
go run ./build image-context --release dist --arch amd64 --out ctx   # checks the binary against dist/SHA256SUMS
docker build --network=none --build-arg SOUNDPOST_VERSION=1.0.0 \
  --build-arg SOUNDPOST_SHA256="$(sha256sum ctx/soundpost | cut -d' ' -f1)" -t soundpost:1.0.0 ctx
export SOUNDPOST_IMAGE=soundpost:1.0.0
docker compose -f deploy/compose.single.yaml up -d
```

The image is `FROM scratch` with the static binary and an empty data directory: no shell, no package manager, nothing downloaded at build time (so `--network=none` works). It runs as `65532:65532`, with `read_only`, `cap_drop: ALL` and `no-new-privileges`. `/var/lib/soundpost` is owned by that user with mode **0700**; everything the server writes inside it (control and apply databases, envelope keys, `bootstrap.token`, generated `server.key`) is **0600**. The server also re-checks at start: a data directory it cannot make 0700, or a supplied `--tls-key` readable by group or other, stops the start (exit 1, `soundpost: the data directory or TLS private key is accessible to other users...`). The compose file publishes only `127.0.0.1:8443` unless `SOUNDPOST_PUBLISH` says otherwise, keeps data in the named volume `soundpost-data`, and has no default password.

## 3. systemd (nonroot)

```sh
useradd --system --home-dir /var/lib/soundpost --shell /usr/sbin/nologin soundpost
install -m 0755 dist/linux-amd64/soundpost /usr/local/bin/soundpost
install -m 0644 deploy/systemd/soundpost.service /etc/systemd/system/
systemctl daemon-reload && systemctl enable --now soundpost
```

`deploy/systemd/soundpost.service` runs as `soundpost`, creates `/var/lib/soundpost` with `StateDirectoryMode=0700` and `UMask=0077`, grants **no capability**, a read-only system, private `/tmp` and a syscall filter. No committed test or script runs `systemd-analyze security`; the exposure rating is not reproducible from this repository, so run `systemd-analyze security soundpost.service` on the installed host and judge its output yourself. A bring-your-own TLS key is a `LoadCredential=` (a 0400 copy only the service can read); delete the two `LoadCredential`/`--tls-*` pieces to use the generated identity. The server never runs as root and never receives `CAP_PERFMON`.

## 4. TLS and first boot

* No HTTP listener exists; TLS 1.3 is required.
* With no `--tls-cert/--tls-key`, first boot creates a stable self-signed `server.crt` / `server.key` in the data directory (valid for `localhost`, `127.0.0.1`, `::1` and the `--listen` address if it is a specific IP or name). Copy `server.crt` to clients through an authenticated channel and trust exactly that file; never disable verification. For a server reached by other names, bring your own certificate (a systemd credential, or a host file owned by uid 65532, mode 0600, bind-mounted read-only; Docker file secrets in non-swarm Compose are mounted 0444 and the server refuses such a key).
* There is no default account, password or public signup. The first start writes a **one-time bootstrap token** to `bootstrap.token` (0600) in the data directory and logs only that file's path, never the token. Read it from the file (as the data-directory owner), use it once: `POST /api/v1/bootstrap` with `Token`, `Email`, `Password` (16–1024 bytes) and an `Origin` equal to the server origin (`docs/operations/bootstrap.md`). It is consumed and the file removed.

## 5. Readiness: what "ready" means

`GET /readyz` is the only unauthenticated route besides the UI. It answers `200` only when the node's own state says it can take traffic and `503` otherwise, with a closed JSON body: `{"ready":true,"version":"…","applied_cursor":{…}}` or `{"ready":false,"reason":"…"}`. It never carries an error string, path, address or credential, and unready answers carry nothing but the reason. A node is ready only when **all** of these hold on this node, read from its real state (not a listening port):

| `reason` when not | check |
|---|---|
| `restore_pending` | a disaster-restored installation has been activated |
| `schema_old` / `schema_newer` | the stored control-state format equals what this binary supports (old needs a migration, newer was written by a newer binary) |
| `sync_failed` | no replication group (the control group and every data group) has stopped after a failed durable write |
| `no_quorum` | every group completes one quorum read round now |
| `apply_lag` | no group has more than 256 committed-but-unapplied entries |
| `policy_stale` | no source revocation/retirement fence is still draining |
| `disk_pressure` / `disk_unknown` | disk usage is below the 90% deny-low level and the meter is readable. Leaving the deny-low level has a 2-point hysteresis (`internal/storage/pressure.go`): a node that reached it stays unready until usage falls to about 88%. 80% warns but stays ready; a platform without a meter is reported as unmetered and stays ready |
| `state_unavailable` | the local state could not be read at all |
| `starting` / `startup_hold` | the process is listening but storage has not opened yet (recovery, or the operator's startup gate) |

The HTTPS listener starts before storage opens, so during recovery a probe gets `503 starting` instead of a refused connection or an early "ready". `serve --startup-hold-file PATH` keeps storage closed (`startup_hold`) until `PATH` exists: use it as a volume-mount or unseal sentinel; only the file's existence is read. Results are shared for one second, so probing does not multiply the quorum reads.

`serve --authority-keys FILE --authority-dir DIR` (or the `--authority-s3-*` set; both or neither, full keys only) connects deletions to the independent restore authority so a restore of an older backup cannot revive deleted data; see [backup-restore.md](backup-restore.md#the-deletion-authority-c12-restore-authority). Without them serve runs deletions with no authority checkpoint.

`soundpost ready [--json] [--url https://127.0.0.1:8443] [--ca-cert PEM | --data-dir DIR]` asks the **running** server's `/readyz` with TLS verification (`--data-dir` only selects that installation's public `server.crt` as the trust root) and exits **0 only when the answer is 200 with `ready: true`**. Every other outcome — not ready, unreachable, untrusted certificate, malformed or inconsistent answer — exits 1 with a closed reason (`unreachable` when the server could not be asked). It deliberately does not open the data directory: a second opener would contend for the running process's database locks, and a read-only open of a replicated store says nothing about quorum. The container health check is this command.

## 6. Native acquisition is opt-in and never server-wide root

Host collection is a separate, optional unit, `deploy/systemd/soundpost-agent.service`, with its own account, state directory and credential. It starts with **no capability**; kernel-level CPU/off-CPU acquisition needs `CAP_PERFMON` and stays off until an operator uncomments it for a specific reviewed collector (the seccomp profile is `deploy/seccomp/soundpost-perf.json`). The server unit and the container never hold a capability, and nothing runs as root. The agent binary is `cmd/soundpost-agent` (`build release` builds it when present). The unit passes only the flags the agent registers (`-config`; `-once` and `-validate` are for manual runs). The source credential is not a flag: `agent.json` names it in `credential_file`, which must be the absolute path systemd gives the loaded credential (`/run/credentials/soundpost-agent.service/source.token`). `build/deploy_test.go` fails if the unit ever names a flag the agent does not define.

## 7. Verify an installation

```sh
go run ./tools/smoke install-single --artifact-dir smoke-out --release dist --binary dist/linux-amd64/soundpost
go run ./tools/smoke install-single --artifact-dir smoke-out --container soundpost:1.0.0
```

The smoke runs the produced static binary as a real subprocess (or the image as a real container; never `go run`), holds its start so the process is listening with storage closed, requires `soundpost ready` to exit 1 with `startup_hold` and `/readyz`, the UI and intake to be refused, then bootstraps over HTTPS, onboards a source, ingests a float metric, an integer-histogram metric, a log, an error and a span over authenticated ingest, runs a real PromQL query as a project reader, fetches the embedded UI assets (byte-compared with `web/dist`), force-kills the server, restarts it held again (not ready, intake not acknowledged), and requires the same five original receipts, the same query answer and graceful exit, 0700/0600 data modes and no credential in the service log. It writes `install-single.json` with no credential in it. The hold is how the unready window is made deterministic; it is not storage recovery taking a long time.
