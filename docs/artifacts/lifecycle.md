# Artifact lifecycle in the served process

`artifacts.Lifecycle` owns artifact references, the retention decision for a map and the read fences. `appcore.Open` builds exactly one, over the application's own artifact service (`appcore.NewArtifactLifecycle`, exposed as `App.ArtifactLifecycle`), and installs it in two places.

| Install point | Effect |
|---|---|
| read gate of `App.Artifacts` | every read (`Get`, `ReadAuthorized`, `ReadSourcesAuthorized`, the HTTP read operation) also fences on the organization delete generation and on the artifact's reference state, and uses the visibility-bound fragment cache (4 MiB) |
| `App.Retention` as its `References` source (`retention.Service.UseReferences`) | an expiry pass asks `LatestReference` before it erases an artifact root |

The retention service is built before the lifecycle, because the lifecycle takes it as its delete-generation source (`LifecycleConfig.Deletes`). `UseReferences` binds the source once after `retention.New`, in the style of `UseAuthority`; a second binding is a `Conflict` and replaces nothing, and `nil` is `Invalid`.

## What a retention pass does with a map

The upload's own deadline (`RetainUntil` of the manifest) makes a root a candidate for `EraseExpired`. The guard then asks `LatestReference`:

* a deletion that covers the root answers zero: **deletion takes precedence** over any live reference, and the root is erased by the deletion's own saga (the deletion path never consults references);
* the latest deadline of any unreleased reference (error occurrence, profile or build record; `Reference` without a deadline means 90 days, at most 10 years) or the upload's own deadline, whichever is later, holds the root: the pass keeps it;
* when nothing holds it, the answer is zero **and the GC fence is taken in the same control transaction as the last check**: the reference ledger is marked retired and the artifact intent moves from `published` to `retired` together (see below), the map is unreadable from that moment, no reference can be added to it, and the erasure that follows removes it. A reference racing the erasure either was seen by the check or is refused afterwards;
* a durable journal pin (below) answers "retained": the map is neither fenced nor erased;
* a reference ledger that does not verify (edited, removed, rolled back to an older valid copy) makes `LatestReference` fail. The guard error aborts the whole pass **before anything is erased**; `RunOnce` returns the typed fault and `WorkerStatus.LastError` carries its code. The next pass over readable state erases what has expired.

A retention service with **no** References source never erases an artifact root: nothing could prove the root fenced, and erasing it would leave a published intent over missing bytes. The root is kept, `WorkerStatus.UnfencedBlobs` counts it, and the pass does not fail (records expire as always). The served process always binds a source.

## The retired intent and restart

Startup validation (`control.Store.ValidateArtifactReferences`) requires the bytes of every `published` artifact intent: a published intent whose blob is missing or corrupt stays `corrupt` (control never repairs authority from missing files). The GC fence therefore flips the intent itself to `retired` in the **same** control transition that sets the ledger's retired flag, before retention erases anything. Control reads only the plain intent state (it cannot import `artifacts`); a retired intent is still validated for structure and reservations but owns no bytes, is never returned by `LookupArtifact`, and cannot be published again (a re-upload of the same root is a conflict).

Crash safety follows from the order: a crash after the fence leaves a **retired** intent over **present** bytes, an orphan the next pass erases (`LatestReference` answers zero for a retired root); a published intent over missing bytes cannot arise from the lifecycle. A ledger fenced by an earlier build over a still-published intent is healed to `retired` by the next lifecycle operation on it, but an installation already in that state, with the bytes erased, still fails startup validation.

## Snapshot pins

`artifacts.SnapshotPins` is answered by the real durable journal pins of the control group and of every data group (`storage.Engine.JournalPins`, `replica.Group.Pins`), which are what a backup in flight and the copy of a snapshot hold. The control group's pins are answered conservatively: **while any control pin is live every map is pinned**. A data-group pin is answered per root (`storage.Engine.RootPinned`): only a live pin of the data group that owns the root, and only if the root has evidence in the journal that pin protects, holds it. A backup pins the journal after its high-water mark (the highest application index it had processed per group), so a root with a fragment committed after that mark, which includes every root written while the backup runs, is held; a root whose fragments are all at or below the mark lies inside the snapshots the backup seals, is not held, and may be fenced and erased while the backup runs. A restore that revives such a root's published intent from the older control state retires it again at activation (`Lifecycle.ReconcileRetired`, before `RestoreReady`). A pin that recorded no root set (taken by an earlier build) holds every root of its group, and a root a pin did record stays held by it. Pins carry a lease; a pin left by a dead backup stops holding maps when it lapses or is dropped. A pin source that cannot be read is an error, never "no pin": the lifecycle reports `Unavailable` and the pass keeps the map.

## Not wired, and known gaps

* **The issue producer holds the maps its occurrences name.** The leader-only issue producer runs under the system principal (D1), which holds `issues.write` and cannot hold `artifacts.write`, so it does not call `Reference`: before it applies a batch of error occurrences it calls `Lifecycle.HoldIssues` (one ledger entry of kind `issue` per issue and map, deadline = the project's audited error retention from the lifecycle clock, rolled forward by later occurrences), and every pass it calls `Lifecycle.SettleIssues`, which reads the committed issue book in the same control transaction and drops the holds of an issue that is resolved or ignored and takes them again when it reopens (only while the map is still retained: a late hold never revives an elapsed map). A name in a frame that is no published map of the project is skipped. `Reference`/`Unreference` (user or server-token scope, `artifacts.write`) remain for build and profile usage and are reachable from Go code and the smoke only. A ledger that does not verify stops the issue producer of that project (fail closed: the hold is taken before the occurrence is applied, the checkpoint does not move). An occurrence that names a map before it is published, an issue re-pointed by a grouping migration (kept until its hold deadline) and more than 32 distinct maps per issue are not held.
* **The profile producer holds the maps retained profile chunks name (09.04-W3).** The leader-only `ProfileMapProducer` (same system principal, same reason as above) scans the project's profile records and, for each profile whose frames carry an `artifact_id` that is a canonical artifact ID, calls `Lifecycle.HoldProfiles`: one ledger entry of kind `profile` per (profile, map), cursor = the profile root with index 1, deadline = the project's audited profile retention from the lifecycle clock. Nothing releases it early; it lapses by its deadline, and a late hold never revives an elapsed, retired or deleted map. A frame name that is not an artifact ID (a module path) is ignored. Limits: progress is an in-memory checkpoint per data group (a restart or leader change rescans the retained profiles once; holds are idempotent); a project whose retained profiles exceed 64 MiB to scan in one pass is refused as `too_large`; a ledger already holding 1024 usages of one map has no room and the hold is counted as skipped.
* **Reads follow the effective retention (D-new C07).** The scope check every read runs (`auth.Scope.ValidateArtifactState`) refuses a map only when the later of the upload's own deadline and every unreleased reference has elapsed, using the same verified ledger as `Lifecycle.EffectiveRetention` (`internal/artifacts/refledger`). An elapsed map is `not_found` with detail `retention_elapsed`; a GC-fenced one is plain `not_found`; a ledger that does not verify refuses every read of the project's maps as `corrupt`. A reference with no deadline retains for the audited source-map retention of the project (`retention.Resolve`, per-organization and per-project versions), 90 days without one.
* A ledger removed together with its project-index entry is detected by an anchor over the index bytes; a retired intent over a ledger that is missing or not fenced is `corrupt`. Removing the ledger, the index and the anchor of a project together reads as a project that never had references (control-state integrity, the same boundary as the intents themselves).
* A published intent under a verified GC fence (left by an earlier build that erased the bytes, or by an older control snapshot) is retired by startup validation instead of refusing to start.
* A published intent whose root a deletion that is not held covers (an entity deletion naming it, `retire_project`, `retire_org`) does not need its bytes at startup: a completed deletion erased them, the read gate already refuses the root, and the intent stays `published` (only an expiry or a fence retires it). Without this rule the process refused to start (`corrupt`) after the first completed deletion of a published artifact (independent review of 10.09, F1). A deletion that is held keeps its bytes, so its intents are verified as before.
* The expiry pass runs at most hourly (`WorkerConfig.ExpiryInterval`), so an expired map stays unerased until the next pass.
* The lifecycle reads the wall clock, the same clock `retention.New` defaults to; a test that needs time travel must restart the process or wait.
