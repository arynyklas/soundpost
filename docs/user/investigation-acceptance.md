## Accessibility decisions observed

`web/e2e/accessibility.spec.ts` runs first-party DOM audits (`web/e2e/support/audit.ts`: interactive names, form labels, heading
order, landmark uniqueness, status text, ARIA references, SVG/table alternatives, document language and title, contrast) over every
page the app renders, and real keyboard checks. No third-party audit library was added.

- The DOM audits found **no** defect in the committed pages (names, labels, landmarks, heading order, contrast all passed on first
  run). They are proven to have teeth separately: each of nine defects injected into the live page is reported under its own rule.
- The real keyboard checks found four defects; 1 to 3 were observed red first (`05.09-red-web.txt`) and then fixed:
  1. The skip link pointed at `#main`, but the address hash is the router: activating it destroyed the scope and moved no focus.
     It now moves focus to the main landmark and leaves the address alone.
  2. After a section change, focus went to a heading that only said `Investigation`. It now reads `Investigation: <section>` and the
     page title follows the section.
  3. After opening an incident, trace, replay or other entity from its form, focus stayed on the submit button. It now moves to the
     entity's heading once it exists.
  4. Going Back from an entity left focus on a removed element; focus now lands on the section heading (asserted in the same test as
     item 3, so it was not separately observed red).
- Every `LoadState` reachable on a real server says its state in words, uses `role=status` (`alert` for not-found, rate-limited and
  error) with the matching `aria-live`, and passes the audit: loading (the real answer, delayed), ready, empty, not found,
  not available, partial. Under an emulated achromatopsia the words, not colour, carry the state. `error` and `rate_limited` were
  produced by a **transport fault injected in the browser** (one request answered 500 / 429), not by the server. `stale` cannot be
  produced by any committed route; it is covered only by the server-rendered unit test `web/src/app/accessibility.test.ts`.
- Reduced motion: under `prefers-reduced-motion: reduce` no animation, transition or smooth scroll runs, even against an author rule
  that tries to animate (control: the same rule animates when motion is allowed). The rule itself already existed in `style.css`.
- Conflict dialog: verified in Chrome on a real incident (opened by the runner from an ingested error, found through `POST /api/v1/queue`):
  the losing person's alert takes focus, the DOM audit is clean, and the keyboard reaches and operates "Reload the current incident".

## What was looked at

Headless Chrome screenshots of the audit pages, the journey legs and the load states (also under achromatopsia) were opened and
looked at for the error state and the replay leg: the state words and the focus ring on the heading and on the Step button are
visible, and the investigation controls sit far below the account-administration panels, so a keyboard user depends on the skip
link and the heading focus to reach them. The other screenshots were produced and used by the automated checks but were not
individually reviewed by eye. No Firefox or WebKit rendering was seen.

## Known limits

- The session boundary remounts the whole investigation view on every address change, so held state in the view is reset on
  navigation. This was observed (it is why focus is restored on mount) and was not changed.
- A hashed asset is cached as immutable only when its file name carries an 8+ character hash that includes a digit or capital letter;
  a build whose hash is all lowercase letters is served `no-store` (correct, merely uncached).
- Native deep links live in the URL fragment, so the server never sees them; the shell is public and every data read behind a deep
  link is authenticated. There is no server-side path fallback: an unknown path is a 404, never the shell.
