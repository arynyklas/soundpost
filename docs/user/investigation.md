# Investigation reads and what each state means

The investigation console reads Soundpost's own scoped API (`POST /api/v1/investigate`, `GET /api/v1/capabilities`). Every read is authorized by the server for your own account. Choosing an organization, projects, time zone and window in the console is navigation, not access.

## Scope

- The bar at the top of the investigation area always shows the organization, projects, environment, time zone and window the current view was computed for.
- The scope is kept in the address bar as organization/project IDs, nanosecond timestamps, the time zone name and the section. Back and forward restore it. Query text, credentials and telemetry values are never placed in the address.
- Windows are half open: the start is included, the end is not. Timestamps stay exact decimal strings.
- The environment is selected by its ID (empty means all). The server applies it: the **Services** view lists only the services an active source policy admits in that environment, and a service that policy does not list in it is **Not found**. Other views do not have an environment dimension yet and show every environment; the bar says which environment was asked for. Telemetry (metric names) cannot be narrowed to one service or environment, so a narrowed Services view marks that part **Not available** instead of showing a project-wide answer in its place.
- A project or organization that does not exist, that you may not read, or that was revoked is shown as **Not found**. The console cannot and does not tell these apart. Changing scope discards what was loaded for the old scope; a slow answer for an earlier scope is dropped and never drawn.

## States

Every view shows exactly one of these, spelled in words (never colour alone):

| State | Meaning |
| --- | --- |
| Loading | The read for the current scope has not answered. Nothing from any other scope is shown. |
| Ready | The requested data is complete for the window. |
| Empty | The read completed with nothing missing and found nothing. It is not a health signal. |
| Partial | The answer is real but incomplete: some data did not answer, or some parts of the view are not available. Missing data is not zero and not healthy. |
| Stale | The newest data is older than expected. Treat figures as possibly out of date. |
| Not available | The service behind this view (or a separate grant it needs) is not available in this installation. This is never presented as empty or successful. |
| Not found | The selection does not exist or is not available to your account. |
| Signed out | Your session ended. Sign in again. |
| Rate limited | Too many requests; wait and retry. Nothing was changed. |
| Error | The request failed. The request ID shown can be given to your administrator. |

## What is available today

- **Services**: there is no separate service registry. A service exists while an active source policy of a selected project lists its ID among the services it admits (so it appears as soon as a source is onboarded for it, and is not found if no policy admits it). A service page shows its identity, the environments and builds those policies admit, the dependency names they declare (declared, not observed), the readable evidence sources, and its **current health**, which is read only from stored evidence: **failing** when an open incident is linked to the service, **degraded** when no open incident is linked but at least one active condition (firing, or recovering with its hold running) names the service, **healthy** when neither exists. Only a typed link names a service (the incident's service link, a condition's linked IDs): a label, a name or a timestamp is never read as one. Each incident and condition is listed with a link to its own page. If the installation cannot read incidents and conditions, or your account may not, the health part is **Not available** with the reason and the service is never shown as healthy. Release records (labels, ancestry) need an organization-administrator account, so the page lists the builds and points to Releases. Telemetry for one service is **Not available** (the query engine has no service dimension).
- **Trace**: a link is shown only when your scope can resolve the trace. The console has a trace page that reads `POST /api/v1/traces/view`; the `/api/v1/investigate` seam still answers **Not available** for some kinds, so a view reached only through the seam may show a link without content. The critical path also states two limits that live outside the spans: **late spans** (a span its producer reported more than five seconds after it ended; it stays in the analysis exactly as recorded, with its report time shown) and **producer gaps** (loss records of the producers that sent a span of this trace, for the signal span, over the time the trace covers: how many spans never reached storage, from which producer and for which reason). Which trace the lost spans belonged to cannot be known, so a gap says spans may be missing; it never adds or repairs a span, and a trace read across a gap is not marked complete. A read that could not reach some shards and found nothing in the others is **Partial**, never an empty answer.
- **Trace view bounds**: one trace view carries at most 100,000 path edges. A longer list is cut at that bound and the view says so (state **Incomplete**, reason `edges_truncated`, an `edges` section): the critical path then covers only part of the trace, and a missing edge is not proof that no work happened. The loss records read to find the producers of a trace are bounded at 50,000; past that the read stops and the view reads **Incomplete** (`spans_partial`) instead of scanning without limit. A replay or profile link whose grant check could not be made (an authorizer failure, as opposed to the grant being absent) fails the whole read; it is never shown as an unavailable target.
- **Queue and incidents**: every row is a real committed incident, visible as soon as it is committed (not held for a digest). The alert condition (what the source reports), the issue workflow and the incident response (what people decided) are separate badges and timelines. Through the `/api/v1/investigate` seam, **issue workflow, delivery attempts, the digest, urgency and unread changes** remain **Not available** until their services are wired there. A missing denominator is shown as **Rate unknown** with the observed count and freshness, never as 0%.
- **The `/api/v1/investigate` kinds**: `queue`, `incident`, `issue`, `release`, `job`, `service`, `trace`, `replay` and `profile` are the closed set. `queue` lists the committed incidents of the requested projects (open first, then severity, newest activity, ID; at most the requested limit, and **more** says the list is cut). `incident`, `issue`, `release` and `job` need a target ID and answer one typed summary (identity, state names, versions, counts; never telemetry or label text); an erased, missing, guessed or out-of-scope target is the one **Not found**. `release` and `issue` need organization administration, otherwise the answer is **Not available** with the reason `release_records_need_org_admin` or `issue_evidence_needs_org_admin`. A kind whose owner is not wired in the installation is **Not available** with its own reason (`incident_source_not_wired`, `job_service_not_wired`, `release_reader_not_wired`, `issue_evidence_view_not_built`), never an empty list. The full views stay on their own routes.
- **Release and issue over the route**: `POST /api/v1/investigate` derives a project-read scope for its caller (it never selects the organization-administrator scope), so through the route `release` and `issue` always answer **Not available** with the reasons above, even for an administrator. The records themselves are read through `POST /api/v1/evidence/release` and `POST /api/v1/evidence/issue`, which do derive the administrator scope. The two kinds read an administrator scope only where one is handed to the investigator directly (for example by another in-process service).
- **Explore, issues, jobs, releases, replays and profiles** are separate console pages with their own API routes (for example `POST /api/v1/jobs/list`, `/api/v1/jobs/view`, `/api/v1/replays/stream`, `/api/v1/profiles/view`); the pages live in `web/src/explore`, `issues`, `jobs`, `releases`, `replays` and `profiles`. They answer for your own scope and show **Not available**, **Not found** or an empty result under the rules above. Whether they have data depends on what your installation ingests: the SDKs do not currently enqueue replay chunks or profiles (`docs/acceptance/reference-journeys.md`). The seam's replay and profile kinds still need separate grants and are **Not available** without probing for the target.
- **Explore profiles and feature sets**: the console does not carry a copy of the pinned PromQL and LogQL profiles. Explore reads them from `GET /api/v1/query/profiles` before it shows a query form: every accepted profile with its language, the features its feature sets enable, and every registered feature set (identifier and enabled features) in committed order, the registry the engine itself resolves requests against. The route holds no tenant data and carries no profile configuration, so any signed-in account may read it; without a session it answers 401. A feature set is chosen by the exact combination of features you enable, never computed; a combination the profile does not register has no feature set and the form says so. If the registry cannot be read (or is not a consistent registry) Explore shows that state and no form: it never falls back to a guessed set.
- **Saved views**: Explore keeps a query only when you press Save, and then stores it on the server, owned by one project (`POST /api/v1/saved-views`, a JSON body, never a URL). The saved text is readable by every account that holds telemetry.read on the owning project, and only by them: a reader whose grant is revoked loses the list at once, and a wrong organization, an unreadable project and an absent view are the same Not found. Anyone who can read a project's views can open them; changing or deleting a view takes its owner or an organization administrator, and a stale revision is refused (409), never merged. A view has a name (1 to 120 bytes), the query text (1 to 16384 bytes, stored exactly as typed), the profile and registered feature set, the projects it runs over (up to 16, all readable by you, one of them the owner), the evaluation mode and, for LogQL, the page size and order. A project keeps at most 100 views and refuses another rather than dropping one. A query over a restricted raw source is not saved. Saving or deleting is audited (who, which view, which project) without the name or the text, and neither changes the organization's policy epoch, so a save never disturbs a live stream or an export. Deleting a project deletes its saved views. Opening a view fills the form with what was saved; a profile or feature set the server no longer registers, or a project outside the selected scope, is refused with the reason instead of being switched or dropped. **Export** downloads the project's views as a JSON document (`soundpost.saved-views`, version 1) exactly as the server lists them.
- **Project settings**: the source capabilities your account may read, per project (a project without a readable source is Empty), and the progress of a restriction, revocation or deletion operation you look up by ID. Notification destinations, retention, source policy, SSO and organization/team administration are **Not available**; no destination secret is ever shown.

A restricted raw source appears only to its named readers; other readers of the same project never see it, its counts or its discovery results.

Values from telemetry are shown as plain text; they are never interpreted as HTML.

## Acting on an incident

Assign, acknowledge, resolve, link evidence, report impact, snooze, end a snooze, start maintenance and end maintenance need organization administration of the incident's organization. The actor is always your signed-in account; no field of the request can name another actor, origin or organization.

- Every action names the revision you were looking at. If someone else committed first, the server applies nothing, tells you the current revision and does not retry. Your typed reason stays in the form until you reload the incident and submit again. Nothing is shown as committed before the server acknowledges it.
- If the connection fails after an action was sent, the outcome is **unknown**. **Resend the same request** is safe: the server returns the original result instead of applying the action twice.
- Acknowledging pauses reminders only; the source stays firing and is still shown as firing. A worse impact is still eligible to notify unless an active maintenance window suppresses it.
- Resolving while the source is firing needs a reason and leaves a persistent banner: the incident was resolved by a person, the source was not recovered.
- Snooze and maintenance are separate, expiring, reasoned windows. Neither hides the source, the timeline or ingestion problems.
- Operation progress: **fencing** is pending (reads are denied but the fence is not complete) and is never success; **held** and **failed** are not success; a logically complete deletion is not physical erasure, and the physical and backup deadlines are the real ones the server holds.

## Live tail and request logs (SO-04)

- A live stream is opened in two steps: `POST /api/v1/live-tickets` carries the selector, projects and expression in its body and answers a single-use ticket; `GET /api/v1/live?ticket=<id>` carries only that ticket. Nothing but the ticket is ever in the URL; any other query parameter is refused.
- The server writes no per-request access log (no handler logs `RequestURI`, the URL or its query), so no query string, the ticket included, reaches a Soundpost log. Each response carries an `X-Request-ID` header that identifies the request without the URL.
- A reverse proxy or load balancer in front of the server is outside that guarantee. Configure it to strip or not log the query string of `/api/v1/live`. A logged ticket is already spent after its stream opened, or expires unused, and it opens nothing without the caller's own session cookie, CSRF header and `Origin`.
