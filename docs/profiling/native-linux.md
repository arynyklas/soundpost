# Native Linux profiling

The native capability probe is not a profiler or a qualification certificate. It opens and immediately closes a disabled, fixed perf CPU event for each requested process, reads host permission settings and fixed scheduler tracepoint ABI IDs, and attempts disabled tracepoint opens. It never changes sysctls, escalates privileges, samples a workload, or returns invented samples. Support means this narrow event-open check succeeded, not that callchains, scheduler correlation, overhead or loss have been qualified. Frame/thread coverage remains unmeasured.

CPU acquisition requests 99 Hz, at most 128 frames, a 100 ms reorder window and at most 64 MiB acquisition/export memory. Native event timestamps have an explicit boot/host monotonic domain. Process-start plus namespace and generation identities prevent PID-reuse joins. Engine sample deltas are not OS nanosecond durations and cannot be added as the same unit.

The closed sanitized union permits only CPU addresses, numeric scheduler events, mapping/build identities, loss and target-generation events. Strict decoding rejects unknown fields. No command names, environment, register/stack byte arrays, heap, locals, object values or argument values are accepted. A future kernel ring may transiently contain kernel ABI names/paths: acquisition must skip these in place, never copy them to diagnostics/socket/export, and never persist raw perf.data. No ptrace or memory-unwind fallback is permitted.

Only authorized scheduler participants have nullable TaskKeys; idle/foreign identities are omitted. A missing switch-out callchain is explicit rather than reconstructed from an unrelated stack. Mapping updates bind a process identity without an invented TID, and per-CPU loss needs no invented task. Native CPU metadata separates software-CPU-clock period nanoseconds from hardware cycles and engine samples; callchain context markers are never instruction addresses. Throttle/unthrottle evidence is distinct from lost sample counts. Coverage validators reject unmeasured nonzero claims. Monotonic zero is a valid time in its explicit domain; identity/generation zero is not.

`Open` remains an explicit acquisition dependency error on Linux until task04.02 authorization/resource accounting and task04.03 helper/ring acquisition deliver real sessions. Capability probe success must not be presented as end-to-end capture. Non-Linux calls return typed unsupported results.

Run only against an authorized local workload:

```
go run ./fixtures/nativeperf/capability --probe-only --target-pid "$TARGET_PID"
```

The fixture resolves namespace/process-start identity locally and prints only capability metadata (no samples). Qualification rows in `fixtures/nativeperf/qualification.json` stay `not_run` (kernel build and configuration null) until a real runner exercised them; once one did, the row pins the exact kernel build, the digest of the configuration it was built with (`/proc/config.gz` or `/boot/config-<release>`), the toolchain and the runtime build flags (the 6.1 and 6.6 LTS amd64 rows are pinned; `TestShippedManifestPinsTheKernelBuildConfigAndFlagsOfEveryExercisedRow` enforces it). The arm64 LTS rows are `out_of_release_scope`: decision D10 limits this release to linux/amd64, so they are not exercised, not claimed and not required by the gate (`release_platforms`; `TestShippedManifestIsTheReleaseGateInput`). WSL is functional evidence only, not Linux LTS production qualification. Public fixtures must never include customer inventory or private process data.

Linux ABI constants/layouts are independently authored from the Linux perf_event_open manual and kernel trace event documentation, linked in the manifest. No GPL scheduler implementation, third-party profiling engine, restricted corpus or raw kernel buffers are redistributed. First-party files are Apache-2.0; the kernel remains an OS prerequisite.

## Qualification matrix, acceptance runner and measured limits (task 04.09)

Qualification is evidence, never a probe result. Four first-party commands under `fixtures/nativeperf/` produce it; every row they write is one of `supported` (exercised on this host, criterion measured and met), `unqualified` (cannot be exercised here, exact reason recorded), `not_run`, `denied`, `error` or `failed`. A row that was not exercised, was denied or errored can never be `supported`: `qual.Row.Validate` rejects it, and the release gate re-validates every report it reads.

```
cc -O2 -pthread -fno-omit-frame-pointer -g -o fixtures/nativeperf/acceptance/workloads fixtures/nativeperf/acceptance/workloads.c
go run ./fixtures/nativeperf/acceptance --manifest fixtures/nativeperf/qualification.json \
    --workload fixtures/nativeperf/acceptance/workloads --duration 60s --seed 451 \
    --endpoint-env SOUNDPOST_FIXTURE_API --out acceptance.json
go run ./fixtures/nativeperf/overhead --manifest fixtures/nativeperf/qualification.json --hz 99 --seconds 120 --repeats 5 --out overhead.json
go run ./fixtures/nativeperf/qualification --manifest fixtures/nativeperf/qualification.json --results acceptance.json,overhead.json --require-all
```

* `acceptance` starts the real `nativeperf.Helper` in its own process, sends a signed grant over its private socket and reads the sanitized stream with its own decoder. Frames are resolved by a verifier-side ELF symbol lookup over snapshots of the target's `/proc/<pid>/maps`; addresses outside the workload executable stay unresolved. It never exports to a node (04.08 covers export, storage and read privacy); `--endpoint-env` only records that an external endpoint was named.
* The workload (`workloads.c`) has a named hot function, a 200 ms timed sleep, pipe and futex waits woken by a foreign process, two threads pinned to one CPU, a migrating thread, an exec, a build without frame pointers and a 16-thread fan-out. It records every blocking interval, CPU phase and runnable delay itself with `CLOCK_MONOTONIC` and verifies its own ground truth. Threads and the foreign waker are created before the `ready` line and parked until `exit`, because the helper treats a thread or process creation or exit inside a live capture as a coverage change and ends the session.
* Before the real path runs, the capture checker (`qual.CheckCapture`) must reject a staged `acquisition_pending` session and capability, a successful empty session, a synthetic perfect-cadence sampler and two no-op samplers, and must accept a plausible capture. A report that lacks these controls is rejected by the gate. A genuine permission denial stays a distinct typed failure.
* The `acceptance` exit codes are 0 (every required row supported), 1 (an exercised row failed), 2 (usage), 4 (the checker accepted a contaminated capture) and 10 (required rows unexercised). `qualification --require-all` prints every unqualified required row and exits 10 or 1; without `--require-all` it only writes the machine report. Node success never qualifies Bun, amd64 never qualifies arm64, and a functional-evidence row never qualifies an LTS row.
* The runtime fixtures (`fixtures/nativeperf/runtime/{python.py,node.mjs,bun.ts}`) use the exact C09 supplements (`startProfile` in `packages/node` and `packages/bun`, `start_profile` in `sdk/python`). Their samples are runtime engine samples in their own column; they are never native engine output and never OS CPU time. The native capture of the same process is taken independently by the helper.
* `overhead` alternates baseline and capture runs, reports the target's CPU per iteration and throughput separately from the collector's CPU (helper process and client), and evaluates the budgets (<= 3% workload CPU, <= 64 MiB combined helper+client+ring memory) as constants it never adjusts. A run shorter than 120 s or with fewer than 5 repeats is marked reduced and is never promoted to the full result. The combined memory is the helper's resident high-water mark, this client's resident high-water mark since that capture began (the client reads the stream into counters and keeps no event, and resets its own high-water mark before each capture) and the rings accounted again on top (one per thread of the target, data plus metadata page; they are resident in the helper only as far as they were touched, so this counts them twice on purpose). Each fixture's `detail.memory_ledger` breaks the worst run down (helper resident split anonymous/file/shmem, client size at capture start, rings). A fixture whose target cannot fit the session's fixed 256-descriptor ceiling (one ring per thread plus 5, so at most 251 threads) is refused at admission with `resource_limit`, as the plan requires, and the report records it as `admission_refusal` with the arithmetic instead of a measurement.

### Measured on this host (WSL2, kernel 6.6.87.2-microsoft-standard-WSL2, amd64, paranoid=2, root)

* CPU: real software CPU-clock samples at 99 Hz through the signed-grant helper process; the hot function `spqual_hot` appears in the frame-pointer callchains and is resolved by the verifier-side ELF lookup. Frame coverage of the true call chain is about 1.00 with frame pointers and about 0.40 without (the frames the unwinder cannot see are absent, never invented).
* Injected limits: a 4 KiB ring with a stalled reader produced explicit loss events; `RLIMIT_NOFILE` in the helper child and tiny `MaxMemory` values were refused with the closed code `resource_limit` and released every FD.
* Overhead (full approved command, `cpu` fixture only): -0.34% +- 0.57% workload CPU (budget 3%), throughput +0.37%, collector 4.6% of one core, about 36 MiB combined helper+client+ring memory (budget 64 MiB). The 16-thread fan-out fixture was only measured in short development runs and is not advertised.
* Scheduler off-CPU, runqueue split and blocked-time rows are **unqualified**. tracefs is readable as root in this session and the scheduler tracepoints open and fire, but their raw PIDs are init-namespace PIDs and this distribution runs in another PID namespace (`/proc/self/ns/pid` inode is not 4026531836), so no authorized task ever matched: a scheduler session succeeded and stayed empty. The engine now refuses instead. As a non-root user tracefs is denied (`EACCES`). A rerun on a host in the initial PID namespace (hostPID) is required; the capture/correlation runner exists but has never produced attributed events.
* Scheduler stream protocol (wave 13, found on real kernels 6.1.0-54 and 6.6.162): the live stream carries the initial topology proof, then **progress proofs**, then the final proof. A progress proof (`"progress": true`) certifies that one pass over every scheduler and CPU ring, begun at boot-clock time `T`, found all of them empty, so everything admitted through `T` was already delivered; it is emitted at most every 10 ms while the rings are drained and its `through` strictly advances. The client applies each one where it arrives (`ReportProgress` for every CPU, then `Advance`), which is what drains the correlator's bounded reorder buffer (about 511 events per 16 MiB reserved, 1022 per 32 MiB: 100 ms of reorder window of a contended CPU holds hundreds of events). Without them a capture of more than a few hundred scheduler events overflowed the buffer, every overflow revoked all scheduler coverage and cleared the task states, and the runnable delay of a contended CPU was reported as about 0.4% of the truth (blocked time dominated). A source never emits one while a CPU sample or scheduler event is still waiting, and a CPU sample that is newer than a waiting scheduler event leaves after it, so a lagging reader cannot starve the scheduler stream. Both kernels are `PREEMPT_DYNAMIC` booted in voluntary mode: a tick-preempted task is reported with `prev_state=R` (0), not `R+` (0x100) (tracefs, sched_switch); both are runnable delay.
* Correlator coverage scope (wave 14, real kernels 6.1.0-54 and 6.6.162): a switch-in of a task whose switch-out was never retained (it was already off the CPU when the capture began, or its state was revoked earlier) is a missing baseline of THAT task. The correlator returns one task-scoped correction for it (`Interval.Correction`, the task's `TaskKey`, reason `coverage_unmeasured`, from the start of the epoch to the switch-in) and leaves every other task's retained state and returned intervals alone. It used to revoke the whole domain and clear every task's state; with three or more tasks taking turns on a CPU (two pinned workers and their coordinator) every following switch-in then lacked a baseline again and the revocation repeated for the rest of the capture (52 to 208 domain-wide revocations in 4 s with no record loss and no buffer overflow, which scored runnable delay at 0.2% to 99% of the ground truth). Explicit loss, clock, identity-generation, unknown-CPU, overflow and task-capacity evidence still revoke the whole domain. After the change every real capture shows exactly one task-scoped correction per thread that was first seen switching in, and no domain-wide one.
* The engine ends a session at the first thread or process creation/exit in the target (`thread_coverage_changed`); runtimes that create threads dynamically are therefore only partly capturable. Node and Bun native captures were refused with `resource_limit` in the recorded run (cause not investigated); Python 3.12.3 produced genuine native samples, all inside the interpreter binary (stripped, unresolved).
* Ring memory bound (investigated in wave 9): every perf ring (256 KiB of data plus a metadata page by default) is locked memory. The kernel lets an unprivileged-for-`CAP_IPC_LOCK` process map `perf_event_mlock_kb` (516 KiB) times the online CPUs plus `RLIMIT_MEMLOCK` of rings in total. On an 8-CPU VM at the default 8 MiB `RLIMIT_MEMLOCK` the 48th ring failed with `EPERM`, so a 64-thread target (64 rings, 16.6 MiB) could never be mapped and used to end as the opaque `acquisition_failed` after every perf event was already opened. The helper now computes this bound from the live limits and refuses such a capture up front with `resource_limit` (and reports a mapping `EPERM` as `resource_limit` too). The maximum thread count is therefore `(RLIMIT_MEMLOCK + 516 KiB x CPUs) / (RingBytes + page)` (47 on that VM) unless the helper holds `CAP_IPC_LOCK`, runs with `perf_event_paranoid=-1` or has an unlimited `RLIMIT_MEMLOCK`; a deployment profiling wide thread pools raises `LimitMEMLOCK` of the helper unit. The FD cap of 256 (rings plus target FDs) is a second, independent bound.
* Transparent huge pages (D53): the helper calls `prctl(PR_SET_THP_DISABLE, 1)` as its first action, before it allocates, so its resident size does not depend on the host's THP mode (on a 6.1 host with THP `always` the Go heap of the helper sat on 2 MiB pages and held about 7.7 MB more). The setting is per process and needs no privilege; `deploy/seccomp/soundpost-perf.json` allows `prctl` only for option 41 with argument 1, and the privacy source audit admits only that call. The overhead memory formula (helper VmHWM + client VmHWM + nominal ring bytes, budget 64 MiB) is unchanged.
* Syscall surface of the helper (wave 20): `ppoll` (the per-event ring exit probe) is allowed only with `nfds == 1` and a NULL signal mask in its own seccomp rule, and the bulk allow rule's name set is pinned by `internal/config/manifest_test.go`. The privacy policy mirrors both calls: the source audit accepts exactly `syscall.Syscall6(SYS_PPOLL, fds, 1, ts, 0, ...)` and `SYS_PRCTL(41, 1)` with literal arguments, and the dynamic `strace -f -v` audit now traces `prctl` and `ppoll` too (only `PR_SET_THP_DISABLE, 1`, the runtime's/canary's own thread and VMA naming, and nfds 1 + NULL sigmask are admitted) and fails as vacuous unless the real run shows the helper process's THP opt-out (and, in a scheduler capture, the ppoll probe). The report lists every audited `perf_event_open` attribute under `syscall_audit.perf_event_open_attributes`.

### End-to-end check of the real helper binary

`fixtures/nativeperf/helper-e2e` starts the built `cmd/soundpost-perf-acquire` for real: as root it installs a root-owned operator policy at the helper's fixed path `/etc/soundpost/perf-policy.json` (refusing to overwrite an existing file, removing it and any directory it created afterwards), runs the helper as a child with its socket in `/run/soundpost-perf`, opens a signed CPU capture against a controlled workload through `nativeperf.OpenAuthorized`, counts real samples, then reads the helper's `/proc/<pid>/status` (`THP_enabled` must be `0`) and requires it to exit 0 on SIGTERM. The driver never calls `prctl` itself and fails unless its own `THP_enabled` is `1`, so the helper's `0` cannot be inherited. The fixture operator key is derived from a documented public seed; `operator-policy.json` carries only its public half. Run it as root on a Linux host that may create `/etc/soundpost` and `/run/soundpost-perf`:

```
go build -o /tmp/helper ./cmd/soundpost-perf-acquire
go build -o /tmp/helper-e2e ./fixtures/nativeperf/helper-e2e
cc -O2 -fno-omit-frame-pointer -g -fno-pie -no-pie -pthread -Wl,--build-id -o /tmp/loop fixtures/nativeperf/cpu/loop.c
sudo /tmp/helper-e2e --helper /tmp/helper --workload /tmp/loop --policy-template fixtures/nativeperf/helper-e2e/operator-policy.json --seconds 10
```

It prints one JSON line (kernel, `thp_sysfs_enabled`, `driver_thp_enabled`, `helper_thp_enabled`, `helper_seccomp`, `helper_no_new_privs`, `helper_vmhwm_kb`, `cpu_samples`, loss counters, `helper_exit_code`, `pass`) and exits non-zero when `THP_enabled` is not `0`, no sample arrived or the helper did not exit cleanly. Recorded on a 6.6.162 kernel with THP `always [madvise] never`: `helper_thp_enabled: 0`, driver `1`, about 1980 samples in 10 s, helper exit 0 (`.superpowers/sdd/approved-product/l4w20-evidence/helper-e2e/`).
* Not run: arm64 (out of release scope, decision D10: this release is linux/amd64; the arm64 matrix rows are `out_of_release_scope`, never passed and not required by the gate), bare-metal hardware (the runners are KVM guests) and a real Kubernetes cluster (none was available; only the Compose recipe and a DaemonSet-shaped Docker run were recorded). The Linux 6.1.0-54 and 6.6.162 amd64 runners ran the full acceptance (`--host-scenarios cpu_hotplug,container_modes,python_trampolines,runtime_db_wait`, 60 s, seed 451) with the runtime columns CPython 3.12.16/3.13.18/3.14.10, Node 22.21.1, Node 24.11.0 and Bun 1.3.14 (rows pinned in `fixtures/nativeperf/qualification.json`: kernel build, configuration digest read from `/boot/config-<release>`, toolchain and runtime build flags; results in `docs/support/native-linux.md`).
* Permission matrix (04.02-C12, `fixtures/nativeperf/permission-cases.json`, 9 cases): seccomp, host capability, LSM (AppArmor ptrace mediation with the audit line on both kernels; a BPF-LSM program on `perf_event_open` on 6.1 only, since 6.6's LSM list has no `bpf`), tracefs mount, tracefs DAC (denied, then granted with the same account), target visibility (hidepid x capabilities x uid) and the real helper under the shipped unit all have an independently evidenced denied case and a passing control. `Probe` reports a tracefs the caller may not read (the default root-only 0700 mount) as off-CPU/runqueue split `denied` with reason `permission_denied`; an absent tracefs stays `unsupported`/`tracefs_unavailable`; a lookup that mixes both is the permission denial; CPU capture stays supported independently. Granting off-CPU to a CAP_PERFMON-only account needs tracefs access (group access plus a traversable `events/` view, or a host-wide `gid=`/`mode=` option on the single global tracefs superblock) and, with the shipped unit, `ProtectKernelTunables=no` when a unit-private view is used.
* CPU hotplug (04.09-C17): a scheduler capture ends with `topology_changed` (the proof instant is carried and the correlation revoked from it) when a CPU leaves or joins the online set or a per-CPU event stops counting (an offline+online cycle leaves the kernel's per-CPU events off; the helper reads their enabled time once per 100 ms round to notice); CPU captures continue and name no sample from the offline CPU. `acceptance --host-scenarios cpu_hotplug` (root, at least 4 online CPUs, restores the online set) took the highest CPU offline on both runners; its result is in the support doc.
* Container and namespace modes (04.06-C16, 04.09-C19): `--host-scenarios container_modes` runs ten real captures in disposable namespaces (nested target with the helper in the initial PID namespace, helper inside the target's PID namespace, exec, cgroup move, layer overlay, replaced executable, mount-namespace swap, mount unshare, PID reuse across a namespace boundary, a `/proc` of another PID namespace) and eight negative controls. NSpid decision: scheduler capture outside the initial PID namespace stays refused (`event_unavailable`; the kernel hides outer PIDs from inside a namespace, so NSpid cannot map them); CPU capture across a PID-namespace boundary is allowed only when proven (`/proc` is the helper's own and the target's `ns/pid` link agrees with its `NSpid` chain; `ErrPIDNamespaceUnproven` otherwise). Hybrid cgroup v1+v2 hosts resolve the cgroup2 mount from mountinfo. Docker (host PID, private PID, private cgroup namespace) and the repository Compose recipe were run on a 6.12 host as record-only rows.
* CPython trampolines and a native extension (04.09-C13): `--host-scenarios python_trampolines` captures a CPython 3.12, 3.13 and 3.14 process with the interpreter's perf trampoline off and on: CPU sample counts and rates agree, the native extension `spnative` is resolved from its own ELF through the product's module+offset (`spext_hot` leaf, `spext_mix` and `spext_burn` in the chains: the extension keeps a frame record in its leaf), and the trampoline frames are announced as `jit_or_anonymous_map_unavailable` and left unresolved; no perf-map name or path reaches the stream and only the interpreter touches the map.
* Scheduler-mode overhead (04.04-C15, 04.09-C23), measured on the final tree with the full approved run (120 s x 5, fixtures `cpu` and `fanout16` with `--capture-mode offcpu`, collector and workload pinned to two CPUs): 6.1.0-54 `cpu_offcpu` -0.64 +- 0.64% and `fanout16_offcpu` 0.71 +- 0.42% workload CPU, 39.2 / 49.9 MB combined memory; 6.6.162 0.02 +- 0.84% and 1.13 +- 0.80%, 36.3 / 45.0 MB. The 3% workload-CPU and 64 MiB budgets apply unchanged to these two fixtures (they are advertised fixtures and the gate fails the row when over budget) and were met; fanout16 throughput falls 13-14% because the collector and the workload share the pinned CPUs, and correlator overflows are explicit loss. CPU-mode numbers (cpu, fanout16, fanout64) are in `docs/support/native-linux.md`.
* Release gate scope (04.09-C29, D10): `fixtures/nativeperf/qualification.json` advertises the five fixtures (`cpu`, `fanout16`, `fanout64`, `cpu_offcpu`, `fanout16_offcpu`; the CPU-mode and scheduler-mode overhead reports are separate runs and the gate pools them, refusing a duplicate or an unbound one), requires the scenarios `cpu_hotplug`, `container_modes`, `python_trampolines` and `runtime_db_wait`, the runtime columns `python@3.12`, `python@3.13`, `python@3.14`, `node@22`, `node@24` and `bun` (a requirement may name a version prefix of whole components; Node success never qualifies Bun) and the release platform `linux/amd64`. `qualification --require-all` over the two runners' reports exited 0: both amd64 LTS rows qualified, no unqualified required row, the two arm64 rows listed as `out_of_release_scope`.
* Database wait (04.09-C15): every runtime column (each CPython, each Node, Bun) takes a separate capture of at least 10 `pg_sleep(0.2)` queries against a real PostgreSQL 16.16 (image `postgres:16`, trust auth, over the LAN); the blocked-time lower bound is the hold time the server itself reports in the same statement, and the row is judged against it and the runtime's own round trips (the HTTP wait phase stays a second capture).
* PID reuse: numeric PID reuse was **steered** (`fixtures/nativeperf/identity/smoke -steer-ns-last-pid`, which writes `ns_last_pid` only inside a disposable `unshare --pid --fork --mount-proc` namespace) on 6.1.0-54 and 6.6.162: the reused PID resolves to a different process start and generation, and a mutant that drops the process start joins the generations (`real_pid_reuse_joined`). Unforced reuse in the host namespace was **not observed** in 256 attempts (`actual_numeric_pid_reuse_not_observed_within_budget`); it is reported, not claimed (`.superpowers/sdd/approved-product/l4w29-evidence/nativekernel/pid-reuse/`).
* PID reuse in the qualification runner: `tools/qualify` (`native_identity`, capability `pid_reuse`) forces the reuse the same way (`unshare --pid --fork --mount-proc identity/smoke --steer-ns-last-pid`: only `ns_last_pid`, only inside the disposable namespace; the host PID namespace and `pid_max` are untouched) when it is run as root with `SOUNDPOST_QUALIFY_HOST_MUTATION=1`, and the row says it forced the cursor. Without that opt-in the smoke runs unforced (a 4096-attempt run on 6.1.0-54 with `pid_max` 4194304 ends `actual_numeric_pid_reuse_not_observed_within_budget`) and the row is `not_exercised`, never a pass.
* CPU hotplug (`fixtures/nativeperf/hotplug`, qualify capability `cpu_hotplug`): the harness takes a real CPU (never cpu0) offline and back under live captures of a real workload through the helper as a child process. It needs root and `SOUNDPOST_QUALIFY_HOST_MUTATION=1` and restores the CPU on every exit path (the runner checks and restores the online set too). A scheduler capture over a changed topology must end with the closed code `topology_changed` and no final proof, and the consumer revokes from the last proof the stream names (`proven_through`), never a silently complete capture; the per-thread CPU capture owns no per-CPU stream and keeps delivering; a capture opened afterwards on the same helper completes over every online CPU. The scheduler source notices a CPU that went away and came back between two looks at `/sys/devices/system/cpu/online` from the kernel's own state of its per-CPU events (`read_format` TOTAL_TIME_ENABLED of the scheduler events: an event bound to a CPU is detached when that CPU goes offline and its `time_enabled` stops, `internal/nativeperf/sched_liveness_linux.go`). Before that check, 5 of 10 flaps of a sparse target on 6.1.0-54 completed with a final proof over a dead ring; after it 12 of 12 were refused (`.superpowers/sdd/approved-product/l2w20-evidence/L2w20NatPid/`).
* Recipes run on real hosts (wave 31, `.superpowers/sdd/approved-product/l4w31-evidence/NativeA/`): `fixtures/nativeperf/helper-smoke/drive` runs the five helper-smoke scenarios (authorized, denied, expired, fd-cap, cancel) plus a 3 s real capture against the real helper as a child process (6.1.0-54, 6.6.162), as the installed `packaging/systemd/soundpost-perf-acquire.service` under real systemd (LimitCORE 0, CapabilityBoundingSet/CapEff/CapAmb = CAP_PERFMON only, Seccomp 2, NoNewPrivs, MemoryMax 64 MiB, TasksMax 16, a LimitNOFILE drop-in for fd-cap) and as a container entrypoint under `deploy/seccomp/soundpost-perf.json` (Docker 26.1.5, kernel 6.12.74, record only, not a qualification row). `deploy/sandboxprobe` shows allowed calls reaching the kernel and denied calls failing in the unit and the profile, and fails against units/profiles missing one protection. Container findings: the helper image needs the host `/etc/machine-id` read-only (without it every capture is refused as an invalid target identity; compose and Helm mount it); Docker's default AppArmor profile denies ptrace-read of host PIDs (audit `apparmor="DENIED" operation="ptrace" profile="docker-default"`, capability reported denied, also at `perf_event_paranoid=2`); on that Debian 6.12 host with `perf_event_paranoid=3` the probe reports CPU denied for PERFMON alone and for PERFMON+SYS_PTRACE+DAC_READ_SEARCH while a privileged container is allowed (the exact extra capability was not isolated); with paranoid 2 and AppArmor unconfined the PERFMON-only container under the audited seccomp profile captured 591 samples in 3 s.
* CPU event attributes request executable-mapping `MMAP2` sideband records (path bytes stay in the kernel ring and are never copied; `privacy/policy.json` allows `mmap`/`mmap2` on the CPU event only and requires them zero on the scheduler event).
