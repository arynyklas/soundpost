# Report: Product and licensing research

# Keep + Sentry product reuse research

Research date: 2026-11-03. Primary official sources only; live documentation/default branches, not a pinned legal bill of materials. Research, not an architecture decision or deployment recommendation. Product intent: an own OSS platform, not merely installing an alternative; custom first-party frontend/backend SDKs and compatibility protocols remain undecided.

## Executive findings

- **Strongest permissive reuse candidates:** Keep's MIT core for alert/workflow mechanics, GlitchTip's MIT backend for error tracking, and SigNoz's MIT core for observability. Each has different product/security boundaries; do not treat its entire repository or enterprise feature set as MIT.
- **Do not describe current Sentry server or Bugsink as OSI-approved OSS.** Sentry's current core is FSL (eventually Apache-2.0); Bugsink is PolyForm Shield with an explicit noncompete covering even free competing products. They are useful benchmarks and potentially separately operated integrations, not clean default foundations for this competing OSS product. Sentry SDK licensing is a separate matter: Sentry says its SDKs use MIT, with third-party exceptions. [Sentry policy](https://open.sentry.io/licensing/), [Bugsink license](https://github.com/bugsink/bugsink/blob/main/LICENSE).
- **Important isolation trap:** GlitchTip's published onboarding says any organization member can view/modify projects; teams determine notifications. That is not the requested team-scoped data access. Keep's custom-role Keycloak integration, SigNoz fine-grained RBAC, and OpenObserve fine-grained RBAC/source maps have commercial boundaries. A team dropdown or project tag is not authorization.

## License and feature comparison

### Keep

**License:** MIT outside `ee/`; `ee/` has a commercial subscription license requiring a valid subscription for production and substantially restricting copying/distribution. MIT is OSI-approved; the EE license is not. [Root license](https://github.com/keephq/keep/blob/main/LICENSE), [EE license](https://github.com/keephq/keep/blob/main/ee/LICENSE).

**Capabilities:** Official docs cover alert deduplication, fingerprints, manual/AI/topology correlation, incidents, workflow automation and provider integrations. Sentry, Grafana/Loki, Prometheus and OpenObserve providers are already listed. These are alert/incident and external context integrations, not evidence Keep itself supplies a full logs/traces/metrics store or JavaScript source-map/error-symbolication engine. [Official documentation index](https://docs.keephq.dev/llms.txt), [incident overview](https://docs.keephq.dev/incidents/overview.md), [workflow overview](https://docs.keephq.dev/overview/workflow-automation.md).

**Access boundary:** The official authentication matrix identifies DB predefined roles/resource permissions as OSS; Keycloak custom roles, LDAP and resource-level permissions as EE. Generic OIDC is OSS with predefined roles but no resource-based permissions in that matrix. Do not assume all SSO or RBAC is paid, or that OSS authentication proves team-data isolation. Verify exact desired permissions against selected core paths. [Authentication matrix](https://docs.keephq.dev/deployment/authentication/overview).

**Reuse assessment [INFERENCE]:** Good reference/reuse source for normalized alerts, provider adapters and workflow concepts; selectively review code paths and dependencies, excluding EE. No need to recreate every provider. AI/correlation feature availability must be audited per implementation; docs alone do not establish which are MIT.

### Sentry self-hosted

**License:** Main web-app components use **FSL-1.1-Apache-2.0**, expressly not OSI-approved. Each version changes to Apache-2.0 after two years; this does not make the latest server OSS today. SDKs are MIT according to policy, subject to component/dependency notices. Commercial competing offerings using FSL code are restricted. Assess actual license text for any chosen version and use; do not infer permission to build a competitor from permission to self-host internally. [Licensing policy](https://open.sentry.io/licensing/), [actual server license](https://github.com/getsentry/sentry/blob/master/LICENSE.md).

**Capabilities:** Rich issue grouping/fingerprints and SDK error investigation are established features; source maps/debug artifacts, tracing and alerts make it the closest functional benchmark. [Grouping](https://docs.sentry.io/concepts/data-management/event-grouping/), [JavaScript source maps](https://docs.sentry.io/platforms/javascript/sourcemaps/), [alerts](https://docs.sentry.io/product/alerts/), [organization/team management](https://docs.sentry.io/organization/).

**Self-hosted limits:** Official docs describe a Docker Compose blueprint with no guarantees/dedicated support; minimum 4 cores, 16 GB RAM plus 16 GB swap, 20 GB disk, with 32 GB RAM recommended. They explicitly exclude closed-source Seer/other AI/ML, billing-linked features and some platform symbol sources. Therefore the licensing site's aspiration to feature parity is not literal complete self-hosted parity. [Self-hosted documentation and exclusions](https://develop.sentry.dev/self-hosted/).

**Reuse assessment [INFERENCE]:** Benchmark and optional adapter target; do not copy current server code into the OSS platform by default. MIT SDK reuse is legally/technically distinct from server reuse. An older version that has converted to Apache-2.0 is a possible legal branch to investigate, not a recommendation to inherit an old server and its maintenance/security burden. No promise of infrastructure-metrics replacement or exact team-isolation semantics is made here.

### GlitchTip

**License:** Backend's current license is **MIT**, granting modification/distribution/commercial rights with notice. Audit frontend, CLI and dependencies independently before incorporating them. [Backend license](https://gitlab.com/glitchtip/glitchtip-backend/-/raw/master/LICENSE).

**Capabilities:** Sentry-client-compatible error capture, issues, performance monitoring and uptime monitoring are advertised. Project alerts support frequency conditions, team email and webhook recipients. JavaScript source-map uploads with debug-ID injection are documented through GlitchTip CLI (marked beta). Fingerprint grouping is explicitly documented in its release history. [Product](https://glitchtip.com/), [error tracking/source maps/alerts](https://glitchtip.com/documentation/error-tracking), [CLI](https://glitchtip.com/documentation/cli), [fingerprinting announcement](https://glitchtip.com/blog/2023-07-15-glitchtip-3-3/).

**Critical access limitation:** Published getting-started docs say any organization member can view and modify organization projects; project teams control who receives notifications. Separate organizations may be a boundary, but mapping those to the desired admin-wide/team-scoped experience needs investigation rather than assumption. [Official team semantics](https://glitchtip.com/documentation/getting-started/).

**Reuse assessment [INFERENCE]:** Best permissively licensed specialist candidate to study before writing error ingestion/grouping/source-map handling from scratch. It is not evidenced as a complete Keep-style incident workflow system or unified infrastructure logs/metrics store. Sentry API compatibility does not guarantee envelopes, every SDK feature, native symbolication, replay, profiling or tracing parity.

### Bugsink

**License:** Current default is **PolyForm Shield 1.0.0**, with exceptions for `ee/`, older Sentry BSD code, icons and other third-party files. Its noncompete prohibits providing a competing product, including free products and different interfaces/platforms. It is source-available, not OSI-approved OSS; the existence of some BSD/MIT files does not relicense Bugsink as a whole. [Actual license](https://github.com/bugsink/bugsink/blob/main/LICENSE).

**Capabilities:** Error-focused Sentry SDK ingestion, issue triage, normalized grouping/custom fingerprints, releases, email and multiple webhook/chat notification integrations. Source maps use uploaded artifact bundles/debug IDs through `sentry-cli`; docs require Bugsink 2.0.14 or newer and explicitly avoid runtime fetching for deterministic/security reasons. [Docs/index and integrations](https://www.bugsink.com/docs/), [grouping](https://www.bugsink.com/docs/grouping/), [source maps](https://www.bugsink.com/docs/sourcemaps/).

**Access:** Superusers have global control; team/project admin members manage settings/membership, team admins imply project administration. The permissions page labels the model beta/subject to change. Do not infer a fully audited data-isolation guarantee from these administration rules. [Permissions](https://www.bugsink.com/docs/permissions/).

**Reuse assessment [INFERENCE]:** Useful operational/product benchmark for a focused error tracker; avoid server-code incorporation for the competing product without separate permission. No primary evidence in this research establishes a general logs/metrics/distributed-tracing backend or Keep-equivalent incident automation.

### SigNoz

**License:** **MIT Expat** outside `ee/` and `cmd/enterprise/`; those directories use a separate enterprise license. Do not label the complete enterprise distribution MIT. [Root license](https://github.com/SigNoz/signoz/blob/main/LICENSE), [EE license](https://github.com/SigNoz/signoz/blob/main/ee/LICENSE).

**Capabilities:** Unified OTel-based traces, metrics, logs, exceptions and alerting. The current exception docs are unusually precise: exceptions come from **span events, not log records**, grouped by service/type/message, linking to traces and correlated span logs. A self-host collector option changes grouping to service/type only. This differs materially from Sentry-style stack-based issue grouping. Newer OTel log-based exception instrumentation can therefore fail to populate this view unless routed/duplicated to spans. [Overview](https://signoz.io/docs/what-is-signoz), [exception ingestion/grouping and limitations](https://signoz.io/docs/userguide/exceptions/).

**Access/commercial boundary:** Current pricing puts fine-grained RBAC in enterprise beta and multitenancy as enterprise coming soon; its RBAC announcement explicitly says enterprise plans only. Basic dashboard access control is not equivalent to underlying telemetry restrictions. These are moving product claims, so recheck before selection. [Pricing matrix](https://signoz.io/pricing/), [RBAC announcement](https://signoz.io/blog/fine-grained-rbac-for-observability/).

**Reuse assessment [INFERENCE]:** Strong candidate to integrate as an OTel telemetry investigation backend instead of building storage/query/exploration. Exception views do not establish Sentry source-map/debug-artifact parity; no source-map server capability was confirmed here. Fine-grained isolation cannot be assumed in Community Edition.

### OpenObserve (pertinent telemetry alternative)

**License:** Public core root license is **AGPL-3.0**, an OSI-approved copyleft license, not permissive MIT/Apache. Modifying/incorporating covered code can entail source obligations, including AGPL network-interaction requirements. Enterprise capabilities must not be assumed covered by the public core license. [Core license](https://github.com/openobserve/openobserve/blob/main/LICENSE), [official repository/features](https://github.com/openobserve/openobserve).

**Capabilities:** Logs, metrics, traces, RUM, alerting and dashboards; RUM error tracking/source-map resolution exists, but official current source-map docs explicitly mark it **Enterprise only**, requiring sourcemaps RBAC permissions. It is therefore incorrect to present OpenObserve's full error investigation feature set as AGPL core. [RUM source-map guide](https://openobserve.ai/docs/user-guide/data-exploration/rum/source-map).

**Isolation:** Organizations are documented logical boundaries for data/users/access and have distinct ingestion org identifiers. OSS mode allows authenticated users to create organizations; enterprise organization management is RBAC controlled, with unrestricted root. Fine-grained RBAC is documented in the enterprise context. [Organizations and mode differences](https://openobserve.ai/docs/user-guide/account-administration/identity-and-access-management/organizations), [RBAC](https://openobserve.ai/docs/user-guide/account-administration/identity-and-access-management/role-based-access-control).

**Reuse assessment [INFERENCE]:** Plausible integrated telemetry backend alternative, especially where org separation fits; not evidence of permissive reusable source-map/error engine. Evaluate API integration separately from copying/deriving AGPL code; no blanket legal claim that a process boundary automatically resolves every obligation.

## What to build vs integrate — recommendations, not final architecture

1. **Build the distinctive product experience:** unified incident/error investigation records, evidence links/correlation, shared service/environment/release identity, ownership and admin/team policy, urgent notifications plus queue/digest, and metadata-first privacy controls. [INFERENCE] These requirements cross the documented boundaries above and are not shown to be solved by a single OSS edition.
2. **Investigate reuse before implementing specialist internals:** Keep MIT provider/workflow pieces and GlitchTip MIT backend error/grouping/source-map paths deserve focused code evaluation. Compare semantics and extensibility rather than simply iframe/embed their UIs. Keep the source/license provenance per imported file.
3. **Integrate telemetry storage/query where viable:** SigNoz Community or OpenObserve core are evidence-backed logs/traces/metrics candidates; selection depends on isolation, license preference, operations and API requirements, not a presumed feature-equivalence table. Sentry/Bugsink can remain external targets where legally appropriate, without importing their restricted server code.
4. **Keep SDK decision open:** an own frontend/backend SDK can expose product-specific context and safe defaults, wrap/reuse permissively licensed SDK instrumentation, or implement chosen standards/protocols. Owning an SDK does not require inventing a wire format. Conversely, accepting Sentry envelopes does not implement source maps, grouping, trace semantics, replay, attachments or SDK remote configuration. Scope interoperability by tested feature/language/version, not a generic “Sentry compatible” promise. [SDK license policy](https://open.sentry.io/licensing/).
5. **Treat privacy and isolation as end-to-end:** error messages, stack locals, breadcrumbs, URLs, user fields and source artifacts can contain secrets even without request bodies. [INFERENCE] Metadata-only must define allowed fields and artifact access explicitly. None of the product marketing statements above proves these requested defaults or authorization invariants; test APIs, artifact downloads, search, notifications and external deep links under team/admin identities before relying on integration.

# Report: SDK, ingestion, and privacy research

# Application ingestion: evidence, minimum contracts, risks

Research date: 2026-11-03. Official live documentation, not an interoperability test. **Updated user decision: fully custom SDK + protocol and ownership of the entire data stack/engines, with replay, profiling and multiple isolated organizations.** Comparisons below remain historical research context, not recommendations to reuse standard SDKs or require Sentry compatibility. SDK versions must be pinned when evaluating prior art: current Sentry docs describe new `dataCollection` / `data_collection` controls whose defaults differ materially from older `sendDefaultPii` guidance.

## Executive distinctions

- **Sentry SDK compatibility** buys existing error capture, structured frames, integrations and build tooling, not Sentry's server-side grouping, symbolication, release workflows or UI. An envelope receiver alone is not a Sentry replacement.
- **OTel/OTLP** supplies vendor-neutral signals and correlation. Its exception convention carries type/message and usually a language-native stacktrace string; it does not define Sentry-style issue grouping or source-map artifact management. Current conventions are migrating exceptions from span events to logs; a receiver expecting only one loses real inputs.
- **A branded first-party SDK is a separate option**, not synonymous with reinventing instrumentation or requiring Sentry wire compatibility. It can expose the product's privacy/API contract while wrapping Sentry capture or OTel instrumentation/exporters. Fully custom runtime capture and transport is substantially more responsibility (details below).

## 1. Minimum Sentry-compatible backend contract

### Transport / routing

Support DSN-derived `POST {base}/api/{project_id}/envelope/`, project/key validation and the authentication methods used by supported SDKs: `X-Sentry-Auth`, query `sentry_key`/`sentry_version=7`, and, if advertised, envelope `dsn`. Keys in browser DSNs are public ingestion identifiers, **not read/admin credentials**. Authentication docs explicitly deprecate DSN secrets. Route tenant/project from validated credentials, not untrusted event tags. [Authentication](https://develop.sentry.dev/sdk/foundations/transport/authentication/)

Parse UTF-8 JSON envelope headers followed by item headers and raw payloads; `length` is **bytes**, not characters; omitted length ends at newline. Mixed items and binary attachments make `split('\n')` insufficient. Honor compression at HTTP level and apply decompressed limits. Unknown item types/headers must not make supported error items disappear; the envelope spec requires gracefully skipping/retaining unknown items and forwarding unknown attributes in relays. Browser submissions may use `text/plain` to avoid preflight as well as `application/x-sentry-envelope`. [Envelope spec](https://develop.sentry.dev/sdk/foundations/envelopes/)

For a deliberately error-only supported profile, explicitly configure clients not to emit unwanted replay/profiling/attachments/etc.; still recognize envelopes containing `event`, `client_report`, and incidental items such as `session` rather than rejecting the entire upload. Return real admission failures instead of a blanket success that silently discards errors. Current Sentry limits include 1 MiB error/transaction items and 200 MiB decompressed envelopes; these are reference limits, not a requirement to allocate that much. [Envelope spec](https://develop.sentry.dev/sdk/foundations/envelopes/), [item types](https://develop.sentry.dev/sdk/foundations/envelopes/envelope-items/)

The old `/api/{project_id}/store/` JSON endpoint is a **legacy compatibility extension**, not sufficient for modern SDKs. The old store documentation now redirects to transport; authentication docs retain a store example. Do not promise legacy encodings/compression without testing a declared old-client matrix. [Transport](https://develop.sentry.dev/sdk/foundations/transport/), [authentication](https://develop.sentry.dev/sdk/foundations/transport/authentication/)

### Error data and grouping

Preserve event identity/time/platform, severity, exception chain/type/value/mechanism, structured stack frames, release/dist/environment, SDK identity, tags, optional fingerprint and trace context. Frames are oldest-to-newest, attached to exception/thread; preserve `filename`, function/module, line/column, `in_app`, plus debug metadata needed for symbolication. `vars`, absolute paths and source context are privacy-sensitive, not mandatory for readable frame structure. [Frame schema](https://develop.sentry.dev/sdk/foundations/envelopes/event-payloads/stacktrace/), [error schema](https://develop.sentry.dev/sdk/telemetry/errors/)

Implement **your own documented grouping semantics** or explicitly adopt a server implementation. Sentry computes default fingerprints server-side from stacktrace/exception/message; an SDK does not deliver Sentry's finished grouping algorithm. Preserve explicit fingerprint arrays and define expansion of `{{ default }}` if claiming this feature. Normalization/versioning matters: changing grouping changes issue identity. [Fingerprinting](https://docs.sentry.io/platforms/javascript/enriching-events/fingerprinting/)

### Releases / source maps

Keeping `release` and `dist` is necessary metadata, not symbolication. Browser/TS minified frames require exact generated artifacts, maps and matching identifiers; current Sentry build tools inject Debug IDs by default, with legacy release/path association alternatives. A third-party service needs an artifact acceptance/lookup contract and mapping engine. Existing `sentry-cli`/bundler plugins use additional authenticated server APIs: envelope compatibility does **not** establish upload-tool compatibility. A custom artifact upload API/build plugin is a valid alternative, but not drop-in tooling parity. Source maps may embed proprietary source via `sourcesContent`; source uploads need separate privacy/access/retention policy. [Source maps](https://docs.sentry.io/platforms/javascript/sourcemaps/)

### Browser / propagation / backpressure

Browser capture includes default global `onerror` and `unhandledrejection` handlers. Node needs its own runtime/framework handling; the browser integration explicitly only works for Browser/Deno. Do not use the browser integration's availability as evidence of Node parity. [GlobalHandlers](https://docs.sentry.io/platforms/javascript/configuration/integrations/globalhandlers/)

Support CORS on the ingestion host, including preflight where needed and exposing response rate-limit headers. Separately, application API servers must permit propagated headers from browser origins. Sentry uses `sentry-trace` + `baggage`, **not automatically W3C `traceparent`**. Current spec adds `propagateTraceparent`, default false. Both header families must refer to the same active trace if used together. Propagation targets must be allowlisted; baggage is not a trusted tenant/user authorization carrier. Sentry propagation can continue even with span collection disabled; an error trace ID does not prove corresponding spans exist. [Propagation spec](https://develop.sentry.dev/sdk/foundations/trace-propagation/)

Return `429` + `Retry-After`; implement category-aware `X-Sentry-Rate-Limits` if needed, including headers on successful responses. Categories differ from envelope item names. SDKs discard during backoff rather than providing a durable queue. Current client-report spec says HTTP error responses discard the envelope; 429 and 413 must not be retried. Network failures may be retried. Receive `client_report` counters (`reason`, `category`, `quantity`) to distinguish no errors from capture loss. Browser JavaScript must be allowed to read these headers (CORS expose). [Rate limits](https://develop.sentry.dev/sdk/foundations/transport/rate-limiting/), [client reports](https://develop.sentry.dev/sdk/telemetry/client-reports/), [transport](https://develop.sentry.dev/sdk/foundations/transport/)

## 2. What defaults actually send

| Runtime | Officially documented defaults and privacy caveats |
|---|---|
| Python | Legacy/no `data_collection`: filtered request headers, full URLs/query strings, eligible incoming bodies (`max_request_body_size='medium'`), source context and frame-local variable names/values. Cookies/user identity/IP generally off with `send_default_pii=False`, but that flag is **not metadata-only**. Current docs warn that merely passing a `data_collection` dictionary switches unspecified categories to more permissive defaults: cookies, identity, query and AI content can become enabled. Set every relevant category intentionally. Disable bodies (`max_request_body_size='never'` and/or body categories), locals and source context explicitly. [Python data](https://docs.sentry.io/platforms/python/data-management/data-collected/) |
| Browser JS | Current docs say all `dataCollection` categories enabled with sensitive-key filtering. URLs/queries, referrer, device/runtime and console breadcrumbs are collected. Browser headers normally Referer/User-Agent; browser cookies require optional `httpClient` integration. Client JS does not capture frame locals. Current docs describe IP collection enabled unless `userInfo:false`; payload control does not stop the ingress server seeing network source IP. Replay is separately opt-in/configured and not controlled by `dataCollection`. Wizard-configured source maps are uploaded at build time. [JS data](https://docs.sentry.io/platforms/javascript/data-management/data-collected/) |
| Node/server JS | Incoming request headers/cookies and request bodies can be attached to errors/spans; current body defaults include framework-specific data such as tRPC input, Remix forms, Next.js server-action outputs. Explicit `setUser()` data is still sent regardless of inferred-user controls. Framework/version-specific audit is necessary; browser defaults cannot be applied to Node. [Node data](https://docs.sentry.io/platforms/javascript/guides/node/data-management/data-collected/), [JS data](https://docs.sentry.io/platforms/javascript/data-management/data-collected/) |
| Rust | `send_default_pii` false; filtered incoming headers in actix/tower, cookies/IP not automatic by default. **Actix can still collect JSON/form bodies without PII enabled**, subject to conditions/size. Disable with `MaxRequestBodySize::None`. Loaded debug-image metadata can be enabled by default; source upload is explicit. Panics, manual errors and integrations are supported, but not identical feature/default sets to Python/JS. [Rust data](https://docs.sentry.io/platforms/rust/data-management/data-collected/), [Rust SDK](https://docs.sentry.io/platforms/rust/) |

Sensitive-key scrubbing cannot detect secrets in exception messages, arbitrary log text, URLs or values under innocuous keys. Some docs rely on **Sentry server-side scrubbing** in addition to SDK filtering: a third-party receiver does not inherit that protection. The dynamic live docs are not evidence for every currently deployed SDK major.

### What “metadata-only” can mean usefully

A defensible allowlist can retain service/build/environment, event/trace/span IDs, exception class, deliberately templated error code/message, normalized route, status/duration and sanitized frame module/function/file/line, plus bounded safe tags. Remove free text messages or template them; omit request/response bodies, headers/cookies, query/fragment, user data, locals, console/log text, DOM/UI breadcrumbs, source snippets, AI content and arbitrary `extra`/context/attachments. Runtime/device detail should also be explicitly decided. Preserve normalized safe breadcrumb categories/timestamps/status only if desired.

This is a **product privacy definition**, not an SDK switch or a promise that stack traces are non-sensitive. Paths/function names can reveal identities or business details; stable IDs are linkable metadata. Source maps/native symbols are code artifacts, not runtime request payloads, and need a separate explicit exception if allowed. Disabling maps does not prevent collecting errors, but produces poorer minified investigations. Redaction must occur before serialization/network egress for a true no-payload-leaves-app guarantee; server scrubbing only protects downstream storage. Error-only `beforeSend` cannot by itself cover spans, logs, breadcrumbs, replay and artifact uploads; configure/transform each enabled signal. [Python collection](https://docs.sentry.io/platforms/python/data-management/data-collected/), [JS collection](https://docs.sentry.io/platforms/javascript/data-management/data-collected/), [frame schema](https://develop.sentry.dev/sdk/foundations/envelopes/event-payloads/stacktrace/)

Rust native crash reporting is a separate opt-in surface: current docs specify `minidump` support since 0.49.3 for Linux/macOS/Windows and a separate crash-reporter process. Dumps may contain memory/passwords; Sentry's own postprocessing/deletion guarantees do not apply to another backend. Supporting Rust panic events does not imply supporting minidumps, debug-file upload or symbolication. [Rust native crashes](https://docs.sentry.io/platforms/rust/native-crash-reporting/)

## 3. OTLP / OTel minimum contract and limits

- OTLP defines stable traces/metrics/logs over gRPC and HTTP, protobuf or OTLP JSON. HTTP defaults are `POST /v1/traces`, `/v1/logs`, `/v1/metrics`; gzip/identity, size limits **after decompression**, correct response message/content type and signal-specific partial-rejection counts matter. JSON trace/span IDs are hex, unlike ordinary protobuf JSON bytes. Use full/partial success truthfully. Partial-success responses must not be retried; retryable HTTP codes are 429/502/503/504; other 4xx/5xx are non-retryable. OTLP acknowledgements are hop-by-hop, not end-to-end durability guarantees. [OTLP specification](https://opentelemetry.io/docs/specs/otlp/)
- Retain Resource and instrumentation Scope along with signal identity, timestamps, severity, attributes, trace/span IDs, span parents/links/status and metric type/temporality. This is the context needed for joins, not just `exception.message`. Product tenancy/auth is an additional receiver/collector configuration contract, not established by a `service.name` string. [OTLP proto schemas](https://github.com/open-telemetry/opentelemetry-proto), [logs data model](https://opentelemetry.io/docs/specs/otel/logs/data-model/)
- Current exception convention recommends exception LogRecords linked to corresponding span context, `exception.type`, `exception.message`, `exception.stacktrace`. Message is explicitly sensitive. Existing instrumentation should preserve span events unless opted into `OTEL_SEMCONV_EXCEPTION_SIGNAL_OPT_IN=logs` or `logs/dup`; dual mode requires duplicate awareness. The stack is a language-native **string**, not a guaranteed structured frame/causal-chain contract. Some details/event naming are still development status. [Exception logs convention](https://opentelemetry.io/docs/specs/semconv/exceptions/exceptions-logs/)
- OTel exception conventions do not themselves guarantee global unhandled capture, source maps, error grouping, handled/unhandled mechanics, release artifact resolution or breadcrumbs. A collector/OTLP receiver is not an error tracker by itself. Browser OTel instrumentation is officially **experimental and mostly unspecified**: evaluate exact JS components rather than treating backend OTLP maturity as browser capture maturity. [Browser guide](https://opentelemetry.io/docs/languages/js/getting-started/browser/)
- Exceptions encoded only inside sampled spans can disappear with span sampling. Independent correlated exception logs avoid that coupling only if their own filters/export queues retain them. Trace IDs without recorded spans must be supported as incomplete context, not manufactured complete traces. [Exception convention](https://opentelemetry.io/docs/specs/semconv/exceptions/exceptions-logs/), [Sentry propagation](https://develop.sentry.dev/sdk/foundations/trace-propagation/)

## 4. First-party SDK choices (including user interjection)

| Choice | Practical contract / benefit | Remaining responsibility / risk |
|---|---|---|
| Branded wrapper over official Sentry capture | Product `init`, capture/error-code, safe context, privacy preset and correlation API; retain existing Python/framework and browser/Node capture/stack parsers. Can target a Sentry-compatible receiver or a custom transport/normalizer. | Pin/upstream-test supported SDKs. SDK upgrade defaults can widen collection. These rows are engineering deductions from the cited protocols/runtime behavior, **not a selected architecture**. A first-party public API and upstream instrumentation can coexist; product identity does not require a new wire protocol.

### Cross-option operational acceptance questions, not implementation steps

- **Privacy:** Is a disallowed value ever materialized/enqueued or only deleted before send? Are unknown enrichment fields dropped by allowlist? Does console/object serialization invoke getters/repr and leak secrets? Does diagnostic/drop reporting obey the same policy?
- **Failure isolation:** SDK outages and callback exceptions must not break application logic; avoid recursive self-capture. OTel explicitly forbids unhandled runtime exceptions and prioritizes losing telemetry over changing application behavior. [OTel error handling](https://opentelemetry.io/docs/specs/otel/error-handling/)
- **Delivery:** Bounded queue and event/attribute/stack limits, asynchronous export, bounded flush on shutdown, browser unload/offline losses, sampling/backpressure visibility. Do not promise all critical-path telemetry arrives merely because it is captured. Sentry and OTLP differ on retries; a custom protocol needs declared retry/backoff/idempotency semantics rather than assuming one. [Sentry transport](https://develop.sentry.dev/sdk/foundations/transport/), [client reports](https://develop.sentry.dev/sdk/telemetry/client-reports/), [OTLP](https://opentelemetry.io/docs/specs/otlp/)
- **Overhead:** Bundle bytes, initialization/patching cost, per-request hooks, stack serialization and symbolication work, breadcrumb buffer and queued payload memory are separate costs. No primary evidence here establishes a universal numeric budget. Wrapper size is upstream feature selection plus wrapper, not just wrapper bytes; experimental browser OTel is not automatically smaller. Benchmarking selected versions/builds would be necessary before numerical claims.
- **Correlation:** Choose/bridge propagation deliberately; browser CORS, cross-origin allowlists, async request-local context, queues and sampling all affect end-to-end joins. A trace identifier is correlation, not authorization, completeness, or permission to view another team's data.

## Evidence gaps / uncertainty

No runtime/browser acceptance tests or version-specific source audit were performed. Live docs surfaced new SDK collection controls and a Rust minidump feature; these must not be projected onto older installed versions. Legacy store protocol details and compatibility with Sentry release/artifact APIs were not validated. No claim is made that Sentry SDK transport compatibility, OTel support, or using a branded wrapper automatically supplies Sentry-equivalent issue semantics. The remaining product choice is which compatibility/privacy promises to offer, not whether every protocol must be implemented.

## 5. Updated decision: custom SDK/protocol, replay/profiling, isolated organizations

The Sentry/OTLP receiver details above are comparative contracts only. **The product's first-party protocol is selected; Sentry wire compatibility is not.** Reusing standards as references does not delegate ownership of the product's SDK or engines. No external storage/query engine recommendation is made here.

### Browser runtime hard boundaries

- Global errors and rejected promises need distinct capture hooks; non-Error rejection values, browser stack differences, causes, duplicate capture and deliberately muted cross-origin errors remain custom SDK responsibilities. Source-map artifact identity must be in the custom protocol even though its shape need not match Sentry.
- Browser CPU sampling is constrained by runtime APIs, not solved by owning the SDK. Official Sentry docs report JS Self-Profiling availability only in Chromium (Chrome/Edge) and require response `Document-Policy: js-profiling`. Unsupported browsers must be reported as unsupported, not silently represented as zero CPU usage. Long tasks/timings are useful but **not equivalent to sampled CPU stacks**. [Browser profiling](https://docs.sentry.io/platforms/javascript/profiling/)
- The WICG API has finite sample buffers, `samplebufferfull`, resource/frame/stack/sample tables, time-origin-relative timestamps, best-effort sampling and recommended pausing in background tabs. Cross-realm/muted cross-origin frames are filtered; marker exposure depends on cross-origin isolation. Its evolving draft includes newer policy modes beyond deployed-header examples: feature detection and a declared browser-version matrix are essential. No promise of exact sampling frequency or complete cross-origin/worker visibility follows from API availability. [JS Self-Profiling specification](https://wicg.github.io/js-self-profiling/)
- Replay is a reconstructable DOM/event stream, not simply a video upload or a set of breadcrumbs. Incremental events depend on snapshots; arbitrary deletion/reordering can render the recording unreplayable. Recorder API/version, sequence ordering, snapshot checkpoints, timestamps and missing-chunk reporting therefore belong in the custom capture/storage contract. Cross-origin iframe capture requires cooperation/injection; unrestricted access is not available to a parent SDK. [rrweb official recorder guide](https://raw.githubusercontent.com/rrweb-io/rrweb/master/guide.md)

### Python / Node backend constraints

- Node's `uncaughtException` listener changes default termination behavior. `uncaughtExceptionMonitor` observes without overriding the exit; no SDK should imply the process can safely continue after a fatal exception. `exit` listeners cannot complete asynchronous uploads, and `beforeExit` is not emitted for explicit exit/uncaught exceptions. Rejections can become handled later (`rejectionHandled`), so “unhandled” is timing-sensitive and must not lead to unbounded pending-promise tracking. These are runtime semantics the custom SDK must preserve. [Node process API](https://nodejs.org/api/process.html)
- Node can obtain V8 CPU profiles via in-process `node:inspector` `Profiler.enable/start/stop`; the API also exposes heap snapshots, which are a different and much more sensitive payload class. An SDK does not need to expose a remote debugger port merely to create a local inspector session. Inspector/session lifecycle, workers and debugger coexistence must be distinguished from application request tracing. API support varies by Node version (e.g. promises interface versus older callbacks). [Node inspector API](https://nodejs.org/api/inspector.html)
- Python `sys.monitoring` exists since 3.12 and provides execution/exception callbacks with limited tool IDs (0–5) and coexistence rules. It is not a universal sampling-profiler export format and cannot be assumed available on earlier versions. Raise/handled/unwind events do not identify product incidents by themselves: normal exceptions and framework control flow are plentiful. Event callbacks, wall-time sampling, CPU sampling, native-frame capture and allocation profiling are different features requiring explicit runtime/version guarantees. [CPython official source documentation](https://raw.githubusercontent.com/python/cpython/main/Doc/library/sys.monitoring.rst)
- Python framework/task hooks, threads/processes and async request-local context need a supported matrix; a top-level exception hook alone cannot provide critical-path tracing or capture framework-handled failures. This is an engineering consequence, not evidence of a particular chosen hook design.

### Metadata-only default versus replay/profiling

**Real replay cannot honestly be described as metadata-only.** Even fully masked DOM structure, event timings, positions, URLs, selectors/attributes and interaction sequences expose application/user behavior. CPU profiles include code/resource/function/line identity; heap snapshots and native dumps may include raw application values. Keep capability availability separate from default collection policy: replay/profiling may exist while off unless a documented organization/project/session policy permits them. Whether masked replay is permitted under the user's intended “metadata-only” baseline remains an explicit privacy definition to settle, not a reason to remove the requested feature.

Prior art demonstrates masking limitations: Sentry masks text/input and blocks media client-side, yet explicitly warns to test UI changes; CSS background-image avatars and srcdoc iframes need special handling. Character-for-character masking retains text length. Network bodies/console logs are independent replay channels and can bypass DOM masking. A custom recorder must apply privacy before emitting/buffering snapshots and mutations, not merely scrub the server's final replay blob. [Replay privacy and documented edge cases](https://docs.sentry.io/platforms/javascript/session-replay/privacy/)

Source maps/symbols need explicit artifact policy separate from runtime metadata. For profiles, capture sanitized code identity/sample timing without heap/local values if that is the promised profile class; do not equate CPU profiles with memory dumps. Browser session buffers may contain sensitive recordings even when nothing has yet uploaded.

### Custom protocol / isolation minimum assurances

Engineering deductions from the runtime and transport evidence, not an implementation sequence:

- Each enabled signal needs versioned payload semantics, authenticated project/org attribution, bounded compressed/decompressed sizes and a defined acceptance/partial-drop contract. Browser credentials are public write-only ingestion keys; project/org identifiers inside a payload cannot authorize cross-org access.
- Error IDs, trace/span IDs, profile IDs and replay/session IDs need explicit links and time bases. IDs alone must never bypass organization-scoped authorization. Treat resource/artifact cache keys, query indexes, replay chunks, profile samples, source maps, quotas and deletion as organization-scoped, not just the main error rows. The requirement applies equally to product-owned engines.
- Recordings need ordered chunk IDs/checkpoints and explicit gap handling. Profiles need capture capabilities, sample interval/time origin and loss/truncation metadata. Batch retries require declared deduplication/acknowledgement boundaries; trace/error/replay/profile event classes must not accidentally share incorrect throttling or privacy semantics.
- Failure isolation, bounded queues, sampling/budgets and drop reporting remain required even with owned engines. Inability to export must not convert an application failure into an SDK-induced outage; no API can guarantee reporting after process kill or every page unload. [OTel failure-isolation principles as reference](https://opentelemetry.io/docs/specs/otel/error-handling/), [Node exit semantics](https://nodejs.org/api/process.html), [self-profiling buffers](https://wicg.github.io/js-self-profiling/)

### Licensing boundaries

rrweb's upstream repository license is **MIT**, requiring retention of copyright/permission notice in copies/substantial portions. Its default guide sets `maskAllInputs:false`, with password-only default masking: copying a permissively licensed capture library is **not** copying Sentry's privacy defaults. This is comparative evidence, not a recommendation to replace the selected custom recorder. [rrweb license](https://raw.githubusercontent.com/rrweb-io/rrweb/master/LICENSE), [rrweb options](https://raw.githubusercontent.com/rrweb-io/rrweb/master/guide.md)

Using the browser/runtime's profiling API does not require bundling a Sentry profiler. Any copied third-party capture/profiling component still requires exact-version license and dependency review; this research did not establish licenses for every possible library, nor select a product license. “Own SDK/protocol” and “all code authored from scratch” are different requirements; no assumption is made about permission to reuse implementation dependencies.

# Custom SDK runtime and profiling feasibility

Research date: 2026-11-03. External primary sources only; **no installation, execution, benchmarks, deployments, or repository inspection**. Recommendations below are architecture proposals, not claims of a tested SDK. The custom SDK owns instrumentation, privacy filtering, transport and profile normalization; using a runtime's profiler API is not wrapping Sentry/OTel.

## Decision summary

1. **Bun 1.3.14 is not CLI-only for CPU profiling.** Its tagged `node:inspector` implementation has working native-backed `Profiler.enable`, `setSamplingInterval`, `start`, `stop`, `disable`, and callback `Session.post`. A Bun-team issue comment reports testing these on `oven/bun:1.3.14`; tagged source independently corroborates the API. Use this narrow in-process API for the gateway acceptance path, with bounded windows and explicit capability detection. Do not claim full Node inspector compatibility. [B1–B4]
2. Node 22/24 expose the equivalent in-process V8 CPU profiler. Use callback `node:inspector`, rather than require the experimental promises API, as the common Node/Bun adapter seam. No debugging listener is necessary. [N1–N3, B1]
3. Python 3.12–3.14 expose suitable building blocks for **custom deterministic CPU/wall execution profiling** (`sys.monitoring` + thread CPU/monotonic clocks), and documented-but-specialized `_current_frames()` for **best-effort wall stack sampling**. These are distinct capabilities. They do not establish an unbiased, all-thread, native-aware continuous CPU sampler. That stronger requirement needs an explicitly designed native/OS component; Linux CPU callchain collection can use CPython's supported perf trampolines. Do not present a pure-Python timer thread as complete CPU profiling. [P1–P8]
4. Chrome/Edge have an experimental page-facing JS Self-Profiling API; Firefox/Safari currently do not, per compatibility data. Browser DevTools profiling is not an API available to an ordinary production-page SDK. Therefore **uniform automatic sampled CPU/wall stacks across all four browsers cannot be promised using public in-page APIs**. This is a real scope/architecture decision for the owner, not permission to silently replace profiling with event-loop timing. [W1–W4]
5. Separate `runtime_js_stack_samples`, `thread_cpu_time`, `wall_stack_samples`, `instrumented_execution_profile`, and `span_duration`. Runtime “CPU profile” sample timestamps/deltas are not a guarantee of exact OS on-CPU nanoseconds or full off-CPU/async waiting stacks. [N3, B4, P4, W1]

## Bun 1.3.14: pinned evidence, not latest-doc extrapolation

### In-process start/stop: available, but a narrow subset

Tagged `src/js/node/inspector.ts` explicitly says “Profiler APIs are implemented; other inspector APIs are stubs.” `Session.connect()` sets local connected state; it does **not** open a socket. `post` supports callback dispatch; `Profiler.stop` returns `{profile: JSON.parse(stopCPUProfiler())}`. Unsupported protocol methods return errors; coverage methods are unsupported. `open`, `close`, `waitForDebugger` throw not-implemented; `url()` returns undefined. Consequently `inspector.url() === undefined` is **not** proof profiling is unavailable, and opening a debugger is not a valid feature probe. [B1]

The native bridge calls `Bun::startCPUProfiler`, `stopCPUProfiler`, `setSamplingInterval`, `isCPUProfilerRunning`; the implementation creates a JSC `SamplingProfiler`, sets its timer, identifies the current JSC execution thread, starts it and serializes stack samples. This is real engine sampling, not an event-loop timer pretending to collect busy stacks. The native source uses static running/interval/start-time state, while JS Session enabled/connected state is per instance. **Recommendation:** one profiler owner per process; do not assume independent nested sessions, simultaneous CLI/SDK profiling, or multiple-worker safety. Even `disconnect()` / `Profiler.disable` can stop a running profiler. Worker/isolate concurrency requires explicit later acceptance evidence. [B1,B3,B4]

`Profiler.setSamplingInterval` accepts positive numeric input in JS; the native bridge validates an integer. The shared adapter should use a positive integer in microseconds, set it before starting, and record requested versus observable sampling resolution. Windows tagged test comments report effective JSC sampling ticks around the default ~15.6ms timer quantum, so 1ms requested must not be advertised as 1ms achieved everywhere. [B1,B3,B5]

### Importable `bun:jsc` API: present, not the preferred long-running SDK contract

Tagged `jsc.d.ts` exports `profile(callback, sampleInterval?, ...args)` and conditionally returns a promise when the callback does. Its declared result is `SamplingProfile {functions:string, bytecodes:string, stackTraces:string[]}`; **not** the same declared structured `Profiler.stop` `.cpuprofile` object. It is described as “pretty low-level.” Tagged types also expose `startSamplingProfiler(optionalDirectory?)`, but no matching `stopSamplingProfiler` declaration: do not invent a start/stop pair. [B2]

A user proposed making `profile` wrap an unresolved promise as a manual start/stop workaround; the Bun-team reply says `profile()` works and reports testing the callback inspector start/stop path on 1.3.14. That is useful corroboration, but not reason to build the production adapter on a promise-lifetime trick or `v8-profiler-next`. Native-package compatibility was specifically **not verified** in that reply. [B6]

### CLI and file import: available; do not mistake import for live SDK control

The **tagged** CLI tests cover `--cpu-prof`, `--cpu-prof-name`, `--cpu-prof-dir`, profile function names, structured `nodes/startTime/endTime/samples/timeDeltas`, and also `--cpu-prof-md`. Thus Markdown output is not exclusively a later-release assumption. Current docs describe importing `.cpuprofile` into Chrome DevTools or VS Code; the product can build its own strict parser/normalizer for that public structured format. This does not require installing a runtime profiler package or wrapping an existing telemetry SDK. [B5,B7,N3]

Current docs say combining `--cpu-prof` and `--cpu-prof-md` produces both formats; the 1.3.14 tagged test explicitly expects **Markdown only** when both are supplied. **Use `.cpuprofile` alone for pinned import/acceptance; do not import current CLI combinator semantics into the pin.** Prefer programmatic bounded windows for long-lived gateways instead of leaving CLI recording on until exit. Signal/abrupt-exit profile persistence and worker behavior have not been established for the exact deployed build by this desk research. [B5,B7]

The inspected Bun “CPU profile” source constructs `timeDeltas` from wall timestamps and assigns inter-sample elapsed deltas in text reports. It does not expose a distinct public selectable `wall` versus strict OS `cpu` sampling mode. Preserve raw sample counts/time deltas and engine identity; do not assert every elapsed delta is consumed CPU time or every idle wait has a meaningful suspended application stack. It emits epoch-like start times, whereas the common protocol only specifies microsecond timestamps: normalize with explicit clock-domain metadata rather than assuming Node/Bun clocks are identical. [B4,N3]

## Python: feasible custom designs and their boundaries

- **Custom deterministic profiler:** `sys.monitoring` was added in 3.12. Python 3.12/3.13/3.14 have `PY_START`, `PY_RETURN`, `PY_RESUME`, `PY_YIELD`, `PY_THROW`, `PY_UNWIND` and C-call events. Own callbacks can build execution-segment call trees and measure `thread_time_ns()` for per-thread CPU and `perf_counter_ns()` for elapsed time. This is a design inference from public APIs, **not** proof of overhead, task attribution or accuracy. Name it deterministic/instrumented profiling, not statistical CPU sampling. Returning/yielding must close the active segment; otherwise one task's suspended wait can be charged to unrelated work on the same thread. [P1–P4]
- Monitoring callbacks include objects such as return values/call targets/arguments for some event kinds. **Privacy design:** ignore them; never serialize or inspect values, frame locals/globals, arguments, heap objects or source lines. Build the profile from code identities/locations and clocks only; release transient references. Python frames inherently provide access to locals, so “we only serialize stack metadata” needs implementation discipline, not a false claim the runtime cannot expose contents. [P1–P3,P5]
- Tool IDs are limited to 0–5. Reserve a free ID cooperatively, never evict another profiler. In 3.12/3.13, `free_tool_id` does **not** disable events/unregister callbacks: clean up global and local events/callbacks first. In 3.14, `clear_tool_id` exists and `free_tool_id` calls it. This version difference belongs in the adapter. [P1–P3]
- `sys.setprofile` / `threading.setprofile_all_threads` (added in 3.12) are another deterministic hook path; they are not time-based samplers. Stdlib `cProfile` is explicitly deterministic and provides `enable/disable`; it is a reference/import possibility, not evidence that a custom continuous sampler already exists. Do not replace other libraries' hooks without a coexistence design. [P6,P10]
- **Best-effort wall stack samples:** `_current_frames()` returns each thread's active Python frame without requiring the target thread's cooperation, including blocked threads; docs warn frames may be stale and call this internal/specialized use. A timer thread can walk `f_back` and record only code metadata. This samples Python thread states, not all suspended asyncio tasks or native C stacks. Under the GIL the sampling thread cannot execute freely while another thread monopolizes it; scheduling/GIL bias means this must not be labeled unbiased CPU sampling. [P5,P7]
- Python `signal` callbacks execute later in the main Python thread, not directly in the low-level signal handler. A long C calculation can delay them arbitrarily. Therefore `ITIMER_PROF` plus a Python signal callback is **not** a general all-thread/native-aware CPU sampler, even though the interval timer itself measures process CPU execution. [P7]
- **True sampled CPU option on Linux:** since 3.12, CPython perf trampoline mode exposes Python functions to Linux perf callchain profiling; `-X perf`, `PYTHONPERFSUPPORT`, and `sys.activate_stack_trampoline('perf')` / deactivation are documented. A product-owned collector can use the OS capability and own normalizer/protocol, but still requires build/architecture/permissions validation. Frame-pointer callchains are preferable for the no-contents requirement: documented DWARF mode dumps raw process-stack bytes (default 8192), which can contain local data. Do not persist/export such raw stack dumps under a “no local contents” policy. Comprehensive portable CPU + off-CPU wall stack sampling remains **additional native-engine scope**, not solved by public Python hooks. [P8]
- Do not cite current `profiling.sampling` documentation as a 3.14 feature: that page explicitly says **Added in 3.15**. Likewise 3.14's debugger improvements/free-threaded/subinterpreter support are not a drop-in cross-version statistical profiling API. [P9,P11]

## Node 22 / 24 implementation contract

Use an internally owned `Session`, `connect()`, `Profiler.enable`, `Profiler.setSamplingInterval`, `Profiler.start`, then bounded `Profiler.stop`, `disable` and disconnect. Callback API is stable; promise module is marked experimental in both inspected version families. `setSamplingInterval` is microseconds and must precede recording. `stop` returns nodes plus sample IDs and microsecond time deltas; allowlisted `Runtime.CallFrame` metadata is sufficient for CPU stack records without local scope contents. [N1–N3]

Use no `Debugger.enable`, `Runtime.evaluate`, heap profiler commands, `--inspect`, `inspector.open`, debug WebSocket, public/private listener, or automatic SIGUSR1 attach. Node warns even loopback inspector clients have unrestricted access and network clients can execute arbitrary code; an internal session is a fundamentally different transport from exposing that server. Worker coverage must be explicit: a session on the main isolate is not evidence every worker is profiled; the documented `connectToMainThread()` specifically connects from a worker to main. [N1,N2,N4]

**Wall-time boundary:** a timestamped CPU sampler can show execution over a window, but its profile schema contains no complete suspended-Promise ancestry or all-thread off-CPU callchain field. Keep duration spans and async causality distinct. If full wall-stack coverage is non-negotiable for Node/Bun, the architecture must fund an additional custom task-state/native profiling design and define acceptance; do not set `wall_stack_full=true` based only on `.cpuprofile`. [N3,B4]

## Browser support and feature negotiation

The standard proposal samples execution-context stacks, has constructor-triggered start and asynchronous `stop()`, and a finite `maxBufferSize`; UA sampling is best effort, may be paused in background, and is realm/origin-filtered. Current draft includes newer markers and worker exposure/policy-mode extensions: these are **specification text**, not evidence those extensions ship across the named browsers. Base the initial web adapter only on the implemented constructor/stop trace fields and actual feature detection. [W1–W3]

Require serving-page opt-in with `Document-Policy: js-profiling`; MDN states the document policy must include that configuration point. Current draft additionally describes mode policies; do not assume these newer modes are required/supported by Chrome 94-era implementations. Detect `typeof globalThis.Profiler === 'function'`, then treat constructor policy-denial/permission errors as unavailable. A symbol alone is insufficient. Set bounded size/interval/window; handle buffer-full and invalid stop state. Do not require COOP/COEP just because a newer draft conditionally exposes extra markers under cross-origin isolation. [W1,W3]

Feature-detect `PerformanceObserver` entry types individually for supplemental timing. Event-loop delays, Long Tasks, Long Animation Frames, Resource Timing and span durations must remain separately typed timing telemetry; none is a substitute for interrupted busy-thread stack sampling. **Inference:** `setInterval(() => new Error().stack)` observes the sampler callback stack after the main thread becomes runnable, not the stack that blocked it. It cannot meet sampled CPU/wall-stack acceptance. [W1]

Proposed runtime capability envelope (design): runtime/version/build/platform; profiler engine and method; sampling-vs-instrumented; frame coverage (`python`, `js`, `native`); thread/worker/task scope; clock domain; requested interval and observed sample deltas; supported CPU semantics; off-CPU/async-wait coverage; policy denial/unavailable reason. No fake samples on unsupported clients. All profile frames/URLs/function names still require privacy filtering; “no locals” does not make paths or URLs harmless. [Design derived from source contracts above]

## Architecture gate / acceptance implications

- Keep Bun 1.3.14 gateway CPU sampling in the written architecture: pinned source + maintainer-reported results make it a justified target, not a reason to force Node migration. Later acceptance must use the **exact deployed image/OS/architecture**, prove start/stop on a long-lived concurrent request workload, no listener, correct frame/symbol mapping, bounded overhead/memory, profiler coexistence and no content leakage. Nothing here reports those tests as done. [B1–B6]
- Do not claim universal browser sampled profiling. Owner must choose whether Firefox/Safari have an explicitly unavailable optional profiling capability, or whether a separate user-operated/privileged collection channel is in product scope. The latter cannot be silently assumed to be an ordinary SDK. [W2]
- Do not mark full CPU + wall-stack requirements complete merely because Python deterministic profiles, Node/Bun runtime CPU samples and browser timing metrics can all be ingested. They are different observations. Full off-CPU/native/task-aware profiling is a distinct engineering deliverable; this note establishes public-API limits, not a reduction of requested scope.

# PromQL / LogQL compatibility: contract, sources, and acceptance

Research date: 2026-11-03. **Research only:** upstream documents/source inspected; no binaries run, conformance results claimed, installations, or deployments. Recommendations below are design proposals, not verified product capabilities. Deployment versions supplied by the parent task are treated as requirements, not independently re-probed.

## 1. Freeze explicit reference profiles, not “Prometheus-compatible”

| Proposed profile | Exact upstream reference | Contract |
|---|---|---|
| `promql-prometheus-3.13.5` | tag `v3.13.5` → commit `f497435984d1ca1d84cda5ed309387ac2eb1f8f6` | Entire language/type/evaluation surface of this release under a recorded feature/configuration manifest, plus its declared read-API profile. [P0] |
| `promql-prometheus-3.1.0` | tag `v3.1.0` → commit `7086161a93b262aa0949dbf2aba15a5a7b13e0a3` | Legacy deployment profile, independently tested; do not replace its expected answers with 3.13.5 answers. [P1] |
| `logql-loki-3.5.2` | tag `v3.5.2` → commit `257d2f62bf8a81b44dea6fe88968d1d28c8e01e7` | Both log and metric LogQL, including pipeline and Go-template behavior, plus declared HTTP/WebSocket read APIs. [L0] |

**Recommended meaning of full compatibility:** for every accepted expression/request and admissible dataset/configuration in a named profile, match observable upstream semantics: accepted/rejected syntax, types, evaluation times, labels, samples/logs, absence, histograms, errors, annotations, ordering where defined, and HTTP/WebSocket representation. This is **not** “supports the functions used by our dashboards.” The feature inventory must come from the whole pinned grammar/function/feature registries, not a hand-picked query list. Sources provide grammar, implementations, docs, and tests rather than one complete independent formal semantics specification. [P2–P7, L1–L8]

Record per profile: reference binary/container digest and build revision; enabled flags; lookback and default subquery interval; timestamp/name validation policy; relevant ingestion normalization; histogram support; limits; timezone/time source; API version and client build. Feature flags alter semantics, not only performance: e.g. delayed metric-name removal, experimental functions, duration expressions, extended selectors and fill modifiers. 3.1.0 gates native-histogram ingestion behind `native-histograms`; 3.13.5 documents native histograms as stable (the old flag is a no-op since 3.9; scraping is separately configured). [P6, P7, P11]

Recommended packaging: a stable/default profile **and a complete, separately enumerated gated-extension matrix** for each version. An upstream-disabled feature should reject as that upstream profile does; this is different from our engine not implementing it. Do not silently exclude all experimental features from an unqualified “full” promise. Include all promised upstream-valid combinations; label any incomplete extension as an incompatibility, not a passing test exclusion. Changing profile defaults or adopting upstream semantic changes requires a versioned compatibility change.

**Own engine boundary:** compatible syntax/results/wire APIs do not require copying the upstream parser/evaluator, TSDB/WAL/block layout, Loki chunks/indexes, or production service topology. Recommendation: implement the parser/type checker/planner/evaluator and telemetry persistence/query execution in own Apache-2.0 code; use upstream binaries only as isolated development/CI oracles, never as production query proxies/fallbacks. Even Apache-permitted Prometheus evaluator reuse would fail the user's *own query engine* requirement. Prometheus itself warns its server repository is not designed as a stable Go library. [P12] Remote read/write, exposition, OTLP and Loki push compatibility are **separate protocols**, not an automatic consequence of query compatibility; custom SDK/ingest must nevertheless preserve data required to obtain the same query answers. [P2, P3, L2]

## 3. PromQL semantic obligations and adversarial cases

| Area | Required behavior / acceptance cases |
|---|---|
| Grammar/types | Entire grammar, comments, quoting/escapes, literals including duration forms, precedence, unary/binary/aggregation operators, function signatures/default/variadic arguments and static errors. Scalar, string, instant vector and range vector are distinct; instant query may return any of them; range-query root must be scalar or instant vector. Include nested subqueries, `offset` (including negative), `@`, `start()`/`end()` modifiers, and gated extensions. [P2, P4–P6, P8, B1, B2] |
| Float semantics | IEEE-754 binary64 arithmetic, NaN, infinities, signed zero, division/modulo/power edge cases, overflow/underflow, NaN-sensitive aggregations/order/quantiles. Missing data is not zero and ordinary NaN is not staleness. HTTP float values are strings because JSON lacks NaN/Inf; result timestamps are seconds. [P2, P4, P5, P9] |
| Native histograms | Preserve counter/gauge flavor, integer/float histogram inputs, exponential/custom bucket layouts, zero bucket, schema reconciliation, reset detection, and float↔histogram transitions. Implement each operator/function's documented handling, not generic “convert to floats.” In 3.13.5: histogram×scalar and histogram/scalar have specific flavor rules; histogram+histogram and histogram−histogram are valid; invalid combinations remove elements with info annotations; incompatible layouts/mixed ranges can remove elements with warnings. `rate`, `delta`, `irate`, `*_over_time` differ in mixed-type handling. Include histogram trim operators present in this release and quantile interpolation/monotonicity repairs. [P2, P4, P5, P8, P11] |
| Time | Independent evaluation grid; query-range start/end are inclusive evaluation bounds, but selectors/lookback are left-open/right-closed in both requested 3.x versions. Test exactly-on-boundary and ±1 ms samples, fractional step/time parsing, subquery grid alignment/default resolution, nested `@`+offset, lookahead, irregular/missed scrapes, and extrapolation/reset behavior of `rate`/`increase`. Do not confuse evaluation end inclusion with a raw log-range bound. [P2–P5, P10, B1, B2, M1] |
| Staleness | Default lookback is 5 minutes; stale series disappear at evaluation after the marker rather than retaining a last value. New samples restore visibility. Preserve stale markers separately from ordinary NaN through custom ingest/storage/compaction: upstream identifies `StaleNaN` by bit pattern `0x7ff0000000000002`. Cover explicit-timestamp scrape behavior separately; exporter timestamp staleness tracking is configurable. [P9, B1, B2] |
| Labels/matching | Missing and empty label values match as documented; selectors need a name or a matcher that cannot match empty. `on`/`ignoring`, group modifiers, collision/cardinality errors, metric-name dropping and its feature-flag variation are semantic. RE2, not host JS/Python/PCRE regex: fully anchored selector matches, v3 `.` matching newline, escaping/captures/Unicode/inline flags and unsupported lookaround/backreferences. UTF-8 metric/label names and label-value URL escaping require version-specific checks. [P2, P4, P6, P7, B1, B2, M1, S1] |
| Errors/annotations/order | Prometheus JSON `status`, `errorType`, `error`, `warnings`, `infos`; documented handler errors include 400 invalid parameters, 422 non-executable expressions, 503 timeout/abort. Successful data with warnings/info is not a total failure or silent success. Compare sample-removal reasons and severity as well as values. Instant-vector order is generally unspecified unless an ordering function is used; matrices are sorted by metric in 3.13.5, and `sort` does not reorder range results. Version exact error wording/positions may need a stricter optional wire-fidelity layer, but never normalize away error category/severity/data-loss behavior. [P2–P5, P10] |

**Legacy caution:** 3.1.0 documentation gives much less histogram-operator detail than 3.13.5. Do not infer legacy native-histogram semantics from new docs; use its tagged evaluator and own version-specific fixtures/oracle. No exhaustive 3.1.0↔3.13.5 semantic diff has been executed in this research. [P3, P4, P7]

## 4. LogQL semantic obligations (not merely PromQL over logs)

- **Whole language:** selectors; chained line/string/RE2/pattern/IP filters; JSON, logfmt (including flags and extraction forms), regexp, pattern and unpack parsers; label filters and conversions; `line_format`, `label_format`, `drop`, `keep`, `decolorize`; log/unwrapped range aggregations; offset; vector aggregations/functions, arithmetic/comparison/set operators and matching. Include `|>`/`!>` and grammar-visible `variants` with the appropriate runtime gate, not only examples in the docs. LogQL scalar comparison differs from PromQL: its docs say scalar/scalar comparison must *not* include `bool`; PromQL requires it. [L1, L3, L4, L7, L8]
- **Pipeline order/state:** stages process left-to-right and later stages see mutated line/labels. Parsed-label sanitization, existing-name `_extracted` collisions, duplicate extracted keys, missing/empty labels, parser failure and label retention are observable. Label-filter `and`/`or` precedence is documented as left-to-right unless parenthesized, not conventional SQL boolean precedence. [L3]
- **Important documentation/source discrepancy:** Loki 3.5.2 log-query docs say selector regex `.` excludes newline by default, while line-filter regex is unanchored and includes newline. But its vendored Prometheus `NewFastRegexMatcher` parses `syntax.Perl|syntax.DotNL` and compiles `^(?s:...)$`; `Matcher` calls this implementation. **[INFERENCE from static source]** selector dot-newline behavior therefore differs from that prose. Do not settle this by copying docs: add an explicit label-value-containing-newline oracle case and retain both citations. No runtime confirmation was performed. [L3, L15, L16] RE2 syntax itself also rejects lookaround/backreferences; a PCRE or JavaScript approximation is not sufficient. [S1]
- **Templates:** LogQL embeds Go `text/template`, not only `{{.label}}` substitution. Cover pipelines (previous output as final argument), variables/control flow/whitespace, built-ins, conversions and the *exact* Loki/Sprig whitelist, regex replacement syntax, missing-key behavior, `__line__`, `__timestamp__`, date layouts/timezones, errors and `now`. Tagged `fmt.go` uses `missingkey=zero`; execution failures attach template-format error labels and retain the original line. Its `__line__` callback uses the current line at that pipeline stage; do not assume it can recover raw pre-pipeline content despite the docs' “original log line” description. **[INFERENCE from static source]** fix clock/TZ when testing deterministic templates and test time-dependent functions separately. Permit no additional host/environment functions merely because another template engine exposes them. [L5, L9, S2]
- **Errors versus missing data:** parser/conversion failures normally pass the line onward with `__error__` (and possible details), not silently drop it. Filtering must occur after the stage creating the error; errors remaining in a metric query cause query failure. Unwrap converts strings to float64 or specified duration/byte units. Count/rate of lines, bytes rate, rate of unwrapped values and `rate_counter` are different: tagged source computes line rate as count/window seconds, unwrapped `rate` as sum/window seconds, and counter rate by counter extrapolation. [L1, L3, L4, L10]
- **Times/result types:** raw log timestamps are nanosecond integers encoded as strings; metric values use Prometheus-style results. `query` instant endpoint accepts metric queries and rejects log queries with 400. `query_range` raw logs use start-inclusive/end-exclusive bounds; metric evaluation uses steps, whereas log `interval` samples entries without filling gaps. Tagged range aggregation selects `(t-window,t]` and emits metric timestamps at millisecond precision. Explicitly test precision conversions rather than parse nanos into JS `Number`. [L2, L10, L11]
- **Ordering/duplicates:** `direction=backward` is default; entries in each returned stream are newest-first or oldest-first according to direction. Limits interact with the global merge and equal timestamps, not independently per stream. Tagged iterators preserve original same-timestamp order and deduplicate identical timestamp+line entries across merged iterators within the stream-hash group; a single iterator is not deduplicated by that wrapper. Equal-time cross-stream comparison may use stream hash, falling back to labels when hash is absent—there is no justified universal “sort every response by timestamp,line” normalization. Add ingestion-order, repeated identical legitimate entries, replica duplicates, sharding/split-query, same-time limit-cutoff, and forward/backward tests; distinguish observable behavior from undocumented internal tie-breaking. [L2, L12]
- **Wire errors/warnings/tail:** Loki query response model includes `warnings`. Common error writer uses text/plain (not Prometheus's JSON error envelope), mapping parse/limit/pipeline errors to 400, deadline to 504, cancellation to 499 and unhandled errors to 500. Tail is a WebSocket stream with `streams` and optional `dropped_entries`; it is not a polling alias or guaranteed lossless transport. Compare handshake, history/live boundary, `delay_for` (0–5 seconds), drop signaling, close/cancellation and late arrivals, not exact packet timing/batch boundaries. [L2, L11, L13]

## 7. Honest differential acceptance design

All items here are recommendations for later implementation, not checks performed now.

1. **Requirements ledger:** enumerate every grammar production/operator/function/signature/stage/template function, valid type pairing, feature gate, error/annotation class and read endpoint/parameter/codec from the pinned evidence packs. Map each to implementation and tests; include invalid/disabled cases. Track missing coverage explicitly. Keep 3.1.0 and 3.13.5 expected results separate.
2. **Reproducible oracles and inputs:** isolated exact-version Prometheus and Loki, immutable binary digests, fixed flags/TZ/clock where possible. Load identical logical samples/log entries into reference and own engine via independent adapters. Include NaN versus stale, mixed native histograms, custom buckets, counters/reset/schema changes, gaps, label absence/empty/UTF-8, nanos, malformed logs, structured metadata and same-timestamp multiplicity. Do not let a translator silently discard an unsupported data kind. Separate input-admission/normalization tests from query evaluation so ingest differences cannot masquerade as evaluator bugs or passes.
3. **Layers:** (a) parser/type/validation differential tests; (b) raw deterministic evaluation fixtures; (c) public HTTP wire comparison, including errors/warnings/info; (d) full ingest→flush/compact/restart→read; (e) sharding/split-query/cache and tail; (f) pinned Grafana/read-client workflows and org-isolation tests. Own cold and hot storage must agree without upstream production fallback.
4. **Coverage expansion:** run all legally usable versioned upstream Prometheus fixtures plus compliance suites, independently authored LogQL cases, grammar/type-directed randomized expression+dataset generation, boundary-directed cases and mutation/fuzz testing. Cross operators, stages, types and gates, not only test them singly. Shrink failures into reproducible permanent regressions. Test mathematically valid metamorphic properties only where their preconditions hold—float reassociation, arbitrary pipeline reordering, or sorting before `limit` are not safe universal invariants.
5. **Comparator contract:** exact result type/label identity/timestamps/log bytes/absence/structured metadata/cardinality; exact integer counts; NaN/Inf classes and sign-sensitive zero where observable; compare native-histogram bucket boundaries/count/sum/flavor at the appropriate internal or public layer. Predeclare per-operation numerical tolerances (ULP/absolute/relative with reasons), not one broad epsilon that hides bugs. Do not demand internal reset hints missing from HTTP JSON; exercise them in internal fixture/ingest tests.
6. **Only normalize documented freedom:** JSON object key order and unspecified instant-vector order may be canonicalized; never erase defined sorting, dropped elements, stream direction, duplicate multiplicity, warnings/info, or errors. For Loki ties/limits and Prometheus approximate metadata time windows, classify documented freedom, source-specific behavior and actual incompatibility explicitly. Compare deterministic diagnostic category/severity and relevant text/positions; exclude nondeterministic timing/physical I/O stats from exact equality while validating schema and truthfulness. Do not fabricate Prometheus/Loki physical-engine stats in an independent engine.
7. **Failure conditions and evidence:** zero unresolved semantic/wire mismatches in promised profiles; zero unimplemented ledger entries; zero silent skips or substitutions; every accepted tolerance/normalization and upstream bug documented. Record reference digests/config, corpus commit and license, total/covered/skipped cases by semantic family, random seeds, minimized counterexamples, client build and raw sanitized diffs. Mismatches known in upstream require explicit version-specific policy, not silently changing the oracle or skipping inconvenient cases.
8. **Claim precisely:** “Implements profile X; passes corpus revisions Y and generated campaigns Z under configurations C; known deviations D.” A finite suite cannot prove equivalence for all programs, datasets, time bounds and future versions. Full semantics is the engineering contract and ongoing obligation; a green finite corpus is supporting evidence, **not a proof**. Production query replay alone proves even less. A formal proof would require a sufficiently complete formal semantics and implementation refinement argument not supplied by upstream test counts.
